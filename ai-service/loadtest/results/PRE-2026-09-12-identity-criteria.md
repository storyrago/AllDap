# 파도 2 동일성 확인: 돌리기 <전에> 못박은 판정 기준

작성 시각: 실행 전. 숫자를 보고 고치지 않는다. 고치면 그것은 판정이 아니다.

## 0. 무엇을 판정하는가

"도구를 고쳤는데 <재는 대상>은 안 바뀌었다" 를 판정한다. 새 측정이 아니다.

🔴 **before 와 after 가 <비트 단위로> 같을 수 있는 축과, 원리적으로 같을 수 없는 축을 먼저 가른다.**
가르지 않으면 "달라졌다" 가 두 가지 뜻을 갖는다: 재는 대상이 바뀐 것 / 원래 매 판 흔들리는 값.

| 축 | 성질 | 판정 |
|---|---|---|
| S3 상태코드 히스토그램 | 결정적(한도 20, 총 100건) | **정확히 일치해야 한다** |
| S3 지연 p50/p95/max | 매 판 흔들린다 | 밴드만 본다(아래 §1-3) |
| S4 구조 신호(재시도·전이 수·어느 코드가 나오는가) | 결정적 | **정확히 일치해야 한다** |
| S4 처리량 유래 수치(200 건수, 503 건수, python_5xx) | 기계 상태에 딸린다 | 밴드만 본다(아래 §2-2) |

## 1. S3 A판 (run-id `2026-09-12-A`)

before 원본: `docs/superpowers/2026-09-11-loadtest-s3-result.md` §3.

### 1-1. 정확히 일치해야 하는 것

| 축 | before | 기준 |
|---|---|---|
| 404 | 20 | = 20 |
| 429 | 80 | = 80 |
| 400 / 200 / 0 / 500 / 503 | 0 | 전부 = 0 |
| 합계 | 100 | = 100 |
| `alldap_ratelimit_rejected_total{bucket="widget-chat",mode="check"}` 증가분 | 80 | **k6 429 와 정확히 일치**(±1 여유 없음) |
| `mode="blocked"` 증가분 | 0 | = 0 |

### 1-2. 고쳐졌는지 보는 것 (①)

- `verdict.valid` 가 **`true`**. before 는 `false` 였고 사유가 `recorded_total{bucket="widget-chat"}` 부재였다.
- `after` 의 종료코드가 **0**.
- 판정 사유에 `recorded_total` 부재가 <무효 사유로> 남아 있지 않다.

### 1-3. 밴드로만 보는 것

- k6 100건 총 실행 시간 **5초 미만** (before 329ms)
- 최대 지연 **100ms 미만** (before 21.2ms)
밴드를 벗어나면 "숫자가 달라졌다" 가 아니라 <기계가 다른 상태다> 로 읽고 보고한다.

## 2. S4 F2판 (run-id `2026-09-12-F2`)

before 원본: `docs/superpowers/2026-09-11-loadtest-s4-result.md` §4.

### 2-1. 정확히 일치해야 하는 것

| 축 | before | 기준 |
|---|---|---|
| 정상 구간 상태코드 | 200 만 | 200 외 0건 |
| 주입 구간 상태코드 | 503 만 | 503 외 0건 |
| `alldap_ai_retry_total` 증가분 | **0** | **= 0** (이 판의 반증 가능한 주장) |
| `circuit_transition_total{to="open"}` 증가분 | 4 | = 4 (90초 ÷ 30초 톱니) |
| 가짜 CF 리랭커 호출 증가 | 0 | = 0 |
| 가짜 CF 생성 호출 증가 | 0 | = 0 |
| `python_5xx` : 가짜 CF 임베딩 증가 : `fault.injected` 증가 | 73:73:73 | **셋이 정확히 같다** |
| fallback | 0 | = 0 |
| `verdict.valid` | true | true |

### 2-2. 고쳐졌는지 보는 것 (②)

🔴 **`success` outcome 증가분이 k6 가 센 200 건수와 <정확히 같아야> 한다(차 0).**
옛 순서(`recover → after`)면 `recover` 가 서킷을 닫으려고 직접 만든 성공 1건이 섞여 **+1** 이 된다.
before 에서 실제로 F3 가 1,800 이 아니라 1,801 이었다. 차가 1 이면 ②가 안 고쳐진 것이다.

또한 `recover` 를 `after` <앞>에서 돌리면 verdict 파일이 없어 **종료코드 1 로 거부**되어야 한다
(순서를 절차가 아니라 코드가 지키는지). 이건 일부러 시험하지 않고, `s4_check` 의 순수 함수 시험과
실제 순서 실행으로 갈음한다.

### 2-3. 밴드로만 보는 것 (±20%)

| 축 | before | 밴드 |
|---|---|---|
| 정상 구간 200 | 720 | 576 ~ 864 |
| `python_5xx` | 73 | 58 ~ 88 |
| 주입 구간 503 | 235,700 | 188,560 ~ 282,840 |
| 정상 구간 avg 지연 | 1676.8ms | 1,340 ~ 2,010ms |

🔴 밴드를 벗어나도 그 자체로는 "재는 대상이 바뀌었다" 가 아니다. 이 셋은 전부 <기계의 처리량>에
딸린 값이라 CPU 상태에 흔들린다. 벗어나면 **멈추고 보고**하되, 구조 신호(§2-1)가 전부 맞았는지를
함께 적는다. 둘을 뭉개면 "도구가 바꿨다" 와 "기계가 느렸다" 를 못 가른다.

## 3. 판을 폐기하는 조건 (설계서 §5)

- `alldap_anyio_threads_total != 40` — 이 판은 40 을 잰 것이 아니다
- fallback > 0
- 가짜 CF 호출 배수가 정상 경로에서 3 이 아니다
- Spring 재시작. 로그에서 `ExitOnOutOfMemoryError` 여부를 직접 확인한다. 못 가리면 무효로 두고 다시 돈다

## 4. 관문

히스토그램·상태코드 숫자(§1-1 · §2-1)가 before 와 달라지면 **거기서 멈추고 보고한다.**
파도 3 으로 넘어가지 않는다.
