### 🔴 1번이 진짜 발단이다. 앞 문서에 아예 없던 것이다

```
publish  34426916250  01:48:13 시작 -> 01:50:47 완료
deploy   run1         01:48:13 시작 (event=push)
   +-- 01:48:23 image pull      <- publish 가 끝나기 2분 24초 <전>
```

`deploy.yml` 이 `workflow_run`(publish 성공 뒤)과 `push` **두 문**으로 들어왔다.
PR #99 가 `docker-compose.prod.yml` 을 고치자 둘이 동시에 걸렸고, push 쪽 배포가
아직 GHCR 에 없는 새 이미지 대신 **옛 api 이미지**를 올렸다. 옛 이미지의 actuator 는
8080 에 있는데 함께 배포된 새 compose 의 헬스체크는 8081 을 찌른다. 영원히 unhealthy 다.

**`deploy.yml` 이 그 위험을 자기 주석에 세 줄로 적어두고, 바로 아래에 그 문을 열어뒀다.**
`concurrency` 는 <겹침>만 막고 <순서>는 못 막는다는 것이 이번에 드러났다.

→ `push` 트리거를 없애고, 그 트리거가 담당하던 경로(`Caddyfile`·`docker-compose.prod.yml`·
`deploy.yml`)를 **`publish.yml` 의 `paths` 로 옮겼다.** 문이 하나면 순서가 어긋날 자리가 없다.

### 🔴 3번: compose 가 옳았고 검사가 틀렸다

앞 문서는 *"`up -d` 가 Running 으로 판정해 재생성하지 않는 것으로 보인다"* 고 적었다.
**반증됐다.** compose 는 태그 이동을 정상적으로 감지한다(로컬에서 4가지 조건으로 재현했고,
서버와 같은 v5.5.1 바이너리로도 재현했다).

두 이미지는 **내용이 한 바이트도 다르지 않았다**:

```
=== 779b4761be04 ===                        === 725cabba6f18 ===
Created  2026-09-09T07:55:56.998224677Z      2026-09-09T07:55:56.998224677Z
Size     517410301                           517410301
RootFS.Layers  9개 전부 동일 · Config 동일
```

다른 것은 OCI index 껍데기뿐이고, 원인은 `build-push-action@v6` 이 기본으로 붙이는
**provenance attestation** 이다. 그 매니페스트는 빌드마다 달라서, 캐시가 100% 맞아도
index digest 가 새로 나온다.

- compose 는 index 안의 **플랫폼 매니페스트 digest** 를 본다 → "안 바뀌었다" (옳다)
- `verify-deploy.sh` 는 `.Id`(= index digest)를 본다 → "바뀌었다" (거짓 경보)

→ `publish.yml` 에 **`provenance: false`**. 두 파일에 서로를 가리키는 주석을 남겼다.
한쪽만 고치면 다시 거짓 실패가 난다.

⚠️ **앞 문서가 안내한 수동 복구(`up -d --force-recreate ai-service`)를 상시 대책으로
따라 하지 말 것.** 증상만 덮고, 내용이 같은데 매 배포마다 Python 을 재시작하게 된다.

## 2. 🔴 손으로 한 번 개입했다 (서버 상태를 바꿨다)

**PR #100 을 머지했는데 배포가 또 빨간불이었다.** 값은 바뀌었다:
`받은 것` 이 `725cabba`(index) → **`5570d090`**(플랫폼 매니페스트)으로 옮겨갔다.
= `provenance: false` 자체는 동작했다.

**남은 것은 일회성 이월이었다.** 도는 ai-service 컨테이너는 provenance 를 끄기 **전에**
만들어져서 `.Image` 에 옛 index digest 가 박혀 있었다. 그리고 여기에 기제가 하나 더 있다:

> **`.Image` 와 compose 라벨은 서로 다른 것을 기록한다.**
> compose 는 `com.docker.compose.image` 에 platform manifest 를 적고,
> containerd 런타임은 `.Image` 에 pull 당시 저장한 index 를 적는다.
> 그래서 compose 는 "안 바뀌었다"(라벨 = 태그 = `5570d090`)고 판정해 재생성하지 않고,
> `.Image` 는 영원히 옛 형식(`779b4761`)으로 남는다. **스스로 수렴하지 않는다.**

서버에서 한 줄 돌려 끊었다:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --force-recreate ai-service
```

```
전:   .Image = 779b4761...
후:   .Image = 5570d090...   = 태그가 가리키는 값
검사: OK api / OK ai-service   종료코드 0
```

**이 이월은 provenance 를 껐다 켠 이번 한 번만 생긴다.** 다음 배포부터는 저절로 맞는다.
근거는 api 컨테이너다. 이번에 재생성돼서 `.Id`·`.Image`·라벨 셋이 전부 같은 값이다.

⚠️ **`ai-service` 를 재시작했으므로 그 사이 몇 초간 채팅이 502 였을 수 있다.**
재생성 뒤 위젯 JS 200 · 봇 설정 조회 200 을 확인했다.

## 5. 미룬 것

### ⓐ `verify-deploy.sh` 의 비교 기준

지금 방식(`.Id` vs `.Image`)은 **provenance 를 다시 켜면 다시 깨진다.** 스크립트 주석에
그 숙제를 적어뒀다("want/have 를 플랫폼 매니페스트 digest 로 바꿀 것").

**대안: `RootFS.Layers` 로 <내용>을 비교한다.** digest 형식 차이에 원리적으로 면역이고,
2026-09-09 의 진짜 사고(32시간 된 컨테이너)는 여전히 잡는다. 대가는 검사의 뜻이
"받은 이미지로 도는가" 에서 **"받은 이미지와 <같은 내용>으로 도는가"** 로 약해지는 것이다.
그 차이를 주석에 적어야 한다.

🔴 **"verify 실패 시 자동으로 `--force-recreate` 후 재검사" 는 하지 말 것.**
이 검사가 잡아야 하는 진짜 사고를 자동으로 무마해버린다. 실패가 실패로 안 남으면
검사가 없는 것과 같다. 이 저장소가 반복해 적어둔 "무시되는 검사는 없는 것과 같다"의
자동화 버전이다.

### ⓑ `if: failure()` 진단 수집이 절반만 쓸모 있었다

이번 실패(run `34448407972`)에서 실제로 평가해봤다.

- ✅ `ps` 는 결정적이었다. `alldap-ai-service-1` 의 IMAGE 칸이 태그가 아니라
  `sha256:779b4761...` 로 찍혀 "옛 이미지로 돈다" 가 눈으로 보인다.
- ❌ 나머지는 이 실패와 무관했다. api 는 healthy 로 정상 기동(19.58초)했고 ai-service
  로그는 4줄뿐이었다. 🔴 **정상 부팅 로그 200줄이 결정적인 `ps` 한 줄을 화면에서 묻는다.**
- 🔴 **내가 짠 진단이 "기동이 안 됐을 때"만 상정했다.** verify 실패용으로 필요한 값
  (`image inspect .Id` · 컨테이너 `.Image` · compose 라벨 · `imagetools --raw` 의
  `mediaType`)이 하나도 없어서 전부 손으로 캐야 했다.

→ 어느 단계가 실패했는지에 따라 다른 것을 남기게 고칠 것.

### ⓒ `publish.yml` 의 매트릭스별 경로 필터가 없다

`paths` 필터가 워크플로 트리거에만 걸려 있고 매트릭스 잡별로는 없어서,
**`api/**` 한 글자만 바뀌어도 `ai-service` 까지 항상 다시 빌드·푸시된다.**
PR #99 가 `ai-service/**` 를 0줄 고쳤는데 이미지가 새로 밀린 이유가 이것이다.

⚠️ 붙이면 "이번 배포의 ai-service 는 어느 태그를 쓰나" 가 복잡해진다. **아래 ⓓ 와 함께
설계할 것.** 따로 하면 두 번 고치게 된다.

### ⓓ `IMAGE_TAG=latest` 와 롤백

`publish.yml` 은 이미 `:latest` 와 `:${{ github.sha }}` 를 **둘 다** 푸시한다. 배선만 하면
되는데 넣지 않았다. 필요한 것 셋:

1. `Caddyfile`·compose 만 바뀐 배포는 그 SHA 로 태그된 이미지가 없을 수 있다. 트리거별 분기
2. SHA 태그는 이름이 붙어 있어 `docker image prune`(dangling 만)으로 안 지워진다.
   t3.micro 에 무한 축적되므로 디스크 정리를 함께
3. 전달 방식은 서버 `.env.prod` 의 그 한 줄만 `sed -i` 로 치환.
   🔴 **`.env.prod` 를 통째로 덮어쓰지 말 것** (`BILLING_CRYPTO_KEY` 를 잃으면 전 고객이
   카드를 재등록해야 한다). 셸 환경변수로 넘기는 안은 배포 후 값이 사라져, 나중에 사람이
   손으로 `up -d` 를 돌리면 `verify-deploy.sh` 가 정상 배포를 실패로 부른다.

🔴 **"롤백은 `IMAGE_TAG` 한 줄" 은 거짓이고 반례가 지금 저장소에 있다.** 서버는
`git pull --ff-only` 로 항상 최신 compose 를 갖는다. `IMAGE_TAG` 만 옛 SHA 로 되돌리면
최신 compose 의 헬스체크(8081)와 옛 이미지의 actuator(8080)가 어긋나 영원히 unhealthy 가
되고, `ai-service` 가 `depends_on: service_healthy` 에 걸려 안 뜬다.
실효 절차와 detached HEAD 복귀 절차는 `docs/DEPLOY.md` §9 "롤백" 에 적어뒀다([추정] 표시).

### ⓔ 앞 문서에서 넘어온 것 셋 (그대로 남아 있다)

- `ANSWER_INCOMPLETE` 안내문이 "같은 질문을 다시 보내도 같은 결과" 라고 단언하는데,
  같은 질문이 66회 중 65회 성공했다. `generator.generate` 가 <잘림>과 <빈 응답>을 같은
  예외로 던지는 것이 원인이다. **가르려면 uvicorn 로그를 파일로 받아야 한다.**
- 부하 드라이버가 세션 id 를 재사용해 집계가 샌다. 실행 구분자를 넣을 것.
- `fake_cf_check` 의 지연 검사 창이 절대값(`expected + 300`)이라 헐겁다. 비율로 바꿀 것.

## 7. 내가 틀렸던 것 (기록)

앞 문서의 정정과 별개로, **이번 작업 중에 내가 낸 것**이다.

1. **PR #100 본문에 "내용이 같으면 index digest 도 같아져 기존 검사가 그대로 옳아진다"
   고 썼는데, <이미 만들어져 있는 컨테이너>를 고려하지 않았다.** 그래서 머지 직후 배포가
   또 빨간불이었다. 검사의 양쪽 중 한쪽만 새 형식이 된 것이다.
2. **헬스체크 단계를 옮기면서 `deploy.yml` 끝에 낡은 주석 덩어리를 남겼다.** 어느 스텝에도
   안 붙은 채로 있었다. 동료 세션이 잡았다.
3. **진단 수집 단계를 "기동이 안 됐을 때"만 상정하고 짰다.** 정작 이번 실패에는 안 맞았다.
