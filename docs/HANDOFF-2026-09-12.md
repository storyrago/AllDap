## 1. PR 5a 셀프 리뷰: 새로 만든 계기판 자체에서 셋이 나왔다

브랜치가 이미 스레드 상한을 40 → 80 으로 올리고 psycopg 풀 지표를 낸 상태에서 리뷰를 돌렸다.

### 🔴 ① `sample_db_pool` 이 꺼진 풀의 옛 값을 계속 그렸다

`stats is None` 분기가 `open` 만 0 으로 내리고 나머지 네 게이지는 그대로 뒀다.
prometheus 게이지는 마지막 값을 계속 들고 있다. 재현:

```
db._pool = Stub(waiting=5) → sample → db._pool = None → sample
open 0.0 / size 7.0 / max 10.0 / available 2.0 / requests_waiting 5.0
```

`requests_waiting` 은 Grafana 패널이 "0 이 아니면 풀이 벽이다" 로 **판정에 쓰는** 값이다.
즉 **"지금 5건이 기다린다" 와 "옛날에 5건이었다" 가 같은 값**이 됐다.

🔴 **더 나쁜 것은 검사 쪽이었다.** `metrics_check` ⑧ 의 주석이
*"풀이 사라지면 다시 0 으로 돌아간다. 게이지는 마지막 값을 계속 들고 있으므로 이걸 안 하면
꺼진 풀의 옛 숫자가 계속 그려진다"* 라고 **반대를 단언**하는데, 검사는 `open` 만 봐서 통과했다.

> **이 저장소가 두 번 기각한 "정상을 실패로 부르는 검사" 의 <반대편>이다: 고쳐졌다고 믿게
> 만드는 검사.** 앞의 것은 빨간불이 거짓이고, 이건 초록불이 거짓이다.
> 두 부류를 쌍으로 기억할 것.

고친 뒤 **일부러 되돌려 빨간불이 되는지 확인했다.** 깨뜨린 상태 종료코드 1 → 되돌린 뒤 0.
그 출력에 `open` 만 OK 로 남아서, **옛 검사가 왜 아무것도 못 잡았는지가 그대로 보인다.**

### ② `ANYIO_MAX_THREADS=0` 이면 영어 예외로 기동이 막혔다

anyio 의 `total_tokens` setter 가 `ValueError: total_tokens must be >= 1` 을 던진다.
막히는 것 자체는 옳지만 **어느 설정 키 때문인지가 안 나온다.** 같은 PR 에서
`.env.example` 에 새로 노출한 키라 사람이 손으로 고치는 자리다.
→ `config._check_ranges` 로 1~200 을 한국어로 안내한다. `_check_prod` 와 달리 **모든 환경에서** 돈다.

### ③ 풀 포화의 모습이 "Python 이 죽었다" 와 구분되지 않았다

psycopg_pool 3.3.1 기본값을 소스로 확인했다: **`timeout=30.0` · `max_waiting=0`(무제한)**.
커넥션이 마르면 스레드 최대 70개가 줄을 서고, 각자 30초 뒤 `PoolTimeout` → `main.chat` 에
핸들러가 없어 500 → Spring 이 Python 5xx 를 **서킷 실패로 세므로** 5건 누적에 30초 전면 차단.

🔴 **풀 설정은 <바꾸지 않고> 예측만 적었다.** 이 브랜치가 세운 "한 번에 한 변수만 바꾼다"
원칙 때문이다. `timeout` 을 함께 줄이면 다음 S2 에서 "스레드를 올린 효과" 와
"풀 정책을 바꾼 효과" 가 한 그림에 섞인다. `waiting > 0` 이 관측되면 그때 바꿔 한 판 더 돈다.

### 정확성 정정 셋

- `ci.yml` 의 개수(`4개`·`넷`·`3개`)가 **이 브랜치에서 `upload_e2e_check` 를 목록에 추가하며
  낡았다.** 추론은 맞고 숫자만 어긋났다. 고치면서 "개수를 늘리거나 줄일 때는 위 문장의 수도
  함께 고칠 것" 을 그 자리에 적었다
- HWPX run 병합 예시를 설명하는 주석 2곳이 `제3조` 를 가리키는데 실제 fixture 와 단언은 `제7조`다
- `upload_e2e_check` docstring 의 `.venv/uvicorn` → `.venv/bin/uvicorn`

**검증:** 자체 점검 11개 전부 종료코드 0, `compileall` 통과,
`ANYIO_MAX_THREADS=0/-5/201` 셋 다 한국어 안내로 기동 중단 확인.

## 2. PR 5 설계 (#135)

설계서의 `PR 5: 개선 1건 + 재측정` 한 덩이를 셋으로 쪼갰다.
전문은 `docs/superpowers/specs/2026-09-12-loadtest-pr5-remeasure-design.md`.

| | 내용 | 상태 |
|---|---|---|
| 5a | 스레드 상한 80 + 풀 지표 | ✅ #132·#134 |
| **5b** | 도구 결함 ①②④ + A판·F2 재실행으로 동일성 확인 | ⬜ |
| **5c** | S2 재측정(160 추가) + 최종 리포트 | ⬜ |

정한 것 중 **다음 세션이 반드시 알아야 할 넷**만 옮긴다.

### 🔴 ⓐ VU 사다리에 160 을 더해야 한다. 옛 사다리로는 결론이 안 난다

새 천장 예측이 `80 스레드 ÷ 1.68초 = 47.6 req/s` 이고, 그 천장에 닿으려면 동시 요청이
80건은 되어야 한다. **옛 사다리의 마지막 칸(80 VU)이 새 벽과 정확히 겹친다.**
80 까지만 돌리면 처리량이 47 까지 선형으로 오르는 것만 보이고 꺾이는지는 못 본다
= "벽이 어디로 옮겨갔나" 에 답할 수 없다.

40 이하를 버리지 않는 이유: before 에서 그 구간이 선형이었으므로 after 에서도 선형이어야
"원래 느렸던 것이 아니다" 를 보일 수 있고, 한 표에 올리려면 같은 칸이 필요하다.

### 🔴 ⓑ `circuit_state` 를 단계마다 찍는다. 이것이 유효성 장치의 핵심이다

§1-③ 의 경로대로 풀이 마르면 **처리량이 갑자기 0 으로 떨어진다.**
그건 "천장에 닿았다" 가 아니라 **"차단됐다"** 다. 뭉개면 리포트가
*"160 VU 에서 처리량이 무너졌다"* 고 쓴다. 여덟 번 낸 그 부류를 **미리** 막는 자리다.

⚠️ 30초짜리 `PoolTimeout` 대기는 15초 스크레이프 두 번 사이에 통째로 들어갈 수 있다
= 포화가 있었는데 그래프에 안 남는 판이 가능하다. 그래서 `waiting` 을 단계마다 찍는다.

### 🔴 ⓒ "오염" 과 "결과" 를 가르는 규칙이 새로 필요해졌다

before 에서 Spring 재시작은 **오염**이었다. 그런데 after 에서는 **힙이 벽이라는 결론
그 자체**일 수 있다(S2 의 2순위 가설이 "틀렸다" 가 아니라 "발현하지 않았다" 로 남은 이유가
스레드 40 이 살아 있는 객체 수도 함께 묶고 있었기 때문이다).
**같은 사건을 어느 쪽으로 읽을지가 반대다.**

→ `-XX:+ExitOnOutOfMemoryError` 로 죽었으면 **결과**, 그 외 사유면 **오염**.
로그에서 OOM 을 직접 확인한다. 못 가리면 그 판은 무효로 두고 다시 돈다.

### ⓓ 리포트는 A·B·C 를 층으로 쌓는다

결론(before/after) → 시나리오별 → 측정을 믿을 수 있게 만든 과정.
C 를 앞에 두면 **"변명" 으로 읽히고**, 개선을 증명한 뒤에야 강점이 된다.

🔴 **B 절의 규칙: 표 하나 + 판정 한 줄 + 원본 링크까지만.** 시나리오별 결과 문서가
이미 넷 있어서, 증거를 다시 서술하면 같은 사실이 두 곳에 있게 된다.
이 규칙이 있으면 B 절은 "종합" 이고, 없으면 "복사" 다.

## 4. 이 라운드에서 배운 것

### 🔴 ⓐ 같은 누락으로 두 번 틀렸다. 열린 PR 목록을 안 봤다

| 무엇 | 실제 |
|---|---|
| "측정 계정 문제는 아직 아무도 안 했다" | **PR #133 이 열려 있었고 이미 해결돼 있었다** |
| "이 브랜치의 5a 작업은 PR 이 없다" | **PR #132 가 같은 커밋으로 열려 있었다.** #134 는 중복이다 |

① 때문에 설계서에서 같은 문제를 **다시 설계했고, 더 나쁜 방식으로** 제안했다
(기존 계정의 비밀번호를 고정하는 안). 게다가 #133 이 건드리는 파일
(`s2_context.py`·`s2_breakpoint.js`·`s4_context.py`)과 겹쳐서, 설계서의 핵심 주장
**"5b·5c 는 파일이 안 겹쳐 나란히 열 수 있다" 가 그 시점에 거짓**이었다.
정확히 2026-09-08 의 스택 브랜치 함정이고, 설계서는 그 함정을 피했다고 적어놨다.

② 는 SHA 가 같아 사고가 안 났다. 브랜치 이름이 `feat/anyio-threads-db-pool-metrics` 와
`feat/anyio-threads-**and**-db-pool-metrics` 로 한 낱말만 달랐다.

**문서(AGENTS.md·핸드오프·decisions.md)와 `main` 은 훑었다. 그것으로 부족했다.**

> 🔴 **규칙: 파일 겹침을 따지거나 "아직 아무도 안 했다" 를 적기 전에
> `gh pr list --state open` 과 `git branch -r` 을 본다.** 열린 PR 이 건드리는 파일까지
> 확인한다(`git diff --stat origin/main...<branch>`).
>
> 핸드오프 7 §4-ⓐ·ⓔ 가 정리한 것과 같은 부류다: **좁게 보고 전체를 단언한 것.**
> 그때는 파일과 히스토리였고 이번엔 브랜치다. 7 번이 *"`git log --grep` 에 `| wc -l` 을
> 붙이는 데 1초면 된다"* 고 적었는데, 같은 1초가 `gh pr list` 에도 든다.

### 🔴 ⓑ 기각을 적을 때는 <무엇을 전제했는지>도 적어야 한다

설계서 초고가 "측정 전용 계정" 안을 이렇게 기각했다.

> S2 가 재는 것은 검색 SQL 부하라 새 봇에도 청크 306개가 있어야 하고, 그러려면 진짜
> 임베딩으로 코퍼스 50건을 다시 올려야 한다. 그러면 before 와 다른 청크에서 재는 셈이 된다.

**틀린 곳은 결론이 아니라 전제다. "새 계정 = 새 봇" 을 전제했는데 그게 틀렸다.**
#133 은 봇을 새로 만들지 않고 `bots.user_id` 를 옮긴다.

전제를 안 적었기 때문에 **그 전제가 틀렸다는 것을 아무도 짚을 수 없었다.**
결론만 적힌 기각은 검증할 수가 없다.

### ⓒ 정정은 지우지 않고 조건이 바뀐 것으로 남긴다

#133 이 머지돼 "나란히 열 수 있다" 가 **참이 됐다.** 그래도 설계서에서 그 문단을 지우지
않고 "초고 시점에는 거짓이었다" 를 함께 적었다.
**지운 것이 아니라 조건이 바뀐 것이고, 지우면 다음 사람이 같은 판단을 처음부터 다시 한다.**
핸드오프 7 §4-ⓐ 의 결론("숫자는 낡고 이유는 안 낡는다")과 같은 이유다.

### ⓓ 리뷰가 "고쳐졌다고 믿게 만드는 검사" 를 처음으로 잡았다

§1-① 이다. 이 저장소의 상습 부류 목록에 **한 칸이 늘었다.**

| 부류 | 증상 | 예 |
|---|---|---|
| 정상을 실패로 부르는 검사 | 빨간불이 거짓 | `recorded_total` 무효 판정 · Forwarded 점검 명령 · provenance 거짓 경보 |
| **고쳐졌다고 믿게 만드는 검사** | **초록불이 거짓** | **`metrics_check` ⑧ (주석은 단언하고 검사는 절반만 본다)** |
| 안 도는 검사 | 불이 아예 안 켜짐 | `redirect.check.ts` |

**셋은 서로 다른 실패다.** 세 번째는 검사를 CI 에 태우면 닫히는데, 두 번째는 태워도 안 닫힌다.
막는 방법은 하나뿐이다: **고친 뒤 일부러 되돌려 빨간불이 되는지 본다.**
`parsers_check` 가 파서를 셋 망가뜨려 본 것과 같은 절차다.
