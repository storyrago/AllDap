### ⓐ `ai-service` 가 옛 이미지로 돈다

`verify-deploy.sh` 가 잡아냈다. **이 스크립트는 제 일을 했다** ("돌았다" 와
"새것으로 바뀌었다" 는 다르다를 검사하려고 만든 것이고, 정확히 그 차이를 잡았다).

- 받은 이미지: `725cabba6f18`
- 실제로 도는 것: `779b4761be04`
- `Up 16 hours` 라 재생성 자체가 없었음이 드러난다

`deploy.yml` 은 `caddy` 만 `up -d --force-recreate` 하고(104행) `api`·`ai-service` 는
평범한 `up -d`(98행)로 올린다. **[추정]** `up -d` 가 `ai-service` 를 "Running" 으로 판정해
재생성하지 않은 것으로 보인다. **원인은 서버를 봐야 안다. SSH 하지 않았다.**

수동 복구: `docker compose ... up -d --force-recreate ai-service`

> 🔴 **정정: 이 진단은 반증됐다. `ai-service` 는 옛 이미지로 돌고 있지 않았다.**
> 서버에서 실측하니 `779b4761be04` 와 `725cabba6f18` 는 **내용이 완전히 같은 이미지**였다:
> `Created`(2026-09-09T07:55:56.998224677Z) · 크기(517410301) · `RootFS.Layers` · `Config`
> 가 전부 동일했고, 도는 컨테이너의 `com.docker.compose.image` 라벨이 레지스트리의 amd64
> 매니페스트와 일치했다.
>
> 다른 것은 **OCI index 껍데기뿐**이었고 원인은 `build-push-action@v6` 이 기본으로 붙이는
> **provenance attestation** 이다. 그 매니페스트는 빌드마다 달라서 내용이 같아도 index digest
> 가 바뀐다. compose 는 index 안의 <플랫폼 매니페스트 digest> 를 보므로 "안 바뀌었다" 고
> **정확히 판정**했고, `verify-deploy.sh` 는 `.Id`(= index digest)를 보므로 매번 바뀐다고 봤다.
> **compose 가 옳고 검사가 틀렸다.**
>
> → 그래서 원문의 *"이 스크립트는 제 일을 했다"* 도 정정한다. 이번 건에서는 **거짓 경보**였다.
> 이 저장소의 상습 부류인 <정상을 실패로 부르는 검사>에 다른 경로로 또 걸린 것이다
> (앞선 두 번: `--images <svc>` 가 의존 서비스까지 낸 것 · `.Config.Image` 자기 비교).
>
> 🔴 **위 "수동 복구" 를 따라하지 말 것. 증상만 덮는다.** 내용이 같은데 매 배포마다 Python 을
> 재시작하게 된다. 실제 수정은 `publish.yml` 에 `provenance: false` 를 넣어 <내용이 같으면
> digest 도 같게> 만든 것이다(`ad17f5a`). 두 파일에 서로를 가리키는 주석을 남겼다,
> 한쪽만 되돌리면 다시 거짓 실패가 난다.

### 롤백이 없다

> 🔴 **정정: 롤백 경로가 없다는 것은 맞지만, `IMAGE_TAG` 한 줄로는 <안 된다>.**
> 서버는 배포 1단계의 `git pull --ff-only` 로 **항상 최신 compose** 를 갖는다. 이미지만

### 🔴 `git add .` 하면 딸려 들어가는 것

`AllDap-pr2` 에서 `git status` 에 잡히는 미추적 파일이 셋이다.

```
?? .pr2-body.md
?? .s1-old-hash.txt
?? ai-service/.venv
```

앞의 둘은 `.gitignore` 에 규칙이 없다(의도적으로 임시 파일이라 그렇다).

⚠️ **`ai-service/.venv` 는 사정이 다르고, 앞선 진단이 한 겹 얕았다.**
`.gitignore` 44행에 `.venv/` 가 있으므로 메인 worktree(`AllDap`)에서는 정상적으로 걸린다.
`AllDap-pr2` 에서만 안 걸리는 이유는 **거기의 `ai-service/.venv` 가 디렉터리가 아니라
메인 worktree 를 가리키는 심볼릭 링크**이기 때문이다.
`.venv/` 처럼 슬래시로 끝나는 패턴은 **디렉터리만** 매치하고 심볼릭 링크는 매치하지 않는다.

→ 즉 "`.gitignore` 가 `.venv` 를 안 잡는다" 가 아니라 **"슬래시 패턴이 심볼릭 링크를
안 잡는다"** 다. 규칙을 고칠 일이 아니고, `AllDap-pr2` 에서 **파일 경로를 명시해서
`git add`** 하면 된다. `git add -A` 와 `git add .` 를 쓰지 말 것.

## 5. 별도 슬라이스로 미룬 것

### ⓐ `ANSWER_INCOMPLETE` 안내문이 사실과 다르다

현재 문구(`ErrorCode.java` 109행):

> "답변이 길어져 끝까지 완성하지 못했습니다. **같은 질문을 다시 보내도 같은 결과이니**,
> 질문을 더 좁혀서(한 번에 한 가지만) 물어봐 주세요."

**"같은 결과" 라고 단언하는데, 오늘 같은 질문이 66회 중 65회 성공했다.**

원인 구조는 확인했다. `generator.generate` 가 서로 다른 두 실패를 **같은
`GenerationFailed`** 로 던진다.

| 실제 실패 | 재시도하면 |
|---|---|
| **잘림** (`finish_reason == "length"`) | 같은 결과다. `temperature=0` 이라 같은 자리에서 잘린다 |
| **빈 응답** (`not answer`) | **풀릴 수 있다** |

문구는 잘림만 설명한다.

**[추정] 이번 건은 빈 응답 쪽이 유력하다.** 근거는 답변 최대 길이가 83자인데
`max_tokens` 가 1024 라 잘릴 이유가 없다는 것이다.
🔴 **단정할 수 없다.** 둘을 가르는 유일한 신호가 `main.chat` 의 `_log.warning` 인데
**uvicorn 로그를 파일로 남기지 않아 확인할 수가 없다.**

→ **다음 측정부터 uvicorn 로그를 파일로 받을 것.**

### ⓑ 세션 id 재사용으로 집계가 샌다

드라이런이 `s1-0` ~ `s1-4` 를 재사용해서 Spring 이 같은 대화 행에 이어 붙였다.
그래서 `LIKE` 로 세면 67건인데 시각으로 자르면 66건이 된다.

→ **다음 측정부터 세션 id 에 실행 구분자를 넣을 것** (예: `s1-<실행시각>-0`).

### ⓒ `fake_cf_check` 의 지연 검사 창이 헐겁다

상한이 `expected + 300` 이라는 **절대값**이다. generate 지연을 100ms 대로 낮추면
허용 창이 상대적으로 4배 헐거워져 **계측이 틀려도 검사가 안 걸린다.**
비율 기준으로 바꾸는 것이 맞다.
