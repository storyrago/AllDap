# 무엇이 어디까지 검증됐나

> README 에 있던 "W1 완료 기준" · "PDF·DOCX 는 어디까지 확인됐나" · "알아둘 것" 절을 옮겨온 문서입니다.
> **"안 나빠졌다" 와 "재보지 않았다" 는 다릅니다.** 이 문서는 그 둘을 갈라 적는 자리입니다.

## 환각 억제 (이 제품의 핵심 가치)

### W1 완료 기준: ✅ 3개 전부 실측 통과 (2026-07-31)

- [x] 문서 업로드 → 상태가 `ready` 로 바뀜
- [x] 질문 → 출처(`sources`)가 포함된 답변이 나옴
- [x] **문서에 없는 질문 10개 → 10개 모두 `is_fallback: true`** (기준: 8개 이상)

세 번째가 가장 중요합니다. 환각을 막지 못하면 이 제품은 의미가 없습니다.

재현: `cd ai-service && .venv/bin/python -m app.fallback_e2e_check`

⚠️ **대조군이 있어야 합니다.** 문서에 답이 **있는** 질문을 안 섞으면
"전부 fallback 하는 고장난 봇" 도 10/10 을 받습니다. 현재 대조군 3/3.
그리고 **코퍼스를 바꾸면 질문 목록도 반드시 함께 점검하세요.**
실제로 코퍼스를 늘리다 기존 질문 3개의 답이 문서에 생겨 7/10 이라는 거짓 미달이 나왔습니다.

⚠️ **측정된 fallback 수치는 그때그때의 모델 조합 기준입니다.**
생성 모델이든 임베딩 모델이든 바꾸면 반드시 다시 재야 합니다.

### 1차 방어선을 되살린 방법 (2026-09-06)

환각 억제는 두 겹입니다. 검색 단계 컷오프(`max_distance`)와 생성 단계(`NO_ANSWER`).

> ⚠️ **당시 10/10 은 2차 방어선이 혼자 막아낸 결과였습니다.**
> 1차인 `max_distance=0.55` 는 거의 작동하지 않아서,
> "근거가 없으면 LLM 을 아예 호출하지 않는다" 는 비용 절감 경로가 열리지 않았습니다.

✅ **2026-09-06 에 1차 방어선을 되살렸습니다. 다만 `max_distance` 를 낮춰서가 아닙니다.**
낮추는 쪽은 실측으로 기각됐습니다. 컷을 낮추면 근거로 쓸 청크가 **함께** 줄어들고,
근거가 줄면 답이 틀립니다(0.45 는 회당 오답 2건, 0.43 은 3건).

살린 방법은 **판정과 컷을 분리한 것**입니다. 한 값이 반대 방향을 원하는 두 일을 겸하고 있었습니다.

| 역할 | 원하는 값 |
|---|---|
| 어떤 청크를 근거로 쓸지 (개수) | **높아야** 한다 → `max_distance = 0.55` 유지 |
| 근거가 있기는 한가 (판정) | **낮아야** 한다 → `answerable_max_distance = 0.44` 신설 |

벡터 최근접 거리가 `answerable_max_distance` 보다 멀면 근거를 통째로 버리고 LLM 을 부르지 않습니다.
그 결과 **검색컷(LLM 미호출)이 1/10 에서 8/10 으로 올라갔고**, 평가 문항은 하나도 걸리지 않아
전체 충실성·관련성·응답률이 소수점까지 그대로입니다.
**"효과가 없다" 가 아니라 "부작용이 없다" 로 읽어야 합니다.**

옛 기록의 "0.33 근처면 작동한다" 는 **반증됐습니다.** 그 숫자는 정답 청크까지의 거리였고,
판정에 쓰는 최근접 거리(`d1`)의 최대는 0.4026 이라 0.33 으로 자르면 멀쩡한 문항이 잘립니다.

재현: `cd ai-service && .venv/bin/python -m app.answerable_check`

⚠️ **이 값은 코퍼스와 임베딩 모델에 딸려 있습니다.** 둘 중 하나라도 바뀌면 무효입니다.

**한계: 홀드아웃이 6/10 입니다**(임계값 결정에 쓴 10문항은 8/10).
낮은 이유는 과적합이 아닙니다. 감시 낱말이 코퍼스에 0건이어도 **의미가 가까운 문서**가 있으면
`d1` 이 작습니다. "사내 벤처 제도" 가 `45_아이디어_제안제도` 때문에 0.3283 으로
정답 문항 중앙값(0.3642)보다도 가깝습니다. **거리로는 원리적으로 못 가르는 부류이고
2차 방어선의 몫입니다.** 임계값은 홀드아웃을 보기 **전에** 골랐고 보고 나서 바꾸지 않았습니다.
바꾸면 홀드아웃이 아니게 됩니다.

## 통합 테스트가 초록불인 채로 난 버그들

**통합 테스트가 초록불이어도 진짜 상대와 붙여보기 전까지는 연동을 검증했다고 말하지 않습니다.**
그 교훈이 실제 버그 셋에서 나왔습니다.

### 진짜 uvicorn 과 붙이자 나온 것 (2026-08-01)

첫 업로드가 422 로 실패했습니다. JDK `HttpClient` 기본값이 HTTP/2 라 평문 상대에게
h2c 업그레이드를 함께 요청하는데, uvicorn(h11)이 그걸 지원하지 않아
**chunked 본문을 FastAPI 까지 전달하지 않습니다.** multipart 는 완벽한데
"file 필드가 없다" 는 422 가 났습니다.

→ `RestClientConfig` 에서 `HTTP_1_1` 로 고정해 해결했습니다.
회귀 테스트는 본문 대신 **"보내면 안 되는 헤더가 없는가"** 를 검사합니다.

가짜 서버는 multipart 를 파싱하지도, 업그레이드 요청을 처리하지도 않아
**재현 자체가 불가능한 버그**였습니다.

### 진짜 브라우저로 열자 나온 것 (2026-08-02)

**버그 ①: 로그인한 채 새로고침하면 로그아웃됐습니다.**
`useSyncExternalStore` 의 세 번째 인자(서버 스냅샷)는 **하이드레이션 첫 렌더에도 쓰입니다.**
거기서 `null` 을 돌려주니 "토큰이 없다" 와 "아직 못 읽었다" 가 같은 값이 되어,
가드가 첫 렌더에서 바로 `/auth` 로 튕겼습니다. 화면 안에서 이동할 때는 멀쩡해서 안 보였습니다.
→ 서버 스냅샷을 **`undefined`(아직 모름)** 로 바꿔 `null`(확실히 없음)과 갈랐습니다.

**버그 ②: 위젯이 실제로 설치되면 봇 설정 조회가 반드시 403 이었습니다.**
채팅 페이지(`/w/[publicKey]`)가 자기도 `/api/w/{key}/config` 를 불렀는데,
**iframe 에서 나가는 요청의 Origin 은 고객 사이트가 아니라 우리 앱입니다.**
고객이 허용 목록에 우리 주소를 넣을 리 없으니 영원히 막힙니다.
→ 허용 도메인 검증을 통과할 수 있는 요청은 **고객 페이지에서 도는 로더**뿐입니다.
로더가 한 번 부르고 결과를 `host-info` 로 실어 내려주도록 바꿨습니다.

**"누구의 Origin 으로 나가는 요청인가" 를 따지지 않으면 iframe 위젯의 도메인 검증은 반드시 틀립니다.**

🔴 **셋 다 통합 테스트 71건이 전부 초록불인 상태에서 났습니다.**

### 짜둔 검사가 아무 데서도 안 돈 사고 (두 번)

같은 부류를 두 번 냈습니다. **검사를 안 짠 것이 아니라 짜둔 검사가 안 돈 것**입니다.

1. **오픈 리다이렉트.** `web/lib/redirect.ts` 에 검증을 짜뒀는데 자체 점검
   (`redirect.check.ts`)이 CI 에 안 걸려 있었습니다. `url.pathname` 이 `//` 로 시작하면
   반환값이 프로토콜 상대 URL 이 되어 라우터가 외부로 나가는 채로 배포됐습니다.
2. **`Forwarded` 헤더 점검 명령.** 본문에 `sessionId` 가 없어 `@Valid` 에서 400 이 나
   rate limiter 를 지나가지도 못했는데, 그 모습이 문서의 실패 판정 기준과 겹쳐
   **언제 돌려도 실패를 보고했습니다.**

→ **점검 명령도 한 번은 실제로 돌려서 걸려야 할 것이 걸리는지 봐야 합니다.**
`parsers_check` 를 만들 때 파서를 일부러 셋 망가뜨려본 것이 이 교훈의 적용입니다.

## PDF · DOCX 는 어디까지 확인됐나 (섞어서 말하지 말 것)

축이 다섯입니다. **2026-09-11 에 종단과 재현 가능성이 닫혔고, 대용량 하나가 열려 있습니다.**

🔴 **"재현 가능성이 닫혔다" 의 뜻을 좁혀 읽으세요.** 2026-07-31 에 쓴 그 파일을 되살린 것이
아니라 **앞으로는 다시 돌려볼 수 있다**는 뜻입니다. 새로 만든 자산이라 옛 ✅ 를 소급해서
증명하지 않습니다.

| 축 | 판정 |
|---|---|
| 파서 단위 (파일 → 텍스트 추출) | ✅ 저장소 안 한글 PDF·DOCX·HWPX 로 확인. **CI 에서 돈다** |
| 업로드 파이프라인 종단 (→ `status=ready`) | ✅ 세 형식 전부 `ready` 까지. Spring 경유도 봤지만 **자동화는 Python 직행만** |
| 여러 문서에서의 동작 | ✅ 코퍼스 50문서·306청크 |
| **대용량 문서** | ❌ **미검증. 아래 이유로 일부러 안 닫았다** |
| 재현 가능성 | ✅ **앞으로는 다시 돌려볼 수 있다.** 옛 파일의 복원이 아니라 새 자산이다 |

**닫은 방법.** `ai-service/testdata/fixtures/` 에 한글 PDF(2페이지)·DOCX(본문+표)·
HWPX(`<hp:run>` 3분할 문단)를 넣고 점검 둘을 붙였습니다.

```bash
cd ai-service && .venv/bin/python -m app.parsers_check      # 파일 → 텍스트 (DB·외부 API 없음)
cd ai-service && .venv/bin/python -m app.upload_e2e_check   # 업로드 → ready (진짜 DB·진짜 임베딩)
```

- `parsers_check` 15건은 **CI 에서 돕니다**(DB 도 외부 API 도 안 씁니다). 이 저장소는 짜둔 검사가
  아무 데서도 안 도는 사고를 두 번 냈습니다(오픈 리다이렉트, `Forwarded` 점검 명령).
- **파서를 일부러 셋 망가뜨려 점검이 빨간불이 되는 것을 보고 되돌렸습니다.** HWPX run 병합 제거,
  DOCX 표 순회 제거, PDF 페이지 구분자 제거. 통과하는 검사를 만드는 것과 **실패할 줄 아는**
  검사를 만드는 것은 다른 일입니다.
- `upload_e2e_check` 는 `ready` 가 무엇을 뜻하는지까지 봅니다. `chunk_count` 컬럼만 보지 않고
  DB 의 청크 수·**임베딩이 전부 찼는지**·차원이 `EMBEDDING_DIM` 과 맞는지를 직접 셉니다.
  그 컬럼은 *INSERT 하려던 개수*고 임베딩이 실제로 들어갔는지는 다른 사실입니다.
- 종단은 셋 다 태웠습니다. **Python `/internal` 직행 · 진짜 uvicorn + 진짜 HTTP · Spring 경유.**
  Spring 경유는 자동화돼 있지 않고 손으로 한 번 돌렸습니다(`pending → processing → ready` 전이를
  직접 봤습니다. 한글 파일명과 camelCase 변환도 정상). 자동화하지 않은 이유는 계정·봇을 만들어야
  하는데 `users`·`bots` 쓰기가 Spring 소유이기 때문입니다.
- 옛 간접 증거("실제 PDF 51쌍 0 오탐", `decisions.md` 2026-08-05)는 **이제 근거로 쓰지 않습니다.**
  직접 본 것이 생겼습니다. 지우지 않고 남기는 이유는 **무엇이 왜 추론이었는지가 재료이기 때문**입니다.
  그 "쌍" 은 청크 쌍을 pgvector 최근접으로 고른 것이라 *청킹·임베딩까지는 갔다*는 뜻이었지,
  `status=ready` 로 바뀌는 것을 본 것이 아니었습니다. 게다가 **DOCX 에는 그 간접 근거조차 없었습니다.**

🔴 **대용량 문서는 ❌ 그대로입니다. 못 한 것이 아니라 안 한 것입니다.**
fixture 는 수 KB 라 pymupdf 가 PDF 를 통째로 메모리에 올리는 문제(운영 1GB 인스턴스 OOM)의
구간에 아예 못 갑니다. 거길 재려면 **수십 MB PDF 를 저장소에 커밋해야 하는데 그건 재현 자산이
아니라 짐입니다.** 메모리 프로파일이 필요한 별도 슬라이스입니다. 지금 그 구간을 피해 가는 방법은
업로드 상한을 환경변수로 빼둔 것뿐입니다(`UPLOAD_MAX_SIZE` / `UPLOAD_MAX_BYTES`, 기본 10MB).

⚠️ **위 ✅ 가 덮지 않는 것 셋.** 적어두지 않으면 ✅ 가 실제보다 넓게 읽힙니다.

- **줄바꿈된 PDF 는 검증되지 않습니다.** pymupdf 의 `insert_text` 는 줄바꿈을 하지 않고 넘치면
  조용히 자르므로, fixture 는 각 줄을 페이지 폭 안에 맞춰 만들었습니다(생성기가 폭 초과를 빌드
  시점에 막습니다). **실제 PDF 는 문단이 여러 줄로 접혀 오고 추출 결과도 그 줄바꿈을 갖습니다.**
- **fixture PDF 는 "한글·워드가 만든 PDF" 가 아닙니다.** pymupdf 내장 CJK 폰트로 우리가 만든
  것이라, 그 도구들이 내는 글리프 매핑·CID 인코딩 변종은 못 잡습니다(외부 폰트를 저장소에 넣지
  않으려고 택했습니다).
- **fixture HWPX 는 최소 골격입니다.** `Contents/section*.xml` 의 `<hp:p>`·`<hp:t>` 만 갖췄습니다.
  파서가 읽는 것이 정확히 그 둘뿐이라 파서 관점에서는 충분하지만 "진짜 한글 파일" 은 아닙니다.

## 알아둘 것

### 임베딩 차원은 코드와 스키마를 함께 고쳐야 한다

임베딩 모델을 바꾸면 `EMBEDDING_DIM` 과 마이그레이션의 `VECTOR(n)` 을 **함께** 바꿔야 합니다.
V1 은 수정 금지입니다(Flyway 체크섬이 깨집니다). 새 마이그레이션으로 `ALTER` 하세요.
`V2__embedding_1024.sql` 이 그 예입니다.

순서도 중요합니다. 실측으로 확인했습니다.

```
인덱스 드롭 → UPDATE chunks SET embedding = NULL → ALTER ... TYPE VECTOR(n)
→ 인덱스 재생성 → 재임베딩(.venv/bin/python -m app.reembed)
```

데이터가 있는 채로 `ALTER` 하면 `expected N dimensions, not M` 로 실패합니다.

🔴 **`V1__init.sql` 의 "1536 = OpenAI text-embedding-3-small 기준" 주석은 사실이 아니고,
차원도 1536 이 아닙니다.** 현재 임베딩은 **Cloudflare Workers AI `@cf/baai/bge-m3`(1024차원)**
이고, V2 에서 차원을 바꿨습니다. 주석 한 글자만 고쳐도 Flyway 체크섬이 깨져 기동이 막히므로
**일부러 두었습니다.** 이 줄이 그 정정본입니다.

### 제공자가 둘이다

⚠️ **임베딩과 생성의 제공자가 다릅니다.** 임베딩·답변 생성·채점·리랭커는 Cloudflare,
테스트 질문 생성만 Google Gemini 입니다. 한쪽만 보고 "Cloudflare 로 옮겼다" 고 말하면 안 됩니다.

임베딩을 옮긴 이유는 **성능이 아니라 약관과 한도**입니다. Gemini 무료 등급은 입력을 학습에
쓰는데, 이 제품은 고객 사내 문서를 받는 것이 목적입니다.
**"한국어 성능이 더 좋아서 바꿨다" 고 말하면 안 됩니다.** 두 모델을 같은 한국어 벤치마크에서
나란히 잰 측정치가 없습니다. 방어 가능한 답은 이것입니다:
*"비용과 데이터 정책 때문에 바꿨고, 성능 우위는 공개 비교가 없어서 W4 에서 직접 쟀습니다."*

🔴 **Gemini 에 남은 경로 하나도 안전해진 것은 아닙니다.** `evaluator.make_question` 이
프롬프트에 실어 보내는 것은 **`chunks.content`, 즉 고객이 올린 문서 본문 그대로**입니다.
달라진 것은 위험의 크기입니다. 상시 경로(모든 채팅·모든 업로드)가 아니라
**봇 주인이 "테스트 질문 생성" 을 누를 때만**, 표본으로 뽑힌 청크들만 나갑니다.
→ **파일럿 전에 결제 계정을 연결하거나 질문 생성도 제공자를 바꿔야 합니다.**
지금은 테스트 코퍼스뿐이라 문제없습니다.

### 그 밖에

- 구버전 `.hwp` 는 바이너리 포맷이라 미지원입니다. 사용자에게 `.hwpx` 저장을 안내합니다.
  (Java 쪽 `hwplib` 으로 붙이는 것도 방법이지만 아직 안 했습니다)
- 백그라운드 처리는 FastAPI `BackgroundTasks` 라 프로세스가 죽으면 작업이 유실됩니다.
  트래픽이 붙으면 Redis + RQ 로 교체할 것입니다.
- pgvector 는 수백만 벡터 규모에서 전용 벡터DB보다 불리합니다. 현재 규모에선 문제없습니다.
- rate limit 은 **인메모리**입니다. 인스턴스를 늘리면 각자 세므로 실질 한도가 배가 됩니다.
  **수평 확장 시작 시점이 교체(Redis) 시점입니다.**
- `.env` 는 커밋되지 않습니다(`.gitignore`). 새 키가 필요해지면 `.env.example` 에 항목만 추가하세요.

## 이 저장소가 반복해서 낸 버그의 부류

여덟 건이 **전부 같은 모양**입니다. 원인이 다른 사실들을 같은 값으로 뭉갠 것입니다.

| 버그 | 무엇을 뭉갰나 |
|---|---|
| `answered_rate` 분모에 처리 실패를 포함 | "답을 못 했다" 와 "물어보지도 못했다" |
| `avg_faithfulness` 로 설정 비교 | 답을 덜 할수록 올라가는 지표였다 (생존 편향) |
| 채점자·리랭커가 청크 앞 200자만 봄 | 생성 모델은 전체를 보는데 판정자는 절반만 봤다 |
| `generate` 의 `or not answer` | "토큰이 없어 빈 응답" 과 "문서에 답이 없다" |
| `judge.score` 의 `None` 을 fallback 과 같은 값으로 | "답을 못 했다" 와 "재지 못했다" |
| `NoResourceFoundException` 이 catch-all 로 | "서버가 아프다" 와 "그런 주소가 없다" |
| `parse_prom_counter` 가 `NaN` 을 정상 값으로 | "계측이 살아 있다" 와 "계측이 죽어 NaN 이다" |
| 배포 SSH 의 종료코드 255 | "옛 이미지" 와 "기동 실패" 와 "SSH 끊김" |

🔴 **새 신호를 만들 때마다 같은 질문을 하세요**(지표든 종료코드든 상태 코드든 파서든):

1. **여기서 뭉개지는 서로 다른 사실이 있는가.**
2. **이 값을 읽지 못했을 때와, 읽어서 이 값이 나왔을 때가 구분되는가.**

자세한 경위는 [`../AGENTS.md`](../AGENTS.md) 에 있습니다.
