# 코드리뷰 출력 형식

이 저장소의 PR 에 리뷰를 게시할 때 쓰는 **고정 형식**이다.
형식의 근거가 되는 실제 예시는 `hwanh2/kcalog` PR #56 의 리뷰이고, 아래 구조는 그것을 그대로 옮긴 것이다.

**왜 형식을 고정하는가.** 리뷰를 쓸 때마다 구조가 달라지면 ① 읽는 쪽이 "반드시 수정이 있는가" 를
매번 본문에서 찾아야 하고 ② 무엇을 실제로 돌려봤는지가 흐려지고 ③ 나중에 리뷰끼리 비교할 수가 없다.
특히 ②는 이 저장소가 반복해 낸 버그 부류(원인이 다른 사실들을 같은 값으로 뭉개는 것)와 같은 문제라,
리뷰 문서에도 같은 규칙을 적용한다.

---

## 심각도 축

지적은 **4축 + nit** 로 분류한다. 한 항목이 여러 축에 걸리면 더 무거운 축으로 센다.

| 축 | 판정 기준 |
|---|---|
| **정확성** | 이 코드가 의도한 결과를 내지 못한다. 오동작, 잘못된 계산, 놓친 분기, 경계 조건 |
| **보안** | 인증·권한·`bot_id` 스코프 격리·비밀값 취급이 깨진다. 데이터가 새거나 남의 것을 볼 수 있다 |
| **스펙** | 동작은 하는데 합의된 계약과 다르다. API 컨트랙트, 에러 응답 포맷, 필드 표기(snake/camel), 문서와의 불일치 |
| **유지보수** | 지금은 맞지만 다음 사람이 틀리기 쉽다. 중복된 진실, 테스트 없는 불변식, 이름과 실제가 다른 것 |
| **nit** | 고치면 좋지만 안 고쳐도 사고가 나지 않는 것. 문구, 네이밍, 미세한 중복 |

### 존재 확신 ≠ 심각도

**문제가 실재하는지**와 **그게 얼마나 심각한지**는 다른 판단이다. 둘을 섞으면
"확실하니까 반드시 수정" 이라는 잘못된 승급이 일어난다.

- 확정했더라도 **범위가 단발성**이면(한 화면·한 경로에서만, 사용자 피해가 없음) nit 으로 내린다.
- 확신이 낮아도 **깨지면 격리·결제·fallback 이 무너지는 자리**면 올려 적고, 대신 "확인하지 못했다" 를 명시한다.
- **올리거나 내렸으면 그 근거를 `검증 결과` 에 남긴다.** 근거 없이 옮기면 다음 리뷰에서 기준이 또 달라진다.

## 구조 (순서 고정)

### 1. 제목

```
## 🤖 코드리뷰
```

### 2. 한 줄 카운트

```
정확성 2 · 보안 0 · 스펙 1 · 유지보수 1 (+ nit 3)
```

0 인 축도 지운다: 축이 통째로 사라지면 "안 봤다" 와 "봐서 없었다" 가 구분되지 않는다.

### 3. 요약 단락

1~2문장으로 **무엇을 바꾼 PR인지** 적고, 이어서 **수정 유무를 굵게 단언**한다.

```
**🔴 반드시 수정은 없습니다.**
```

단언을 요구하는 이유: 리뷰를 받는 쪽이 가장 먼저 알아야 할 것이 그것 하나이고,
본문을 끝까지 읽어야 알 수 있게 두면 "없다" 와 "못 봤다" 가 섞인다.

그다음 **견고했던 축을 짧게 나열**한다(`bot_id` 격리, 트랜잭션 경계, 에러 코드 분리 등).

### 4. `### 🔴 반드시 수정`

없으면 `- 없음` 한 줄. 칸 자체를 생략하지 않는다.

### 5. `### 🟡 개선 권장 (nit N건)`

항목마다 아래 네 가지를 **모두** 갖춘다.

1. **굵은 제목 한 줄**: 무엇이 문제인지 한 문장으로
2. **퍼머링크**: `파일#L줄`
3. **왜 문제인지**: 어떤 상황에서 무엇이 잘못되는지. "안 예쁘다" 가 아니라 결과를 적는다
4. **`→ ` 로 시작하는 제안 한 줄**

### 6. `### 🟢 좋은 점`

굵은 제목 + 근거. **칭찬이 아니라 구조가 이 사고를 어떻게 막는가**를 적는다.

- ❌ "테스트가 꼼꼼합니다"
- ✅ "**기본 카드 삭제 거부를 DB 부분 유니크 인덱스로 받쳤다.** 서비스 코드를 우회해 직접 UPDATE 해도 기본 0장 상태가 만들어지지 않는다."

좋은 점을 적는 이유는 분위기가 아니라 기록이다. **다음에 그 구조를 건드리려는 사람이
왜 그렇게 돼 있는지 알아야** 하고, 그 설명이 남는 자리가 여기다.

### 7. `### 검증 결과`

**실제로 무엇을 돌렸고 무엇을 대조했는지.** 명령과 결과를 그대로 적는다.

🔴 **"돌렸다" 와 "정적으로 검산했다" 를 섞지 말 것.**
실제 실행한 것만 실행했다고 쓰고, 코드를 읽어서 판단한 것은 그렇게 쓴다.
돌리지 못한 것은 이 칸이 아니라 `다 보지 못한 범위` 로 내린다.
이 저장소는 "초록불인데 진짜 상대와 붙이자 깨진" 경험이 두 번 있다(HTTP/2 업그레이드, 위젯 Origin).
**통합 테스트 통과를 연동 검증이라고 쓰지 않는다.**

심각도를 올리거나 내린 항목이 있으면 그 근거도 여기 적는다.

### 8. `### 다 보지 못한 범위`

- 환경이 없어 돌리지 못한 것(외부 API 키, 브라우저 종단, 결제창)
- 도구 한계로 확인 불가한 것(iframe 자동 입력, 운영 DB)
- 시간을 이유로 의도적으로 보지 않은 것

**비워두지 않는다.** 전부 봤다고 말할 수 있는 리뷰는 거의 없고,
빈 칸은 "다 봤다" 로 읽힌다.

## 공통 규칙

- **모든 지적에 퍼머링크.** 커밋 SHA 가 박힌 `blob/<sha>/path#L줄` 형태로 쓴다.
  브랜치 이름 링크(`blob/main/...`)는 커밋이 쌓이면 **가리키는 줄이 바뀌어** 엉뚱한 코드를 가리킨다.
- **모든 지적에 `→ ` 제안 한 줄.** 문제만 적고 끝내지 않는다. 제안이 안 떠오르면
  그건 대개 문제를 충분히 좁히지 못한 것이다.
- **줄표(em dash) 금지.** 쉼표·콜론·괄호로 대체한다. 가운뎃점(·)은 카운트 줄처럼 나열에만 쓴다.
- 한국어로 쓴다. 에러 메시지·코드 식별자는 원문 그대로 인용한다.

## 빈 템플릿

다음 리뷰 때 아래를 복사해 채운다.

```markdown
## 🤖 코드리뷰

정확성 0 · 보안 0 · 스펙 0 · 유지보수 0 (+ nit 0)

<무엇을 바꾼 PR인지 1~2문장>. **🔴 반드시 수정은 없습니다.** <견고했던 축 나열>.

### 🔴 반드시 수정

- 없음

### 🟡 개선 권장 (nit 0건)

**<무엇이 문제인지 한 문장>**
[`path/to/File.java#L42`](https://github.com/<owner>/<repo>/blob/<sha>/path/to/File.java#L42)

<어떤 상황에서 무엇이 잘못되는지>

→ <제안 한 줄>

### 🟢 좋은 점

**<구조적으로 무엇이 안전한가>**

<그 구조가 어떤 사고를 막는지>

### 검증 결과

- 실행: `<명령>` → <결과>
- 정적 대조: <무엇을 무엇과 맞춰봤는지>
- 심각도 조정: <올린/내린 항목과 근거>

### 다 보지 못한 범위

- <돌리지 못한 것과 이유>
```
