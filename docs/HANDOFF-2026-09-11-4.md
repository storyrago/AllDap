## 2. 리뷰 출력 형식을 7칸으로 고정했다

`docs/code-review-format.md`. 형식의 근거가 된 실제 예시는 `hwanh2/kcalog` PR #56 의 리뷰다.

**심각도 4축 + nit**: 정확성 · 보안 · 스펙 · 유지보수 · nit. 각 축의 판정 기준을 이 저장소
맥락으로 맞췄다(보안은 `bot_id` 격리·비밀값, 스펙은 API 컨트랙트·에러 포맷·snake/camel).

**순서 고정 7칸**: 제목 → 카운트 한 줄 → 요약(수정 유무 굵게 단언) → 🔴 반드시 수정 →
🟡 개선 권장 → 🟢 좋은 점 → 검증 결과.

담은 규칙 중 중요한 셋:
- **존재 확신 ≠ 심각도.** 문제가 실재하는지와 얼마나 심각한지는 다른 판단이다. 확정했더라도
  단발성이면 nit 으로 내리고, 올리거나 내렸으면 근거를 `검증 결과` 에 남긴다.
- **"돌렸다" 와 "정적으로 검산했다" 를 섞지 않는다.** 돌리지 못한 것도 그 칸에 적는다.
  HTTP/2 업그레이드와 위젯 Origin 두 사건이 근거다(통합 테스트가 전부 초록불인 상태에서 났다).
- **모든 지적에 커밋 SHA 퍼머링크와 `→ ` 제안 한 줄.**

> ⚠️ **처음에는 8칸이었다. `다 보지 못한 범위` 를 따로 두었다가 빼서 7칸이 됐다.**
> 검증 결과와 같은 사실을 두 자리에 나눠 적게 되어서다(실제로 #117 리뷰에서 그랬다).
> 내용을 버린 것이 아니라 7번 칸 안으로 옮겼고, 빈 템플릿에 `돌리지 못한 것` 줄을 남겼다.

## 4. 🔴 파서 위험 조사: 내 리뷰 판정이 틀렸다

#117 리뷰에 "접두사 매칭과 조기 반환은 지금 조회하는 이름들로는 발동 불가" 라고 적었다.
그 판단이 **실제 메트릭 목록과 대조된 것이 아니었다.** 조사시켰더니 하나가 실재했다.

| 위험 | 판정 |
|---|---|
| 접두사 매칭 (`startswith`) | 🔴 **6개 중 1개 실재** |
| 조기 반환 (`float()` 실패 시 `None`) | ✅ 발동 불가 확정 |

🔴 **`alldap_ratelimit_keys` vs `alldap_ratelimit_keys_cleared_total`.**
`RateLimiter.java:108`·`112` 가 `alldap.ratelimit.keys`(게이지)와 `alldap.ratelimit.keys.cleared`
(카운터)를 등록하고, Micrometer 가 카운터에 `_total` 을 붙여 **앞이 뒤의 접두사**가 된다.
조회는 `s3_context.py:289` 에서 `{}` 로 하므로 라벨 조건이 없어(빈 시퀀스의 `all()` 은 True)
**두 줄 다 통과하고 먼저 나오는 줄이 이긴다.**
- 실측: 실제 노출 순서에서는 `3.0`(게이지, 맞음), 줄 순서를 뒤집으면 `1.0`(cleared 값).
- **막고 있는 것은 파서가 아니라 prometheus-metrics 1.x 의 알파벳 순 출력이다.**
  파서에는 그 순서에 기댄다는 근거가 한 줄도 없다.
- 오늘 피해는 작다. 이 값은 `is None` 존재 확인에만 쓴다. 다만 그 검사가 증명하려던 것
  ("keys 게이지가 붙어 있다")이 **"keys 로 시작하는 무언가가 있다"** 로 약해진다.

🔴 **덤으로 나온 것: `float('NaN')` 은 실패하지 않고 `nan` 으로 통과한다.**
게이지가 참조를 잃으면 Micrometer 는 NaN 을 낸다. `keys_gauge is None` 검사는
**"계측이 살아 있다" 와 "계측이 죽어 NaN 이다" 를 뭉갠다.** 이 저장소의 그 상습 부류다.

**내가 놓친 이유가 명확하다.** 리뷰할 때 조회 이름을 **핸드오프 문서에서 가져왔고**, 거기
없던 `alldap_ratelimit_keys` 가 하필 유일한 충돌이었다. 코드에서 직접 뽑지 않은 대가다.

**근거의 강도**: 서버를 띄워 받은 것이 아니라 **코드 복원 + 라이브러리 실측**이다. 등록 지점에서
미터 8개를 복원하고, 그 8개를 프로젝트 Gradle 캐시의 실제 micrometer 1.16.6 + prometheus-metrics
1.4.3 으로 독립 하네스에 등록해 `scrape()` 출력을 받았다. **완전성은 논증된다**: 조회 이름이
전부 `alldap_` 로 시작하므로 충돌 후보도 반드시 그렇고, `alldap_*` 는 전부 우리가 등록한 것이다.
(저장소의 `results/S4-*-prom-after.txt` 는 `alldap` 로 걸러 저장된 부분 캡처라 전체 목록의
근거로는 못 쓴다)

## 6. 이 세션에서 배운 것 (기록)

### ⓐ 🔴 커밋이 브랜치를 잘못 타서 PR 의 근거가 흐려질 뻔했다

리뷰 형식 문서 연결 커밋(`fd12bcb`)이 `main` 이 아니라 **PR #117 브랜치**에 올라갔다.
공용 워크트리가 그 브랜치에 있던 탓이다. 그대로 두면 "순수 이동" 만 담아야 할 리팩터 PR 에
무관한 문서 변경이 섞여 **그 PR 이 재측정 없이 통과할 근거 자체가 흐려진다.**

→ `main` 에 cherry-pick(`e1b6d56`) 하고 브랜치에서 걷어내려 했으나 **force-push 가 차단됐다.**
되돌리기 대신 `main` 을 브랜치에 병합했다. `main` 이 이미 같은 내용을 가졌으므로 PR 차분에서
그 문서 변경이 사라진다. 지금 #117 차분은 loadtest 4개 파일뿐이다.
자체 점검 3종(`s3_check` · `s4_check` · `fake_cf_check`) 전부 종료 0 으로 재확인했다.

**교훈: 여러 세션이 공용 워크트리를 쓰면 커밋 전에 `git branch --show-current` 를 볼 것.**

### ⓑ 🔴 충돌 원인을 엉뚱한 커밋에 귀속했다

처음에 `7e80b77` 이 `decisions.md` 를 건드려 충돌했다고 적었는데, 그 커밋은 `docs/` 아래
파일을 **하나도 건드리지 않았다**(23개 파일 전부 코드 주석). `docs:` 는 커밋 타입 접두사인데
그것을 파일 목록으로 착각했다. 실제 원인은 `c304be6` 이고, 충돌한 쌍은 `c304be6` 과 `fd12bcb`
로 **둘 다 같은 세션이 만든 것**이다. 즉 "세 세션이 동시에 append 해서" 가 아니라
**"한 세션의 커밋 하나가 브랜치를 잘못 타서"** 다. ⓐ 와 별개 사건이 아니라 같은 사건의 두 증상이다.

**원인을 엉뚱한 커밋에 붙여두면 다음에 같은 충돌을 엉뚱한 데서 찾는다.** 이 저장소가 반복해
낸 "서로 다른 사실을 같은 값으로 뭉개기" 와 같은 방향이다.

### ⓒ 분배한 작업이 세션 `/clear` 로 유실됐다

파서 조사를 맡긴 세션의 컨텍스트가 비워져 지시가 사라졌다. 그 세션이 **"없는 작업을 했다고
하지 않고" 유실됐다고 보고한 것**이 옳은 처리였다. 다른 세션에 재배정해 §4 의 결과를 얻었다.

**교훈: 분배한 작업은 "완료 보고" 가 오기 전까지 완료가 아니다.** 세션이 idle 로 보이는 것은
끝났다는 뜻이 아니다.

### ⓓ 하위 세션의 보고를 액면가로 받지 않은 것이 두 번 유효했다

- 한 세션이 #117 본문의 행 번호를 `main` 기준으로 적었다. 둘 다 실측인데 **서로 다른 커밋을
  본 것**이었다(이 PR 이 `def` 23줄을 지워 아래 코드가 당겨진다). PR 본문은 그 PR 이 만드는
  상태를 설명하는 자리라 브랜치 기준이 맞다.
- 반대로 ⓑ 는 하위 세션이 **나를** 정정한 것이다. 양방향으로 대조해야 한다.

### ⓔ 스캔이 지시 범위보다 넓게 잡은 것을 승인했다

`네 번 냈다` 처럼 다른 문장으로 적혀 검색에 안 걸린 자리 5곳과 grafana JSON 하나를 세션이
스스로 찾아 함께 고쳤다. **목록에 없던 것을 발견하면 함께 고치는 쪽이 맞다** (나중에 또 쓸
이유가 없다). 다만 그 세션이 "범위를 넓혔으니 보고한다" 고 먼저 밝힌 것이 전제다.
