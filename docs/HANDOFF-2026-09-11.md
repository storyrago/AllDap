## 4. PR 4 설계에 그대로 쓸 조사 결과

### S3 - rate limit 구현 (`api/.../global/ratelimit/RateLimiter.java`, 118줄)

- **고정 윈도우.** `windowIndex = currentTimeMillis() / window` 를 키에 섞어 만료 처리가 필요 없다.
- **증가는 원자적**(`computeIfAbsent(...).incrementAndGet()`). **동시성 하의 카운트 누락은 코드상 없다.**
- 버킷 넷: `widget-chat`(IP+publicKey, 20/분) · `widget-config`(60/분) · `login`(IP, 10/분) ·
  `login-failure`(IP+이메일, 5회/**15분**)
- 순서: 형식 검사 → `rateLimiter.check` → 봇 존재 확인. 즉 **형식만 맞고 없는 키**는 카운터를 세면서
  404 로 끝나고 LLM·DB 를 안 건드린다. (부하 스크립트가 이걸 써야 한다)

**로컬 단일 인스턴스로 잴 수 있는 것**: 동시 폭주에서의 정확성 / 분 경계 버스트의 크기(2N) /
제한기 자체의 비용(429 는 Python 을 안 타므로 순수 Spring 경로) / publicKey 축 버킷 분리 /
`MAX_KEYS` clear 사건

**로컬로 원리적으로 못 재는 것 넷**
1. **IP 축 버킷 분리** - k6 가 같은 호스트라 모든 VU 가 `127.0.0.1` 이다. 분산 공격 내성은 답할 수 없다.
2. 🔴 **`Forwarded` / `X-Forwarded-For` 처리 자체** - **`forward-headers-strategy: framework` 가
   `application-prod.yaml` 에만 있다.** 로컬 기본 프로파일의 Spring 은 그 헤더를 아예 파싱하지 않는다.
   로컬에서 위조해도 아무 일도 안 일어나고, 억지로 prod 프로파일을 켜면 **Caddy 가 없는 구성**을
   재는 것이 된다. → **S3 범위 밖. `docs/DEPLOY.md` 의 종단 확인 몫이다.**
3. **다중 인스턴스 한도 배가** - `docker-compose.prod.yml` 에 replicas 가 없어 운영도 1대다.
   로컬에 2개를 띄우는 것은 있지도 않은 구성을 재는 것이다.
4. 재시작 시 카운터 초기화 - 잴 수는 있으나 부하와 무관하다.

### 🔴 S3 스크립트는 새로 짜야 한다

`s2_breakpoint.js` 는 **관리자 채팅**(`/api/bots/{id}/chat`)을 친다. **그 경로에는 rate limit 이 아예 없다.**
S2 가 제한기와 무관하게 잴 수 있었던 이유가 이것이다.

- 좋은 소식: 위젯 경로는 **JWT 가 필요 없어** S2 결과 문서가 적어둔 비밀번호 소동이 안 걸린다.
  `WATCHED_STATUS` 에 이미 429 가 들어 있어 카운터 구조는 재사용된다.
- ⚠️ **위젯 채팅의 상한은 (IP,key) 당 20/분 = 0.33 req/s** 다. S2 프로파일을 그대로 옮기면
  사실상 **거절 경로만** 재게 된다. `WIDGET_CHAT_PER_MINUTE` 로 조절하되 **어느 값으로 쟀는지를
  컨텍스트 파일에 반드시 남기고, 429 와 200 을 한 처리량 곡선에 더하지 말 것.**

### 🔴 S3 는 2026-09-09 사고의 재발 방지 장치를 내장할 것

그때 점검 명령이 **"돌아가는데 아무것도 검증하지 않는"** 상태였던 이유 셋이 그대로 온다.

- **양성 대조**: "429 가 나왔다" 만 보지 말고 **"처음 N 건이 기대한 비429 코드였다"** 를 함께 단언한다.
  그래야 요청이 실제로 제한기를 지났다는 증거가 된다.
- **음성 대조**: `WIDGET_CHAT_PER_MINUTE` 를 아주 크게(예: 100000) 두고 같은 스크립트를 돌려
  **429 가 0건**임을 확인한다. 그러면 본 실행의 429 가 제한기에서 나온 것임이 증명된다.
- **분 경계 정렬**: 버스트가 같은 1분 안에 끝나야 한다. 시작 시각을 초 단위로 컨텍스트에 남긴다.

지표로도 같은 것을 볼 수 있다(#114 의 p14):
`sum(rate(http_server_requests_seconds_count{status="429"}[1m])) - sum(rate(alldap_ratelimit_rejected_total[1m]))`
0 이 아니면 **제한기를 거치지 않은 429 가 있다**는 뜻이다.
⚠️ 다만 이 값은 "둘 다 0건" 일 때도 0 이라 혼자서는 못 가른다. 판정은 **부호가 지속되는가**로 한다.

### S4 - 실패 처리 구현 (`AiServiceClient.call()`, 220~289줄)

- 재시도는 **`ResourceAccessException` + cause 가 `ConnectException`/`HttpConnectTimeoutException` 일 때만.**
  `retry-max-attempts: 2`, `retry-delay: 200ms`. **대기는 요청 스레드에서 `Thread.sleep`.**
- 서킷: **5회 연속** 실패에 열림, **30초** 유지. 4xx 와 DTO 불일치는 실패로 안 센다.
- 타임아웃: connect 3s / read **120s**.

**장애 후보별 실현 가능성**

| 장애 | 실현 | 비고 |
|---|---|---|
| Python 프로세스 종료 | ✅ 코드 0줄 | 포트가 닫혀 `ConnectException` **즉시**. 3초 타임아웃은 안 걸린다. 가장 싸고 값어치 크다 |
| Python 정지(SIGSTOP) | ⚠️ 설정 변경 | 커널이 연결은 받아 **읽기 타임아웃 120초**까지 간다. 그 판만 `read-timeout` 을 5s 로. **별도 실행·별도 컨텍스트** |
| Python 5xx | ⚠️ fake_cf 플래그 1개 | `cf.run` 의 `raise_for_status()` 에 재시도가 없어 FastAPI 500 으로 이어진다 |
| 🔴 **rerank 실패** | ✅ | **`retriever.py:302` 가 삼킨다. 200 이 나가고 순위만 조용히 나빠진다.** 어떤 지표에도 안 잡힌다. S2 실행에서 이미 한 번 났다. **조용한 열화 시나리오로 따로 둘 값어치가 있다** |
| GENERATION_INCOMPLETE(422) | ⚠️ 플래그 | 422 이고 **서킷을 안 센다**. 그 분기가 부하 아래서 실제로 도는지 증명 |
| 헤더 뒤 끊김 | ⚠️ 신규 장애 프록시 | 🔴 S2 에서 `ThreadingHTTPServer` 자체가 부하에 흔들린 전례가 있다(8,316건 중 1건). **주입기가 교란 요인이 되면 안 된다** |

**1순위 가설감: HALF_OPEN 무리 통과.** `allowRequest()` 가 30초 뒤 **동시 요청 전부**를 통과시킨다.
Python 이 아직 죽어 있으면 각 요청이 connect 3s + 200ms + connect 3s 로 **6.2초씩 톰캣 스레드를 붙잡고**,
첫 `recordFailure` 가 창을 다시 여는 동안 80 VU 면 80 스레드가 물린다. **30초마다 반복된다.**
서킷이 막으려던 "Python 장애가 Spring 장애로 번진다" 가 축소판으로 재현되는 자리이고,
`tomcat_threads_busy` 로 관측 가능하다.

🔴 **S4 는 주입 사이에 정지 구간을 두고 "서킷이 닫혔음" 을 확인한 뒤 다음 단계로 갈 것.**
운영 코드에 리셋 경로가 없고(`reset()` 은 테스트 전용), 닫는 유일한 방법은 30초 뒤 성공 한 건이다.
안 하면 앞 단계의 서킷이 다음 단계 숫자를 오염시킨다.
