## 2. 🔴 앞 세션 조사 결과의 사실 오류 셋 (설계하다 나왔다)

앞 문서 §4 를 그대로 설계로 옮기려다 셋이 틀린 것이 드러났다. **정정본이 설계서에 있다.**

### ① "HALF_OPEN 무리 통과 시 요청당 6.2초" → 실제로는 약 200ms

앞 문서 §4 가 **같은 절 안에서** 모순된 말을 한다.

- 장애 후보 표: *"포트가 닫혀 `ConnectException` **즉시**. 3초 타임아웃은 안 걸린다"*
- 다섯 줄 아래 1순위 가설: *"connect 3s + 200ms + connect 3s 로 **6.2초씩**"*

**앞이 맞다.** uvicorn 을 죽이면 8001 을 듣는 프로세스가 없으므로 localhost 는 커널이 즉시 RST 를
돌려준다. `connect-timeout: 3s` 는 **SYN 이 드롭될 때만** 걸리고 그건 방화벽 DROP 규칙이 있을 때다.
실제로 남는 것은 `retry-delay` **200ms** 정도다.

→ **가설의 크기가 30배 줄어든다.** 그래서 1순위 가설을 다시 썼다: "스레드가 얼마나 오래 물리나"
가 아니라 **"`allowRequest()` 가 HALF_OPEN 에서 동시 요청을 몇 건 통과시키나"** 다.
판정 신호는 `alldap_ai_circuit_transition_total{to="open"}` 이 주입 시간을 30으로 나눈 만큼
오르는 것(30초 톱니)이고, `s4_context` 가 그걸 판정한다.

### ② "연결 거부와 읽기 타임아웃이 같은 outcome 으로 뭉쳐 있다" → 아니다

`AiServiceClient.ioOutcome()` 을 읽으면 `READ_TIMEOUT` 은 `read_timeout` 으로 **이미 따로
태깅된다.** 실제로 뭉쳐 있는 것은 `connect_failure` **안쪽**이다:
`ConnectException`(연결 거부, 즉시)과 `HttpConnectTimeoutException`(SYN 무응답, 3초).

🔴 **이 정정이 SIGSTOP 을 빼는 근거를 바꿨다.** 원래 쓰려던 이유("관측이 못 가르는 걸 가른다")는
성립하지 않는다. 실제 값어치는 다른 데 있다: **톰캣 스레드가 오래 물리는 그림**, 즉 ①이 없애버린
"6.2초" 의 유일하게 실현 가능한 대체물이다. 그래도 뺀 이유는 `read-timeout` 을 5s 로 바꾼
**별도 실행**이라 이 PR 의 세 판과 한 표에 못 올린다는 것 하나다. **"재도 나올 게 없어서" 가 아니다.**

### ③ 한도 값을 `/actuator/configprops` 로 물어볼 수 없다

노출 목록이 `health,metrics,prometheus` 셋뿐이고, 열더라도 `SecurityConfig` 가
`/actuator/prometheus` 하나만 `permitAll` 이라 401 이다.

**그렇다고 열지 않았다.** 한도 숫자 하나를 읽으려고 DB 접속 문자열·JWT 시크릿이 같은 응답에
실리는 경로를 만드는 셈이다. → `widget_chat_per_minute` 를 `"source": "driver"` 로 명시하고,
`alldap_ratelimit_recorded_total` 로 **다른 축에서** 같은 실행을 검증한다.

⚠️ **앞 문서 §6-ⓒ 의 "아직 드라이버 값인 것" 목록에 한 줄이 늘었다.**

## 6. 이 세션에서 배운 것 (기록)

### ⓐ 🔴 음성 대조가 <점검 자체의 약점> 둘을 잡았다

이 저장소는 "검사를 짜뒀는데 아무 데서도 안 돈다" 로 두 번 데였고, 그래서 **일부러 깨뜨려보는
것**을 규칙으로 삼았다. 이번에 그게 헛일이 아니었다.

1. **S3: 400 가드를 통째로 없앴는데 점검이 통과했다.** `counts(s400=100)` 은 404 개수 검사에도
   어차피 걸려서 **다른 이유로** 실패하고 있었다. **"실패했다" 와 "그 이유로 실패했다" 는 다른
   사실**이고, 뭉개면 가드가 사라져도 모른다. → 모든 실패 케이스가 `not ok` 만이 아니라
   **사유 문자열까지 단언**하게 고쳤다(`fails_because`).
2. **S4: `injected` 의 `None` 가드를 없앴더니 `TypeError` 로 죽었다.** 종료코드는 1 인데
   **어느 케이스가 문제인지 출력에 안 나왔고** 뒤 케이스가 아예 안 돌았다.
   → 판정이 예외로 죽는 것도 **이름 붙은 실패**로 센다.

> 🔴 **둘 다 "점검이 실패한다" 는 것만으로는 부족하다는 이야기다.**
> 점검을 깨뜨려볼 때 **실패의 <이름>이 기대한 것인지**까지 봐야 한다.

### ⓑ 분배는 절반만 됐다

idle 세션 4개에 파일이 안 겹치게 잘라 보냈는데 **2건이 승인되고 2건이 거절**됐다.
거절된 둘이 드라이버 조각(판정 로직)이라 main 세션이 직접 했다. 결과적으로 그 편이 맞았다.
"틀리면 측정이 통째로 거짓이 되는" 부분이었다.

승인된 두 세션은 둘 다 사양을 넘겨서 왔고, **둘의 제안을 받아들여 설계를 고쳤다**:

- `injected` 를 모드 전환 때 리셋하지 말고 **누적**으로. 리셋하면 "안 늘었다" 와 "방금
  초기화됐다" 가 뭉개진다. `counts` 가 이미 누적인데 `injected` 만 리셋이면 두 카운터의 의미가
  갈려서 나란히 읽는 사람이 반드시 틀린다. → 설계서의 표기를 **증가분**으로 정정했다.
- `/fault` 의 오타난 mode 를 **400 으로 되돌리기**(조용히 `none` 으로 떨어지지 않게). 떨어지면
  주입했다고 믿은 채 정상 90초를 재게 되고 **그 판이 대조군과 구분이 안 된다.**

그리고 k6 동작을 **실측**으로 확인해준 것이 값어치가 컸다(`API=http://127.0.0.1:1` 로 B 판을
태워 감시 코드 전부가 `count: 0` 으로 요약에 존재함을 확인). 그게 없었으면 `judge_round` 의
핵심 규칙("키가 있고 0 = 안 났다 / 키가 없다 = 안 셌다")이 **가정** 위에 서 있었을 것이다.

### ⓒ 가짜 키 기본값이 두 파일에서 달랐다

드라이버는 `pk_` + 20자, k6 는 `pk_` + 22자였다. 그대로 뒀으면 **드라이버는 A 키를 404 로
확인해놓고 k6 는 B 키를 두드려, 사전 확인이 아무것도 보증하지 못했을 자리**다.
서로 다른 세션이 같은 상수를 각자 정할 때 반드시 생기는 부류라, 취합에서 처음 볼 것 중 하나다.
