## 3. 왜 350 이 아니라 327 인가

327건째 요청이 HTTP **422 `ANSWER_INCOMPLETE`** 로 떨어졌고, 스크립트가 거기서 멈췄다.
**중단 장치가 설계대로 동작한 것이다.** 부하 스크립트는 예상하지 못한 응답을 만나면
계속 두드리지 않고 멈추도록 돼 있다. 오늘 뉴런 한도의 86% 를 이미 쓴 상태였으므로
그대로 계속 돌았다면 한도를 넘겼을 것이다.

**p50 · p95 에는 영향이 없다.** 327건은 350건 계획의 93% 이고, 백분위는 표본 수가 아니라
분포로 정해진다. 영향이 있는 것은 **p99 하나뿐**이다(아래 "못 잰 것" 참고).

## 4. 발견 ① 에러 문구가 사실과 다르다

사용자에게 나간 문구는 이것이다.

> 답변이 길어져 끝까지 완성하지 못했습니다. **같은 질문을 다시 보내도 같은 결과이니**,
> 질문을 더 좁혀서(한 번에 한 가지만) 물어봐 주세요.

**그런데 참이 아니다.** 실패한 질문("정규직이 결혼할 때 쉴 수 있는 날이 며칠인가요?")은
같은 실행에서 **66번 물어 65번 성공**했다. 다시 보내면 98.5% 성공한다.

### DB 로 직접 확인한 수치

`conversations` / `messages` 를 직접 세었다(본 실행 구간, `created_at >= 13:38:57`).

| 확인 | 결과 |
|---|---|
| 사용자 메시지 | 328건 |
| assistant 메시지 | 327건 |
| assistant 가 없는 세션 | **`s1-327` 단 하나** |
| "결혼" 질문 출현 | **66회** (그중 성공 65회) |
| `is_fallback=true` | 0건 |
| `sources` 가 비어 있는 답변 | 0건 |

⚠️ 처음에 `session_id LIKE 's1-%'` 로만 세면 **67회**가 나온다. 드라이런 2회가 같은
`s1-0` ~ `s1-4` 를 재사용해 같은 대화 행에 메시지가 얹혔기 때문이다. 본 실행 시각으로
자르면 66회다. **세션 id 를 실행마다 다르게 두지 않으면 집계가 이렇게 어긋난다.**

직전 회차 `s1-322` 는 같은 질문에 "정규직의 결혼 휴가는 5일입니다." 로 정상 답변했다.
`temperature=0`, 같은 문구, 같은 봇, 같은 근거인데 **65 대 1 로 갈린다.**

### 가설 두 개를 코드로 갈랐다

**(b) "잘림이 아닌 실패가 이 코드로 뭉개졌다" 는 전송 계층에서는 성립하지 않는다.**

- `cf.run` 은 429·5xx·타임아웃·`success:false` 를 만나면 `httpx.HTTPStatusError` 나
  `RuntimeError` 를 던진다. **`GenerationFailed` 가 아니다.**
- `main.chat` 은 `GenerationFailed` 만 잡아 503 + `code=GENERATION_INCOMPLETE` 로 바꾼다.
  그 밖의 예외는 잡히지 않고 FastAPI 500 이 된다.
- `AiServiceClient.call` 은 본문에 `detail.code = GENERATION_INCOMPLETE` 가 실려야만
  `ANSWER_INCOMPLETE` 로 바꾼다. 없으면 503 `AI_SERVICE_UNAVAILABLE` 이다.

→ 429 나 타임아웃이었다면 `ANSWER_INCOMPLETE` 가 아니라 503 이 나왔을 것이다.

**그런데 한 겹 안쪽에서는 (b) 가 성립한다.** `generator.generate` 는 서로 다른 두 사실을
같은 `GenerationFailed` 로 던진다.

| 원인 | 조건 | 뜻 |
|---|---|---|
| 잘림 | `finish_reason == "length"` | max_tokens 에 걸려 뒤가 잘렸다 |
| **빈 응답** | `not answer` | 모델이 아무것도 안 돌려줬다 |

둘이 같은 코드로 나가고, 사용자 문구는 **잘림 쪽만** 설명한다. 빈 응답이었다면
"답변이 길어져" 는 그 자리에서 이미 거짓말이다.

**이번 건은 빈 응답 쪽일 가능성이 높다.** 이 실행의 답변 최대 길이가 **83자**인데
`max_tokens` 는 **1024 토큰**이다. 83자짜리 답을 내놓던 모델이 한 번만 1024 토큰을
채우고 잘리려면 폭주해야 한다. 🔴 **다만 단정하지 않는다.** 어느 쪽인지는
`main.chat` 의 `_log.warning("답변 생성 실패 ...")` 한 줄이 말해주는데, uvicorn 을
터미널 stdout 으로 띄워 그 로그를 파일로 남기지 않았다. **다음 측정에서는 반드시
uvicorn 로그를 파일로 받을 것.**

**(a) Cloudflare 쪽 비결정성** 은 어느 쪽이든 남는다. `temperature=0` 은 우리가 보내는
파라미터일 뿐 제공자의 결정성을 보장하지 않는다. 65 대 1 이라는 관측 자체가
"같은 입력이면 같은 결과" 가 이 경로에서 성립하지 않는다는 증거다.

### 왜 이게 중요한가

AGENTS.md 는 **"원인이 다른 두 사실을 같은 값으로 뭉갠" 버그를 다섯 번 냈다**고 적고
"여섯 번째를 조심할 것" 이라고 덧붙였다. 이번 건이 그 여섯 번째다. 뭉개진 두 사실은

- **구조적으로 못 답한다** (질문이 커서 매번 같은 자리에서 잘린다)
- **이번에 운 나쁘게 실패했다** (65 대 1)

이고, 후자에게 "다시 보내도 소용없다" 고 안내하면 **사용자가 성공하는 재시도를
포기한다.** 문구가 사용자를 잘못된 행동으로 보낸다.

🔴 **고치지 않았다.** 어떻게 고칠지는 별도 슬라이스이고 사용자가 정한다.
`ANSWER_INCOMPLETE` 를 만든 근거는 `docs/decisions.md` 2026-09-09 항목과
AGENTS.md 의 "재시도로 안 풀리는 실패 두 경로" 절에 있다. 당시 근거였던
*"`temperature=0` 이라 다시 물어도 같은 자리에서 잘린다"* 가 이 측정으로 반증됐다.

## 5. 발견 ② 실행 중 지연이 단조 상승했다

20건째 p50 **1,676ms** → 320건째 p50 **1,779ms**. **+6%** 다.
350건을 쉬는 구간 없이 순차로 때린 결과다.

🔴 **이 두 수치는 <재확인할 수 없다>. 다른 수치와 근거가 다르다.**
표의 p50 · p95 · p99 는 `results/S1-2026-09-10.json` 에 남아 있지만,
위 중간 p50 두 개는 **드라이버가 돌면서 표준출력에 찍은 진행 로그를 눈으로 읽은 값**이고
결과 파일에는 들어 있지 않다. 그 stdout 도 파일로 받지 않았다.
즉 **본 것은 맞지만 남기지 못했고, 그래서 재현도 재확인도 불가능하다.**
"쟀다" 와 "봤지만 남기지 못했다" 는 다른 사실이라, 나중에 읽는 사람이 다른 수치와
같은 근거로 오해하지 않도록 여기에 못박아 둔다. **+6% 라는 방향과 크기는
이 문서 안에서 검증될 수 없다.**

**원인은 이 데이터로 못 가른다.** 후보가 둘이다.

- Cloudflare 쪽 스로틀(같은 계정이 연속으로 두드린 것에 대한 반응)
- 로컬 누적(커넥션 풀, JVM, pgvector 캐시, 측정 배열 자체의 성장)

🔴 **가짜 Cloudflare 서버는 고정 지연이라 이 성질을 재현하지 못한다.** PR 3 으로 재는
수치는 "부하가 늘어도 앞단이 버티는가" 는 말해주지만 "제공자가 느려지는가" 는 말하지 못한다.
**두 측정은 서로를 대신하지 못한다.**

**다음 측정의 개선 지점 (둘 다 드라이버를 고쳐야 한다)**

1. **중간 스냅샷을 결과 파일에 남길 것.** N건마다 그때까지의 p50 · p95 를
   `progress` 배열로 JSON 에 적으면 단조 상승을 사후에 다시 볼 수 있다.
   (uvicorn 로그를 파일로 받는 것과는 별개 문제다. 이건 드라이버 쪽이다)
2. **세션 id 에 실행 구분자를 넣을 것.** 지금은 `s1-0` ~ `s1-N` 이라 실행마다 겹친다.
   §4 에서 본 대로 드라이런 2회가 같은 id 를 재사용했고, Spring 이
   `(bot_id, session_id)` 로 대화를 재사용하는 탓에 같은 대화 행에 메시지가 얹혀
   `session_id LIKE 's1-%'` 집계가 66 이 아니라 **67** 로 샜다. 실행 시각으로 잘라
   맞추긴 했지만, 그건 사람이 매번 손으로 보정해야 한다는 뜻이다.
   `s1-<시작시각>-<i>` 처럼 실행마다 유일하게 만들면 집계가 그냥 맞는다.

## 6. 발견 ③ 오버헤드가 분리됐다

세 모델 p50 합 **1,586ms**(235 + 414 + 937), 종단 p50 **1,787ms**.
차이 **약 200ms** 가 Spring + pgvector + 로컬 네트워크 몫이다.

⚠️ 백분위끼리의 뺄셈이라 엄밀한 분해는 아니다(각 p50 이 같은 요청에서 나온 값이 아니다).
그래도 자릿수는 맞다. **PR 3 에서 가짜 서버로 돌릴 때 이 200ms 가 재현되면
구성이 제대로 붙었다는 신호다.** 재현되지 않으면 가짜 서버가 우리 경로를 통째로
건너뛰고 있다는 뜻이다.

## 7. 못 잰 것

- **p99.** 표본 327건이라 상위 약 3건이 값을 결정한다. 그 3건이 바뀌면 숫자가 통째로
  움직인다. **p50 · p95 만 믿는다.** 결과 JSON 에도 `p99_caveat` 로 박아뒀다.
- **동시성.** 1명 순차라 여기서 나온 것은 **지연**이지 **처리량**이 아니다. 커넥션 풀
  고갈, 톰캣 스레드 경합, pgvector 동시 조회 같은 것은 하나도 건드리지 못했다. PR 3 의 몫이다.
- **단조 상승의 원인.** 위 발견 ②. 원인 이전에 **중간 p50 값 자체가 결과 파일에 없어
  재확인이 안 된다.**
- **`ANSWER_INCOMPLETE` 의 실제 원인.** 잘림인지 빈 응답인지. uvicorn 로그를 안 남겼다.
- **`per_model` 의 count 가 328 이다.** requests_ok(327) 와 다른 것은 실패한 327번째도
  Cloudflare 를 불렀기 때문이다. 프로세스 누적치라 드라이런 분이 섞이지 않았음은
  실행 전 uvicorn 재기동으로 보장했다.
