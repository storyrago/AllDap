## 2. 🔴 "6.2초" 정정: 실측이 §2 를 확인했다

핸드오프 §4 의 1순위 가설은 *"HALF_OPEN 무리 통과 시 요청당 connect 3s + 200ms + connect 3s
= **6.2초**씩 톰캣 스레드를 붙잡는다"* 였다. 설계서 §2 가 이것을 **약 200ms** 로 정정했다.
근거는 "포트가 닫히면 커널이 즉시 RST 를 돌려주므로 `connect-timeout: 3s` 가 안 걸린다" 였다.

**F1 의 실측값이 그 정정을 확인한다.**

```
alldap_ai_call_seconds_count{operation="chat",outcome="connect_failure"}  68
alldap_ai_call_seconds_sum  {operation="chat",outcome="connect_failure"}  14.015177668
                                            → 평균 206.1 ms
```

`retry-delay` 가 200ms 이므로 **206.1ms = 200ms + 나머지 전부**다. 3초는 한 번도 안 걸렸다.
가설의 크기가 **30배** 틀렸던 것이고, 그래서 설계서가 1순위 가설을 다시 썼다:
*"스레드가 얼마나 오래 물리나"* 가 아니라 **"HALF_OPEN 에서 동시 요청을 몇 건 통과시키나"**.

**그 다시 쓴 가설의 답도 나왔다: 한 번에 약 17건이다.**
90초 주입 동안 서킷이 4번 열렸고 연결 실패가 68건이니 `68 / 4 = 17`.
VU 가 20 이므로 **사실상 in-flight 전부가 통과한다.** `AiServiceCircuitBreaker` 클래스 주석이
*"HALF_OPEN 에서 동시에 여러 요청이 통과할 수 있다"* 고 인정해둔 그대로이고,
이 실행이 **그 값을 숫자로 만든 것**이다.

🔴 **6.2초 그림 자체는 여전히 못 쟀다.** 재려면 SYN 드롭(`pfctl`)이 필요하고 범위 밖이다(§7).

## 3. 판 F1: Python 프로세스 종료

주입: `pkill -f 'uvicorn app.main:app'` (코드 0줄). 90초 뒤 같은 명령줄로 다시 띄웠다.

```
구간        200     0   422   429   500   502   503   504     지연 avg/med/p99/max (ms)
normal      720     0     0     0     0     0     0     0     1690.28 / 1681.38 / 1927.56 / 1929.72
inject        0     0     0     0     0     0 253248     0        6.90 /    6.65 /   12.61 /  223.96
```

| 지표 증가분 | 값 |
|---|---|
| `call_seconds_count{outcome="connect_failure"}` | **+68** |
| `call_seconds_count{outcome="circuit_open"}` | **+253,180** |
| `alldap_ai_retry_total{operation="chat"}` | **+68** (연결 실패와 정확히 1:1) |
| `circuit_transition_total{to="open"}` | **+4** |
| `circuit_transition_total{to="closed"}` | **+2** |

**판정: `valid: true`.** 네 가지가 다 맞았다. 연결 실패로 분류됐고, 재시도가 돌았고,
서킷이 열려 급속 거절로 넘어갔고, **90초 동안 4회 열려 30초 톱니가 재현됐다.**

- 🔴 **재시도 68 = 연결 실패 68 이 1:1 인 것이 중요하다.** `retry-max-attempts: 2` 이므로
  실패 한 건당 재시도 1회다. F2 와 나란히 놓으면 이것이 "연결 실패에만 돈다" 의 절반이 된다.
- **253,248건 중 253,180건(99.97%)이 Python 을 아예 안 두드렸다.** 서킷이 실제로 전파를 끊는다.
- 톱니 4회는 주입 90초 ÷ 30초 = 3 보다 하나 많다. 주입 시작 직후 즉시 한 번 열리고
  그 뒤 30초마다 재개폐가 이어진 것으로 읽힌다(≈60·90·120·150초).

### 🔴 급속 503 과 느린 503: 20 VU 아래서도 갈린다 (이 판의 핵심 산출물)

| | 건수 | sum(s) | **평균** |
|---|---|---|---|
| `outcome="circuit_open"` (급속 거절) | 253,180 | 3.483097 | **13.76 µs** |
| `outcome="connect_failure"` (재시도까지 하고 실패) | 68 | 14.015178 | **206.1 ms** |

**차이 약 14,980배.** 부하 없이 잰 지난 실측은 0.000079s 대 0.211s 로 2,700배였는데,
20 VU 아래서 **유지되는 정도가 아니라 더 벌어졌다**(급속 쪽이 79µs → 13.8µs 로 빨라져서다).

➡️ **#112 의 Timer 가 값어치를 한다.** 사용자에게는 둘 다 똑같은 503 이고 응답만 봐서는
구별할 방법이 없는데, 지표에서는 네 자릿수 배율로 갈린다. 운영자가 "왜 503 인가" 에 답할 수 있다.

⚠️ **이 판정은 평균으로 한 것이다.** `alldap_ai_call_seconds` 에 히스토그램 버킷이 없어
p99 를 못 구한다(§6). 차이가 네 자릿수 배율이라 평균으로도 갈리지만, 갈린 근거는 평균이다.

주입: `POST /fault {"mode":"error_all","status":500}`. 가짜 CF 가 모든 모델 호출에 500.

```
구간        200     0   422   429   500   502   503   504     지연 avg/med/p99/max (ms)
normal      720     0     0     0     0     0     0     0     1676.81 / 1673.05 / 1749.48 / 1773.03
inject        0     0     0     0     0     0 235700     0        7.44 /    7.11 /   14.57 /  301.42
```

| 지표 증가분 | 값 |
|---|---|

### 🔴 이 PR 에서 유일하게 반증 가능한 주장: 5xx 에 재시도가 안 돈다

**증가가 0 이다.** 그리고 그것을 **다른 축에서 한 번 더** 확인했다. 가짜 CF 의 호출 카운터다.

| 가짜 CF `counts` | 주입 켤 때 | 끌 때 | 증가 |
|---|---|---|---|
| `@cf/baai/bge-m3` (임베딩) | 1442 | 1515 | **+73** |
| `@cf/baai/bge-reranker-base` | 1442 | 1442 | +0 |
| `@cf/meta/llama-3.3-70b-...` (생성) | 1442 | 1442 | +0 |
| `fault.injected` | 1 | 74 | **+73** |

**Spring 이 센 `python_5xx` 73 건 = 가짜 CF 가 받은 임베딩 호출 73 건 = 주입 73 건. 전부 1:1 이다.**
재시도가 돌았다면 가짜 CF 쪽이 두 배로 셌을 것이다. 안 셌다.

➡️ **`AiServiceClient` 주석의 약속("5xx 는 요청이 도달했다는 뜻이라 재시도하지 않는다")이
부하 아래서 지켜진다. LLM 중복 과금이 실재하지 않는다.**

- 임베딩만 늘고 리랭커·생성이 0 인 것은 맞는 그림이다. **파이프라인의 첫 외부 호출이
  임베딩**이라, 거기서 500 이 나면 `raise_for_status()` 가 즉시 올라가 뒤 단계를 안 탄다.
- 235,700건 = 73(도달) + 235,627(급속 거절). **99.97% 가 Python 을 안 두드렸다** (F1 과 같다).
- `python_5xx` 평균 266.8ms 는 가짜 CF 의 embed 지연 235ms 에 왕복이 붙은 값이다. 재시도가
  돌았다면 여기에 200ms 가 더 붙었을 것이고, **그것도 안 붙었다.**

## 5. 판 F3: rerank 조용한 실패 (`mode=error_rerank`)

주입: `POST /fault {"mode":"error_rerank","status":500}`. 리랭커 호출에만 500, **지연은 유지.**

### 🔴 산출물: 장애 1,080건, 그것을 드러내는 지표 없음

| 무엇을 보는가 | 정상 60초 | 주입 90초 | 바뀌었나 |
|---|---|---|---|
| HTTP 상태 | 200 × 720 | **200 × 1,080** | ❌ 안 바뀜 |
| 종단 지연 avg / med | 1675.33 / 1671.43 ms | **1674.85 / 1678.16 ms** | ❌ 안 바뀜 (차이 0.03% / 0.4%) |
| 종단 지연 p95 / p99 | 1725.89 / 1739.54 ms | 1703.92 / 1726.30 ms | ❌ 안 바뀜 |
| `isFallback` | 0건 | **0건** | ❌ 안 바뀜 |
| `call_seconds{outcome}` | `success` | **전부 `success`** (+1,080) | ❌ 안 바뀜 |
| 실패 outcome 9종 | (없음) | **하나도 안 움직임 (+0)** | ❌ 안 바뀜 |
| `alldap_ai_retry_total` | 68 | **68** | ❌ 안 바뀜 |
| `circuit_state` / `transition_total` | 0 / open 8 | **0 / open 8** | ❌ 안 바뀜 |
| 가짜 CF `counts[리랭커]` | (없음) | **+1,080** (호출은 됐다) | (해당 없음) |
| 가짜 CF `fault.injected` | 74 | **1,154 (+1,080)** | (해당 없음) |
| **uvicorn 로그 `리랭킹 실패(원래 순서 유지)`** | 0줄 | **1,080줄** | ✅ **유일한 신호** |

**1,080 = 1,080 = 1,080.** 주입 건수 · 리랭커 호출 수 · 로그 줄 수가 정확히 일치하고,
**k6 의 주입 구간 요청 수 1,080건과도 같다.** 즉 **주입 구간의 모든 요청이 리랭킹에 실패했고,
그 사실이 Spring 쪽 어떤 숫자에도 남지 않았다.**

**판정: `valid: true`. 🔴 이것은 "통과" 가 아니라 "결함이 재현됐다" 이다.**
판정 함수가 True 를 돌려준 뜻은 *기대한 신호 변화가 전부 맞았다* 인데, 이 판의 기대가
**"아무것도 안 바뀐다"** 이기 때문이다.

- 이 판정이 **"계측이 아예 없는 경우"와 구별되는 근거**는 앞의 정상 60초다. 같은 실행 안에서
  `success` 가 720건 늘었으므로 계측은 살아 있었고, 그 상태에서 실패 지표가 안 움직였다.
  (설계서 §5-③ 이 대조군 검사를 판정 맨 앞에 둔 이유가 이것이다)
- **지연을 유지한 것이 결정적이다.** `time.sleep` 을 건너뛰었으면 종단 지연이 414ms 빨라져
  "장애인데 빨라졌다" 가 되고, 원인이 다른 두 사실이 한 숫자에 섞였을 것이다.
  유지했더니 **avg 차이가 0.48ms(0.03%)** 로, 지연으로도 못 알아챈다는 것이 확인됐다.
- 답변 품질은 실제로 나빠졌을 것이다(리랭커 없이 원래 순서). AGENTS.md 의 W4 실측에 따르면
  리랭커를 끄면 회당 오답이 0 → 1.00 이 된다. **그 손해가 어떤 운영 지표에도 안 뜬다.**

⚠️ **로그 줄 수는 `grep -c '리랭킹 실패'` 로 세야 한다.** 이 WARNING 은 뒤에 MDN 링크가
한 줄 더 붙어 **두 줄**로 찍히므로 `wc -l` 로 세면 2배가 된다.

## 6. 관측이 아직 못 가르는 것

- 🔴 **`connect_failure` 안쪽이 뭉쳐 있다.** `ConnectException`(연결 거부, 즉시)과
  `HttpConnectTimeoutException`(SYN 무응답, 3초)이 **같은 태그**로 들어간다.
  **F1 이 만든 것은 앞쪽뿐**이라 이 실행으로는 그 뭉개기를 드러낼 수 없고, 드러내려면
  SYN 드롭이 필요하다(§7).
  ⚠️ 핸드오프 §6-ⓓ 의 *"연결 거부와 읽기 타임아웃이 뭉쳐 있다"* 는 **부정확하다.**
  `ioOutcome()` 이 `READ_TIMEOUT` 을 `read_timeout` 으로 **이미 따로** 태깅한다.
- **히스토그램 버킷이 없어 p99 를 못 구한다.** §3 의 14,980배는 **평균으로 낸 값**이다.
- 🔴 **`circuit_transition_total{to="half_open"}` 은 존재하지 않는다.** 시계열이 아예 없고
  `s4_context` 가 세 판 모두 `"half_open": null` 로 기록했다. `HALF_OPEN` 은 "열린 시각" 에서
  시간으로 파생되는 값이라 전이 사건이 없기 때문이며, **버그가 아니다.**
  다만 시작 조건 파일의 `null` 은 *"0회 일어났다"* 가 아니라 *"그런 계측이 없다"* 이다.
  (`parse_prom_counter` 가 0.0 대신 `None` 을 돌려주도록 짜인 이유가 정확히 이 구별이다)
- 🔴 **`to="open"` 과 `to="closed"` 는 정산이 안 맞는다.** F1·F2 둘 다 **open +4 / closed +2** 다.
  락 없는 구현이라 그렇다. `recordSuccess` 는 `openedAtNanos != NOT_OPEN` 을 본 스레드만
  닫힘을 세는데, HALF_OPEN 통과 무리 20건이 동시에 성공하면 그중 하나만 세고 나머지는
  이미 닫힌 것을 본다. 클래스 주석이 *"이 값은 눈금이지 정산 대상이 아니다"* 라고 적어둔 그대로다.
  **두 카운터를 대차대조표처럼 읽으면 틀린다.**
- **톱니의 <횟수>는 카운터로 정확하고 <주기>는 근사다.** 15초 스크레이프로는 30초 창의
  경계를 정확히 못 짚는다.

## 7. 못 잰 것 (알고 뺀 것)

| 안 잰 것 | 근거 |
|---|---|
| **SIGSTOP 으로 읽기 타임아웃** | `read-timeout` 을 5s 로 바꾼 **별도 실행**이라 이 세 판과 한 표에 못 올린다. 값어치는 있다. §2 가 없앤 "6.2초" 의 유일하게 실현 가능한 대체물이다. "재도 나올 게 없어서" 가 아니다 |
| **헤더 뒤 끊김(`CONNECTION_LOST`)** | 새 장애 프록시가 필요한데, S2 에서 `ThreadingHTTPServer` 자체가 부하에 흔들린 전례가 있다(8,316건 중 1건). **주입기가 교란 요인이 되면 안 된다** |
| **SYN 드롭(`pfctl`)** | §6 의 `connect_failure` 뭉개기와 §2 의 "6.2초" 를 재는 유일한 방법이지만, 호스트 방화벽 규칙을 부하테스트가 만졌다 지우는 것이라 실패하면 맥이 이상한 상태로 남는다 |
| **"몇 % 실패율부터 서킷이 열리는가"** | 채팅과 업로드를 섞어야 나온다. 부하 프로파일이 달라지므로 별 슬라이스 |
| **결함 수정** | 핸드오프 §5 의 서킷브레이커 결함(전 엔드포인트 공용 싱글턴 · "연속" 이라 성공마다 리셋)은 **S4 가 드러내려는 것 자체**다. 고치면 before 가 사라진다 |
| **Grafana 그림** | 안 그려진다(§1). 원인 규명은 이 실행의 범위 밖이고, 판정 근거는 원본 지표라 그림 없이도 성립한다 |

## 8. 이 실행이 드러낸 도구·읽기 쪽 문제 (보고만, 고치지 않았다)

1. 🔴 **`s4_context after` 의 스냅샷에 `recover` 의 성공 1건이 섞인다.**
   절차가 `clear → recover → after` 라서, `after` 가 긁는 `/actuator/prometheus` 에는
   회복용으로 직접 만든 채팅 1건이 이미 반영돼 있다. 실제로 F3 의 `success` 증가분은
   **1,801** 이다(정상 720 + 주입 1,080 + 회복 1). 세 판의 판정은 전부 *"늘었나 / 0인가"*
   를 묻기 때문에 **결론은 바뀌지 않지만**, 숫자를 그대로 인용하면 1 씩 어긋난다.
   원리적으로는 `to="closed"` 전이도 여기서 한 건 섞일 수 있다.
   → 고치려면 `after` 를 `recover` **앞에** 두거나, `recover` 가 만든 건수를 빼면 된다.
2. **`judge_fault_round` 는 정상 구간에 실패가 있었는지 안 본다.** 대조군 검사가
   `normal[200] > 0` 하나뿐이라, 정상 60초에 503 이 섞여 있어도 통과한다.
   이번 세 판은 정상 구간이 전부 `200 × 720` 이라 문제가 안 됐다.
3. **F2 판정이 "서킷이 열린다" 를 단언하지 않는다.** 설계서 §4-F2 의 기대표에는 있는데
   `judge_fault_round` 의 F2 분기는 `python_5xx > 0` 과 `retry == 0` 둘만 본다.
   이번엔 실제로 4회 열렸으므로 결과에 영향은 없다.
4. **F1 의 `clear` 는 안내문만 찍는 no-op 이다.** uvicorn 이 정말 돌아왔는지를 확인하는 것은
   `recover` 뿐이라, `recover` 를 건너뛰면 "죽은 채로 다음 판" 이 가능하다.
   (그래서 핸드오프가 `recover` 를 규칙으로 못박은 것이고, 이번엔 세 판 모두 돌렸다)

**넷 다 판정을 뒤집지 않는다.** 이번 실행의 세 결론은 그대로다.
