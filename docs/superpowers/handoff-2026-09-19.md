## 2. 어제 알아낸 것 (이 핸드오프의 전제)

**난이도를 만들려고 두 측정점을 돌렸고, 두 가지가 갈렸다.**

① **질문 변형은 거의 아무 일도 하지 않았다.** 변형 규칙 셋 중 `target` 만 3건 중 1건이
작동했고 `lexical` 4 · `clause` 3 은 순위를 **한 칸도** 못 움직였다. 특히 `lexical` 은
질문의 낱말을 **코퍼스 전체에 0회인 말**로 바꿔 키워드 검색을 완전히 무력화했는데도
**벡터가 혼자 전부 1위로 찾아냈다.** `bge-m3` 가 한국어 동의어를 그만큼 잘 다룬다.

② **코퍼스는 숫자를 내렸지만, 내린 것이 난이도가 아니었다.** 그리고 이것이 다음 세션의 일이다.

🔴 **핵심 실측 (2026-09-18, 채점자 직접 호출 35회 · 952 뉴런)**

q3 의 답변 문자열을 **글자까지 고정**하고 근거 집합만 바꿔 채점자를 반복 호출했다.

| 조건 | 근거 (청크 id) | 충실성 |
|---|---|---|
| A = run 11 의 근거 | 207 · 214 · **27(정답)** · 190 · 283 | **1.0 ×10** |
| B = run 14 의 근거 | 207 · 214 · **27(정답)** · **327** · 190 | **0.0 ×10** |
| C = A∩B | 207 · 214 · **27(정답)** · 190 | **1.0 ×5** |

- **조건 안 분산 0.0000.** `judge_temperature = 0` 에서 채점자는 이 입력에서 흔들리지 않는다.
  "채점자가 랜덤하다" 는 기각됐다.
- **C 가 원인을 한 칸 더 좁힌다**: B 의 0.0 은 283 이 빠져서가 아니라 **327 이 들어와서**다.
  327 은 `56_시간제근로자` 의 근무시간 절로 이 질문과 무관하다.
- 🔴 **그때 채점자가 댄 사유가 사실과 다르다**: *"근거에는 기간제 직원의 재택근무에 대한
  내용이 없습니다"* - 정답 청크 27 은 B 에서도 **3번째 자리에 있다.** A 에서는 같은 청크를
  "근거 3" 이라고 정확히 지목한다. 방어 가능한 엄격함이 아니라 **오독**이다.

> **무관한 청크 하나가 근거 목록에 끼는 것만으로 채점자가 있는 근거를 못 본다.**

**따라서 전체충실성은 "답이 나빠졌다" 와 "채점자가 다르게 읽었다" 를 한 값으로 뭉갠다.**
`AGENTS.md` 의 "낸 버그" 표 **아홉 번째**가 이것이고, 앞의 여덟과 달리 **이미 만들어 계속
쓰고 있는 신호**에서 났다. 이 저장소의 모든 before/after 비교표가 그 지표 위에 서 있다.

⚠️ **어제 확인한 것의 범위를 정확히 적는다.** 본 것은 **정밀도**(한 입력에서 15회씩 같은 값을
낸다)까지다. **정확도**(맞게 채점하는가)는 안 쟀다. 오히려 q3 에서는 **정밀하게 틀렸다** -
10회 내내 일관되게 0.0 을 줬고 그 사유가 거짓이었다. **흔들리면 반복 측정으로 걸러지는데
일관되게 틀리면 안 걸러진다.** 그래서 이쪽이 더 나쁘다.

**어제 실측이 이 TODO 를 정면으로 겨눴다.** 지금까지는 "안 쟀다" 였는데, 이제는
**"적어도 한 자리에서 틀리는 것을 봤다"** 다. 둘은 다른 사실이다.

### 3-1. 이미 확보된 재료 (새로 재지 않아도 되는 것)

🔴 **평가를 새로 돌리지 말 것.** 필요한 원자료가 DB 에 박제돼 있다.

- `eval_runs` 에 run **11~16** 이 있다(11·12·13 = 306청크 · 14·15·16 = 360청크). 전부
  `status='completed'` 이고 **처리실패 0**이다.
- `eval_results` 에 run 당 26행씩 있고 각 행에 **`generated_answer` · `retrieved_chunks` ·
  `faithfulness` · `relevancy`** 가 박혀 있다. 즉 **사람이 채점할 재료 156건이 이미 있다.**
- 그중 **점수가 갈린 자리를 이미 알고 있다**: q3(1.0 ↔ 0.0, 답변 문자열 동일) ·
  q14(1.0 ↔ 0.5) · q21(1.0 ↔ 0.5, 근거가 6회 모두 동일한데 답이 갈렸다).

### 3-2. 무엇을 재는가 (두 축을 섞지 말 것)

| 축 | 질문 | 상태 |
|---|---|---|
| **정밀도** | 같은 입력에 같은 점수를 주는가 | ✅ 어제 확인(두 입력에서 15회씩, 분산 0) |
| **정확도** | 사람이 보기에 맞게 채점하는가 | ❌ **한 번도 안 쟀다. 이것이 다음 세션의 일** |

**정확도를 재는 최소 설계 (제안, 다음 세션이 고쳐도 된다)**

1. **사람이 먼저 채점한다.** `eval_results` 에서 30~50건을 뽑아 `question` · `ground_truth` ·
   `generated_answer` · `retrieved_chunks` 를 보고 사람이 0 / 0.5 / 1 을 매긴다.
   🔴 **채점자 점수를 보기 <전에> 매겨야 한다.** 보고 나서 매기면 대조가 성립하지 않는다.
   (`answerable_check` 의 임계값을 홀드아웃 보기 전에 골랐던 것과 같은 규칙이다)
2. **표본을 의도적으로 치우치게 뽑는다.** 무작위로 뽑으면 1.0 이 대부분이라(24/26) 일치율이
   높게 나오고 아무것도 배우지 못한다. **점수가 갈린 자리**(q3 · q14 · q21)와 **정답 문자열이
   쌍둥이와 겹치는 8문항**(q24 · q25 · q27 · q30 · q2 · q4 · q5 · q11)을 반드시 넣을 것.
3. **일치율만 내지 말고 <어느 방향으로> 틀리는지 세라.** 채점자가 후한지 박한지가 다른 사실이다.
   q3 는 **박하게** 틀렸다(맞는 답에 0.0). 이 방향이면 전체충실성이 **실제보다 낮게** 나온다.
4. 도구는 `ai-service/app/` 아래 `judge_agreement_check.py` 같은 이름이 자연스럽다.
   ⚠️ **DB 를 읽고 사람이 적은 라벨 파일을 읽는 도구라 CI 에서는 못 돈다.** `rank_trace` ·
   `answerable_check` 와 같은 부류이니 그 자리에 맞춰 문서화할 것(`ci.yml` 의 주석에
   "사람이 손으로 돌리는 것" 목록이 있고 **개수가 적혀 있다. 늘리면 그 숫자도 고칠 것**).

### 3-3. 어제 실측이 이미 가리킨 가설 하나

**근거 목록에 무관한 청크가 끼면 채점자가 있는 근거를 못 본다.** 이것이 일반적인지
(q3 한 문항의 성질인지) 모른다. 재는 방법은 어제와 같고 싸다: **답변을 고정하고 근거에
무관한 청크를 한 건씩 늘려가며** 점수가 언제 무너지는지 본다. 채점 호출 수십 회면 된다.

🔴 **이건 평가 도구만의 문제가 아니다.** 채점자와 생성 모델은 **같은 근거 목록**을 받는다
(`judge.score` 와 `generator.generate` 둘 다 `sources` 를 받는다). 채점자가 그렇게 밀렸다면
생성 모델도 같은 자리에서 그럴 수 있다. 어제 3문항에서는 답이 다 맞았지만,
**"top_k 에 무관한 청크가 끼는 것은 무해하다" 는 전제는 이미 깨졌다.**
생성 쪽까지 재면 이 슬라이스가 평가 도구 개선을 넘어 **검색 설정(top_k · max_distance)의
근거**가 된다.

### 3-4. 고칠 수 있는 것과 고치면 안 되는 것

⚠️ **채점 모델을 바꾸는 것으로 시작하지 말 것.** 두 가지 이유가 있다.
① 원인을 모른 채 손대는 것이다. ② **채점자를 바꾸면 과거 모든 표와 축이 어긋난다** -
2026-08-03 이후의 before/after 비교가 전부 `mistral-small-3.1-24b` 기준이다.
바꿔야 한다는 결론이 나오면 그때는 **옛 설정으로 한 번 더 돌려 두 채점자를 나란히** 놓아야 한다.

⚠️ **답변 생성 모델과 계열이 달라야 한다는 제약은 그대로다**(자기 채점 방지).
`judge.py` 첫머리에 근거가 있다. 후보를 고를 때 `llama-3.3-70b` 계열은 제외다.

## 4. 난이도 확보로 돌아가지 말 것 (이유)

어제 두 측정점으로 낸 결론이다.

- **질문 변형만으로는 안 내려간다.** 규칙 셋 중 둘(`lexical` · `clause`)이 무효였다.
- **코퍼스만 바꿔도 판정 분포가 안 바뀐다**(①1 ②0 ③1 ④24, 문항 단위 이동 0건).
- 🔴 **2026-08-11 에 통한 레버는 "코퍼스" 가 아니라 "코퍼스 + 그것을 겨냥한 질문" 이었다.**
  그때는 문서 6개를 넣으면서 **동시에** 기존 문항에 대상을 명시했다("업무용 컴퓨터…" →
  "**정규직의** 업무용 컴퓨터…"). 어제는 원인을 분리하려고 따로 바꿔서 그 상호작용이 없었다.

**그래서 난이도를 다시 만들려면 문서와 질문을 같이 바꿔야 한다.** 그건 `BACKLOG` §5 에
남겨뒀다. 다만 **지금 하면 안 된다** - 난이도를 만들어봐야 그것을 재는 지표(전체충실성)를
믿을 수 없는 상태다. **순서가 채점자 먼저다.**

## 5. 어제 새로 생긴 것과 그 사용법

```
cd ai-service
.venv/bin/python -m app.eval_set dump --bot-id 1        # DB → 파일 (사람이 적은 칸을 이어받는다)
.venv/bin/python -m app.eval_set load --bot-id 1        # 파일 → DB (글자 완전일치로 청크를 찾는다)
.venv/bin/python -m app.eval_set_check                  # CI 에서 돈다
.venv/bin/python -m app.eval_set_review                 # 검수 재료. DB 안 씀
EVAL_BOT_ID=1 .venv/bin/python -m app.answerable_check  # 임계값 트레이드오프
RERANKER_PROVIDER=local .venv/bin/python -m app.rank_trace --bot-id 1
```

**`difficulty` 칸이 문항마다 붙었다.** `rule` 은 `lexical` / `target` / `clause` / `""`(손대지
않음) 중 하나이고, `words` 에는 **검색이 보는 단위인 낱말 하나**만 적는다(띄어쓴 구를 적으면
검사가 뚫린다 - 아래 참고). CI 가 `lexical` 낱말이 코퍼스에 0회인지, `target` 낱말이 정답
문서 안에 있는지 검사한다.

**어제 고친 검사 구멍 둘 (되돌리지 말 것)**

1. **`lexical` 검사가 검색이 보지 않는 단위를 재고 있었다.** `count_in_corpus("직위 등급")` 은
   공백 포함 한 덩어리를 세는데 `_keyword_rows` 는 `_keywords()` 가 **공백에서 쪼갠 토큰마다**
   LIKE 를 건다. 그래서 "등급"(코퍼스 27회 · 8문서)이 0회로 통과했다. 이제 토큰 단위로 센다.
2. **`answerable_check` 가 아무것도 못 재고 "OK" 를 찍었다.** `EVAL_BOT_ID` 기본값이 2(없는
   봇)라 `0/0` 표를 그리면서 통과했다. 기본값을 1 로 바꾸는 대신 **박아둔 값 자체를 없앴다** -
   청크가 있는 봇이 정확히 하나일 때만 자동 선택하고, 아니면 봇 목록을 찍고 종료코드 1 이다.
   출력도 `자체 점검(합성 데이터)` 절과 `실제 봇 측정` 절로 갈랐다.

## 6. 🔴 다음 사람이 밟을 함정

- **`eval_set load --replace` 는 `eval_results` 를 CASCADE 로 지운다.** §3-1 의 원자료
  156건이 그 안에 있다. **누르기 전에 반드시 백업할 것**:
  `pg_dump -t eval_questions -t eval_runs -t eval_results --data-only`
  (로컬에 `psql` · `pg_dump` 가 없다. `docker exec -i alldap-db pg_dump -U alldap alldap ...` 로 쓴다)
- **전체충실성 = `avg_faithfulness × scored_count / question_count`** 다. fallback 이 많으면
  `scored_count` 가 자연히 작아지는 것이 정상이고, **오염 지표는 `generated_answer IS NULL`**
  (= 처리 실패)이다. 2026-08-13 에 이 둘을 섞어 틀린 결론을 한 번 냈다.
- **⓪(16문항) 수치와 ①②(26문항) 수치를 이어 붙이지 말 것.** 분모가 다르다. 같은 16문항만
  따로 보면 ① 에서도 15/16 = 0.9375 로 그대로다.
- **감시 낱말 가드에 구멍이 있다**(`BACKLOG` §5). `학자금`·`장학` 은 코퍼스 0건인데
  `42_해외주재원` 에 *"자녀 **학비**는 1인당 연 1500만원"* 이 있다. **낱말은 그 <표현>만 보고
  <개념>을 못 본다.** 그래서 지금 `fallback 10/10` 이 **거짓 합격일 수 있다.**
- **코퍼스에 중복 규정 27쌍이 있다**(`docs/코퍼스-중복-감사-2026-09-18.md`).
  🔴 **`취업규칙.md` 은 10개 조 중 9개가 쌍둥이, `휴가규정.md` 은 4절 전부 중복이라
  정답 청크로 쓰면 안 된다**(코퍼스에서 지우지는 말 것 - 정당한 경쟁 후보다).
  기존 평가셋 **4문항(q2 · q4 · q5 · q11)이 이미 이것에 오염돼 있다.** 어제는 고치지 않았다.
- **경계 문항은 q11 하나**(리랭킹 후 정확히 5위). 순위를 건드리는 변경은 이 문항을 제일 먼저
  깨뜨린다. 그리고 q11 은 위 오염 4문항에도 들어 있다.
- **하루 한도 10,000 뉴런**이고 평가 1회가 1,300 이다. **채점자만 직접 부르면 회당 약 25 뉴런**이라
  같은 질문에 훨씬 싸게 답할 수 있다. 어제 35회에 952 뉴런이었다.
  ⚠️ 한도 리셋은 문서의 00:00 UTC 가 아니라 **소진 시각 + 약 24~33시간**이다.

## 7. 재현하려면

```
docker compose up -d
# api 는 스키마 변경이 없으면 건너뛰어도 된다 (Flyway 최신 = V9)
cd ai-service && .venv/bin/uvicorn app.main:app --port 8001

# 박제된 원자료 보기 (평가를 돌리지 않는다)
docker exec -i alldap-db psql -U alldap -d alldap -c "
SELECT id, status, question_count, scored_count,
       round(avg_faithfulness * scored_count / question_count, 4) AS 전체충실성
  FROM eval_runs WHERE bot_id = 1 ORDER BY id;"
```

어제 쓴 채점자 실험 스크립트는 **스크래치패드에 있었고 세션이 끝나 사라졌다.** 설계는 §2 의
A · B · C 표가 전부이고, `app/judge.py` 의 `score(question, ground_truth, sources, answer)` 를
직접 부르면 된다(`sources` 는 `retrieved_chunks` 에서 그대로 꺼낸다).
🔴 **다음 세션은 그 스크립트를 저장소에 남길 것.** 어제 것이 사라진 것이 이 핸드오프에
표를 손으로 옮겨 적어야 하는 이유다.

## 8. 안 한 것 · 안 잰 것 (정직하게)

- **채점자의 정확도를 안 쟀다.** 이것이 다음 세션의 일이고, 어제 본 것은 정밀도뿐이다.
- **채점자가 일반적으로 결정적인지 모른다.** 확인된 것은 **두 입력에서 15회씩 안 흔들렸다**까지다.
- **q14 의 0.5 가 오독인지 억지스러운 엄격함인지 안 정했다.** q3 는 명백한 오독이지만
  q14 는 트집("본인 출산" vs "자기 아기")이 완전히 거짓은 아니다.
- **생성 모델이 같은 함정에 빠지는지 안 쟀다.** 어제 3문항에서는 답이 다 맞았다.
- **오염 4문항(q2 · q4 · q5 · q11)의 꼬리표를 안 고쳤다.** 고치면 기존 16문항이 "한 글자도
  안 건드린 대조군" 이 아니게 되어 과거 수치와 잇는 근거가 약해진다. 알고 남겼다.
- **난이도는 확보하지 못했다.** 판정 ① 이 0 → 1 로 늘었을 뿐이고 26문항에서 한 문항의 무게
  0.038 은 실측 편차 0.032 와 거의 같다. **"기각" 이 아니라 "이 방법으로는 측정 가능한
  난이도를 못 만들었다"** 다.
