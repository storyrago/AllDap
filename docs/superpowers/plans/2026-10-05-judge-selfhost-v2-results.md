## 결론

**M3 와 M1 의 비교는 "구별되지 않음" 이고, M3 와 M4 의 비교는 "M3 가 대응표에 더 가깝다" 다. 교체 후보는 없다.**

- M3 와 M1: M3 가 더 가까운 문항 44개, M1 이 더 가까운 문항 46개, p = 0.9161. 서비스의 채점 모델을 M3 로 바꿔도 되는지는 이 시험으로 가르지 못했다.
- M3 와 M4: M3 가 더 가까운 문항 84개, M4 가 더 가까운 문항 36개, p = 0.0000. 같은 바탕 모델(Qwen2.5-14B)에 채점 학습을 더한 M3 가 대응표에 더 가깝다.
- M3 는 거리 1 이하 문항이 216개로 M1 의 209개보다 많지만, 심각한 놓침이 5개로 M1 의 1개보다 많아 스펙 6-3절의 기준 4에서 떨어졌다. M4 는 기준 넷 모두에서 떨어졌다.

이 결과는 **대응표와 맞는가**에 대한 답이다. 정답 점수가 사람의 판단이 아니라 변형 유형에서 정해졌기 때문이다(스펙 1-3절, 9절). 서비스의 채점 모델은 바꾸지 않는다(스펙 6-3절).

### 2-1. 검색에서 버린 질문

**버린 질문은 0개다.** 네 분야 모두 75개 중 75개가 `ok` 였다.

| 분야 | 검색한 질문 | ok | 근거 유무 판정(`answerable`) | 검색용 컷(`max_distance`) | 호출 실패 |
|---|---|---|---|---|---|
| hr | 75 | 75 | 0 | 0 | 0 |
| shop | 75 | 75 | 0 | 0 | 0 |
| manual | 75 | 75 | 0 | 0 | 0 |
| finance | 75 | 75 | 0 | 0 | 0 |

- **호출 실패는 첫 시도에서 0건이었다.** 그래서 다시 검색한 질문이 없고, 다시 한 뒤의 실패 수도 0이다. 호출 실패의 원인은 둘이다. 리랭커 실패(`rerank_failed`)는 스펙 2-3절에 있는 원인이다. 키워드 검색 실패(`keyword_failed`)는 **스펙에 없던 원인으로, 계획에서 더했다.** 키워드 검색이 실패해도 서비스의 검색 함수는 경고만 남기고 벡터 결과로 계속하므로, 시험지에는 하이브리드를 켠 설정이 적히지만 실제 순서는 벡터 순서가 된다. 리랭커 실패와 같은 이유로 그 질문을 빼도록 했다.
- 검색 설정: 300줄 모두 같은 값이고 기본값과 같다(기본값과 다른 설정의 줄 0개, 최종 시험지의 검색 설정 1가지). top_k 5, max_distance 0.55, answerable_max_distance 0.44, 하이브리드 켬(후보 20, RRF k 60), 리랭커 켬(Cloudflare `@cf/baai/bge-reranker-base`, 후보 20, 점수 융합 끔), 임베딩 `@cf/baai/bge-m3`.
- 가장 가까운 청크의 거리(top1_distance)의 최댓값은 hr 0.358, shop 0.333, manual 0.381, finance 0.361 이다. 모든 질문이 판정 값 0.44 보다 0.06 이상 가깝다.

### 2-2. 정답이 근거 청크 밖이라 뺀 질문

검색은 통과했지만, 돌려받은 근거 청크 다섯 개에 질문의 답이 없어서 배정 후보에서 뺀 질문이 9개다(스펙 2-3절, `excluded.json`).

| 분야 | 정답이 근거 청크 밖(`answer_not_in_top5`) | 답이 두 가지인 질문에서 한쪽 답만 근거 청크 밖(`partial_answer_not_in_top5`) |
|---|---|---|
| hr | 0 | 1 |
| shop | 0 | 1 |
| manual | 0 | 0 |
| finance | 7 | 0 |

- 이 판단은 출제 세션이 멀쩡한 답변을 쓰면서 근거만 보고 내린 것이다. 거리 값으로 정해지는 검색 단계의 원인과 달리 **출제 세션의 판단이 들어갔고, 검수를 거치지 않았다**(검수는 배정된 문항만 본다). 뺀 질문과 이유는 `excluded.json` 에 남아 있다.
- **9개 중 7개가 금융 분야다.** 금융 7개 중 2개는 메모에 "근거에는 다른 상품의 값만 있다" 고 적혀 있다. 금융 문서에서 검색이 정답 청크를 다섯 개 안에 올리지 못하는 일이 잦다는 신호일 수 있다. 검색 품질은 이 실험의 주제가 아니므로 관찰로만 남긴다(스펙 9절). 이 때문에 금융 분야의 시험 문제는 검색이 잘 되는 질문 쪽으로 조금 더 치우쳤다.

## 7. 한계

### 7-1. 스펙 9절의 한계

- 정답 점수는 사람의 판단이 아니라 대응표다. 따라서 이 결과는 대응표와 맞는가까지만 말한다.
- 시험 문제의 잘못된 답변은 출제 세션이 상상한 실수다. 실제 답변 생성 모델이 저지르는 실수와 모양이 다를 수 있다. 이 실험에서 실수를 잘 잡는 모델이 서비스의 실제 답변에서도 잘 잡는다는 보장은 없다.
- 멀쩡한 답변은 Claude 가 llama 의 말투를 따라 쓴 것이다. 문장 길이, 어미, 덧붙이는 말의 습관이 실제 llama 답변과 다를 수 있고, 답이 두 가지인 질문의 답변은 견본보다 길다.
- 말투 견본 하나는 실제 llama 출력에서 언어가 섞인 낱말 하나를 지운 것이다. 이 실험은 언어가 섞인 답변을 채점 모델이 어떻게 매기는지 보지 않는다.
- 출제는 Claude, 검수는 Codex(OpenAI)가 했다. 계열이 다른 두 모델이 함께 놓치는 실수는 검수를 통과한다.
- 검수 세션이 전용 폴더 밖을 읽지 못하게 막는 장치는 없다. 폴더에 시험지 사본 하나만 두었고 지시문에 저장소 경로를 적지 않았으며, 폴더 밖을 읽지 말라고 지시했다.
- ⑥ 과 ⑧ 은 답이 하나인 질문에만 있다. 답이 두 가지인 답변에서 한쪽 값만 틀린 경우는 보지 않는다.
- 새 분야 문서는 Claude 가 쓴 가상 문서다. 실제 고객 문서의 길이, 표, 서식 다양성을 따르지 못할 수 있다.
- 코랩 모델은 한 번만 채점했다. 같은 문항에 같은 점수를 주는지는 앞 실험의 44건에서만 확인했다.
- 점수 읽는 규칙에 더한 규칙(끝의 `[n]` 을 점수로 읽는다, 스펙 6-4절)은 앞 실험의 M4 출력을 보고 만들었다. 이번 측정에 대해서는 미리 고정한 규칙이지만, 규칙을 넓힌 계기가 M4 였다는 점은 남는다(5절의 수치에는 이 규칙이 들어가 있다).
- 코랩 모델은 모두 4비트다. 공통 지시문은 M3 가 학습한 양식이라 M3 에 유리할 수 있다. 이 실험의 M1 점수는 서비스의 M1 점수와 같은 값이 아니다.
- 결과는 이 시점의 모델 리비전과 검색 설정 기준이다.
- 정답이 근거 청크 밖이라 뺀 질문은 출제 세션의 판단이고 검수를 거치지 않았다(2-2절). 9개 중 7개가 금융이라 금융 시험 문제는 검색이 잘 되는 질문 쪽으로 치우쳤다.

### 7-2. 실행하면서 새로 알게 된 한계

- **④ 절반 바꾸기의 대응표 점수(3점)는 하나로 정해지지 않는다. 스펙의 결함이다.** 스펙 3-2절은 근거에 있는 주장 하나와 없는 주장 하나로 된 답변이 4점 정의와 3점 정의에 모두 맞아 정답이 하나로 정해지지 않는다는 이유로, ③ 사소한 말 하나 추가를 주장 2개 이상인 답변에만 만들었다. 그런데 주장이 둘인 답변에서 하나를 바꾼 ④ 가 바로 그 모양이다. 검수가 4점을 준 9개를 버렸지만, **검수가 3점을 준 나머지 27개도 같은 구조라서 최종 시험지의 3점 정답 27개에 같은 애매함이 남아 있다.** 이번 결과에서 M1 은 이 27개 중 25개에 4점을 줬다(5-2절). 대표 지표(거리 1 이하)에서는 맞힌 것으로 세지만, 정확히 같음과 평균 거리에서는 틀린 것으로 센다. 그 4점이 틀린 판단인지 애매한 문항에 대한 다른 읽기인지는 이 시험으로 가르지 못한다.
- **유지한 ⑥, ⑧ 3개(2-4절)도 1점과 3점 사이에서 읽기가 갈린 문항이다.** 사용자가 1점 정의를 따라 대응표대로 두었지만, 검수 세션은 3점으로 읽었다.
- **검색에서 버린 질문 0개는 근거 유무 판정 값 0.44 가 새 세 분야에서 답할 수 있는 질문을 잘못 버리지 않는다는 것만 보여 준다.** 질문을 문서를 보고 썼으므로 모든 질문이 답할 수 있는 질문이다. 0.44 가 새 분야에서 답할 수 없는 질문을 막는지는 재지 않았다.
- **검색 단계의 "200자 이하 근거만 있는 질문" 확인은 이 코퍼스에서 신호가 아니다.** 계획은 검색 함수가 본문 앞 200자만 돌려준다는 점(스펙 2-3절) 때문에 근거가 200자 이하인 질문을 세어 보게 했고, 186개가 나왔다. 확인해 보니 청크가 잘린 것이 아니라 원래 짧았다. 시험지의 근거 1,500개(300문항에 다섯 개씩)의 본문을 DB 의 청크 본문과 대조해 1,500개 모두 글자까지 같았다. 청크를 소제목마다 자르므로 평균 길이가 hr 77자, shop 105자, manual 151자, finance 136자다. 이 코퍼스에서는 200자 이하인 근거가 잘림의 신호가 되지 못한다.
- **M1 의 뉴런이 어림보다 약 1,300 많았다**(6-1절). 이번에는 하루 한도 안에 들었지만, 문항 수를 늘리면 하루에 끝나지 않을 수 있다.

### 7-3. 실행 중의 실수와 도구 문제

모두 시험지, 정답 파일, 결과 파일에 영향이 없다.

- **배정 기록 점검 도구의 옛 판이 두 경로에서 거짓 실패했고, 두 리뷰 세션의 재현 결과가 갈렸다.** 점검 도구(`judge5v2_check`)는 첫 배정 회차의 후보가 그때 검색을 통과한 질문 전부인지 대조한다. 옛 판은 지금의 검색 결과 파일 전체로 정답을 만들었기 때문에, 첫 배정 전에 보충한 질문(76번 이후)이 첫 회차 후보에 든 경우와 첫 회차 뒤에 다시 검색해 `ok` 가 된 질문이 있는 경우에 거짓으로 실패했다. 관문 뒤에 보충한 질문을 덧붙인 경우에는 통과했다. 한 리뷰 세션은 앞의 경로로, 다른 리뷰 세션은 뒤의 경로로 재현해 결론이 달랐고, 둘 다 맞았다. 지금 판은 회차에 기록된 검색 파일 해시와 같은 해시를 내는 앞부분으로 대조하고(`3b494c5`), 두 경로를 점검 항목으로 고정했다(`1e35626`).
- **계획 E12 Step 4 의 `git add $P` 가 zsh 에서 실패했다.** 계획은 커밋할 경로 여러 개를 공백으로 이어 `P` 에 담고 `git add $P` 로 넘긴다. bash 는 따옴표 없는 변수를 공백에서 나누지만 zsh 는 기본 설정에서 나누지 않으므로, git 은 공백이 든 경로 하나를 받아 실패했다. M1 결과 커밋(`c6f69a3`)에는 결과 파일과 실행 기록 두 파일이 모두 들어갔다. PR 전에 계획 문서의 그 명령을 경로를 따로 적는 방식으로 고쳤다.
- 출제 세션이 셸 문법 실수로 빈 업로드를 한 번 보냈다.
- 검색 담당 세션이 점검 실패를 파이프 뒤의 종료 코드로 놓친 채 커밋한 일이 한 번 있었다.
- 점검 도구 담당 세션이 스펙 편집에 실패한 뒤 커밋 본문에 고쳤다고 적은 일이 한 번 있었다. 경위는 다음 커밋에 적었다.

### 9-1. 고른 방향에서 주의할 것

- **학습에 동결 시험지 231문항을 쓰지 않는다.** 시험지로 학습하면 같은 시험지로 효과를 잴 수 없다. 학습 데이터는 같은 파이프라인(문서, 질문, 멀쩡한 답변, 변형)으로 새로 만든다.
- **1점 문항이 72개뿐이다.** 심각한 놓침이 5에서 1로 줄었다는 것을 증명하려면 1점 문항이 더 많은 새 시험지가 필요하다. 지금 시험지로는 5와 1의 차이가 우연인지 가르기 어렵다.
- **파인튜닝은 AGENTS.md 작업 규칙 7번이 연 범위 밖이다.** 규칙 7번은 채점 모델의 추론을 실험 용도로 연 것이지 학습을 연 것이 아니다. 파인튜닝으로 가려면 사용자가 먼저 규칙을 넓혀야 한다. 프롬프트를 고치는 쪽은 지금 범위 안이다.
