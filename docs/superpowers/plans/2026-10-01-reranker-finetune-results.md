# 리랭커 파인튜닝 실험 결과 (2026-10-02 종료)

설계: [`specs/2026-10-01-reranker-finetune-design.md`](../specs/2026-10-01-reranker-finetune-design.md)
계획: [`2026-10-01-reranker-finetune.md`](2026-10-01-reranker-finetune.md)

## 결론

**학습 전 관문을 두 번 통과하지 못해(4/71, 4/71) 학습하지 않고 실험을 마쳤다.**

이 결과는 "파인튜닝은 효과가 없다" 가 아니다. 정확한 서술은 이렇다.
**이 시험 틀(시험용 봇 문서 20개, 시험 문제 71개)에서는 원본 리랭커(B)가 이미 약 90% 를 5위 안에 올려, 파인튜닝이 좋아질 자리가 없어 효과를 잴 수 없다.**
관문은 이런 상황을 학습 전에 막으려고 둔 장치이고(스펙 §5-2), 그 장치가 의도대로 동작했다.

## 1. 측정 설정

- 시험용 봇 8번, 시험 문제 71개, 원본 모델 `bge-reranker-base` 로컬 fp32(`local`) 한 변형
- `answerable_max_distance` 0.44, `max_distance` 0.55, top_k 5, 리랭커 후보 20, 하이브리드 검색 켜짐, `rerank_fusion` 꺼짐
- 명령: `rank_trace --bot-id 8 --compare local --gate local --out ...`
- 관문 기준: 고칠 수 있는 문제이면서 정답 청크가 5위 밖인 문제가 전체의 4분의 1(0.25) 이상

## 4. 가설

- **반증됨: "질문에 대상 이름이 그대로 들어가 낱말 맞추기로 풀린다."** 대상을 돌려 말한 2차에서도 64/71 이 5위 안이었다. 돌려 말한 38문항만 세도 5위 밖은 3개(0.079)다.
- **남은 가설(검증하지 않음): 시험용 봇은 문서가 20개뿐이라 경쟁 문서가 적다.** 같은 주제를 다른 대상으로 적은 문서가 묶음당 2~7개라, 원본 모델도 대상의 단서만 잡으면 맞힌다. 실제 고객 코퍼스 규모에서 원본 모델이 틀리기 시작하는지는 재보지 않았다.

## 5. 일부러 택하지 않은 길

- **원본(B)의 순위로 문제를 골라내기.** B 가 틀리는 문제만 남기면 관문은 통과한다. 그러나 그렇게 고른 문제에서는 파인튜닝 모델(D)이 우연히만 달라도 "좋아짐" 이 나온다(선택 편향). 그래서 2차 문제는 1차와 같은 청크를 쓰고, 돌려 말할 문항도 B 결과와 무관한 규칙(말투와 대상)으로 정했다.
- **결과를 본 뒤 판정 기준을 "1위 진입" 으로 바꾸기.** 숨기지 않고 적는다: **기준을 "고칠 수 있는데 1위가 아닌 문제" 로 잡았다면 1차, 2차 모두 19/71 = 0.268 로 4분의 1을 넘어 통과했다.** 그러나 그건 결과를 본 뒤 기준을 바꾸는 것이라 쓰지 않았다. 또 이 실험의 대표 지표는 상위 5개 진입률(최종 근거 5개 안에 드는가)이다. 생성 모델은 근거 5개를 함께 받으므로, 정답 청크가 그 안에서 몇 위인지는 근거 묶음 자체를 바꾸지 않는다(순서가 답변에 주는 영향은 이 실험에서 재지 않았다).
- **세 번째 시도.** 2차 실패 시 종료를 측정 전에 정했다(규칙 11).

## 6. 알고 남긴 것

- **t32, t35, t37**: 재택근무 전담자를 "집에서만 일하는 조건으로 입사" 로 돌려 말했다. 53_자회사도 "전면 재택근무 원칙" 이라 자회사 직원으로 읽힐 여지가 있다. 사용자 결정으로 고치지 않고 유지했다. 2차 결과는 t32 4위, t35 1위, t37 6위(5위 밖)다. t37 이 자회사 쪽으로 끌렸는지는 보지 않았다.
- **주재원 문항의 정답 문서(규칙 9)**: 주재원의 재택, 노트북, 결혼 휴가(t9, t10, t13)는 정답이 `42_해외주재원` 이 아니라 `52_해외지사` 다. 질문은 42 쪽으로 읽히므로 문항 자체가 어렵다. 2차 결과는 t9 3위, t10 1위, t13 1위.
- **토크나이저 경고**: 두 측정 모두 시작할 때 `The tokenizer you are loading from '.../bge-reranker-base-onnx' with an incorrect regex pattern ... You should set the fix_mistral_regex=True flag` 가 떴다. 순위에 영향이 있는지는 확인하지 않았다.
- **잰 것은 B 하나뿐이다.** C(원본 + INT8 양자화)는 재지 않았다. 관문 판정에는 B 만 필요하다.
- **예비 시험 문제(봇 7번, 33문항)는 재지 않았다.** 학습을 하지 않았으므로 5-5절의 원인 가르기가 필요 없다.

## 7. 쓰지 않은 비용

관문에서 멈췄으므로 계획의 Task 8~15 를 하지 않았다: 학습 데이터 생성 도구, 연습 문제 300~400개 작성, 코랩 학습, 파인튜닝 모델 내보내기, B/C/D/E 비교, 전체충실성 측정. 이 실험에서 쓴 비용은 시험 문제 두 벌(71개씩)과 예비 시험 문제 두 벌, 그리고 `rank_trace` 두 번이다.

## 8. 남긴 재료와 다시 열 조건

**남긴 재료** (지우지 않는다)

- 로컬 DB 의 봇 7번(학습용 문서 36개, 예비 시험 문제 33문항), 봇 8번(시험용 문서 20개, 시험 문제 71문항). 계정 `finetune@local.test`
- `testdata/finetune/` 의 `split.json`, `twins.json`, `test_questions.json`, `holdout_questions.json`, `gate_B_round1.json`, `gate_B.json`
- `app/finetune_split_check.py`(누출 검사), `app/rank_trace.py` 의 비교 모드(`--compare`, `--pair`, `--gate`), `app/eval_set.py` 의 `--file`

**다시 열 가치가 있는 때**

- 경쟁 문서가 많은 조건(실제 고객 코퍼스 규모)에서 원본 리랭커가 틀리기 시작할 때
- 실제 대화 로그에서 "정답 문서가 있는데 근거로 못 가져온" 실패가 보일 때

**리랭커를 바꿀 때의 기준선으로 쓴다.** 앞으로 Cloudflare 모델을 직접 만든 모델로 바꿀 때, 이 시험 문제로 "원본(B, 64/71)보다 나빠지지 않았는가" 를 잰다. 그때 묻는 것은 효과가 있는가가 아니라 나빠지지 않았는가(비열등)다. 따라서 이번 관문(고칠 자리가 4분의 1 이상)은 그 용도에 필요 없다.
