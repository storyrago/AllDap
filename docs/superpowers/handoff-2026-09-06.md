## 2. 🔴 배포할 때 반드시 할 것 — 두 건이 밀려 있다

배포는 여전히 보류다(RDS 프리티어 충돌, `docs/decisions.md`). **풀리는 날 이 둘을 빠뜨리면 안 된다.**

**① caddy 를 명시적으로 재생성해야 한다.** `docker-compose.prod.yml` 이 `Caddyfile` 을 bind mount 로 걸어두는데, Compose 는 **이미지 다이제스트나 서비스 정의**가 바뀔 때만 컨테이너를 재생성한다 — **마운트된 파일의 내용 변경은 재생성 조건이 아니다.** 게다가 `caddy:2-alpine` 이 부동 태그라 `pull` 이 새 caddy 를 받으면 우연히 재생성되고 아니면 안 된다. **"확실히 안 된다" 가 아니라 "될 때도 있고 안 될 때도 있다" 라 더 나쁘다.**

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --force-recreate caddy
```

이 한 줄이 없으면 PR #44 의 유일한 실효 조치(`header_up -Forwarded`)가 **운영에 적용조차 안 된다.** 절차는 `docs/DEPLOY.md` §9 에 적어뒀다.

**② 배포 후 rate limit 종단 확인.** 테스트가 닿을 수 없는 자리라 실제 요청으로만 잴 수 있다. `Forwarded` 헤더를 바꿔가며 위젯 채팅을 25회쯤 부르고, 한도 이후 429 가 나오는지 본다. **25개가 전부 200 이면 ①이 안 먹은 것이다.**

**③ 계량 때문에 새로 생긴 것:** `V5__usage_events.sql` 이 적용돼야 한다. Flyway 라 `api` 기동 시 자동이지만 **`api` 가 `ai-service` 보다 먼저 떠야 한다**(테이블이 없으면 Python 이 실패한다).

## 3. 요금제 연동 — 4조각 중 어디까지

과금 방식은 **정액 + 초과 사용량**, PG 는 **토스페이먼츠 직접 연동, 테스트 키까지**로 정했다. 실결제는 사업자등록 심사가 필요해 범위 밖이고, 그 사실을 숨기지 않는다.

| # | 조각 | 상태 |
|---|---|---|
| 1 | **계량** — 과금 대상 사건을 계정별 원장에 쌓는다 | ✅ 완료 (PR #52·#53) |
| 3 | **결제 수단 등록** — 토스 빌링키 발급·저장·삭제 | 🚧 **설계 중 — 여기** |
| 2 | 플랜·포함량 — 개수에 플랜을 곱한다 | ⬜ **의도적으로 뒤로 미뤘다** (아래) |
| 4 | 청구 — 마감·금액 산정·자동결제·실패 처리 | ⬜ |

### 🔴 2번과 3번의 순서를 바꿨다 — 근거가 중요하다

원래 순서는 1 → 2 → 3 → 4 였다. **2번을 하려다 멈췄다.**

`/pricing` 의 중심 주장이 **"금액이 아직 없다"** 이고 그게 의도다. PRD §13.1 은 *무엇에 값을 매길지*(과금축)를 확정하고 *얼마를 받을지*는 **"파일럿 4주 후"** 로 미뤄뒀다 — **실사용 데이터 없이 정하면 근거 없는 숫자가 되기 때문이다.**

그런데 2번(플랜·포함량)은 정확히 그 숫자들을 요구한다(월 정액·포함 답변 수·초과 단가). 지금 만들면 `/pricing` 은 "금액 없다"고 하는데 DB 엔 금액이 있게 되고, **이 저장소가 여러 번 지켜온 원칙("근거 없는 숫자를 쓰지 않는다")을 정면으로 어긴다.**

**3번은 금액이 하나도 필요 없다.** 빌링키 발급은 "이 고객의 카드를 저장한다"까지고 얼마를 청구할지는 4번의 일이다. 그래서 3번을 먼저 한다. 2번은 파일럿 데이터가 나온 뒤에 금액과 함께 만든다.

## 4. 3번 조각 — 여기까지 정해졌다

### 토스페이먼츠 자동결제의 모양

```
① 브라우저: 토스 SDK 가 카드 입력 창을 띄운다  →  authKey 를 받는다
② 서버: authKey + customerKey  →  토스에 빌링키 발급 요청
③ 서버: billingKey 를 저장한다        ← 3번 조각은 여기까지
④ 나중에: billingKey 로 금액을 청구한다  ← 4번 조각
```

**카드번호가 우리 서버·우리 페이지에 닿지 않는다.** 토스가 자기 창에서 받고 우리는 `authKey` 만 받는다. PCI-DSS 대상 데이터를 우리가 갖지 않는다는 뜻이라, 설계 문서와 PR 에 반드시 적을 것.

### 확정된 결정 3건

**① 범위 = 등록 + 조회 + 삭제.**
삭제가 있어야 완결이다 — 카드를 넣을 수만 있고 뺄 수 없으면 기능이 아니라 함정이다. 그리고 "결제 수단 없음 → 있음 → 다시 없음" 을 한 바퀴 돌 수 있어야 종단 검증이 성립한다.
카드 *교체* 는 넣지 않는다. 삭제 후 재등록으로 같은 일이 되고, 상태 전이만 하나 늘어난다.

**② `billingKey` 는 앱 레벨에서 암호화해 저장한다 (AES-GCM, 키는 환경변수).**

먼저 이게 얼마나 민감한지 — `billingKey` 는 **카드번호가 아니다.** 토스가 카드를 들고 있고 우리는 "이 카드에 청구해달라" 고 말할 수 있는 열쇠만 받는다.
- PCI-DSS 대상이 아니다
- 다른 가맹점이 훔쳐도 못 쓴다(우리 상점 계정으로만 동작)
- 🔴 **그래도 새면 "우리 상점 명의로 그 고객에게 청구" 가 가능하다.** JWT 시크릿과 같은 급의 자격증명이다

평문(대부분의 튜토리얼) 대신 암호화를 택한 이유는 보안보다 **설명 가능성**이다. *"결제 수단을 어떻게 저장했나요?"* 는 거의 확실히 나오는 질문이고, 평문은 *"평문으로 넣었습니다"* 로 끝난다.
`JwtService` 가 이미 환경변수 시크릿을 다루고 **운영에서 기본값이면 기동을 막는 가드**까지 갖고 있으니 그 패턴을 그대로 따른다.
대가도 그대로 적을 것: **키를 잃으면 전 고객이 카드를 다시 등록해야 한다.**

**③ ⚠️ 토스에는 빌링키를 폐기하는 API 가 없다.**
만료도 없고 취소 엔드포인트도 없다. 그래서 **"카드 삭제" 는 우리가 그 열쇠를 잊는 것**이지 토스 쪽에서 무효화되는 게 아니다. 실질은 같지만(우리만 쓸 수 있는 열쇠를 우리가 지웠다) **"삭제했다" 와 "폐기됐다" 는 다른 사실**이라 설계 문서·PR·화면 문구에 그대로 적을 것.

### ⬜ 답을 못 받고 멈춘 질문 — 여기서 이어가면 된다

**`customerKey` 를 무엇으로 할 것인가.** 빌링키를 발급받으려면 고객마다 식별자를 하나 정해 토스에 넘겨야 한다. 토스 문서의 요구는 둘 — **추측 불가**(순번 금지), **개인정보 금지**(이메일·전화번호 금지).

- **A. `users.id`(UUID) 를 그대로 쓴다** — 컬럼이 안 는다. UUIDv4 라 추측 불가 조건은 만족한다.
  대가: **내부 기본키가 외부 업체에 그대로 나간다.** 토스 대시보드·로그·CS 문의에 우리 DB 의 PK 가 찍히고, 나중에 이 값을 바꿔야 할 일이 생기면 외부 연결이 함께 깨진다.
- **B. 전용 랜덤 키를 따로 둔다 ← 권장** — `billing_customer_key` 컬럼을 더하고 등록 시점에 생성한다.
  **저장소에 이미 같은 선례가 있다** — `bots.public_key`(`pk_...`) 가 정확히 그 패턴이다(봇 UUID 를 고객 사이트 HTML 에 노출하지 않으려고 별도 공개키를 만들었다). 그래서 *"왜 UUID 를 안 썼나요?"* 에 일관된 답이 된다: **"내부 식별자를 외부에 흘리지 않는다는 규칙을 이미 봇에 적용했고 결제도 같게 뒀습니다."**
  대가: 컬럼 하나와 생성 로직 몇 줄.

이 질문에 답하면 설계 문서(`docs/superpowers/specs/`)를 쓰고 → 구현 계획 → subagent-driven 실행 순으로 가면 된다. 앞의 두 조각이 그 흐름이었다.

## 5. 미룬 것 (알고 남긴 것)

- **대시보드의 `cancelled` 플래그가 실효 없다.** `web/app/(dashboard)/dashboard/page.tsx` 의 두 effect 가 `await` **뒤에** 플래그를 검사해서, 언마운트 후 setState 를 막지 못한다. 기존 `loadBots` 패턴을 그대로 따른 것이라 계량 작업이 만든 결함은 아니고, React 19 에서 실질 피해도 없다. **고칠 때 두 effect 를 함께 다룰 것.**
- **계량 이전 데이터는 세어지지 않는다.** 채팅은 소급이 불가능하고(지워진 봇의 대화는 못 만든다) 평가 실행은 메꾸기가 과거 것까지 집는다 — **두 종류의 시작점이 다르다.** 화면에 이 비대칭을 적을지는 2번 조각에서 정한다.
- **평가와 채팅의 `occurred_at` 이 서로 다른 시계에서 온다.** 채팅은 Postgres `now()`, 평가는 `eval_runs.created_at`(Spring `@CreatedDate`, JVM 시계). 월 경계 ±수백 ms 에서 갈릴 수 있다. 맞추려면 flush 순서에 의존하게 돼서 구조를 안 바꾸고 주석으로만 남겼다.

## 6. 이번에 두 번 틀렸고, 기록으로 남겼다

다음 세션이 같은 판단을 다시 할 때 재료가 된다. 둘 다 **지우지 않고 "틀린 것으로 드러났다" 형태로** spec·plan·`decisions.md`·PR 본문에 남겼다.

- **`usage_events.user_id` 에 CASCADE 를 걸지 않는다** → 뒤집혔다. 계정 삭제 시 청구 근거를 지키려던 결정인데, **계정 삭제 기능이 없는 반면 대가는 실재했다** — 통합 테스트가 공유 컨테이너에서 `userRepository.deleteAll()` 로 정리하는데 그 FK 가 정리를 막아 무관한 테스트 11건이 깨졌다. 설계가 지키려던 것("봇을 지워도 남는다")은 `bot_id` 에 FK 를 안 건 쪽이 담당하며 그대로다.
- **"평가 메꾸기의 비원자성은 4번 조각의 일"** → 틀렸다. *"마감 시점에만 닫을 수 있다"* 고 봤는데 **봇 삭제 경로에서 삭제 전에 한 번 메꾸면 같은 트랜잭션 안에서 닫힌다**(한 줄). 리뷰가 Critical 로 잡았다.

그리고 **`X-Forwarded-For` 가 rate limit 의 구멍이다** 라는 앞선 판단도 실측으로 반증됐다 — caddy 2.11.4 는 신뢰하지 않는 피어의 `X-Forwarded-*` 를 **잇지 않고 버린다**. 진짜 구멍은 `Forwarded`(RFC 7239) 였다. `decisions.md` 2026-09-04 항목 참고.
