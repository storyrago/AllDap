## 2. 이 슬라이스가 답한 것

**같은 16문항 · 50문서 · 306청크 · `temperature=0` · 리랭커+하이브리드 ON · 설정당 3회.**
바꾼 변수는 **리랭커를 어디서 돌리는가** 하나다.

| 설정 | 전체충실성 | 응답률 | 회당 오답 | fallback | 모델 크기 | 회당 리랭커 뉴런 |
|---|---|---|---|---|---|---|
| A · Cloudflare | 0.812 ×3 | 0.813 | 0.00 | 3.00 | (Cloudflare) | 9.7 |
| B · 로컬 fp32 | 0.812 ×3 | 0.813 | 0.00 | 3.00 | 1060.9MB | **0** |
| C · 로컬 INT8 | 0.750 ×3 | 0.750 | 0.00 | 4.00 | 265.9MB | **0** |
| C' · INT8 per-channel | (안 쟀다. 아래 참고) | | | | 266.3MB | **0** |

**① A 와 B 는 구별되지 않는다.** 16문항 × 3회가 한 칸도 다르지 않고 top5 순서까지 15/15 같다.
⚠️ 증명된 것은 "Cloudflare 가 같은 가중치를 쓴다" 가 아니라 **"이 입력들에서 두 구현의 top5 가
갈리지 않았다"** 까지다.

**② 양자화의 대가는 정확히 한 문항이다** (q7, 추천 보너스 지급 시점). 정답 청크 77 이 top5 밖으로
밀렸다. **오답은 0건 유지**이므로 잃은 것은 "틀린 답" 이 아니라 "안전한 실패" 다.
0.0625 는 편차 0.032 의 2배라 구별되지만, 16문항이라 **한 문항이 곧 0.0625** 라는 것도 사실이다.

**③ B·C 의 뉴런 로그에는 `bge-reranker-base` 항목이 아예 없다.** 0 으로 찍힌 것이 아니라
목록에서 사라졌다. 로컬에서 돌았다는 가장 단단한 증거다.

**④ 기본값은 `cloudflare` 그대로다.** B 가 A 와 구별되지 않지만 로컬 제공자는 운영 이미지에서
기동하지 않고(`onnxruntime` 이 `requirements-lab.txt` 에만 있다), 아끼는 것은 회당 9.7 뉴런(1.4%)뿐이다.
**코드는 지우지 않는다** (`rerank_fusion` 을 남긴 것과 같은 이유다. 지우면 재현할 수 없는 주장이 된다).

## 3. 🔴 다음은 <평가셋 정비>다. 리랭커 파인튜닝이 아니다

설계문서 §6 과 그전의 `BACKLOG` 는 "다음은 파인튜닝" 이라고 못박아 뒀다. **측정이 그 전제를 무너뜨렸다.**

`app/rank_trace.py` 로 16문항의 정답 청크를 단계별로 추적한 결과다.

- **15/16 문항에서 정답 청크가 이미 근거 top5 안에 있다.**
- **"후보 안인데 순위가 낮아 밀려난" 문항이 0개다.** 리랭커가 할 일이 남아 있지 않다.
- 즉 **리랭커 파인튜닝이 회복할 수 있는 문항은 0개다.**

세 설정이 똑같이 실패하는 3문항의 정체는 이랬다.

| 문항 | 정답 청크 | 판정 |
|---|---|---|
| q1 수습 직원 학습 시간 | 리랭킹 후 **1위**, LLM 에 전달됨 | **질문 생성 결함** |
| q16 업무용 컴퓨터 네트워크 연결 | 리랭킹 후 **2위**, 전달됨 | **질문 생성 결함** |
| q6 토의 공간 대여 한도 | 게이트가 잘라 근거 `[]` | 임계값 + 어휘 불일치 (판정 애매) |

q1 의 정답 청크는 *"인턴은 입사 첫 주에 40시간의 온보딩 교육을 이수해야 한다"* 인데 질문은
**수습 직원**을 묻는다. q16 은 문서가 *"개인 노트북"*, 질문이 *"업무용 컴퓨터"* 로 **대상이 반대**다.
**둘 다 거절이 옳은 동작**인데 지표에서는 fallback 으로 집계돼 천장을 만든다.

🔴 **즉 지금 천장 0.8125 를 만드는 것은 검색 품질이 아니라 평가셋의 결함이다.**

**그리고 원래 노리던 실패(재택 · 기간제)는 이번 세트에 없다.** V9 가 지운 옛 질문 세트의 문항이다.
코퍼스는 `testdata/corpus/` 로 재현되는데(재적재하니 청크 306개로 정확히 일치) **질문은 저장소
어디에도 파일로 없다.** 파인튜닝은 이 세트를 학습 데이터로 쓰므로 직접 걸리는 문제다.

⚠️ **파일로 남기는 것만으로는 부족하다.** q1·q16 이 보여주듯 자동 생성 질문에는 문서에 없는
대상을 묻는 결함이 섞인다. 검수 절차가 함께 필요하다.

## 4. per-channel 양자화는 끝났다 (가설이 절반만 맞았다)

C 가 잃은 한 문항의 원인이 "스케일을 텐서 하나가 공유해서" 인지 재봤다.

| | PyTorch 대비 최대 로짓 오차 | q7 정답 청크(77)에 실린 오차 | 77 의 순위 |
|---|---|---|---|
| INT8 | 1.158 | 0.733 | 7위 |
| INT8-pc | **0.288** (약 1/4) | **0.691** (거의 그대로) | **6위** |

**모델 전체의 오차는 1/4 로 줄었는데 문제의 항목에 실린 오차는 거의 안 줄었다.**
77 은 여전히 top5 밖이고 경계와의 차이가 **0.00115** 다. 사실상 동점이라
**"거의 돌아왔다" 로 쓰지 않았다** (0.032 짜리 편차를 아는 저장소가 0.001 로 주장을 세울 수 없다).

→ **평균 오차를 줄이는 것과 특정 항목의 순위를 지키는 것은 다른 문제다.**

**평가 3회(약 2,000 뉴런)는 돌리지 않았다.** 정답 청크의 top5 진입 여부가 C 와 C' 에서 완전히
같아, 돈을 써서 얻을 것이 "C 와 같다" 뿐이었기 때문이다(임베딩만 써서 0.4 뉴런으로 판정했다).
⚠️ 문서에 **"돌렸더니 같았다" 가 아니라 "돌리지 않았다"** 로 적혀 있다. top5 <안에서의> 순위
변화가 생성 품질을 바꾼다는 것은 2026-08-11 에 실측돼 있고, **그 부분은 안 쟀다.**

## 5. 새로 생긴 것과 그 사용법

```bash
cd ai-service
.venv/bin/pip install -r requirements-lab.txt        # 실험 전용. 운영 이미지에는 안 들어간다
.venv/bin/python -m app.export_reranker              # 내려받기 → ONNX → INT8 (세 변형)
.venv/bin/python -m app.local_reranker_e2e_check     # 진짜 모델로 계약·크기·지연·RSS
RERANKER_PROVIDER=local_int8 .venv/bin/uvicorn app.main:app --port 8001
```

| 파일 | 무엇 |
|---|---|
| `app/local_reranker.py` | 로컬 추론. Cloudflare 와 **똑같은 출력 계약**이라 `retriever._rerank` 는 무수정 |
| `app/export_reranker.py` | 리비전 고정 · ONNX 변환 · **등가 검증** · INT8 양자화 |
| `app/rank_trace.py` | **정답 청크가 단계별로 어디 있는지** 추적. 이번 판단의 근거를 낸 도구 |
| `app/rerank_compare.py` | 제공자별 평가 결과 집계(`completed` 인 실행만) |
| `requirements-lab.txt` | 실험 의존성. `requirements.txt` 와 갈라 운영 이미지를 안 무겁게 한다 |

```bash
RERANKER_PROVIDER=local .venv/bin/python -m app.rank_trace --bot-id 1     # 문항별 표
.venv/bin/python -m app.rank_trace --bot-id 1 --scores 7                  # 제공자별 점수 비교
.venv/bin/python -m app.rerank_compare --bot-id 1                         # A·B·C 집계
```

## 6. 🔴 다음 사람이 밟을 함정

**① 경계 문항은 고정된 목록이 아니다.** q11 이 fp32 에서 리랭킹 후 정확히 5위라 경고로 남겼는데,
**INT8 에서는 q12 가 5위로 내려와 경계에 서고 C' 에서는 3위로 돌아온다.** 경계에 서는 문항이
설정마다 옮겨 다닌다. **순위를 건드리는 변경을 할 때마다 `rank_trace` 로 다시 볼 것.**

**② 지연 수치를 이어 붙이지 말 것.** 2026-09-16 의 `B 14.6ms / C 10.9ms` 와 2026-09-17 의
`18.5 / 17.2 / 16.9ms` 는 같은 기계지만 다른 시각이고 그때는 다른 작업이 함께 돌았다.
**연달아 잰 한 표 안에서만 비교가 성립한다.** 20회로는 꼬리(p95)를 말할 표본이 아니다.
그리고 전부 **Apple M4 Pro(ARM) 기준**이다. INT8 가속은 아키텍처마다 다르다.

**③ `export_reranker` 를 다시 돌려도 기존 산출물을 덮지 않는다** (`--force` 로만 덮는다).
그 가드가 없던 동안 **스크립트를 한 번 더 돌리는 것만으로 대조군이 사라질 뻔했다.**
`ORTQuantizer` 가 변형과 무관하게 `model_quantized.onnx` 로 떨구기 때문에 디렉터리를 나눠뒀다.

**④ 로컬 제공자는 운영 이미지에서 기동하지 않는다.** 의도한 것이다. 모델이나 의존성이 없으면
조용히 Cloudflare 로 떨어지지 않고 한국어 오류를 낸다. **채팅은 그때도 벡터 순서로 살아남지만
평가는 시작조차 하지 않는다** (리랭커 없이 돈 결과가 "로컬 리랭커 측정치" 로 표에 실리면 안 된다).

**⑤ Spring 은 아직 `RERANKER_MODEL_UNAVAILABLE` 을 모른다.** Python 은 503 + `detail.code` 로
내보내는데, Spring 은 5xx 를 전부 `AI_SERVICE_UNAVAILABLE` 로 바꾸고 **서킷브레이커 실패로 센다.**
모델 없이 로컬 제공자로 둔 채 평가를 몇 번 누르면 **멀쩡한 Python 이 차단되고 채팅까지 막힌다.**
`AGENTS.md` 의 "서킷은 우리 잘못을 실패로 세지 않는다" 와 어긋나는 자리다.
이번 슬라이스 범위가 `ai-service/` 안이라 고치지 않았고, 운영 이미지에는 `onnxruntime` 이 없어
실제 위험은 낮다.

## 8. 안 한 것 · 안 잰 것 (정직하게)

- **C' 의 평가 지표.** 위 4번 참고. 근거 집합이 같아 생략했고, top5 안에서의 순서 변화가 생성에
  주는 영향은 안 쟀다.
- **운영 환경(x86_64)에서의 속도.** 전부 맥북에서 쟀다.
- **`rank_trace` 는 CI 에서 돌지 않는다.** DB 와 실제 모델이 필요해서다. 이 도구 자체는
  자동으로 회귀를 잡아주지 않는다.
- **판정 ④(정답 청크가 근거에 들어갔는데도 답을 못 했다)를 `rank_trace` 가 단정하지 못한다.**
  생성 모델을 부르지 않으므로 그 뒤는 사람이 `testdata/corpus/` 원문을 봐야 한다.
- **BAAI 가 배포한 `onnx/model.onnx` 와의 대조.** 우리가 내보낸 것이 PyTorch 와 등가임은
  확인했으므로(최대 오차 1.431e-05) 급하지 않아 넘겼다.
