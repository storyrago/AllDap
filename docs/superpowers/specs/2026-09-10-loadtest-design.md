# 부하테스트 설계 (2026-09-10)

## 목적

네 가지를 전부 얻는다.

1. **용량 한계** - t3.micro 가 동시 몇 명까지 버티는가
2. **병목 찾기** - 먼저 막히는 계층이 어디인가
3. **방어선 검증** - rate limit·서킷브레이커·타임아웃이 실제 부하에서 설계대로 도는가
4. **포트폴리오 재료** - 병목을 찾아 하나 고치고 before/after 를 남긴다

3번과 4번의 순서가 중요하다. 먼저 목표치(SLO)를 정하지 않는다.
근거 없는 숫자를 먼저 적으면 가정값이 되고, 이 저장소는 요금을 가정값으로
정했다가 `decisions.md` 에 정정을 남긴 적이 있다.
**꺾이는 지점을 먼저 재고, 그 실측 위에서 목표치를 정한다.**

## 설계를 강제한 제약: LLM 한도

`retriever.search` 의 판정 게이트(`ai-service/app/retriever.py:133-135`)가
하이브리드·리랭커·LLM 보다 **앞에서** 빈 목록을 돌려준다. 그래서 요청 한 건의
비용이 두 갈래로 갈린다.

| 경로 | Cloudflare 뉴런 | 하루 10k 로 가능한 횟수 |
|---|---|---|
| 근거 있는 질문 (생성·리랭커까지 탐) | **24.64** | 약 **406회** |
| 게이트에 걸리는 질문 (임베딩 + pgvector 만) | 0.025 | 약 40만회 |

24.64 의 분해: 생성 23.77 + 리랭커 0.85 + 임베딩 0.025.
AGENTS.md 의 실측(평가 1회 16문항 = 804 뉴런)에서 채점(judge, 410)만 뺀 값이다.

**초당 5건으로 2분만 돌려도 600건이라 하루치를 넘긴다.**
즉 진짜 LLM 을 태우는 지속 부하는 원리적으로 불가능하다.
그래서 **가짜 Cloudflare 서버**를 세우고 URL 을 갈아끼운다.

## 결정 사항

| # | 결정 | 근거 |
|---|---|---|
| 1 | 목적 4개 전부 | 사용자 요청 |
| 2 | **로컬에서 만들고 운영에서 짧게 확인** | staging 이 없다. 프리티어 750시간을 둘로 나눌 수 없다 |
| 3 | **가짜 CF 서버 + 진짜 LLM 소량 기준선** | 지속 부하는 한도상 불가능. 가짜 서버의 지연값은 실측으로 정한다 |
| 4 | **주 부하는 관리자 채팅, rate limit 은 별 시나리오** | 관리자 채팅에는 rate limit 이 없다. 위젯 한도를 올렸다 잊는 위험을 피한다 |
| 5 | **breakpoint 먼저, 개선 before/after 로 닫는다** | SLO 를 먼저 정하면 근거 없는 숫자가 된다 |
| 6 | **관측은 현업 방식(management 포트 분리 + Prometheus + Grafana)** | 껐다 켜는 편법 대신 상시 켜고 포트로 격리한다 |
| 7 | **p50·p95·p99 를 잰다. 평균은 참고만** | 평균은 느린 꼬리를 감춘다. `avg_faithfulness` 로 이미 데인 부류다 |
| 8 | **S1 표본 380건(뉴런 94%)** | p99 를 최악 1건이 아니라 상위 4건이 결정하게 한다 |

### 결정 2 를 덧붙임: 무엇을 어디서 재도 되는가

staging 이 없으므로 staging 의 역할을 쪼개 나눈다.

| 일 | 어디 | 왜 |
|---|---|---|
| 시나리오 개발·디버깅 | 로컬 | 사양이 달라도 상관없다 |
| 병목 찾기 | 로컬 | "어디가 먼저 막히나" 는 구조의 문제라 사양과 무관하다 |
| 장애 주입 | 로컬 | 운영에서 하면 진짜 장애다 |
| **절대 수치(동시 N명, p95)** | **운영** | t3.micro 실측이어야 말이 된다 |
| rate limit 정확성 | 양쪽 | 운영은 한도를 안 올리고 돌리므로 안전하다 |

## 검증 대상 가설 (설정을 읽어서 나온 예측)

부하테스트의 목적은 이걸 맞히는 것이 아니라 **틀리는 걸 보는 것**이다.

| 계층 | 현재 값 | 출처 | 이론적 상한 (지연 1.5초 가정) |
|---|---|---|---|
| Tomcat 스레드 | 200 (미설정 기본값) | `application.yaml` 에 없음 | 약 133 req/s |
| Hikari 커넥션 풀 | 10 (미설정 기본값) | 같음 | 채팅은 짧게만 잡는다 |
| **Python anyio 스레드풀** | **40** (`chat` 이 `def`) | `ai-service/app/main.py:208` | **약 26 req/s** |
| Python DB 풀 | 10 | `ai-service/app/db.py:22` | 짧게만 잡는다 |
| uvicorn 워커 | 1 | `ai-service/Dockerfile:34` | 프로세스 1개 |
| Spring 힙 | 256m + `ExitOnOutOfMemoryError` | `docker-compose.prod.yml` | 마르면 죽고 재시작 |

**1순위 가설: Python 이 먼저 막힌다.**
`main.py:208` 의 `chat` 이 `async def` 가 아니라 `def` 라 FastAPI 가 스레드풀에서
돌린다. 일부러 그렇게 뒀다(주석: 블로킹 호출이라 이벤트 루프를 막는다).
그 대가가 동시 처리 상한 40 이고, Spring 의 200 스레드보다 5배 먼저 찬다.

**2순위 가설: 그보다 먼저 메모리가 터진다.**
`ExitOnOutOfMemoryError` 가 켜져 있어 Spring 이 죽고 재시작한다.
유휴에 이미 스왑 506Mi 인 상태라 이쪽이 먼저일 수 있다.
그러면 k6 에서 보이는 증상은 "느려진다" 가 아니라
**"연결이 끊기고 30초쯤 뒤 돌아온다"** 이다.

두 가설의 순서가 뒤집히는지가 이 테스트의 핵심 관전 지점이다.

## PR 1: 관측 구축

부하테스트보다 **먼저** 한다. 관측이 없으면 k6 의 응답시간만 보고
"아마 풀이 말랐겠지" 라고 추측하게 된다. 리랭커 비용을 추정하고 켰다가
실측에서 빗나간 것과 같은 자리다.

### Spring

`micrometer-registry-prometheus` 의존성 1개 추가
(`spring-boot-starter-actuator` 는 이미 있다).

```yaml
management:
  server:
    port: 8081                        # 서비스(8080)와 분리
  endpoints:
    web:
      exposure:
        include: health,metrics,prometheus
```

**운영에서도 이 설정 그대로 켠다.** 안전한 이유는 `docker-compose.prod.yml` 이
8081 을 `ports:` 에 안 쓰기 때문이다. Caddy 는 `api:8080` 만 안다.
이건 이 저장소가 이미 쓰는 논리다. `ai-service` 에 `ports:` 를 안 쓰면서 적어둔 문장:

> "방화벽으로 막는다" 가 아니라 애초에 호스트에 뜨지 않게 하는 것이 훨씬 안전하다.
> 규칙은 잊거나 실수로 지울 수 있지만, 안 열린 포트는 실수할 여지가 없다.

Spring Security 규칙 한 줄(`permitAll` 오타)에 기대는 것보다 이쪽이 강하다.

### 같이 고쳐야 하는 것 (안 고치면 배포가 깨진다)

- `docker-compose.prod.yml` 의 헬스체크가 `localhost:8080/actuator/health` 를 부른다.
  **8081 로 옮긴다.** 안 고치면 healthcheck 가 영원히 실패하고
  `ai-service` 가 `depends_on: service_healthy` 에 걸려 영영 안 뜬다.
- `api/Dockerfile` 의 `EXPOSE 8080` 에 8081 추가 (문서 목적).

### 확인이 필요한 것 (문서를 믿지 말고 테스트로)

management 포트를 분리하면 Spring Boot 가 **별도 자식 컨텍스트**를 만드는데,
이때 `SecurityConfig` 의 필터 체인이 8081 에도 적용되는지가 버전마다 다르다.
**Boot 4 에서 어떻게 되는지 통합 테스트로 확인한다.**
적용 안 되면 8081 은 인증 없이 열린다. 포트를 안 여니 실질 위험은 없지만,
"그렇게 되어 있다는 걸 아는 것" 과 "그럴 것이라 믿는 것" 은 다르다.

### 로컬 관측 스택 (`docker-compose.yml`, 운영에는 없음)

```
prometheus  :9090   15초마다 Spring :8081/actuator/prometheus 를 긁는다
grafana     :3001   대시보드 JSON 을 저장소에 커밋해 재현 가능하게 둔다
```

t3.micro 에는 안 올린다. 둘이 합쳐 200~300MB 인데 유휴에 이미 스왑을 쓴다.
얹으면 **모니터링이 장애 원인**이 된다.
나중에 서버를 키우거나 옮기면 Prometheus 가 그 8081 을 가리키게만 하면 된다.

**Grafana 패널 6개**

| 패널 | 지표 |
|---|---|
| 처리량·지연 | `http.server.requests` (2xx 만) |
| 커넥션 풀 | `hikaricp.connections.active`, `.pending` |
| Tomcat 스레드 | `tomcat.threads.busy` |
| 힙 | `jvm.memory.used` / `.max` |
| GC | `jvm.gc.pause` |
| 가짜 CF 호출 수 | 가짜 서버가 내주는 카운터 |

`hikaricp.connections.pending` 이 0 보다 크면 **커넥션 대기 중인 스레드가 있다**는
확정 증거다. 추측이 아니라 숫자다.

## PR 2: 가짜 CF 서버 + S1 기준선

### 코드 변경 (최소)

| 무엇 | 어디 | 크기 |
|---|---|---|
| `cf_base_url` 설정 | `ai-service/app/config.py` + `cf.py:57` | 2줄 |
| 가짜 CF 서버 | `ai-service/loadtest/fake_cf.py` | 표준 라이브러리만, 50줄 내 |

기본값은 진짜 주소로 둔다. 운영에서 이 값이 잘못 들어가면 **시끄럽게 실패한다**
(Cloudflare 에 못 붙는다). 조용히 가짜 답변을 내보내지 않는다.
"생성을 가짜로 돌리는 플래그" 를 넣는 것보다 이쪽이 안전한 이유다.
현업에서 WireMock 으로 하는 것과 같은 방식이다.

### 가짜 서버가 하는 일 3가지

1. 지정한 시간만큼 잔다 (모델별로 다르게)
2. 모델별 고정 응답을 돌려준다
   (임베딩은 1024차 벡터, 생성은 짧은 문장, 리랭커는 점수 배열)
3. **호출 횟수를 센다.** 0 이면 그 경로를 안 탄 것이므로 측정이 무효다

### 함정: 임베딩 벡터를 아무거나 주면 안 된다

가짜 CF 가 임베딩 요청에 무작위 벡터를 돌려주면, 그 벡터와 DB 청크의 거리가
무작위라 `answerable_max_distance = 0.44` 게이트에 걸려 **LLM 을 아예 안 부른다.**
그러면 S2 가 재려던 생성 경로를 한 번도 안 타고 "빠르다" 는 거짓 결과가 나온다.

**해결: 가짜 서버가 기동할 때 DB 에서 실제 청크 벡터 하나를 읽어,
임베딩 요청에 그걸 그대로 돌려준다.** 거리가 0 이 되어 게이트를 항상 통과한다.
반대로 게이트 경로를 재고 싶으면 직교하는 벡터를 돌려주면 항상 차단된다.
**모드 하나로 두 경로를 다 잰다.**

### S1 지연 기준선 (진짜 LLM)

가짜 서버에 넣을 지연값을 **추측하지 않고 실측한다.**

| 항목 | 값 |
|---|---|
| 대상 | 관리자 채팅 `POST /api/bots/{botId}/chat` |
| 동시 사용자 | 1~2 |
| **표본** | **380건** |
| 예산 | 9,363 뉴런 (하루 한도의 **94%**) |
| 얻는 것 | 모델별 p50 / p95 / p99 |

**왜 380건인가.** 상한은 `10,000 / 24.64 = 406건`. 약 640 뉴런(채팅 26건)을 남긴다.

- 한도를 완전히 태우면 **언제 풀리는지 모른다.** AGENTS.md 실측: 대시보드 카운터가
  `0/10k` 로 리셋돼도 차단은 안 풀렸고 실제로는 소진 시각으로부터 **약 24~33시간 뒤**에
  풀렸다. 문서의 `00:00 UTC` 는 안 맞는다.
- 중간에 스크립트 버그를 발견하면 남은 26건으로 최소한 확인은 할 수 있다.

**p99 의 한계를 리포트에 적는다.** 380건이면 p99 는 상위 약 4건이 결정한다.
100건이면 최악 1건이 곧 p99 라 우연이 지표가 된다. 1,000건 이상이어야 튼튼한데
그건 이틀 반 치 한도라 못 한다. **p50 과 p95 는 380건이면 충분하고,
S1 이 실제로 하는 일(가짜 서버 지연값 확보)에 쓰이는 건 p50 이다.**

**S1 을 돌릴 때 지킬 것 2개**

1. **다른 측정이 없는 날에 돌린다.** 하루 예산의 94% 를 쓴다. 평가 실행이나
   재임베딩을 겹치면 도중에 429 가 나고, **부분 측정이 정상 측정처럼 남는다.**
   이 저장소가 이미 겪었다(16문항이 전부 429 로 죽었는데 실행이 `completed` 로 남았다).
   -> **스크립트에 중단 조건을 넣는다.** 429 나 503 이 나오면 즉시 멈추고
   "N건에서 중단됨" 으로 표시한다. 끝까지 돈 것처럼 보이는 부분 측정을 만들지 않는다.
2. **순서상 늦게 돌린다.** 코퍼스 재적재가 필요하면 그 임베딩(약 8 뉴런)을 먼저 쓰고,
   스크립트가 다 검증된 뒤에 S1 을 돌린다. 가짜 CF 로 도는 S2·S3·S4 는 한도와
   무관하므로 **S1 에 한도가 걸려도 나머지 작업은 안 막힌다.**

## PR 3: S2 breakpoint (주 시나리오)

| 항목 | 값 |
|---|---|
| 대상 | 관리자 채팅 (rate limit 없음. JWT 는 1회 로그인해 재사용) |
| LLM | 가짜 CF (S1 의 p50 을 지연값으로) |
| 부하 | 동시 사용자 1 -> 5 -> 10 -> 20 -> 40 -> 80, 단계당 2분 유지 |
| 표본 | 단계당 수천 건. p99 가 튼튼하다 |

**보는 것: 어디서 선형성이 깨지는가, 그때 무엇이 포화됐는가.**
Grafana 에서 부하 곡선과 내부 지표를 같은 시간축에 겹쳐 본다.
"동시 30 을 넘긴 순간 `hikaricp.pending` 이 치솟았다" 를 한 화면에서 본다.

위의 가설 두 개(Python 스레드풀 40 vs 힙 256m)가 여기서 판정된다.

## PR 4: S3 rate limit + S4 장애 주입

### S3: rate limit 정확성

| 항목 | 값 |
|---|---|
| 대상 | 위젯 채팅 `POST /api/w/{publicKey}/chat` |
| publicKey | **형식만 맞는 가짜 키** (`pk_` + 22자) |
| 부하 | 같은 1분 안에 **동시 100건** |
| 기대 | 정확히 **20건 통과(404), 80건 429** |

**가짜 키를 쓰는 이유.** `WidgetController` 의 순서가
`형식 검사 -> rate limit -> findByPublicKey` 라, 존재하지 않는 키면 카운터는
그대로 세면서 404 로 끝난다. **LLM 호출 0건, 대화 로그 0건.**
`docs/DEPLOY.md` §9 가 쓰는 방식과 같다.

**이게 새로 재는 것.** `DEPLOY.md` §9 의 점검은 `curl` 25번을 **순차로** 돌린다.
그래서 **동시 요청에서 카운터가 새는지는 아직 아무도 안 봤다.**
`computeIfAbsent` + `incrementAndGet` 이 안전하다는 건 코드를 읽으면 맞는데,
**읽어서 맞는 것과 재서 맞는 것은 다르다.**

⚠️ `RateLimiter` 는 고정 윈도우(`now / 60000`)라 100건이 분 경계를 넘으면
카운터가 둘로 갈린다. **분 경계를 맞춰 쏜다.**

**운영에서도 돌린다.** 한도를 올리지 않으므로 위험은 429 로그가 쌓이는 것뿐이다.

### S4: 장애 주입 (로컬 전용)

가짜 CF 를 고장 모드로 돌린다.

| 주입 | 기대 동작 | 확인 대상 |
|---|---|---|
| 500 을 5번 | 서킷이 **열린다**. 30초 뒤 닫힌다 | `circuit-failure-threshold: 5`, `circuit-open-duration: 30s` |
| 130초 잠 | `read-timeout: 120s` 가 돌아 504 | `application.yaml` |
| 서버를 죽임 | 연결 실패 재시도 **2회**, 그 뒤 503 | `retry-max-attempts: 2` |

재시도가 **연결 실패에만** 걸리는지 함께 본다. 5xx 에 재시도가 돌면 문서 행이
중복되거나 LLM 이 두 번 과금된다(AiServiceClient 주석의 근거).

## 측정을 무효로 만들지 않기 위한 장치

이 저장소가 반복해 걸린 부류라 시나리오마다 자기 검증을 넣는다.
(생존 편향 지표, 안 도는 `redirect.check.ts`, 아무것도 못 잡던 rate limit 점검)

| 장치 | 막는 것 |
|---|---|
| **상태코드별 따로 집계.** 처리량은 2xx 만 센다 | 초당 500건이 전부 429 인데 "빠르다" 고 읽는 것 |
| **`isFallback` 을 세서 경로 확인.** S2 에서 0 이 아니면 그 실행은 무효 | 게이트에 걸려 LLM 을 안 탄 채 "빠르다" 는 거짓 결과 |
| **가짜 CF 호출 카운터를 실행 전후로 비교** | 요청 수와 안 맞으면 그 경로를 안 탄 것 |
| **시작 조건을 파일로 남긴다** | "그때 뭘로 쟀지" 를 못 답해 숫자가 쓸모없어지는 것 |
| **평균은 참고로만. 판정은 p95·p99** | 평균이 느린 꼬리를 감추는 것 |

**시작 조건 파일에 남길 것:** 커밋 SHA, 설정값(`reranker_enabled`,
`hybrid_enabled`, `answerable_max_distance`, `max_distance`), 코퍼스 크기,
가짜 서버 지연 설정값, 실행 시각.

**k6 옵션** (기본 요약은 p90·p95 만 보여주고 p99 는 안 나온다)

```js
export const options = {
  summaryTrendStats: ['min', 'med', 'p(95)', 'p(99)', 'max', 'avg'],
};
```
