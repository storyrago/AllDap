# 부하테스트 PR 4a 설계: S3 rate limit 정확성 (2026-09-11)

시리즈 전체 설계는 `2026-09-10-loadtest-design.md`, 직전 슬라이스는
`2026-09-10-loadtest-pr3-s2-breakpoint-design.md` 에 있다.
조사 결과는 `docs/HANDOFF-2026-09-11.md` §4 다. 그 문서가 남긴 "제일 먼저 정할 것은
무엇을 범위 밖으로 둘 것인가" 에 대한 답이 §7 이다.

**마스터 설계서와 다르게 정한 것이 둘 있다**(§0, §7). 근거는 각 자리에 적었다.

## 목적

**동시 요청에서 요청 제한기의 카운터가 새는가.** 이것 하나만 본다.

`computeIfAbsent(...).incrementAndGet()` 이 안전하다는 것은 코드를 읽으면 맞다.
**읽어서 맞는 것과 재서 맞는 것은 다르다.** `docs/DEPLOY.md` §9 의 기존 점검은
`curl` 25번을 순차로 돌리므로, **동시 요청은 아직 아무도 안 봤다.**

개선은 하지 않는다(PR 5). 발견한 결함도 고치지 않는다(§7).

## 0. 마스터 설계서와 다르게 정한 것

### ① PR 4 를 4a(S3) 와 4b(S4) 로 쪼갠다

마스터 설계서 §순서는 `PR 4  S3 + S4` 한 칸이다. 쪼개는 근거는 셋이다.

- **건드리는 코드가 안 겹친다.** S3 는 k6 스크립트와 드라이버만 새로 짜면 되고
  **Spring·Python 코드를 한 줄도 안 고친다.** S4 는 가짜 CF 에 장애 주입 제어면을 붙인다.
- **실행 단위가 다르다.** S4 는 장애마다 별도 실행이고 사이에 서킷이 닫히기를 기다리는
  정지 구간이 필요하다. 한 결과 문서에 두 성격을 합치면 "이 표의 어느 줄이 어느 실행인가" 가 흐려진다.
- **리뷰 단위.** AGENTS.md 의 "PR 하나는 리뷰 가능한 크기로" 다. 브랜치를 한 번 더 따는
  대가는 몇 분이고, 안 딴 대가는 면접에서 PR 하나를 열어놓고 두 가지를 설명해야 하는 것이다.

### ② 운영에서는 안 돌린다

마스터 설계서 §결정 2 덧붙임 표는 `rate limit 정확성 | 양쪽` 이라고 적어뒀다. **좁힌다.**

운영에서만 새로 알 수 있는 것은 **IP 축 버킷 분리**와 **`Forwarded` 헤더 처리** 둘인데,
그 둘은 부하가 아니라 `docs/DEPLOY.md` §9 의 종단 확인이 할 일이고 **2026-09-09 에 실제로
그렇게 닫았다**(위조 `Forwarded` 25개로 1~20번 404 · 21~25번 429 를 본 기록).
부하로 바꿔 다시 한다고 나오는 새 사실이 없다. 반면 t3.micro 에 동시 100건을 쏘는 비용은 실재한다.

→ **로컬 전용.** 운영 실행이 필요해지면 별 슬라이스로 둔다.

## 1. 구성

```
 [k6] 맥 호스트
   │  POST /api/w/{publicKey}/chat        ← 위젯 채팅. 여기에만 rate limit 이 있다
   ↓                                         JWT 불필요(인증 없이 열린 유일한 문)
 Spring :8080  (gradle bootRun)
   │   └ :8081/actuator/prometheus         (PR 1)
   └─→ Postgres (docker, alldap-db)        SELECT 1회(결과 없음)
 Prometheus :9090 → Grafana :3001          [타깃: 8081 하나면 충분하다]
```

🔴 **Python(:8001)도 가짜 CF(:9001)도 안 띄운다.** S2·S1 과 다른 점이고, 이 시나리오가 싼 이유다.

근거는 호출 순서다. `WidgetController.chat` 은
`requirePlausiblePublicKey` → `rateLimiter.check` → `chatService.chatAsWidget` 이고,
`chatAsWidget` 의 첫 줄이 `botService.findByPublicKey(publicKey)` 다.
**형식만 맞고 존재하지 않는 키**를 쓰면 카운터는 정상으로 세면서 거기서 `BOT_NOT_FOUND`(404)로 끝난다.

⚠️ **핸드오프 §4 의 "LLM·DB 를 안 건드린다" 는 절반만 맞다.** LLM·대화 로그·Python 왕복은
확실히 0건이지만 **`findByPublicKey` 의 인덱스 단건 SELECT 는 돈다.** 통과분 20건에 대해서만
일어나고 결과가 비어 있어 부하로서는 무시할 수 있지만, "DB 를 안 탄다" 고 결과 문서에 적으면
그것도 뭉개기다. **"통과분에 한해 인덱스 SELECT 1회, LLM 0건"** 으로 적는다.

## 2. 무엇을 재고 무엇을 못 재나

### 잴 수 있는 것 (이 PR 의 산출물)

| # | 질문 | 판정 신호 |
|---|---|---|
| A | **동시 100건에서 정확히 20건만 통과하는가** | 404 가 정확히 20, 429 가 정확히 80 |
| B | 고정 윈도우의 분 경계 버스트가 실제로 **2N** 인가 | 약 4초 안에 404 가 40건 |
| C | **publicKey 축으로 버킷이 갈리는가** | 키 둘에 각각 404 20 · 429 80 |
| D | 거절 경로의 **비용** | 429 의 지연 분포. Python 을 안 타는 순수 Spring 경로다 |

A 가 이 PR 의 본체다. B·C·D 는 A 와 같은 스크립트에 환경변수만 바꿔 얻는다.

### 로컬로 원리적으로 못 재는 것 (결과 문서의 "못 잰 것" 에 그대로 싣는다)

1. **IP 축 버킷 분리.** k6 가 같은 호스트라 모든 VU 가 `127.0.0.1` 이다. 분산 공격 내성은 답할 수 없다.
2. **`Forwarded`·`X-Forwarded-For` 처리.** `forward-headers-strategy: framework` 가
   `application-prod.yaml` 에만 있어 로컬 Spring 은 그 헤더를 아예 파싱하지 않는다.
   억지로 prod 프로파일을 켜면 **Caddy 가 없는 구성**을 재는 것이 된다. `DEPLOY.md` §9 의 몫이다.
3. **다중 인스턴스 한도 배가.** `docker-compose.prod.yml` 에 replicas 가 없어 운영도 1대다.
   로컬에 2개를 띄우는 것은 **있지도 않은 구성**을 재는 것이다.
4. **`MAX_KEYS` 초과 시 전체 clear.** §7 참고.

## 3. 부하 프로파일

**한 실행이 네 판이다.** 각 판 사이에 최소 70초를 쉰다. 고정 윈도우라
`windowIndex = now / 60000` 이 넘어가야 앞 판의 카운터가 다음 판에 안 섞인다.

| 판 | VU | 요청 | 한도 설정 | 기대 |
|---|---|---|---|---|
| **N (음성 대조)** | 100 | VU 당 1건 | `WIDGET_CHAT_PER_MINUTE=100000` | **429 가 0건.** 404 100건 |
| **A (본 판정)** | 100 | VU 당 1건 | `20` (기본값) | 404 20 · 429 80 |
| **B (분 경계)** | 20 | 경계 앞뒤로 20건씩 | `20` | 약 4초 안에 404 40건 |
| **C (키 축 분리)** | 100 | 키 2개에 50 VU 씩 | `20` | 키마다 404 20 · 429 80 |

- **N 을 A 보다 먼저 돌린다.** 순서에 이유가 있다. §4 참고.
- **think time 없음.** 한도가 분당 20건이라 "지속 부하" 개념 자체가 성립하지 않는다.
  S2 처럼 계단을 쌓지 않고 **한 번에 쏘고 끝낸다.**
- 🔴 **한도를 바꾸는 판(N)은 Spring 을 다시 띄워야 한다.** `WIDGET_CHAT_PER_MINUTE` 는
  기동 시 바인딩되는 `@ConfigurationProperties` 라 실행 중에 못 바꾼다. 실행 절차에 넣는다.
  **그리고 그 값을 시작 조건 파일에 반드시 적는다** (핸드오프 §4 의 경고 그대로).

### 🔴 처리량 곡선을 그리지 않는다

S1·S2 는 처리량이 산출물이었지만 **여기서는 아니다.** 한도가 0.33 req/s 라 S2 프로파일을
그대로 옮기면 사실상 거절 경로만 재게 되고, 429 와 200 을 한 곡선에 더하면
마스터 설계서 §측정을 무효로 만들지 않기 위한 장치의 첫 줄
("초당 500건이 전부 429 인데 빠르다고 읽는 것")을 그대로 밟는다.

**이 PR 의 산출물은 곡선이 아니라 개수다.** 지연은 D 에서 거절 경로에 한해 따로 싣는다.

## 4. 2026-09-09 사고의 재발 방지를 내장한다

그때 점검 명령은 **"돌아가는데 아무것도 검증하지 않는"** 상태였다. 이유 셋이 그대로 이 시나리오에 온다.

### ① 양성 대조: "429 가 나왔다" 로는 아무것도 증명되지 않는다

그때의 실패가 정확히 이것이다. 본문에 `sessionId` 가 없어 `@Valid` 에서 400 이 났고,
**`rateLimiter.check` 를 지나가지도 못한 채** 25건 전부 400 이 됐다.
그 모습이 문서의 실패 판정 기준과 겹쳐 **언제 돌려도 실패를 보고했다.**

→ **판정은 429 개수가 아니라 `{404: 20, 429: 80}` 라는 히스토그램 전체 일치로 한다.**
400 이 한 건이라도 있으면 **그 실행은 무효**다. 요청이 제한기까지 갔다는 증거가 404 이기 때문이다.

`ChatRequest` 는 `message`(@NotBlank, 2000자) 와 `sessionId`(@NotBlank, 64자) 둘 다 필수다.
`sessionId` 는 `s3-<runId>-<vu>` 로 만든다.

### ② 음성 대조: 429 가 제한기에서 나왔다는 증거

`WIDGET_CHAT_PER_MINUTE=100000` 으로 같은 스크립트를 돌려 **429 가 0건**임을 확인한다.
그래야 A 의 429 80건이 제한기에서 나온 것이지 다른 무엇(프록시·톰캣 큐)이 아님이 증명된다.

🔴 **N 을 A 보다 먼저 돌리는 이유**: N 이 실패하면 A 를 돌릴 이유가 없다.
순서를 뒤집으면 A 에서 예쁜 숫자를 본 뒤에 N 을 돌리게 되고, 그때는 이미 결론을 믿고 있다.

### ③ 분 경계 정렬: 버스트가 같은 1분 안에 끝나야 한다

A·C 의 100건이 경계를 넘으면 카운터가 둘로 갈려 **정상인데도 404 가 40건**으로 나온다.
정확히 B 가 일부러 재는 현상이라, 정렬하지 않으면 A 와 B 를 구별할 수 없다.

→ 드라이버가 **현재 분에 남은 시간이 20초 미만이면 다음 경계까지 기다린다.**
시작 시각을 밀리초까지 시작 조건 파일에 적는다.

### ④ 지표 교차 검증

핸드오프 §4 가 적어둔 식을 그대로 쓴다(#114 의 p14).

```
sum(rate(http_server_requests_seconds_count{status="429"}[1m]))
  - sum(rate(alldap_ratelimit_rejected_total[1m]))
```

0 이 아니면 **제한기를 거치지 않은 429 가 있다**는 뜻이다.

⚠️ 이 값은 **둘 다 0건일 때도 0** 이라 혼자서는 못 가른다. 판정은 **부호가 지속되는가**로 한다.
그리고 핸드오프 §6-ⓓ 가 적어둔 우회로를 함께 쓴다.
`alldap_ratelimit_keys` 게이지는 항상 나오므로, **게이지가 있는데 `rejected` 시계열이 없으면
"계측이 살아 있고 거절 0"** 이다. N 판의 판정이 정확히 이 모양이다.

## 5. 코드 변경

Spring·Python 은 **한 줄도 안 고친다.** 새로 만드는 것은 둘뿐이다.

```
ai-service/loadtest/s3_ratelimit.js    신규  k6 시나리오
ai-service/loadtest/s3_context.py      신규  경계 정렬 · 시작 조건 · 판정
ai-service/loadtest/s3_check.py        신규  위 판정 로직의 자체 점검
.github/workflows/*                    수정  s3_check 를 CI 목록에 한 줄 추가
```

### ① `s3_ratelimit.js`

`s2_breakpoint.js` 의 구조를 그대로 따른다. 달라지는 곳만 적는다.

- **로그인이 없다.** 위젯 경로는 JWT 를 안 쓴다. `setup()` 이 통째로 사라지고,
  S2 결과 문서가 적어둔 비밀번호 소동(`AllDap-pr2/.s1-old-hash.txt`)이 안 걸린다.
- `WATCHED_STATUS = [404, 429, 400, 200, 0, 500, 503]`.
  **400 과 200 을 감시 목록에 넣는 이유**: 400 은 §4-① 의 사고 재현이고,
  200 은 **실수로 진짜 publicKey 를 쓴 것**이다. 둘 다 "안 나와야 정상" 이라 세어야 안다.
- `PUBLIC_KEY` 는 `pk_` + 22자 형식을 맞춘 **가짜 키**다. 기본값을 코드에 박되
  `__ENV.PUBLIC_KEY` 로 덮을 수 있게 한다. C 판은 `PUBLIC_KEY_2` 를 함께 쓴다.
  ⚠️ **진짜 키로 덮으면 LLM 이 20번 돈다.** 드라이버가 시작 전에 그 키가 실제로 404 를
  내는지 한 번 확인하고, 404 가 아니면 중단한다.
- `scenarios` 는 판마다 하나씩. `ROUND` 환경변수로 고른다(`N`·`A`·`B`·`C`).
- B 판만 `startTime` 을 쓴다. 경계 정렬 자체는 드라이버가 하고, k6 안에서는
  0초에 20건 · 4초에 20건으로 쏜다.

### ② `s3_context.py`

`s2_context.py` 의 `before`/`after` 두 단계 구조를 따른다. 다른 점만 적는다.

- 🔴 **한도 값은 도는 서버에게 물어볼 수 없다. 알고 드라이버 값으로 남긴다.**
  #113 이 "import 상수가 아니라 도는 서버에게" 로 고친 교훈을 여기도 적용하려 했는데,
  **길이 없다.** `application.yaml` 의 노출 목록은 `health,metrics,prometheus` 셋뿐이라
  `/actuator/configprops` 가 아예 없고, 열더라도 `SecurityConfig` 가 `/actuator/prometheus`
  하나만 `permitAll` 이라 401 이다.
  **그렇다고 열지 않는다.** `configprops` 는 설정 전체를 덤프하므로 한도 숫자 하나를 읽으려고
  DB 접속 문자열·JWT 시크릿이 같은 응답에 실리는 경로를 만드는 셈이다.
  → **핸드오프 §6-ⓒ 의 "아직 드라이버 값인 것" 목록에 `widget_chat_per_minute` 를 한 줄 추가한다.**
  시작 조건 파일에 `"source": "driver"` 로 명시해 적는다. **모르는 것을 아는 척 적지 않는다.**
- **대신 독립적인 관측 하나를 함께 남긴다.** `/actuator/prometheus` 는 열려 있으므로
  `alldap_ratelimit_recorded_total{bucket="widget-chat"}` 의 실행 전후 증가분을 적는다.
  이 값은 한도와 무관하게 **제한기가 실제로 몇 건을 셌는가**를 말하므로,
  k6 가 보낸 요청 수와 어긋나면 그 실행은 무효다. 한도 값을 못 물어보는 구멍을
  메우지는 못하지만 **다른 축에서 같은 실행을 검증한다.**
- 시작 조건 파일에 적을 것: 커밋 SHA · `WIDGET_CHAT_PER_MINUTE`(출처: 드라이버) ·
  publicKey(가짜임을 확인한 결과 포함) · **시작 시각(밀리초)** · 판 이름 · 분 경계까지 남은 시간.
- `after` 는 k6 요약 JSON 을 읽어 `judge_round()` 로 판정하고 `verdict` 파일을 쓴다.

### ③ `judge_round()` 와 `next_window_start()` 를 순수 함수로 분리한다

이 PR 에서 **틀리면 가장 비싼 코드**가 판정 로직이다. 여기가 틀리면 측정이 통째로 거짓이 된다.
그래서 서버도 시계도 안 타는 순수 함수 둘로 뽑는다.

```python
def judge_round(round_name: str, counts: dict[str, int], limit: int) -> tuple[bool, str]:
    """상태코드 히스토그램 하나로 그 판의 성패를 가른다."""

def next_window_start(now_ms: int, min_headroom_ms: int) -> int:
    """지금 분에 여유가 부족하면 다음 분 경계의 시각을 돌려준다."""
```

`judge_round` 가 지켜야 하는 규칙:

- **0 건과 계측 실패를 뭉개지 않는다.** 감시 목록의 코드가 요약에 아예 없는 것과
  `count: 0` 은 다른 사실이다. 전자는 "그 코드가 안 났다" 가 아니라 "k6 가 안 셌다" 일 수 있다.
- **400 이 1건이라도 있으면 무효**(§4-①). `False` 와 함께 사고 이름을 문구로 돌려준다.
- **200 이 1건이라도 있으면 무효.** 진짜 봇을 때린 것이다.
- 합계가 기대 요청 수와 다르면 무효. 연결 실패(0)가 섞였다는 뜻이다.

### ④ `s3_check.py` 와 CI

**돌려서 통과한 것은 증거가 아니다** (핸드오프 §7 의 결론). 자체 점검은 **일부러 깨뜨려**
`judge_round` 가 실제로 실패를 보고하는지 본다. 최소 케이스:

| 입력 | 기대 |
|---|---|
| `{404: 20, 429: 80}`, limit 20 | 통과 |
| `{404: 21, 429: 79}` | **실패** (카운터가 샜다) |
| `{404: 20, 429: 79}` | **실패** (합계 부족) |
| `{400: 100}` | **실패** (제한기에 도달 못 함. 2026-09-09 사고) |
| `{404: 20, 429: 79, 200: 1}` | **실패** (진짜 봇을 때렸다) |
| N 판에 `{404: 100}` | 통과 |
| N 판에 `{404: 99, 429: 1}` | **실패** (음성 대조가 깨졌다) |
| `next_window_start` 경계 직전·직후 | 각각 다음 경계 · 현재 유지 |

DB 도 외부 API 도 안 타므로 **#110 의 CI 명시 목록에 넣는다.**
⚠️ 그 목록은 glob 이 아니라 손으로 적는 목록이고, **한 줄을 지우면 그 점검이 조용히 사라진다**는
구멍을 #110 이 이미 기록해뒀다. 줄을 추가하는 커밋에 그 사실을 다시 적는다.

## 6. 측정을 무효로 만들지 않기 위한 장치

| 장치 | 어디서 | 무효/유효를 어떻게 가르나 |
|---|---|---|
| 상태코드 히스토그램 **전체 일치** | `judge_round` | 429 개수만 보지 않는다. 400·200 이 섞이면 그 판은 무효 |
| **음성 대조 판(N)** | 한도 100000 으로 선행 실행 | 429 가 1건이라도 나오면 그날 실행 전체를 중단 |
| **가짜 키 확인** | `s3_context before` | 그 키로 1건 쳐서 404 가 아니면 중단. LLM 20회를 막는다 |
| **분 경계 정렬** | `next_window_start` | 남은 시간 20초 미만이면 대기. 시작 시각을 밀리초로 기록 |
| 지표 교차 검증 | Prometheus | `429 - ratelimit_rejected` 의 **부호가 지속되는가** |
| 판 사이 70초 대기 | 드라이버 | 앞 판의 카운터가 다음 판에 안 섞이게 |
| 시작 조건 파일 | `s3_context before` | 커밋 SHA · 한도 실측값 · 키 · 시각 |

### ① `MAX_KEYS` 초과 시 전체 clear

핸드오프 §5-3 의 결함이다. `counters.clear()` 가 버킷을 안 가려서 위젯 키 10만 개를 흘리면
**15분짜리 `login-failure` 차단이 풀린다.**

**안 넣는다.** 이미 단위 테스트 `clearIsObservableAndWipesOtherBuckets` 로 재현돼 있고,
부하로 다시 재서 새로 알게 되는 것은 "동시 요청에서도 그렇다" 하나뿐이다.
반면 대가는 크다. 서로 다른 키 100,002개는 분당 한도와 무관하게 **요청 10만 건**이라
실행 시간과 메모리가 다른 세 판을 전부 압도한다.

**고치는 것도 이 PR 이 아니다.** 고치면 S4 의 before 가 사라진다(핸드오프 §5 의 원칙).
고칠 때의 방향은 `RateLimiter` 주석이 이미 적어뒀다(버킷별로 맵을 나누거나 오래된 윈도우 키만 지우거나).

- **운영 실행** (§0-②)

  "이 트래픽이 차단 기간을 늘리고 있는가" 인데, **위젯 채팅은 `check` 뿐이라 전부 `check` 로

- **못 잰 것** 네 가지(§2)를 이유와 함께
- 🔴 **DB SELECT 가 통과분 20건에 한해 돈다는 사실**(§1). "DB 를 안 탄다" 로 적지 않는다
