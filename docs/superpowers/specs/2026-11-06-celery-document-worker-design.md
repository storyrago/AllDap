# 설계: 문서 처리를 Celery 워커로 분리한다 (2026-11-06)

이 문서는 ai-service 의 문서 처리(`_process_document`)를 FastAPI `BackgroundTasks` 에서
**Celery 워커 + Redis 브로커**로 옮기는 첫 조각의 설계다.

- **목적은 학습과 포트폴리오다.** 큐·브로커·워커를 직접 다뤄 보고, 면접에서 "왜 이렇게 설계했나"를 답할 수 있게 한다.
- **로컬 전용이다.** 운영(EC2)에는 올리지 않는다. 운영 메모리·비용은 이 설계의 판단 기준이 아니다.
- **이 조각은 "처리를 별도 워커 프로세스로 떼어 내는 것"까지다. "작업 유실 해결"이 아니다.**
  워커가 처리 중에 죽으면 문서가 `processing` 에 멈추는 한계는 그대로 남는다(7절).

저장 위치는 세 관점(학습자, 기술, 면접관)의 분석 팀이 3라운드 교차 검증을 거쳐 합의했다(2절).

---

## 0. 용어

| 용어 | 뜻 |
|---|---|
| 브로커 | 작업 메시지를 보관했다가 워커에게 넘겨주는 서버. 이 설계에서는 Redis |
| 워커 | 브로커에서 메시지를 꺼내 작업을 실행하는 별도 프로세스. `celery -A app.worker worker` 로 띄운다 |
| 작업 | `@celery_app.task` 로 등록한 함수. 이 설계에서는 `process_document` 하나 |
| 메시지 | `delay()` 가 브로커에 넣는 "이 작업을 이 인자로 실행하라"는 쪽지. 이 설계에서는 `doc_id`, `bot_id` 만 담는다 |
| claim check | 큰 데이터는 저장소에 두고 메시지에는 그것을 찾을 열쇠(ID)만 싣는 방식 |
| 상태 가드 | 워커가 처리를 시작하기 전에 `pending → processing` 을 한 SQL 문장으로 바꾸고, 바뀐 행이 없으면 끝내는 검사 |
| 원본 | 사용자가 올린 파일의 바이트. `uploads/{bot_id}/{doc_id}` 에 저장한다 |
| 고아 파일 | DB 에 대응하는 `documents` 행이 없는데 디스크에 남은 원본 |

## 1. 지금 구조와 문제

`upload_document`(`ai-service/app/main.py`)는 `documents` 행을 `pending` 으로 만들어 커밋한 뒤
`background.add_task(_process_document, doc_id, bot_id, filename, data)` 로 파일 바이트를 통째로 넘긴다.

`BackgroundTasks` 는 uvicorn 프로세스 안에서 돈다. 그래서 다음이 성립한다.

- 프로세스가 죽으면 처리 중인 작업이 사라지고 문서는 `processing` 에 멈춘다(main.py docstring 이 이미 적은 한계).
- 처리와 API 가 같은 프로세스라서 무거운 처리가 API 와 자원을 나눠 쓴다.
- 동시에 몇 건을 처리할지 조절할 수단이 없다.

이 조각은 둘째와 셋째를 해결하고, 첫째는 다음 조각을 위한 토대만 놓는다.

## 2. 결정: 원본을 로컬 디스크에 두고 메시지에는 ID 만 싣는다

### 2-1. 후보와 판정

| 후보 | 판정 | 이유 |
|---|---|---|
| **A′ 로컬 디스크 + 저장 함수 3개** | **선정** | 큐의 핵심 개념(메시지는 작게, 데이터와 작업의 분리)에 집중할 수 있다. 마이그레이션이 필요 없다. 로컬에서는 API 와 워커가 같은 호스트의 venv 에서 떠서 같은 디스크를 본다 |
| B MinIO(S3 호환) | 다음 조각 | 실무 구조와 같지만 Celery 와 S3 SDK 를 한 PR 에서 함께 배우게 된다. 저장 함수의 두 번째 구현으로 넣으면 "교체점을 미리 나눠 뒀다"가 실제로 증명된다 |
| C 메시지에 바이트 직접 | 탈락 | 로컬 업로드 상한이 20MB 라 base64 로 최대 약 27MB 메시지가 된다. 큰 객체를 작업 인자로 넘기지 말라는 통용 관행과 정면으로 어긋난다 |
| D PostgreSQL `bytea` 자식 테이블 | 탈락(차점) | 행과 파일이 한 트랜잭션에 묶이고 봇 삭제 CASCADE 로 파일도 사라지는 진짜 이점이 있다. 그러나 학습 초점이 "DB 에 파일을 넣어도 되나"로 옮겨 가고 V10 마이그레이션이 따라온다 |

세 팀 최종 점수(20점 만점, 학습·면접·부담·확장 각 5점): 학습자 18, 기술 17, 면접관 18. 전원 조건부 인정.

### 2-2. 근거의 강도

- "작업에는 큰 객체 대신 ID 를 넘기고 작업 안에서 다시 읽는다"는 **통용 관행**으로 말한다. Celery stable 문서 Tasks 가이드의 State 절은 "작업이 어느 프로세스·어느 머신에서 실행될지 알 수 없다"는 취지와 큰 객체를 인자로 넘기지 말라는 취지를 적고 있다(기술 팀 확인). 그 밖의 근거는 2차 자료다.
- SQS 메시지 크기 상한 같은 다른 시스템의 수치는 확인하지 않았으므로 단정하지 않는다.

### 2-3. 이번에 함께 정한 것

| 항목 | 결정 | 이유 |
|---|---|---|
| 처리 후 원본 | **보존**한다. 문서 삭제 때만 지운다 | 파싱부터 다시 하는 정석 재처리 경로가 열린다(지금 `rechunk.py` 는 원본이 없어 청크를 이어 붙여 복원한다). 다음 조각에서 "ack 전에 파일을 지웠다가 재배달" 경쟁이 원천적으로 없다 |
| 재실행 대비 | 이번에는 **상태 가드만** 넣는다. `DELETE FROM chunks` 는 넣지 않는다 | `acks_late` 를 끄면 재배달 경로가 없다. 다음 조각에서 "켜면 청크가 두 벌이 된다"를 먼저 재현한 뒤 고친다 |
| `acks_late`, 자동 재시도 | **끈다** (명시적으로 `False`) | 처리 함수가 아직 두 번 돌면 안전하지 않다. 재시도는 LLM 이중 과금으로 이어진다 |
| 워커 실행 방식 | **호스트 venv** | ai-service 가 이미 venv 로 뜬다. 같은 디스크 전제가 참이 된다 |
| Celery vs RQ | **Celery** | 목적이 경험이라 실무에서 더 자주 마주치는 도구를 고른다. 기존 문서의 "Redis + RQ" 는 "운영할 것을 최소화한다"는 기준으로 고른 것이었다. `docs/decisions.md` 에 남긴다 |

## 3. 구성 요소

```
[uvicorn: API 프로세스]                    [celery: 워커 프로세스]
  upload_document                             process_document 작업
    ├ documents 행 INSERT                       ├ 상태 가드 (pending → processing)
    ├ storage.save()  ──▶ uploads/{bot}/{doc} ◀── storage.read()
    └ process_document.delay(doc_id, bot_id)    ├ 파싱 → 청킹 → 임베딩
            │                                   └ chunks 저장, ready
            ▼                                        ▲
        [Redis :6380] ── 메시지: {doc_id, bot_id} ───┘
```

| 파일 | 할 일 | 새로/수정 |
|---|---|---|
| `docker-compose.yml` | `redis` 서비스 추가. `127.0.0.1:6380` 에만 바인딩(db 와 같은 이유. 6379 는 호스트의 다른 Redis 와 겹쳐 피했다). profiles 없이 기본으로 뜬다 | 수정 |
| `ai-service/requirements.txt` | `celery[redis]` 를 실제 설치되는 버전으로 고정 | 수정 |
| `ai-service/app/config.py` | `upload_dir`(기본값은 루트 `.gitignore` 가 막는 `uploads/` 아래), `broker_url`(기본 `redis://localhost:6380/0`) | 수정 |
| `ai-service/app/storage.py` | `save(bot_id, doc_id, data)`, `read(bot_id, doc_id)`, `delete(bot_id, doc_id)`. 경로 규칙은 이 파일만 안다. 클래스·Protocol 은 MinIO 구현 때 만든다 | 새로 |
| `ai-service/app/worker.py` | Celery 앱과 `process_document` 작업. `_process_document` 본문을 main.py 에서 옮긴다 | 새로 |
| `ai-service/app/main.py` | 업로드 순서 변경(4-1), 삭제 시 파일 정리(4-3), docstring 갱신 | 수정 |

### 3-1. 처리 코드를 worker.py 로 옮기는 이유

워커는 `app.worker` 를 import 해서 뜬다. 처리 코드가 main.py 에 있으면 워커가 main.py 를 import 해야 하고,
그러면 FastAPI 앱 전체(라우트, 미들웨어, 지표)가 워커 안에서 만들어진다. 워커는 문서 처리만 알면 된다.
반대로 main.py 는 `process_document.delay` 를 부르기 위해 worker.py 를 import 한다. 방향은 main → worker 하나다.

### 3-2. 파일명을 메시지에 넣지 않는 이유

`filename` 은 이미 `documents` 행에 있다. 메시지에도 넣으면 같은 사실이 두 곳에 생긴다. 워커가 `doc_id` 로 행을 읽어 꺼낸다.

### 3-3. 경로 규칙

`{upload_dir}/{bot_id}/{doc_id}`. 두 값은 정수 id 다.

- **원본 파일명을 경로에 쓰지 않는다.** 파일명에 `../` 가 있으면 폴더 밖으로 나가는 경로가 된다.
- 봇 단위 폴더로 둔다. 봇이 삭제되면 고아가 폴더 하나로 모인다(다음 조각의 스위퍼가 치우기 쉽다).
- `documents` 에 경로 컬럼을 추가하지 않는다. 경로가 id 에서 결정되므로 마이그레이션이 필요 없다.

## 4. 데이터 흐름

### 4-1. 업로드 (API 프로세스)

```
1. 파일 검사 (용량, 빈 파일, 확장자)                 ← 지금과 같다
2. with cursor(commit=True):
       INSERT documents (status='pending') RETURNING id
       storage.save(bot_id, doc_id, data)
   # 블록을 빠져나가며 커밋. 저장이 예외를 내면 커밋되지 않는다(행도 롤백)
3. process_document.delay(doc_id, bot_id)
4. 202
```

- **메시지는 커밋 뒤에 보낸다.** 커밋 전에 보내면 워커가 아직 보이지 않는 행을 찾다가 "없는 문서"로 끝날 수 있다.
- **파일 저장은 트랜잭션 안에 둔다.** 저장이 실패하면 행이 롤백돼 "행은 있는데 파일이 없는" 상태가 생기지 않는다. 쓰다 만 파일은 블록 밖 `except` 에서 지운다.

### 4-2. 처리 (워커 프로세스)

```
1. UPDATE documents SET status='processing'
   WHERE id=%s AND status='pending' RETURNING id
   → 0행이면 로그만 남기고 끝 (이미 처리됨, 또는 그 사이 삭제됨)
2. documents 에서 filename 을 읽는다
3. storage.read(bot_id, doc_id)
4. 파싱 → 청킹 → 임베딩 → chunks 저장 + status='ready'   ← 지금 _process_document 본문 그대로
5. 원본은 지우지 않는다
```

- 가드는 **한 SQL 문장**이어야 한다. `SELECT` 로 상태를 읽고 `if` 로 판단하면 워커 둘이 동시에 통과할 수 있다. 조건을 쿼리에 못박는 것은 이 저장소의 `findByIdAndUserId` 원칙과 같은 모양이다.
- 4번은 지금 코드를 바꾸지 않는다. 한 번에 바꾸는 범위를 줄여 문제가 생겼을 때 원인을 좁힌다.

### 4-3. 삭제 (API 프로세스)

```
1. DELETE FROM documents WHERE id=%s AND bot_id=%s   → 커밋   ← 지금과 같다
2. 실제로 1행이 지워졌을 때만 storage.delete(bot_id, doc_id)
```

- **DB 먼저, 파일 나중.** 반대 순서면 파일만 지워지고 행이 남는 경우가 생긴다. 이 순서면 최악의 경우가 고아 파일이고, 고아는 스위퍼로 치울 수 있다.
- **1행이 지워졌을 때만 파일을 지운다.** `/internal/*` 에는 인증이 없다. 남의 `bot_id` 로 부르면 DB 삭제는 `WHERE` 에 걸려 0행이 되는데, 파일 삭제가 그와 무관하게 돌면 안 된다. 경로에 `bot_id` 가 들어 있어 이중으로 막힌다.

## 5. 실패 처리

원칙: 어떤 실패든 문서가 영원히 멈춘 상태로 남지 않고, 사용자에게 무엇을 하면 되는지 보인다.

### 5-1. 업로드 중

| 상황 | 문서 | 응답 | 원본 |
|---|---|---|---|
| 용량 초과, 빈 파일, 확장자 | 행 없음 | 413 / 400 | 없음 (지금과 같다) |
| 파일 저장 실패 | 롤백되어 행 없음 | 503 | 쓰다 만 파일을 지운다 |
| Redis 연결 실패 (`delay()` 예외) | `failed`, `error_message` = "작업 대기열에 연결하지 못했습니다. 잠시 후 다시 올려주세요." | 503 | 남긴다(보존 원칙. 다음 조각의 스위퍼가 정리) |

- `delay()` 는 기본적으로 브로커 연결 실패 시 스스로 재시도해 요청이 몇 초 매달릴 수 있다. 재시도 정책을 짧게 설정하고, **실제 소요 시간은 Redis 를 내리고 재서** PR 에 적는다. 기본값의 정확한 초는 이 문서에서 단정하지 않는다.
- Spring `AiServiceClient` 는 **연결 실패에만** 재시도하고 Python 5xx 는 재시도하지 않는다(AGENTS.md). 503 이 문서 행 중복으로 이어지지 않는다. Spring 코드는 이번에 바꾸지 않는다.

### 5-2. 처리 중

| 상황 | 문서 |
|---|---|
| 파싱 실패, 내용 없음, 임베딩 오류 | `failed` + 지금과 같은 한국어 사유 (지금 코드 그대로) |
| 원본 파일 없음 | `failed`, "원본 파일을 찾지 못했습니다. 다시 올려주세요." |
| 가드에서 0행 | 건드리지 않는다. 로그만 |

### 5-3. 실패는 아니지만 알아야 하는 상태

| 상황 | 보이는 것 | 이번 조각에서 |
|---|---|---|
| 워커를 띄우지 않음 | `pending` 에 머문다. 워커를 켜면 처리된다 | 의도한 동작. 메시지가 Redis 에 남아 있다. 로컬 실행 순서 문서에 워커를 추가한다 |
| 워커가 처리 중에 죽음 | `processing` 에 멈춘다 | 알고 남기는 한계(7절). 실측 결과를 PR 에 붙인다 |

### 5-4. 삭제와 기동

| 상황 | 처리 |
|---|---|
| DB 삭제 성공 후 파일 삭제 실패 | 204 를 그대로 주고 로그를 남긴다. 고아 파일은 스위퍼 대상 |
| `upload_dir` 폴더 없음 | 기동 시 만든다. 만들 수 없거나 쓸 수 없으면 기동을 거절하고 한국어로 이유를 낸다 |

`/internal/*` 의 오류 본문은 기존 규칙대로 FastAPI 기본값 `detail` 이다.

## 6. 검증

이 저장소는 pytest 대신 `tools/*_check.py` 를 쓴다. 같은 틀로 나눈다.

### 6-1. CI 에서 도는 점검: `tools/storage_check.py` (새로)

DB·Redis·외부 API 없이 임시 폴더에서 돈다. `.github/workflows/ci.yml` 의 자체 점검 목록에 한 줄 추가한다.

| 확인 | 이유 |
|---|---|
| 경로가 `{bot_id}/{doc_id}` 이고 원본 파일명이 들어가지 않는다 | 경로 탈출 방지 |
| save → read 가 같은 바이트를 돌려준다 | 기본 동작 |
| 없는 파일을 delete 해도 예외가 없다 | 삭제가 두 번 불려도 안전 |
| 다른 `bot_id` 로 read 하면 읽지 못한다 | `bot_id` 격리 |

### 6-2. 손으로 돌리는 점검: `tools/upload_queue_e2e_check.py` (새로)

DB, Redis, 워커, 진짜 임베딩이 필요해 CI 에서 돌 수 없다. `ci.yml` 주석의 "못 태우는 점검" 목록에 넣고 개수 문장(8 → 9)을 함께 고친다.
Redis 나 워커가 없으면 시간 초과로 기다리지 않고 "워커를 먼저 띄우세요" 로 바로 실패한다.

| 시나리오 | 기대값 |
|---|---|
| 정상 업로드 | `ready`, 처리 후에도 원본이 남아 있다 |
| 같은 `doc_id` 로 작업을 두 번 보냄 | 청크 수가 두 배가 되지 않는다 |
| 워커가 꺼내기 전에 문서 삭제 | 워커가 조용히 끝난다 |
| 문서 삭제 | 행, 청크, 원본이 모두 사라진다 |

### 6-3. 기존 점검 `tools/upload_e2e_check.py`

지금은 서버를 띄우지 않고 앱을 직접 불러 `BackgroundTasks` 가 같은 프로세스에서 도는 것에 기대고 있다. 전환 후에는 워커가 없으면 `pending` 에서 넘어가지 않는다.

- **Redis 와 워커가 떠 있어야 도는 것으로 바꾼다.** 없으면 6-2 와 같은 안내로 바로 실패한다.
- Celery eager 모드(`delay()` 자리에서 큐 없이 바로 실행)는 **쓰지 않는다.** 점검이 바꾸려는 바로 그 경로(큐)를 건너뛰고 초록불을 준다. 검사가 안 도는 것과 통과한 것은 다르다.
- 파일 머리의 실행 방법 문단을 함께 고친다.

### 6-4. 직접 재서 PR 에 붙이는 것

| 실험 | 확인 |
|---|---|
| 워커를 끄고 업로드한 뒤 Redis 안의 메시지를 연다 | 메시지에 ID 만 있고 원본은 디스크에 있다 |

| Spring 을 거친 업로드, `cd api && ./gradlew test` | 회귀 없음 |
| `python -m tools.import_boundary_check` 등 기존 CI 점검 | 그대로 통과 |

## 7. 이 조각의 한계 (PR "한계 & 트레이드오프" 칸에 그대로 옮긴다)

1. **워커가 처리 중에 죽으면 문서가 `processing` 에 멈춘다.** `acks_late` 를 껐기 때문이다. 이 조각을 "유실을 해결했다"고 쓰면 거짓 완성이다.
2. **상태 가드는 다음 조각에서 다시 설계해야 한다.** `acks_late` 를 켜면 워커가 죽어 `processing` 에 남은 문서의 재배달 작업이 "pending 이 아니면 끝" 가드에 막혀 영원히 멈춘다. 다음 조각은 가드를 `pending`·`processing` 으로 넓히고 `DELETE FROM chunks` 를 같은 트랜잭션에 넣어야 한다.
3. **같은 호스트 가정.** API 와 워커가 같은 디스크를 본다는 전제다. 워커를 컨테이너나 다른 호스트로 옮기면 볼륨 공유나 MinIO 가 필요하다.
4. **봇 삭제 시 `uploads/{bot_id}/` 가 남는다.** Spring 이 봇을 지우면 DB 는 CASCADE 로 정리되지만 Python 은 모른다. 결과적 정합성으로 스위퍼가 정리할 예정이다.
5. **고아 파일 두 가지가 더 생길 수 있다.** (a) INSERT → 파일 쓰기 → 커밋 사이에 프로세스가 죽으면 행은 롤백되고 파일만 남는다. (b) `delay()` 실패 시 `failed` 행과 원본이 남는다(사용자가 삭제하면 정리된다). 스위퍼는 "DB 에 없는 doc_id 의 파일"까지 대상으로 한다.
6. **"pending 인데 큐에 메시지가 없는" 틈은 줄였지 없앤 것이 아니다.** `delay()` 실패는 `failed` 로 바꿔 보이게 했지만, 커밋과 `delay()` 사이에 프로세스가 죽으면 여전히 `pending` 이 남는다. 근본 해법(아웃박스 패턴)은 별도 조각이다.
