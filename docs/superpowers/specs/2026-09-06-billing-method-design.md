# 결제 수단 등록 — 설계

- **날짜**: 2026-09-06
- **대상**: 요금제 연동 4조각 중 **3번(결제 수단 등록·조회·삭제)**
- **위치**: `api/`(Spring) · `web/`(Next.js). Python(`ai-service/`)·위젯(`widget/`)은 한 줄도 안 고친다

## 이 문서의 범위

| # | 조각 | 상태 |
|---|---|---|
| 1 | **계량** — 과금 대상 사건을 계정별 원장에 쌓는다 | ✅ 완료 (PR #52·#53) |
| 3 | **결제 수단 등록** — 토스 빌링키 발급·저장·삭제 | 🚧 **이 문서** |
| 2 | 플랜·포함량 — 개수에 플랜을 곱한다 | ⬜ 파일럿 데이터 이후 |

**이 문서가 다루지 않는 것**: 금액 · 플랜 · 실제 청구 · 결제 실패 처리 · 웹훅 · 영수증.
이 조각에는 **숫자가 하나도 나오지 않는다.** "이 고객의 카드를 저장한다"까지가 전부다.

## 왜 2번이 아니라 3번이 먼저인가

`/pricing` 의 중심 주장이 **"금액이 아직 없다"** 이고 그게 의도다.
PRD §13.1 은 *무엇에 값을 매길지*(과금축 3개)를 확정하고 *얼마를 받을지*는 부록 A-1 #10 에서
**"파일럿 4주 후"** 로 미뤘다 — 원문: *"실사용 데이터 없이 정하면 근거 없는 숫자가 된다."*

2번(플랜·포함량)은 정확히 그 숫자들을 요구한다(월 정액·포함 답변 수·초과 단가).
지금 만들면 `/pricing` 은 "금액 없다"고 하는데 DB 엔 금액이 있게 되고,
**이 저장소가 여러 번 지켜온 원칙("근거 없는 숫자를 쓰지 않는다")을 정면으로 어긴다.**

**3번은 금액이 하나도 필요 없다.** 그래서 3번을 먼저 한다.

### 🔴 라이브 전환은 이 조각으로 안 된다 — 숨기지 않는다

> "자동결제는 리스크 검토 및 추가 계약 후 사용할 수 있습니다. 정기 구독형 서비스가 아니라면
> 정책적으로 자동결제 사용이 제한되니 유의하세요."
> — https://docs.tosspayments.com/guides/v2/billing

라이브에는 **전자결제 계약 + 자동결제 추가 계약** 두 개가 필요하고, 둘 다 사업자등록이 전제다.
**테스트 키로는 사업자등록 없이 전 흐름이 돈다** — 카드 등록창·빌링키 발급·삭제까지 전부.
그래서 이 조각의 완료 조건은 **테스트 키 기준**이고, 문서·PR·화면 어디에도
"결제됩니다" 라고 쓰지 않는다.

⚠️ **키 종류를 틀리면 `INVALID_API_KEY` 가 난다.** 자동결제는 **API 개별 연동 키**
(`test_ck_` / `test_sk_`)를 쓴다. 결제위젯 키(`test_gck_` / `test_gsk_`)가 아니다.
토스는 서비스마다 **다른 MID 에 각각 키를 발급**하고, 세트가 아닌 키를 섞으면 거부한다.

## 어떻게 저장하는가

### 🔴 먼저 — 토스 문서 확인 결과 전제가 하나 뒤집혔다

핸드오프(2026-09-06)는 *"토스에는 빌링키를 폐기하는 API 가 없다"* 고 적었다. **틀렸다.**

| 핸드오프의 서술 | 실제 |
|---|---|
| 빌링키 폐기 API 가 없다 | ~~없다~~ → **있다.** `DELETE /v1/billing/{billingKey}` |
| (언급 없음) | 🔴 **빌링키를 <조회>하는 API 가 없다** |

> "발급된 빌링키를 조회하는 API는 제공되지 않습니다. 빌링키 발급 이후 반드시 안전하게 저장하세요.
> 만약에 빌링키를 잃어버렸다면 구매자에게 다시 결제 정보를 받아서 새로운 빌링키를 발급받아주세요.
> 카드·계좌 하나에 여러 개의 빌링키를 중복으로 발급할 수 있어요. **빌링키 중복 발급을 방지하는 방법은 없습니다.**"
> — https://docs.tosspayments.com/guides/v2/billing

**방향이 뒤집혔다.** 원래 설계는 "삭제란 우리가 잊는 것일 뿐"이라 약하게 잡혀 있었는데,
실제로는 **삭제는 진짜 되고, 대신 우리 DB 가 빌링키의 유일한 사본**이다.
이 사실 하나가 아래 세 곳을 바꾼다 — 삭제 순서 · 발급 실패 처리 · 암호화 키 분실의 대가.

### 왜 `users` 컬럼 하나가 아닌가 — 수명이 다르다

| | 무엇 | 언제 죽나 |
|---|---|---|
| `customerKey` | "이 고객" 이라는 **우리 쪽 이름표** | **안 죽는다.** 카드를 빼도 남는다 |
| `billingKey` | "이 카드에 청구해도 된다" 는 **열쇠** | 카드를 빼면 죽는다 |

카드를 지웠다 다시 넣어도 **같은 `customerKey` 여야** 토스 쪽 고객 이력이 이어진다.
한 곳에 두면 삭제할 때 둘 중 하나를 반드시 잘못 다루게 된다.

### 왜 `users.id` 를 `customerKey` 로 쓰지 않는가

토스의 형식 요구는 만족한다(UUIDv4 라 추측 불가). 그런데 **내부 기본키가 외부 업체에 그대로 나간다** —
토스 대시보드·로그·CS 이력에 우리 DB 의 PK 가 찍힌다.

**저장소에 이미 같은 선례가 있다.** `bots.public_key`(`pk_...`) 가 정확히 그 패턴이다 —
봇 UUID 를 고객 사이트 HTML 에 노출하지 않으려고 별도 공개키를 만들었다.
그래서 *"왜 UUID 를 안 썼나요?"* 에 일관된 답이 된다:
**"내부 식별자를 외부에 흘리지 않는다는 규칙을 이미 봇에 적용했고, 결제도 같게 뒀습니다."**

대가는 컬럼 하나와 생성 로직 몇 줄이다.

### 스키마 (`V6__billing_method.sql`)

```sql
-- 결제 수단(토스 빌링키) 저장 (2026-09-06)
--
-- 소유권: Spring 이 쓰고 Spring 이 읽는다. Python 은 건드리지 않는다.
--
-- 왜 테이블을 나눴나: customerKey 는 카드보다 오래 산다(카드를 빼도 남아야
-- 재등록 시 토스 쪽 고객 이력이 이어진다). billingKey 는 카드와 함께 죽는다.
-- 수명이 다른 둘을 한 곳에 두면 삭제할 때 반드시 한쪽을 잘못 다루게 된다.

-- ① customerKey 는 users 에.
--    토스 제약(문서 원문): "영문 대소문자, 숫자, 특수문자 - _ = . @ 를 최소 1개 이상 포함한
--    최소 2자 이상 최대 50자 이하". 'bcus_' + 32 hex = 37자로 들어간다.
ALTER TABLE users ADD COLUMN IF NOT EXISTS billing_customer_key VARCHAR(50);

-- 기존 계정을 메꾼다. 이걸 안 하면 NOT NULL 을 걸 수 없고,
-- NOT NULL 이 아니면 "customerKey 없는 사용자" 라는 다룰 필요 없는 상태가 영구히 남는다.
UPDATE users SET billing_customer_key = 'bcus_' || replace(gen_random_uuid()::text, '-', '')
 WHERE billing_customer_key IS NULL;

ALTER TABLE users ALTER COLUMN billing_customer_key SET NOT NULL;
ALTER TABLE users ADD CONSTRAINT uq_users_billing_customer_key UNIQUE (billing_customer_key);

-- ② 카드는 별도 테이블. 삭제가 "행 하나 지우기" 가 된다
--    (컬럼 4개를 NULL 로 되돌리는 것보다 의도가 분명하다).
CREATE TABLE IF NOT EXISTS billing_methods (
  id                 UUID PRIMARY KEY DEFAULT gen_random_uuid(),

  -- 🔴 ON DELETE CASCADE 는 필수다. V5 에서 이걸 뺐다가 통합 테스트 11건이 깨졌다 —
  --    전 테스트가 userRepository.deleteAll() 로 정리하는데 그 FK 가 정리를 막았다.
  --    UNIQUE 가 "계정당 카드 1장" 을 DB 수준에서 보장한다. 토스는 같은 카드로
  --    빌링키를 몇 개든 발급해주고 중복 방지 수단이 없으므로, 이 제약이 유일한 방어다.
  user_id            UUID NOT NULL UNIQUE REFERENCES users(id) ON DELETE CASCADE,

  -- Base64(IV 12B ‖ 암호문 ‖ GCM 인증태그 16B) 한 덩어리. IV 컬럼을 따로 두지 않는다 —
  -- IV 는 비밀이 아니고 암호문과 반드시 짝이라, 나누면 한쪽만 갱신·복사되어 어긋날 수 있다.
  -- 길이: 빌링키 최대 200자(토스 문서) → 12+200+16 = 228B → Base64 304자. 512 면 넉넉하다.
  -- 컬럼명에 _enc 를 붙여 "여기 든 게 평문이 아니다" 를 스키마에서부터 말한다.
  billing_key_enc    VARCHAR(512) NOT NULL,

  -- ⚠️ 토스가 카드사 <이름> 을 안 준다. 버전 2024-06-01 부터 응답에서 cardCompany 가 제거됐고
  --    card.issuerCode("61" 같은 두 자리 코드)만 온다. 코드→이름 매핑은 우리가 상수로 들고 있는다.
  --    (코드표: https://docs.tosspayments.com/reference/codes)
  issuer_code        VARCHAR(4)  NOT NULL,
  card_number_masked VARCHAR(20) NOT NULL,   -- "43301234****123*" — 토스가 마스킹해서 준다

  created_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**`billing_customer_key` 생성은 `User.create()` 안에 둔다.** `Bot.create()` 가 `publicKey` 를
만드는 것과 같은 이유다 — *"생성 위치가 밖에 있으면 키를 안 넣고 만든 행이 생길 여지가 남는다."*

**넣지 않은 컬럼과 이유**: `card_type`(신용/체크) · `owner_type`(개인/법인) · 토스의 `authenticatedAt`.
카드를 한 장만 두는 동안 구별에 쓸 일이 없다. 등록일은 우리 `created_at` 으로 충분하다.
→ **카드 여러 장을 지원할 때 함께 추가한다.**

## 쓰기 경로 ① — 등록

```
① 브라우저: payment.requestBillingAuth({ method:"CARD", successUrl, failUrl })
                     카드번호는 토스 창 안에서만 존재 ──────────▶ 토스
② 토스 ──▶ /billing?customerKey=..&authKey=..     (실패는 /billing?code=..&message=..)
③ 브라우저 ──▶ POST /api/billing/method { authKey }
④ Spring  ──▶ POST https://api.tosspayments.com/v1/billing/authorizations/issue
               { authKey, customerKey }
               Authorization: Basic base64(secretKey + ":")   ← 콜론 필수
               Idempotency-Key: <UUID>
⑤ 토스 ──▶ { billingKey, card: { issuerCode, number, ... } }
⑥ Spring: billingKey 암호화 저장 + 카드 메타 저장
```

**카드번호가 우리 서버·우리 페이지에 닿지 않는다.** 토스가 자기 창에서 받고 우리는 `authKey` 만
받는다. **PCI-DSS 대상 데이터를 우리가 갖지 않는다는 뜻**이다.

### 🔴 ③에서 쿼리로 돌아온 `customerKey` 를 신뢰하지 않는다

서버가 **JWT 사용자의 것을 DB 에서 읽어** ④에 넣는다. 쿼리 값은 **대조만** 하고 다르면 400.

신뢰하면 남의 `customerKey` 를 적어 보내는 것만으로 **카드가 남에게 붙는다.**
`userId` 를 `@AuthenticationPrincipal` 로만 받는 이 저장소의 규칙과 정확히 같은 이유다 —
*"출처가 '우리가 서명한 토큰' 인 값만 신뢰한다."*

### 🔴 ④가 실패하면 복구 불가능한 자리가 생긴다

④가 타임아웃되면 **"발급됐는데 우리가 모르는 빌링키"** 가 남고,
**조회 API 가 없으므로 영원히 회수할 수 없다.** 그래서 여기만 예외적으로 두 가지를 한다.

- **`Idempotency-Key` 헤더를 붙인다.** 토스의 모든 POST 가 지원하고, 같은 (멱등키·API 키·주소·메서드)
  조합이면 같은 응답을 돌려준다. 처음 쓴 날부터 15일 유효.
- **I/O 실패에 1회 재시도한다 — 같은 멱등키로.**

  ⚠️ **`AiServiceClient` 의 재시도 논리를 그대로 가져오면 안 된다.** 그쪽은
  *"재시도의 전제는 직전 시도가 아무 일도 하지 않았다는 것"* 이라 **연결 실패에만** 재시도한다.
  결제는 그 전제가 안 선다 — **읽기 타임아웃이어도 상대는 이미 발급했을 수 있다.**
  멱등키가 그 전제를 대신 세워준다. **멱등키 없이 재시도하면 고아 빌링키가 하나 더 는다.**

## 쓰기 경로 ② — 삭제

**토스 먼저, 우리 나중.** 순서를 뒤집으면 토스 호출이 실패했을 때 우리는 그 키를 이미 지운 뒤라
**영영 폐기할 수 없는 고아**가 된다(조회 API 가 없으니 다시 알아낼 방법이 없다).

```
DELETE https://api.tosspayments.com/v1/billing/{billingKey}
```

| 토스 응답 | 우리 행 | HTTP | 근거 |
|---|---|---|---|
| 200 | 삭제 | 204 | 정상 |
| ~~**4xx** | **삭제** | 204 | 토스 쪽엔 이미 없다~~ | ~~치울 게 없으니 우리 행만 지운다~~ |
| **404** | **삭제** | 204 | 토스 쪽엔 이미 없다. 치울 게 없으니 우리 행만 지운다 |
| **404 를 제외한 4xx · 5xx · 타임아웃** | **유지** | 503 | 다시 시도하면 치울 수 있다. 지금 지우면 그 기회를 버린다 |

이 분기는 `AiServiceClient` 의 원칙 그대로다 — **코드를 나누는 기준은 "누구 잘못인가"다.**

> ⚠️ **취소선은 최초 설계다.** 구현·리뷰 과정에서 좁혀졌다 — 아래 "한계" 절 참고.

⚠️ **삭제 응답 body 를 파싱하지 않는다.** 토스 문서가 자기모순이다 —
API 레퍼런스는 *"비어있는 body 에 200 응답만 내려갑니다"*, 연동 가이드 FAQ 는
`{"billingKey": "..."}` 를 보여준다. **HTTP 상태로만 판정한다.**

전제가 뒤집힌 덕에 화면 문구를 사실대로 쓸 수 있게 됐다:
**"등록된 카드를 삭제합니다. 토스페이먼츠에서도 함께 폐기됩니다."**
(핸드오프대로였다면 "우리가 잊을 뿐 폐기되지는 않습니다" 라고 적어야 했다.)

## 암호화 — 새 의존성 0개

`spring-boot-starter-security` 가 이미 전이로 끌고 오는 **`spring-security-crypto` 7.0.6** 의
`AesBytesEncryptor` 를 **원시 키 생성자**로 쓴다. AES-256-GCM · 호출마다 새 IV ·
결과는 `IV ‖ 암호문+태그`. **Bouncy Castle 은 필요 없다**(클래스패스에 없고, 넣을 이유도 없다).

### 왜 `Encryptors.text()` / `delux()` 를 쓰지 않는가 (7.0.6 바이트코드로 확인함)

- **`Encryptors.text()` 는 GCM 이 아니라 `AES/CBC/PKCS5Padding` 이다.**
  CBC 는 **인증이 없어** 암호문을 한 바이트 뒤집어도 복호화가 그냥 성공한다.
  DB 를 만질 수 있는 공격자가 남의 빌링키로 바꿔치기해도 **우리가 눈치채지 못한다.**
- `delux()` 는 GCM 은 맞지만 키를 **PBKDF2WithHmacSHA1 1024회**로 유도한다.
  우리는 이미 32바이트 난수를 환경변수로 갖고 있어 유도할 이유가 없고, 1024회는 2026년 기준으로 낮다.

### 키 관리 — `JwtService` 패턴을 그대로 복제

`BILLING_CRYPTO_KEY`(Base64 32바이트, `openssl rand -base64 32`). **생성자에서** 네 가지를 확인한다.

| 검사 | 왜 |
|---|---|
| 미주입 / 공백 | |
| `${` 로 시작 | `@ConfigurationProperties` 는 해석 못 한 플레이스홀더를 **예외 없이 리터럴로 바인딩**한다 |
| 저장소에 공개된 로컬 기본값인가 | 개발 프로파일이면 `log.warn`, 아니면 **기동 중단** |
| **길이 32바이트인가** | ⚠️ JCE 는 16바이트 키를 주면 **말없이 AES-128 로 돈다.** 확인 안 하면 *"AES-256 으로 저장합니다"* 라고 말할 근거가 없다 |

`application.yaml` 은 `${BILLING_CRYPTO_KEY:<로컬기본값>}`, `application-prod.yaml` 은
**기본값 없이 `${BILLING_CRYPTO_KEY}`** — 그 파일의 fail-closed 원칙 그대로다.

### 대가를 그대로 적는다

🔴 **키를 잃으면 전 고객이 카드를 다시 등록해야 한다.**
조회 API 가 없어서 다른 길이 없다 — 우리 DB 가 유일한 사본이다.
**키 회전은 만들지 않는다.** 막다른 길은 아니다: 나중에 새 키를 도입할 때 `v2:` 접두사를 붙여
저장하면 **접두사 없는 행 = 옛 키**로 소급 판별된다. 지금 미리 문법을 만들 이유가 없다.

> 이 조각이 이 저장소의 **첫 암호화 결정**이다 — `decisions.md` 에 암호화 항목이 하나도 없다.
> 가장 가까운 선례가 `JWT_SECRET` 의 fail-closed 취급이고, 그래서 그 패턴을 따랐다.

## API 와 화면

| 메서드 | 경로 | 응답 |
|---|---|---|
| GET | `/api/billing/method` | `{ "customerKey": "bcus_...", "method": null }` 또는 아래 |
| POST | `/api/billing/method` | 아래. 이미 있으면 **409** |
| DELETE | `/api/billing/method` | **204** |

```json
{
  "customerKey": "bcus_9f2c1ab34de54f0a8b7c6d5e4f3a2b10",
  "method": {
    "issuerName": "현대",
    "cardNumberMasked": "43301234****123*",
    "registeredAt": "2026-09-06T14:03:11+09:00"
  }
}
```

🔴 **`billingKey` 는 어떤 응답 DTO 에도 필드가 없다.** 있으면 언젠가 실린다.

**표기 변환은 Spring 책임이다** — 토스는 `issuerCode`(코드)를 주고 프론트는 `issuerName`(이름)을
본다. 매핑을 프론트에 두면 `web/lib/types.ts` 가 백엔드 응답과 어긋난다.

### 실패 처리

`TossClient` 안에서 변환을 끝낸다. 호출 지점마다 try-catch 를 적으면 한 곳이 빠지고,
거기서 예외가 그대로 올라가 **500** 이 나간다 = "토스가 거절했다" 가 "우리 서버가 고장났다" 로 둔갑한다.

🔴 **`RestClient` 빈과 서킷브레이커를 `AiServiceClient` 와 공유하지 않는다.**
공유하면 **토스 장애가 채팅을 끊고, 그 반대도 된다.**

| 상황 | ErrorCode | HTTP |
|---|---|---|
| 카드 거절·정지·유효기간 등 (토스 4xx) | `BILLING_AUTH_FAILED` + **토스의 한국어 메시지 그대로** | 400 |
| 토스 5xx·타임아웃 | `BILLING_PROVIDER_UNAVAILABLE` | 503 |
| 이미 등록됨 | `BILLING_METHOD_ALREADY_EXISTS` | 409 |
| 없는데 삭제 | `BILLING_METHOD_NOT_FOUND` | 404 |

새 `ErrorCode` 4개. `INVALID_INPUT` 으로 뭉치지 않는 이유는 프론트가
**"카드를 바꿔 다시 시도"** 와 **"우리 버그"** 를 구분해 안내해야 하기 때문이다.

### 화면

⚠️ **계정 수준 라우트가 이 저장소에 하나도 없다.** `settings` 는 `bot/[botId]/settings` 하나뿐이고
봇 단위다. 대시보드 헤더에도 계정 메뉴가 없다(로고 + 로그아웃 둘뿐).
→ `app/(dashboard)/billing/page.tsx` 를 새로 만들고 헤더에 진입점을 뚫는다.
`(dashboard)` 그룹 아래 두면 토큰 가드·헤더·레이아웃을 물려받는다.

- **SDK 는 npm `@tosspayments/tosspayments-sdk`.** `web/` 의 첫 런타임 의존성 추가다
  (현재 `next`·`react`·`react-dom` 3개뿐). `next/script` + 전역 객체 대신 이걸 고른 이유는
  타입이 있고 토스가 React 용으로 문서화한 경로라서다. 결제창은 몇 줄로 대체할 수 있는 것이 아니다.
- **리다이렉트 착지도 `/billing` 한 곳.** `authKey` 가 있으면 성공, `code` 가 있으면 실패.
  처리 후 `router.replace("/billing")` 로 URL 을 비운다 —
  **새로고침으로 이미 소모된 `authKey` 를 다시 POST 하지 않게.**
- **삭제 확인은 `bot/[botId]/settings` 의 인라인 `armed` 패널**을 따른다.
  `window.confirm` 은 이 저장소가 금지했다 — 크롬이 반복 대화상자를 차단하면 **항상 `false`** 를
  돌려줘 조용히 아무 일도 안 일어나고 오류도 안 뜬다(2026-08-10, 문서 삭제에서 겪었다).

## 검사

### 1. `BillingCryptoTest` (스프링 컨텍스트 없음)

1. 암복호화 왕복
2. 같은 값을 두 번 암호화하면 **다른 암호문** (= IV 가 매번 새로 생긴다)
3. 암호문을 한 비트 뒤집으면 **복호화 실패** (= GCM 인증태그가 하는 일)
4. **다른 키로는 복호화 불가** (= "키를 잃으면 재등록" 의 실증)
5. 키가 32바이트가 아니면 **기동 실패**
6. `${...}` 리터럴이면 **기동 실패**

> 5·6 이 핵심이다. 이 저장소는 "운영에서 공개 기본값이면 죽는다" 가드를 이미 둘(`JwtService`,
> `application-prod.yaml`) 갖고 있는데 **테스트로 고정된 건 하나도 없다.** 이게 그 부류의 첫 사례다.

### 2. `BillingIntegrationTest` (진짜 톰캣 + 진짜 Postgres + `TossStub`)

`TossStub` 은 `AiServiceStub` 과 같은 패턴(JDK `HttpServer`)으로 만들고
`TestcontainersConfiguration` 에 빈으로 등록해 `app.toss.base-url` 을 주입한다.

1. 등록 성공 → 200 + 카드 정보
2. **DB 의 `billing_key_enc` 에 평문 빌링키가 없다**
3. **어떤 응답 본문에도 빌링키가 없다**
4. 남의 `customerKey` 를 실어 보내면 400
5. 이미 등록된 상태에서 또 등록하면 409
6. 토스 4xx → 400 + 토스의 메시지
7. 토스 5xx → 503
8. 삭제 시 **토스를 먼저 부른다**
9. **토스가 5xx 면 우리 행이 남는다** (503)
10. ~~토스가 4xx 면 우리 행은 지운다 (204)~~ → **토스가 404 면 우리 행은 지운다 (204). 404 를
    제외한 나머지 4xx 는 5xx 와 같이 503(우리 행 유지)** — 아래 "한계" 절 참고
11. 없는 상태에서 삭제 → 404
12. 남의 결제 수단이 내 조회에 안 섞인다

> **2·3·4·9 가 핵심 주장이다.** 나머지는 배관이다.

⚠️ `@BeforeEach` 에서 `userRepository.deleteAll()` 과 함께 **토스용 싱글턴의 `reset()`** 도 부른다.
안 하면 "실행 순서에 따라 나타났다 사라지는" 실패가 난다 — 이 저장소가 두 번 겪은 부류다.

### 3. 테스트 키로 브라우저 종단 1회

등록 → 조회 → **삭제 → 재등록** 한 바퀴. 실패 경로는
`TossPayments-Test-Code: INVALID_CARD_EXPIRATION` 헤더로 강제한다(라이브에서는 무시된다).

⚠️ 자동결제 테스트 환경은 **카드번호 앞 6자리(BIN)만 유효하면 등록된다.**
휴대폰 인증번호는 `000000`. 전용 테스트 카드번호 목록은 제공되지 않는다.

## 한계 — 알고 남기는 것

- 🔴 **우리 DB 가 빌링키의 유일한 사본이다.** 토스에 조회 API 가 없다.
  백업·마이그레이션에서 `billing_key_enc` 를 날리면 전 고객이 카드를 다시 등록해야 한다.
- ~~토스에는 빌링키를 폐기하는 API 가 없다~~ → **틀렸다. 있다**(위 참조).
  핸드오프에 그렇게 적혀 있었고, 문서를 직접 확인해서 뒤집었다.
- **라이브 전환 불가** — 자동결제 추가 계약이 필요하고 사업자등록이 전제다. 테스트 키까지가 범위다.
- **중복 발급을 토스가 막아주지 않는다.** 같은 카드로 빌링키가 몇 개든 생긴다.
  우리 쪽 `UNIQUE(user_id)` 가 유일한 방어이므로, **나중에 카드 여러 장을 지원하면 이 방어가 사라진다.**
- **키 회전 없음.** `v2:` 접두사로 소급 도입 가능하다는 것까지만 확인해뒀다.
- **삭제 API 의 에러 코드표가 토스 문서에 없다.** 없는 빌링키를 지울 때 어떤 코드가 오는지 모른다.
  ~~그래서 4xx 를 전부 "토스 쪽엔 이미 없다" 로 취급한다 — 이 해석이 틀리면 고아가 남는다.~~ →
  **틀렸다. 구현·리뷰 과정에서 뒤집혔다(커밋 `633b029`).** 4xx 를 통째로 삼키면 **401**(우리
  시크릿 키가 잘못됨 — 토스는 빌링키를 쳐다보지도 않았다)에서도 유일한 사본을 지우고 204 를
  줘버려, "토스 먼저" 순서 규칙이 막으려던 바로 그 고아를 만든다. 429(레이트리밋)도 "없다"는
  뜻이 아니다. **지금은 404 하나만 삼킨다.** 원칙은 "모르면 지우지 않는다" — 나머지 4xx 는
  5xx 와 같이 503 으로 묶는다. 바뀐 대가: 토스가 없는 빌링키에 404 가 아닌 코드를 주면
  사용자가 카드를 못 지우고 503 을 본다 — 되돌릴 수 있는 실패를 고른 것이다.
- **카드 유효성은 등록 시점에 다 볼 수 없다.** 토스 문서: 잔고 부족·한도 초과는 **결제 승인을 요청할 때**
  확인된다. 즉 "등록 성공" 이 "청구 성공" 을 보장하지 않는다 — **4번 조각의 실패 처리가 그래서 필요하다.**
- **국내 발급 카드만 지원된다**(토스 제약).

## 다음 조각과의 경계

**여기서 끝난다**: `billingKey` 를 안전하게 갖고 있고, 고객이 그걸 넣고 뺄 수 있다.

**4번(청구)이 시작하는 지점**: 그 열쇠로 **금액을 청구**하는 것.
`POST /v1/billing/{billingKey}` 호출 · 마감 · 금액 산정 · 결제 실패 재시도 · 영수증.
**2번(플랜·포함량)이 그 앞에 있어야 한다** — 청구할 금액이 있어야 청구한다.

토스는 **스케줄링을 제공하지 않는다.** 정기 청구는 우리가 크론으로 짜야 한다.
