## 1. 왜 지금 이것을 하나

`ai-service/app/judge.py` 첫머리가 **2026-08-02 부터** 이렇게 적고 있다.

> ⚠️ 아직 <사람 라벨과 대조하지 않았다>. "채점을 어떻게 믿느냐"에 답하려면 사람이 매긴
> 30~50건과의 일치율(카파)이 필요하다. TODO(W4).

2026-09-18 에 이 TODO 가 <가정>이 아니라 <관측>이 됐다. q3 의 답변 문자열을 글자까지
고정하고 근거 집합만 바꿔 채점자를 35회 불렀더니, 무관한 청크 하나가 끼는 것만으로
충실성이 **1.0 ×10 → 0.0 ×10** 으로 갈렸다. 정답 청크는 두 조건 모두에 <3번째 자리로>
들어 있었고, 채점자가 댄 사유(*"근거에 기간제 재택근무 내용이 없습니다"*)는 사실과 달랐다.

**따라서 전체충실성은 "답이 나빠졌다" 와 "채점자가 다르게 읽었다" 를 한 값으로 뭉갠다.**
`AGENTS.md` 의 "낸 버그" 표 아홉 번째가 이것이고, 앞의 여덟과 달리 **이미 만들어 계속 쓰고
있는 신호**에서 났다. 이 저장소의 모든 before/after 비교표가 그 지표 위에 서 있다.

🔴 **어제 확인된 것의 범위를 정확히 적는다. 본 것은 <정밀도>다** (한 입력에 15회씩 같은
값을 낸다, 조건 안 분산 0.0000). **<정확도>는 한 번도 재지 않았다.** 오히려 q3 에서는
**정밀하게 틀렸다** - 10회 내내 일관되게 0.0 을 줬고 그 사유가 거짓이었다.
**흔들리면 반복 측정으로 걸러지는데 일관되게 틀리면 안 걸러진다.**

이 슬라이스가 재는 것은 **정확도** 하나다.

## 2. 재료는 이미 DB 에 있다 (평가를 새로 돌리지 않는다)

`eval_runs` 의 run **11~16** 이 그것이다(11·12·13 = 306청크 · 14·15·16 = 360청크).
전부 `status='completed'` 이고 **처리 실패 0건**이다.

```
eval_results      156 행 (26문항 × 6회)
  중복 제거        46 건  ← (문항 · 답변 문자열 · 근거 집합) 조합 기준
  fallback 제외    44 건  ← 채점자가 실제로 판정한 서로 다른 입력. 이것이 모집단이다
```

🔴 **44건은 표본이 아니라 모집단이다.** "어떻게 골랐나" 라는 물음이 원천적으로 없다.
핸드오프가 제안한 "30~50건을 의도적으로 치우치게 뽑아라" 는 전수가 그 범위에 들어오므로
필요 없어졌다. 점수가 갈린 자리(q3 · q14 · q21)도 자동으로 전부 포함된다.

⚠️ **한계를 정직하게 적는다.** 44건은 **한 봇 · 한 코퍼스 · 한 채점 모델**에서 나왔다.
말할 수 있는 것은 "이 채점자가 일반적으로 정확하다" 가 아니라 **"이 저장소의 비교표를
만든 그 입력들에서 정확했는가"** 까지다. 다만 알고 싶은 것이 정확히 그것이다.

### 2-1. 🔴 분포가 극단적으로 치우쳐 있다 (설계를 바꾼 사실)

44건의 채점자 점수다.

| 충실성 | 관련성 | 건수 |
|---|---|---|
| 1.0 | 1.0 | **40** |
| 0.5 | 1.0 | 1 |
| 0.5 | 0.5 | 2 |
| 0.0 | 1.0 | 1 (= q3) |

**둘이 따라온다.**

**① 관련성은 라벨링하지 않는다.** 44건 중 43건이 1.0 이라 잴 것이 없다. 충실성만 매긴다
(전체충실성이 이 저장소의 비교 축이기도 하다).

**② 카파 하나로 결론을 말하지 않는다.** 한쪽 값이 91% 를 차지하면 우연 일치 확률이
이미 0.83 쯤이라 카파의 분모가 거의 0 이 된다. 일치율 95% 인데 카파 0.3 이 나오는
**카파 역설(kappa paradox)** 이다. 숫자 하나로 "믿을 수 있다/없다" 를 말하려다
**오히려 아무 말도 못 하게 된다.** 카파는 부수적으로 찍되 그 주석을 함께 박는다.

### 2-2. 진짜 위험은 40건 쪽이다

어제 잡은 q3 는 **박하게** 틀린 것이다(맞는 답에 0.0). 이런 것은 눈에 띈다. 숫자가
내려가니 이상하다고 파보게 되고, 실제로 그래서 발견됐다.

🔴 **반대로 <후하게> 틀린 것은 아무도 찾을 수 없다.** 채점자가 나쁜 답에 1.0 을 주면
화면에는 "잘 되고 있다" 고만 뜨고 **DB 어디를 뒤져도 나오지 않는다.** 그것을 찾는 유일한
방법이 사람이 그 40건을 직접 읽는 것이고, **그것이 이 슬라이스가 존재하는 이유다.**

따라서 결과 문장은 이 모양이어야 한다:

> 채점자가 1.0 을 준 40건을 사람이 다시 읽었더니 N건은 1.0 이 아니었다.
> 즉 전체충실성은 실제보다 약 X 높게(낮게) 나오고 있다.

카파 하나로는 이 문장을 만들 수 없다.

## 3. 만드는 것

```
eval_results (DB, run 11~16 · 156행)
        │
        │  ① app/eval_cases.py            중복 제거 → 44건 복원
        ▼
    Case 레코드 (질문 · 기대답변 · 생성답변 · 근거 전문 · 어느 run 에 나왔나)
        │
        │  ② app/judge_agreement.py dump  🔴 채점자 점수를 <빼고> 쓴다
        ▼
  testdata/judge_labels.json               ← 사람이 label 칸을 채운다 (0 / 0.5 / 1)
        │
        │  ③ app/judge_agreement.py report  파일 + DB 의 채점자 점수를 합친다
        ▼
    혼동행렬 · 방향 집계 · 전체충실성 왜곡량
```

### 3-1. `app/eval_cases.py` (새 파일)

`eval_results` 한 행을 **채점자 입력으로 되돌리는 것** 하나만 한다.
`retrieved_chunks` JSON 을 `Source` 로 복원하고, 같은 (문항 · 답변 · 근거) 조합을 묶는다.

**이 모듈을 따로 뺀 이유는 다음 슬라이스다.** 탐침(§6)도 똑같이 "저장된 케이스를 복원해
`judge.score()` 에 다시 넣는" 일을 한다. 이것만 import 하면 파일 하나 더 쓰는 것으로
끝난다. 🔴 어제 실험 스크립트가 스크래치패드에서 사라져 핸드오프에 표를 손으로 옮겨
적어야 했던 것을 반복하지 않는 자리다.

DB 만 쓰고 외부 API 를 부르지 않는다.

### 3-2. `dump` - 블라인드가 이 도구의 존재 이유다

🔴 **파일에 채점자 점수를 쓰지 않는다.** 보고 나서 매기면 앵커링되어 대조가 성립하지
않는다. `answerable_check` 이 홀드아웃을 기본 모드에서 **읽지도 않게** 만들어둔 것과
같은 규칙이다(임계값을 고르는 표에 홀드아웃을 띄우면 보면서 고르게 된다).

`case_id` 해시로 순서를 섞는다. run 순서·문항 번호 같은 단서를 남기지 않는다.

🔴 **근거는 preview 200자가 아니라 전문을 싣는다**(`fetch_contents`). 2026-08-02 에
**채점자가 앞 200자만 보다가 250번째 글자의 "HR-310" 을 못 보고 맞는 답에 0점을 준**
버그가 있었다. 사람이 채점자보다 덜 보면 이번에는 <사람 라벨이> 거짓이 된다.

**라벨을 이어받는다.** `dump` 를 다시 돌려도 이미 채운 `label` 은 `case_id` 로 찾아
보존한다(`eval_set dump` 가 사람이 적은 칸을 이어받는 것과 같다). 1.5~2시간짜리 일이라
중간에 끊고 이어 할 수 있어야 한다.

**파일 위치**: `ai-service/testdata/judge_labels.json`. `eval_questions.json` 옆이다.
저장소에 남아야 재현된다.

```json
{
  "_readme": "label 칸에 0 / 0.5 / 1 만 적는다. 채점자 점수는 일부러 들어 있지 않다.",
  "generated_at": "2026-09-20",
  "run_ids": [11, 12, 13, 14, 15, 16],
  "cases": [
    {
      "case_id": "<안정 해시>",
      "question_id": 58,
      "question": "...",
      "ground_truth": "...",
      "generated_answer": "...",
      "sources": [{"chunk_id": 27, "filename": "...", "content": "<전문>"}],
      "seen_in_runs": [11, 12, 13],
      "label": null,
      "note": ""
    }
  ]
}
```

### 3-3. `report` - 네 덩어리

```
[1] 혼동행렬           행 = 사람, 열 = 채점자 (3×3)
[2] 방향 집계          후하게 틀림 N건 / 박하게 틀림 N건
[3] 전체충실성 왜곡량   run 별로 <채점자 기준> 과 <사람 기준> 을 나란히
[4] 불일치 상세        case_id · 문항 · 사람 · 채점자 · 채점자가 댄 사유
```

**[3] 이 이 도구의 결론이다.** run 14 의 전체충실성이 0.8465 로 기록돼 있는데, 그 26행의
점수를 사람 라벨로 갈아끼우고 **같은 식**(`avg_faithfulness × scored_count / question_count`)
으로 다시 계산한다.

> run 14 전체충실성: 채점자 **0.8465** → 사람 **0.9xxx** (차이 +0.0xx)

🔴 **실측 편차 0.032 와 나란히 읽을 수 있다.** 채점자 오차가 그보다 크면, 이 저장소가
"노이즈가 아니다" 라고 주장해온 개선들의 근거가 흔들린다. 작으면 비교표는 그대로
유효하고 **그것도 결론이다.**

⚠️ fallback 판정은 사람이 하지 않는다. 사람이 라벨링하는 것은 <채점자가 점수를 매긴>
44건뿐이므로, `scored_count`(24) 와 `question_count`(26) 은 채점자 기준과 사람 기준이
동일한 값을 쓴다. **갈리는 것은 `avg_faithfulness` 하나다.** 즉 이 비교는 "채점이
달라지면 전체충실성이 얼마나 움직이는가" 만 격리해서 보여준다.

**[4] 에 채점자 사유를 붙이는 이유**: q3 에서 채점자가 *"근거에 기간제 재택근무 내용이
없다"* 고 했는데 정답 청크는 3번째에 있었다. **틀린 것과 거짓 사유를 댄 것은 다른
사실**이고, 사유를 나란히 봐야 갈린다.

**카파**는 선형 가중으로 함께 찍되 출력에 역설 주석을 한 줄 박는다. 학계 표준 용어라
이력서·블로그에 옮길 일이 생기는데, 숫자만 옮기면 §2-1 의 함정에 걸린다.

### 3-4. 무엇이 실패인가

| 상황 | 동작 |
|---|---|
| 라벨 파일이 없다 | **실패.** 점검 대상이 없는 것과 통과한 것은 다르다(`eval_set_check` 관례) |
| `label` 이 안 채워진 칸이 있다 | **실패.** 몇 건 남았는지 찍는다. 부분 집계를 내면 그것이 결과로 인용된다 |
| `label` 이 0 / 0.5 / 1 이 아니다 | **실패.** 해당 `case_id` 를 찍는다 |
| run 11~16 이 DB 에 없다 | **실패.** 봇 선택은 2026-09-18 에 고친 규칙을 따른다(자동 선택은 청크가 있는 봇이 정확히 하나일 때만) |

### 3-5. `app/judge_agreement_check.py` (CI 에서 돈다)

혼동행렬 · 방향 집계 · 왜곡량 계산은 순수 함수라 합성 데이터로 검증한다.
DB 도 외부 API 도 쓰지 않는다.

🔴 **특히 "후하게 / 박하게" 의 부호를 회귀 검사로 건다.** 부호 하나가 뒤집히면
결론이 정반대가 된다("실제보다 높게 나온다" ↔ "낮게 나온다").

## 4. `ci.yml` 주석을 고친다

지금 이렇게 적혀 있다.

> DB 가 필요한 점검 4개가 하나같이 외부 API 도 함께 부르기 때문에, DB 를 띄워줘도
> 그 넷 중 어느 것도 CI 에서 돌 수 없다.

🔴 **`judge_agreement` 이 이 문장을 깬다.** DB 만 쓰고 외부 API 를 부르지 않는다
(채점자 점수가 이미 박제돼 있어 다시 부를 일이 없다). 그래도 CI 에서는 못 도는데,
**이유가 API 가 아니라 그 DB 안의 <측정 결과>가 CI 에 없기 때문**이다.

→ 문장을 그렇게 고치고, "이 여섯은 사람이 손으로 돌린다" 의 수를 **일곱**으로 바꾼다
(그 주석이 스스로 "개수를 늘리거나 줄일 때는 위 문장의 수도 함께 고칠 것" 이라고
경고해 두었다).

## 5. 이 슬라이스에 넣지 <않는> 것

- **채점 모델 교체.** ① 원인을 모른 채 손대는 것이고 ② **바꾸면 과거 모든 표의 축이
  어긋난다**(2026-08-03 이후 전부 `mistral-small-3.1-24b` 기준). 바꿔야 한다는 결론이
  나오면 그때는 옛 설정으로 한 번 더 돌려 두 채점자를 나란히 놓아야 한다.
- **관련성 라벨링** (§2-1 ①).
- **난이도 확보.** 핸드오프 §4 가 순서를 못박았다. 난이도를 만들어봐야 그것을 재는 지표를
  믿을 수 없는 상태다.
- **평가 재실행.** §2 의 원자료로 충분하다. 회당 1,300 뉴런을 쓸 이유가 없다.

## 6. 다음 슬라이스 (배관만 지금 만든다)

핸드오프 §3-3 의 가설이다: **근거 목록에 무관한 청크가 끼면 채점자가 있는 근거를 못 본다.**
q3 한 문항의 성질인지 일반적인지 모른다. 재는 법은 어제와 같고 싸다(채점 호출 수십 회,
약 700 뉴런): **답변을 고정하고 무관한 청크를 한 건씩 늘려가며** 점수가 언제 무너지는지 본다.

**지금 하지 않는 이유 둘.** ① 사람 라벨링이 병목인데, 그것이 끝나기 전에는 탐침 결과를
해석할 기준이 없다. "채점자가 무관한 청크에 약하다" 를 알아도 **그것이 숫자를 얼마나
왜곡하는지는 사람 라벨이 있어야 말할 수 있다.** ② 반대로 라벨링 결과가 탐침 설계를
바꿀 수 있다(후하게 틀리는 쪽이 많으면 탐침도 그 방향으로 짜야 한다).

🔴 **다만 이것은 평가 도구만의 문제가 아니다.** 채점자와 생성 모델은 **같은 근거 목록**을
받는다(`judge.score` 와 `generator.generate` 둘 다 `sources` 를 받는다). 채점자가 그렇게
밀렸다면 생성 모델도 같은 자리에서 그럴 수 있다. 생성 쪽까지 재면 이 트랙이 평가 도구
개선을 넘어 **검색 설정(`top_k` · `max_distance`)의 근거**가 된다.
