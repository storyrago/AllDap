# 설계: 리랭커 파인튜닝과 처음 보는 문서에서의 전후 비교 (2026-10-01)

이 문서는 리랭커(`bge-reranker-base`)를 파인튜닝하고, 파인튜닝 전 모델과 후 모델이 **학습에 쓰지 않은 문서**에서 정답 청크를 얼마나 잘 골라내는지 비교하는 실험의 설계다.
진행 상황과 다음 할 일은 핸드오프 [`handoff-2026-10-01.md`](../handoff-2026-10-01.md) 에 있다.

## 0. 용어

이 문서에서 같은 대상은 아래 이름 하나로만 부른다.

| 용어 | 뜻 |
|---|---|
| 리랭커 | 검색이 가져온 후보 청크 20개를 다시 줄 세워 상위 5개를 고르는 모델. 지금은 `bge-reranker-base` (파라미터 약 2억 7천만 개) |
| 원본 모델 | 파인튜닝하지 않은 `bge-reranker-base` |

| 헷갈림 묶음 | 같은 주제를 서로 다른 대상에 대해 다른 값으로 규정한 문서들. 예: 재택 횟수를 계약직 문서는 주 1회, 부설연구소 문서는 주 4회, 자회사 문서는 주 5회로 규정한다 |

| 시험용 봇 | 시험용 문서만 올린 봇. 파인튜닝 전후 비교를 여기서만 한다 |
| 연습 문제 | 학습 데이터로 쓰는 (질문, 정답 청크) 쌍. 학습용 문서에서만 나온다 |
| 시험 문제 | 비교 측정에 쓰는 (질문, 정답 청크) 쌍. 시험용 문서에서만 나온다 |
| 예비 시험 문제 | 학습용 문서에서 뽑되 정답 청크를 학습에서 뺀 문제. 5-4절의 경우에만 쓴다 |
| 상위 5개 진입률 | 정답 청크가 리랭커가 고른 최종 근거 5개 안에 든 문제의 비율. 이 실험의 대표 지표다 |
| 고칠 수 있는 문제 | 정답 청크가 후보 20개 안에 있는 문제. 리랭커는 후보 안의 순서만 바꾸므로 이 문제만 결과가 달라질 수 있다 |
| B, C, D, E | 비교하는 네 모델. 3-3절 표 참고 |

## 1. 왜 이 실험을 하는가

### 1-1. 출발점은 리랭커가 정답을 밀어낸 실패 2건이다

2026-08-13 에 리랭커와 하이브리드 검색을 기본값으로 켠 뒤에도 실패가 2건 남았다(재택 문항, 기간제 연차 문항). 두 실패 모두 리랭커가 정답 청크를 상위 5개 밖으로 밀어낸 것이다. 순위 융합(`rerank_fusion`)으로 풀려던 시도는 2026-08-12 에 반증됐다. 밀어내기를 줄이는 만큼 끌어올리기도 줄었기 때문이다. 남은 방법이 리랭커 파인튜닝이다(`docs/BACKLOG.md` §5).

### 1-2. 지금 평가셋으로는 파인튜닝 효과를 측정할 수 없다

2026-09-17 과 2026-09-18 에 `app/rank_trace.py` 로 정답 청크의 순위를 추적했다. 활성 26문항 중 고칠 수 있는 문제이면서 5위 밖인 문항이 1개뿐이었다. 한 문항의 무게는 0.038 이고, 이 저장소가 실측한 편차 폭은 0.032 다. 따라서 파인튜닝이 효과가 있어도 지금 평가셋에서는 전후 숫자가 거의 같게 나온다. 이 실험은 측정 틀(시험용 봇과 시험 문제)을 새로 만드는 일과 파인튜닝을 함께 한다.

### 1-3. 원래 두 실패는 지금 평가셋에 없다

재택 문항과 기간제 연차 문항은 V9 마이그레이션(2026-09-13)이 지운 옛 질문 세트에 있었다. 따라서 이 실험은 그 두 문항을 직접 고치는 것을 확인하지 않는다. 확인하는 것은 같은 종류의 실패(헷갈림 묶음 안에서 대상을 구분하지 못하는 것)가 줄어드는가이다.

### 1-4. 이 실험이 확인하려는 주장

**파인튜닝 모델은 학습에 쓰지 않은 문서에서도, 헷갈림 묶음 안의 정답 청크를 원본 모델보다 더 자주 상위 5개에 넣는다.**

이 주장을 고른 이유는 제품 구조다. 고객마다 다른 문서를 올리므로, 리랭커를 한 번 학습시켜 모든 고객에게 쓸 수 있어야 한다. 고객 문서마다 따로 학습시키는 방식은 학습 비용과 관리할 모델 수가 고객 수만큼 늘어난다.

## 2. 문서를 학습용과 시험용으로 가르는 방법

### 2-1. 가르는 단위는 문서다

학습과 시험을 청크 단위나 질문 단위로 가르면, 시험용 봇의 문서를 모델이 이미 본 상태가 된다. 그러면 1-4절의 주장(처음 보는 문서)을 확인할 수 없다. 따라서 문서 단위로 가르고, 시험용 봇에는 시험용 문서만 올린다.

### 2-2. 양쪽 모두에 헷갈릴 짝이 둘 이상 남아야 한다

리랭커의 일은 비슷한 후보 중에서 고르는 것이다. 시험용 봇에 재택 문서가 하나뿐이면, 리랭커는 대상을 읽지 않아도 재택 문서를 골라 정답을 맞힌다. 그러면 원본 모델도 맞히므로 전후 차이가 드러날 자리가 없다. 학습용 봇도 같다. 연습 문제에 헷갈리는 후보가 없으면 구분하는 법을 배울 수 없다. 따라서 헷갈림 묶음마다 학습용과 시험용 양쪽에 대상이 둘 이상 남도록 가른다.

### 2-3. 코퍼스를 세어 본 결과

2026-10-01 에 `ai-service/testdata/corpus/` 56개 문서를 사람이 읽고 셌다(코드로 세지 않았으므로 한두 칸 틀릴 수 있다).

- 헷갈림 묶음은 36개다.
- 묶음당 대상 수 분포: 15개 대상 묶음 2개, 13개 1개, 10개 3개, 8개 2개, 7개 2개, 6개 3개, 5개 3개, 4개 3개, 3개 9개, 2개 8개.
- 양쪽에 둘 이상씩 남기려면 대상이 4개 이상이어야 한다. 이 조건을 만족하는 묶음은 19개다. 대상이 2~3개인 17개 묶음은 원리적으로 이 규칙을 지킬 수 없다.
- 큰 묶음의 예: 재택 횟수(15), 건강검진 주기(15), 노트북 교체와 지급(13), 본인 결혼휴가(10), 기본 근무시간(10), 코어타임(10).

### 2-4. 본사 문서 11개는 한 덩어리로 움직인다

`docs/코퍼스-중복-감사-2026-09-18.md` 가 찾은 중복 27쌍을 이으면 아래 문서들이 하나로 연결된다. 이 문서들은 같은 규정을 거의 같은 문장으로 적는다. 따라서 한 문서가 학습용, 짝 문서가 시험용으로 가면 시험 문제의 답을 학습에서 본 것과 같아진다.

본사 덩어리: `01_정규직`, `05_복리후생`, `06_건강검진`, `07_경조사`, `08_징계`, `09_출장`, `12_FAQ`, `31_퇴직`, `32_노사협의회`, `취업규칙`, `휴가규정`.

`03_인턴` 도 식대 문장 하나로 이 덩어리와 겹친다. `10_보안` 과 `48_모바일` 도 비밀번호 규정 한 쌍으로 겹친다.

### 2-5. 분할 결정

| 쪽 | 대상 문서 |

`20` 번대에서 `49` 번대의 일반 문서(사내식당, 동호회, 교육 등)는 특정 대상을 두지 않는다. 시험용 봇에도 주제가 다른 문서가 섞여 있어야 실제 고객 봇과 비슷해진다. 따라서 일반 문서를 번호 순서로 번갈아 학습용과 시험용에 나눈다. 한 문서를 두 봇에 모두 올리지는 않는다. 다만 아래 짝은 같은 쪽에 둔다. 두 문서가 같은 대상에 대해 다른 값을 적어 코퍼스 안에서 서로 모순되기 때문이다.

## 3. 전체 흐름

### 3-1. 단계

1. 로컬 Spring 으로 계정 하나와 봇 두 개(학습용 봇, 시험용 봇)를 만들고, 2-5절과 2-6절의 분할대로 문서를 올린다. 봇 생성은 Spring 이 담당한다(`bots` 테이블 소유권). 기존 봇 1번은 건드리지 않는다. 봇 1번에는 W4 부터 이어온 평가 기록이 있기 때문이다.
2. Claude 가 연습 문제, 시험 문제, 예비 시험 문제를 쓴다(4절).
3. `app/finetune_data.py` 가 연습 문제마다 학습용 봇을 검색해 (질문, 정답 청크, 오답 청크 여러 개)를 만들고 파일로 저장한다(5-1절).
4. 시험용 봇에서 원본 모델로 먼저 잰다. 5-2절의 관문을 통과해야 학습을 시작한다.
5. 사용자가 코랩에서 학습 노트북을 실행하고 결과 zip 을 내려받는다(6절).
6. `app/export_reranker.py` 가 파인튜닝 모델을 ONNX fp32 와 INT8 로 내보낸다.
7. 시험용 봇에서 네 모델을 비교하고 5-3절의 규칙으로 판정한다.
8. 시험용 봇에서 B 와 D 의 전체충실성을 1회씩 잰다(5-5절).

### 3-2. 오답 예시는 검색이 가져온 틀린 후보에서 뽑는다

리랭커가 실제로 틀리는 경우는 검색이 가져온 비슷한 청크를 정답보다 위에 둘 때다. 따라서 오답 예시도 그 청크들이어야 한다. 무작위 청크를 오답으로 주면 구분이 너무 쉬워서 배울 것이 없다.

### 3-3. 비교하는 네 모델

| 이름 | 모델 | 실행 방식 | 이미 있는가 |
|---|---|---|---|
| B | 원본 모델 | 로컬 ONNX fp32 (`local`) | 있다 (2026-09-17) |
| C | 원본 모델 | 로컬 ONNX INT8 (`local_int8`) | 있다 (2026-09-17) |
| D | 파인튜닝 모델 | 로컬 ONNX fp32 (`local_ft`) | 새로 만든다 |
| E | 파인튜닝 모델 | 로컬 ONNX INT8 (`local_ft_int8`) | 새로 만든다 |

- 파인튜닝 전 기준은 Cloudflare 리랭커가 아니라 B 다. B 와 D 는 실행 환경이 같으므로, 두 결과의 차이는 파인튜닝 하나로만 생긴다.
- B 에서 D 로의 변화가 파인튜닝의 효과다. D 에서 E 로의 변화가 양자화의 손실이다. 이 표는 2026-09-17 의 A, B, C 비교표에 D 와 E 열을 더하는 모양이다.

## 4. 문제를 만드는 방법

### 4-1. 출제자는 Claude 하나다

연습 문제, 시험 문제, 예비 시험 문제는 모두 Claude 가 쓴다. 외부 모델(Gemini 질문 생성기)을 쓰지 않는 이유는 셋이다.

1. 리랭커는 우리가 한 번만 학습시킨다(1-4절). 따라서 고객 문서마다 연습 문제를 자동 생성할 필요가 없다.
2. Gemini 무료 등급은 모델당 하루 20회 한도가 있어 수백 개를 만들 수 없다.
3. 자동 생성 질문은 2026-09-18 검수에서 대상을 잘못 묻는 결함이 반복됐다(인턴 문서를 수습 직원으로 묻는 경우).

이 선택의 한계는 9절에 적는다.

### 4-2. 말투를 다섯 가지로 섞는다

실제 사용자의 질문은 말투가 제각각이다. 리랭커가 특정 말투에 기대지 않고 내용으로 고르도록, 모든 문제 파일에서 아래 다섯 말투를 고르게 섞고 문제마다 말투를 표시한다.

| 말투 | 예시 |
|---|---|
| 정중한 문장 | 자회사 직원은 재택근무를 주 몇 회까지 할 수 있나요? |
| 짧은 구어체 | 자회사도 재택 돼요? 몇 번? |
| 키워드만 | 자회사 재택 횟수 |
| 상황 설명형 | 이번에 자회사로 입사했는데 집에서 일하는 날이 일주일에 며칠인지 궁금해요 |
| 오타와 띄어쓰기 오류 | 자회사 재택근무 몇번까지되나요 |

### 4-3. 문제 수

| 파일 | 목표 수 | 출처 문서 |
|---|---|---|
| 연습 문제 | 300~400개 | 학습용 문서 |
| 시험 문제 | 60개 이상 | 시험용 문서 |
| 예비 시험 문제 | 약 30개 | 학습용 문서 |

대표 지표(상위 5개 진입률)는 생성 모델과 채점 모델을 부르지 않으므로 Cloudflare 뉴런이 거의 들지 않는다. 따라서 시험 문제를 기존 평가셋처럼 20~30개로 묶어 둘 이유가 없다. 문제 수를 늘려 한 문제의 무게를 줄인다.

### 4-4. 문제를 쓸 때 지키는 규칙

1. 시험 문제의 대부분은 헷갈림 묶음을 겨냥한다. 즉 질문에 대상(자회사, 시간제 등)이 들어가고, 같은 봇에 같은 주제를 다른 대상에 대해 규정한 문서가 있어야 한다.
2. 질문이 묻는 대상은 정답 청크의 대상과 같아야 한다. 2026-09-18 결함(인턴 규정을 수습 직원으로 묻기)을 되풀이하지 않는다.
3. 시험 문제는 시험용 봇 안의 문서만으로 답할 수 있어야 한다. 예를 들어 `04_파견` 은 보안 규정 `SEC-002` 를 `10_보안`(학습용)에 기대어 적는다. 그 규정을 묻는 문제는 시험용 봇 안에 답이 없으므로 쓰지 않는다.
4. `취업규칙` 과 `휴가규정` 의 청크는 정답 청크로 쓰지 않는다. 두 문서의 거의 모든 조항에 다른 문서의 쌍둥이 조항이 있어, 쌍둥이가 상위 5개에 들면 답은 맞는데 정답 청크는 빠진 것으로 집계되기 때문이다(`docs/코퍼스-중복-감사-2026-09-18.md`).
5. 정답 청크 본문은 청커가 실제로 만든 청크와 글자까지 같아야 한다. 기존 평가셋 도구(`app/eval_set_check.py`)가 쓰는 방식대로 문서를 다시 잘라 대조한다.
6. 사람(사용자)이 시험 문제 전체를 한 번 훑어본 뒤 확정한다.

## 5. 측정과 판정

### 5-1. 학습 데이터 만들기

`app/finetune_data.py` 가 연습 문제마다 학습용 봇에서 실제 검색 경로(벡터 검색, 하이브리드, 거리 컷)를 태워 후보 20개를 얻는다. 그중 정답 청크를 뺀 상위 청크 최대 7개를 오답 예시로 쓴다. 단, 아래 청크는 오답 예시에서 뺀다.

- 정답 청크의 중복 쌍둥이 청크. 쌍둥이는 같은 내용이므로 오답으로 가르치면 모델이 모순된 신호를 받는다.
- 시험 문제와 예비 시험 문제의 정답 청크(학습용 봇에 있는 예비 시험 문제의 정답 청크가 해당한다).

결과는 `ai-service/testdata/finetune/train_pairs.jsonl` 로 저장하고 커밋한다. 코랩 노트북은 이 파일 하나만 입력으로 받는다.

### 5-2. 학습 전 관문

학습을 시작하기 전에 시험용 봇에서 B 로 시험 문제를 잰다. **고칠 수 있는 문제이면서 정답 청크가 5위 밖인 문제가 시험 문제의 4분의 1 이상**이어야 학습을 시작한다. 이 조건을 만족하지 못하면 리랭커가 고칠 자리가 없는 시험이다. 그 경우 학습하지 않고 시험 문제를 다시 쓴다. 이 관문은 1-2절의 상황(고칠 자리가 1개뿐인 평가셋)을 학습 전에 막으려고 둔다.

### 5-3. 대표 지표와 판정 규칙

검색과 로컬 리랭커는 같은 입력에 대해 항상 같은 순위를 낸다(2026-09-17 실측). 따라서 같은 설정을 여러 번 반복해 평균낼 필요가 없고, 각 모델을 한 번씩 잰다. 결과의 불확실성은 반복 실행이 아니라 문제 선택에서 온다. 따라서 문제마다 B 와 D 의 결과를 짝지어 비교한다.

| 지표 | 정의 |
|---|---|
| 상위 5개 진입률 (대표) | 정답 청크가 최종 근거 5개 안에 든 문제 수 ÷ 전체 시험 문제 수 |
| 고칠 수 있는 문제 기준 진입률 | 같은 비율을 고칠 수 있는 문제만으로 계산한 값 |
| 좋아진 문제 수 | B 에서는 5위 밖, D 에서는 5위 안인 문제 수 |
| 나빠진 문제 수 | B 에서는 5위 안, D 에서는 5위 밖인 문제 수 |
| 정답 청크 평균 순위 | 고칠 수 있는 문제에서 정답 청크의 리랭킹 후 순위 평균 |

**판정 규칙 (결과를 보기 전에 정한다).**

- 좋아진 문제 수와 나빠진 문제 수에 양측 부호 검정을 한다. 부호 검정은 두 수가 동전 던지기처럼 반반으로 나올 확률을 계산한다. p 값이 0.05 미만이고 좋아진 문제가 더 많으면 **효과 있음**으로 판정한다. 예: 좋아짐 12개, 나빠짐 2개면 p 값이 약 0.013 이므로 효과 있음이다. 좋아짐 6개, 나빠짐 4개면 p 값이 약 0.75 이므로 효과 없음이다.
- p 값이 0.05 미만이고 나빠진 문제가 더 많으면 **악화**로 판정한다.
- 그 밖은 **구별되지 않음**으로 판정한다.
- 결과 보고에는 판정과 관계없이 나빠진 문제의 목록을 적는다. 2026-08-11 에 리랭커가 고친 문항 수만큼 다른 문항을 깨뜨려 응답률이 그대로였던 일이 있었다. 평균만 보면 그런 교환을 놓친다.

### 5-4. 따로 세는 문제

아래 두 종류의 문제는 리랭커가 결과를 바꿀 수 없으므로 B, C, D, E 에서 결과가 같다. 따라서 대표 지표와 별도로 개수를 적는다.

- 거리 게이트(`answerable_max_distance = 0.44`)나 거리 컷(`max_distance = 0.55`)이 근거를 모두 잘라 리랭커가 호출되지 않은 문제
- 정답 청크가 후보 20개 밖에 있는 문제

### 5-5. 파인튜닝이 효과 없을 때의 추가 측정

시험용 봇에서 판정이 효과 있음이 아니면, 원인은 두 가지 중 하나다.

1. 파인튜닝 자체가 실패했다 (학습 데이터가 부족하거나 나쁘다).
2. 파인튜닝은 됐지만 처음 보는 문서까지 일반화되지 않았다.

두 원인을 가르기 위해 학습용 봇에서 예비 시험 문제로 B 와 D 를 비교한다. 예비 시험 문제의 정답 청크는 학습 데이터에 한 번도 나오지 않지만, 그 문서는 학습에 쓰였다. 예비 시험 문제에서 효과가 있고 시험 문제에서 없으면 원인 2다. 둘 다 없으면 원인 1이다. 시험용 봇에서 효과 있음으로 판정되면 이 측정은 하지 않는다.

예비 시험 문제는 학습 데이터를 만들기 전에 써 둔다. 학습 데이터를 만든 뒤에 쓰면 그 정답 청크가 이미 학습에 쓰였을 수 있기 때문이다.

### 5-6. 전체충실성은 보조 자료다

시험용 봇에 시험 문제를 평가 질문으로 적재하고, B 와 D 로 평가를 1회씩 돌린다. 시험 문제 60개 기준으로 1회에 약 3,000 뉴런이 든다(문항당 약 50 뉴런, 2026-08-13 실측 기준). 이 저장소가 실측한 전체충실성 편차 폭이 0.032 이고 이 측정은 1회씩이므로, 전체충실성으로는 판정하지 않는다. "답변도 나아졌는가" 를 보여주는 보조 자료로만 적는다.

## 6. 학습 방법

### 6-1. 코랩에서 학습한다

학습은 코랩의 무료 GPU(T4)에서 한다. 사용자가 이렇게 결정했다(2026-10-01). 로컬 M4 Pro(24GB)에서도 학습이 가능한 크기지만, 코랩이 더 빠르다.

### 6-2. 노트북이 하는 일

노트북은 `ai-service/notebooks/train_reranker.ipynb` 로 저장소에 둔다. 칸마다 한국어 설명을 붙인다.

1. 라이브러리를 고정된 버전으로 설치한다.
2. 사용자가 `train_pairs.jsonl` 을 올린다. 노트북은 파일의 SHA-256 해시를 계산해 노트북에 적힌 값과 비교하고, 다르면 학습 전에 멈춘다. 다른 파일로 학습하는 실수를 막기 위해서다.
3. 연습 문제의 20%를 떼어 검증용으로 쓴다. 학습 반복 횟수(1, 2, 3 에폭 중 하나)는 이 검증용 문제의 성적으로 고른다. **시험 문제로 고르지 않는다.** 시험 문제 성적을 보고 설정을 고르면 시험 문제가 학습에 영향을 준 것이 되기 때문이다.
4. sentence-transformers 의 CrossEncoder 로 원본 모델(`BAAI/bge-reranker-base`)을 학습한다. 시작 설정은 학습률 2e-5, 배치 16, 질문당 오답 예시 최대 7개다.
5. 난수 씨앗을 고정한다. 다만 GPU 연산은 같은 설정에서도 결과가 조금 다를 수 있다. 그 사실을 결과 기록에 함께 적는다.
6. 학습된 모델과 학습 기록(설정, 씨앗, 라이브러리 버전, 입력 파일 해시, 걸린 시간, 검증용 성적)을 zip 하나로 묶어 내려받게 한다.

### 6-3. 사용자가 하는 일

1. 코랩에서 노트북을 연다(파일 → 노트북 업로드).
2. 런타임 유형을 T4 GPU 로 바꾼다.
3. 첫 칸이 띄우는 파일 선택 창에서 `train_pairs.jsonl` 을 고른다.
4. 런타임 → 모두 실행.
5. 마지막 칸이 띄우는 zip 을 내려받아 위치를 알려준다.

학습 시간은 재지 않았다. 입력이 질문 약 300~400개에 질문당 청크 8개 정도라 수 분에서 수십 분으로 추정한다. 세션이 끊기면 모두 실행을 다시 하면 된다. 실제로 오래 걸리면 그때 중간 저장을 추가한다.

### 6-4. 우리 서버로 가져오기

zip 을 `ai-service/models/` 아래에 풀고(이 폴더는 git 에 올라가지 않는다), `app/export_reranker.py` 로 ONNX fp32(`local_ft`)와 INT8(`local_ft_int8`)을 만든다. 내보내기 도구가 이미 하는 PyTorch 대비 등가 검증도 그대로 거친다.

## 8. 누출 검사

`app/finetune_split_check.py` 는 DB 와 외부 API 없이 파일만 읽고 아래를 확인한다. CI 의 기존 자체 점검 목록(`.github/workflows/ci.yml`)에 더한다.

1. `split.json` 의 시험용 문서가 학습용 목록에 없다. 한 문서가 양쪽에 있지 않다.
2. 시험 문제와 예비 시험 문제의 정답 청크 본문이 `train_pairs.jsonl` 에 정답으로도 오답으로도 나오지 않는다.
3. 중복 감사의 쌍둥이 문서 쌍이 학습용과 시험용으로 갈리지 않았다.
4. `취업규칙` 과 `휴가규정` 이 어떤 문제 파일에서도 정답 문서로 쓰이지 않았다.
5. 시험 문제의 정답 문서가 모두 시험용 문서이고, 연습 문제와 예비 시험 문제의 정답 문서가 모두 학습용 문서다.
6. `train_pairs.jsonl` 의 SHA-256 해시가 노트북에 적힌 값과 같다.

이 검사가 있어야 "학습 때 시험 문제를 본 것 아닌가" 라는 질문에 "CI 가 매번 확인한다" 고 답할 수 있다.

2. **처음 보는 문서의 범위가 같은 분야 안이다.** 56개 문서는 모두 한 가상 회사의 사내 규정이다. 이 실험은 다른 분야(병원 매뉴얼, 제품 설명서 등)의 문서에서 효과가 있는지 확인하지 않는다.
3. **코퍼스가 하나이고 리랭커 모델이 하나다.**
4. **코퍼스의 묶음 구조가 실제 고객 문서보다 깔끔하다.** 가상 코퍼스는 같은 주제를 대상별로 체계적으로 나눠 적는다. 실제 문서의 헷갈림은 이보다 불규칙할 수 있다.
5. **분할 근거가 손으로 센 결과다.** 2-3절 수치는 사람이 읽고 센 것이다. 누출 검사(8절)는 파일 간 관계만 확인하고 묶음 구조 자체를 다시 세지 않는다.
6. **대상이 2~3개인 헷갈림 묶음 17개는 양쪽 규칙을 지킬 수 없다.** 이 묶음들은 한쪽에만 짝이 남는다.
7. **GPU 학습은 완전히 재현되지 않을 수 있다.** 같은 입력과 씨앗에서도 결과 모델이 조금 다를 수 있다. 측정(검색과 로컬 추론)은 재현된다.
