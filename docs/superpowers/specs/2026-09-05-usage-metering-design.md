# 사용량 계량 — 설계

- 날짜: 2026-09-05
- 대상: `api/` (Spring 단독). **Python·위젯은 한 줄도 안 고친다.**
- 위치: 요금제 연동 4조각 중 **1번**

## 이 문서의 범위

요금제 연동은 독립적인 조각 넷이다.

| # | 조각 | 상태 |
|---|---|---|
| **1** | **계량 — 과금 대상 사건을 세어 계정별로 보여준다** | **← 이 문서** |
| 2 | 플랜·포함량 — 계정에 플랜을 붙이고 초과분을 계산한다 | 미착수 |
| 3 | 결제 수단 등록 — 토스페이먼츠 빌링키 발급·저장 | 미착수 |
| 4 | 청구 — 월말 마감, 금액 산정, 자동결제, 실패 처리 | 미착수 |

**이 문서는 1번만 다룬다.** 금액·플랜·결제는 나오지 않는다. 여기서 만드는 것은 *"이 계정이 이번 달에 무엇을 얼마나 썼는가"* 하나다.

과금 방식은 **정액 + 초과 사용량**으로 정했고, PG는 **토스페이먼츠 직접 연동, 테스트 키까지**다. 실결제는 사업자등록 심사가 필요해 범위 밖이며, 그 사실을 숨기지 않는다.

## 왜 계량이 먼저인가

`/pricing`은 이미 과금 방식을 **약속**해놨다.

> **답변 수** — 답하지 못한 질문은 세지 않습니다.
> 봇이 근거를 못 찾아 "담당자에게 문의해주세요" 로 넘긴 응답은 과금 대상이 아닙니다. 실제로 답을 만든 것만 셉니다.

그런데 **지금 아무것도 세지 않는다.** 스키마에 `plan`·`quota`·`usage` 개념이 하나도 없다. 셀 줄 모르는 상태에서 결제를 먼저 붙이면 청구할 금액을 계산할 수 없다.

그리고 이 약속은 지키기 쉬운 편이다 — `messages.is_fallback` 이 이미 있고, `conversations.channel` 이 `widget`/`test` 를 이미 가른다. **약속을 지킬 재료가 이미 있는데 쓰지 않고 있었다.**

## 무엇을 세는가 — 정책

| 사건 | 센다 | 근거 |
|---|---|---|
| 위젯 답변 (`channel='widget'`, `is_fallback=false`) | ✅ | 제품의 가치가 전달된 순간이다 |
| fallback 답변 | ❌ | `/pricing` 이 명시적으로 약속했다 |
| **관리자 테스트 채팅** (`channel='test'`) | ❌ | 아래 참조 |
| **평가 실행 — `completed` 만** | ✅ | 아래 참조 |
| 평가 실행 — `partial`·`failed` | ❌ | 아래 참조 |
| 답변 생성 실패 (Python 503) | ❌ | 답변 행이 아예 안 생기므로 자동으로 안 세어진다 |

**테스트 채팅을 세지 않는 이유.** LLM 비용은 똑같이 나간다. 그런데 이건 고객이 **자기 봇의 품질을 확인하려고** 쓰는 기능이다. 여기에 과금하면 "확인하면 돈이 나간다"가 되어 확인을 덜 하게 되고, 품질이 나쁜 채로 방치된 봇이 방문자를 만난다. `/pricing` 이 *"억지로 답하게 만들 이유가 회사 쪽에 생기지 않도록"* 이라고 쓴 것과 같은 논리다 — **품질 확인을 망설이게 만드는 과금도 같은 종류의 잘못이다.** 비용은 우리가 먹고, 남용은 과금이 아니라 별도 한도로 막는다(2번 조각).

**`partial`·`failed` 평가 실행을 세지 않는 이유.** 그 둘은 **측정이 안 된 실행**이다. 바로 앞 작업(PR #45)에서 "채점 실패를 `completed` 로 남기면 거짓 측정이 된다"는 이유로 `partial` 을 갈라놓았다. **재지도 못한 실행에 돈을 받으면 그 작업이 통째로 무의미해진다.**

> ⚠️ **"첫 리포트는 무료"는 여기서 구현하지 않는다.** 그건 플랜의 포함량 문제이지 계량의 문제가 아니다. 계량은 `completed` 실행을 전부 세고, 무료 몫을 빼는 것은 2번 조각이 한다. **세는 것과 깎아주는 것을 한 자리에서 하면, 나중에 무료 정책을 바꿀 때 과거 사용량까지 바뀐다.**

## 어떻게 세는가 — `usage_events` (append-only)

### 왜 조회 시 집계가 아닌가

가장 작은 방법은 `messages JOIN conversations` 를 그때그때 `COUNT` 하는 것이다. 새 테이블이 0개고 오늘 만들 수 있다. **그런데 두 가지가 깨진다.**

1. 🔴 **봇을 지우면 그 달 사용량이 사라진다.** `conversations`·`messages` 가 전부 `ON DELETE CASCADE` 로 `bots` 에 걸려 있다. 고객이 월말에 봇을 지우면 청구할 근거가 없고, 반대로 **고객에게 청구 내역을 증명할 수도 없다.**
2. 🔴 **과거 청구액이 흔들린다.** "테스트 채팅도 세자"로 정책을 바꾸면 **지난달 청구서 숫자까지 함께 바뀐다.** 이미 받은 돈과 화면이 어긋난다.

**그리고 이 문은 한 방향이다.** 조회 집계로 시작했다가 나중에 이벤트가 필요해지면, 그 사이 기간의 이벤트는 **소급해서 만들 수 없다** — 지워진 봇의 대화는 복구되지 않는다. 반대 방향은 언제든 된다. 비용 차이는 테이블 하나와 `INSERT` 한 줄인데, 잃는 것은 돈이 걸린 자리의 근거다.

### 스키마 (`V5__usage_events.sql`)

```sql
-- 과금 대상 사건의 <불변 원장>. 한 번 들어간 행은 고치지도 지우지도 않는다.
--
-- 🔴 bots 를 FK 로 걸지 않는다. 봇이 지워져도 그 달 사용 기록은 남아야 하기 때문이다.
--    청구 근거가 고객의 삭제 버튼 하나로 사라지면 안 된다.
--    대신 어느 봇이었는지는 bot_id 를 <값으로만> 들고 있는다(참조 무결성 없음, 화면 표시용).
CREATE TABLE IF NOT EXISTS usage_events (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  -- 청구 대상은 <계정>이다. 봇이 아니라 봇의 주인이 낸다.
  user_id     UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,  -- ⚠️ 결정과 그 반전은 아래 참조
  bot_id      UUID,                                 -- 표시용. FK 아님 — 봇이 지워져도 남는다
  kind        VARCHAR(20) NOT NULL,                 -- 'chat_answer' | 'eval_run'
  -- 이 사건을 만든 원본 행. 중복 기록을 막는 열쇠다.
  source_ref  UUID NOT NULL,
  -- 🔴 사건이 <실제로 일어난> 시각이다. 기록한 시각이 아니다.
  --    평가 실행은 나중에 메꾸므로(아래) 둘이 다를 수 있고, 청구 기간을 가르는 것은 이쪽이다.
  occurred_at TIMESTAMPTZ NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  -- 🔴 멱등성의 전부다. 같은 원본으로 두 번 세지 않는다.
  --    평가 실행 메꾸기가 매 조회마다 도는데, 이 제약이 없으면 볼 때마다 사용량이 늘어난다.
  CONSTRAINT uq_usage_source UNIQUE (kind, source_ref)
);

-- 청구는 언제나 "이 계정의 이 기간"으로 조회한다. 그 모양 그대로 인덱스를 만든다.
CREATE INDEX IF NOT EXISTS idx_usage_user_time ON usage_events (user_id, occurred_at);
```

**`user_id` 는 `ON DELETE CASCADE` 다 — 이 저장소의 다른 테이블과 같다. 그런데 이 결정은 구현 중에 한 번 뒤집혔다.** 처음에는 이 문서가 적던 대로 CASCADE 를 빼려 했다 — "계정을 지우면 청구 근거가 함께 사라지면 안 된다"는 논리였고, "청구가 끝나지 않은 계정은 지울 수 없다"를 DB 가 강제해주는 그림이 맞아 보였다.

그런데 구현하고 보니 그 방어가 지키는 기능(계정 삭제)이 **이 제품에 아직 존재하지 않았다.** 없는 기능을 위한 방어였던 반면, 대가는 즉시 실재했다 — 통합 테스트가 전부 `userRepository.deleteAll()` 로 정리하는데 Postgres 컨테이너를 공유하다 보니, 계량된 답변이 하나라도 있으면 FK 가 그 정리를 막아 **이 기능과 전혀 무관한 테스트들이 깨졌다.** 미래의 있지도 않은 기능을 지키려다 지금 있는 테스트를 매번 부수는 거래는 손해라 CASCADE 로 되돌렸다.

이 설계가 실제로 지키려는 것 — "봇을 지워도 청구 근거는 남는다" — 은 CASCADE 여부와 무관하다. 그건 아래 `bot_id` 에 FK 를 걸지 않은 것이 담당하고, 그 결정은 그대로다. 계정 삭제 기능이 실제로 생기면, 그때 "미청구 계정은 못 지운다"를 DB 제약이 아니라 애플리케이션 로직으로 다시 만들면 된다.

**`quantity` 컬럼을 두지 않는다.** 지금 세는 두 가지는 전부 "한 건이 한 번"이다. 토큰 수 같은 다른 단위가 필요해지면 그때 `kind` 를 늘리거나 컬럼을 더한다. 쓰지 않을 컬럼을 미리 두면 그 값이 무엇이어야 하는지를 매번 고민하게 된다.

## 쓰기 경로 ① — 채팅 답변

`ChatTurnStore.saveAnswer(...)` 가 이미 `@Transactional` 안에서 답변 행을 저장한다. **같은 트랜잭션에 한 문장을 더한다.**

```sql
INSERT INTO usage_events (user_id, bot_id, kind, source_ref, occurred_at)
SELECT b.user_id, c.bot_id, 'chat_answer', :messageId, now()
  FROM conversations c
  JOIN bots b ON b.id = c.bot_id
 WHERE c.id = :conversationId
   AND c.channel = 'widget'
   AND :isFallback = false
```

이 한 문장이 네 가지를 동시에 한다.

- **청구 대상 해결** — 위젯 채팅에는 로그인한 사용자가 없다. 대화 → 봇 → 주인으로 거슬러 올라가 **봇의 주인**을 찾는다.
- **테스트 채팅 제외** — `channel='test'` 면 `SELECT` 가 0행이라 아무것도 삽입되지 않는다.
- **fallback 제외** — 같은 방식으로 0행이 된다.
- **원자성** — 답변 저장과 같은 트랜잭션이라 **"답변이 남았는데 계량이 안 된" 상태가 존재할 수 없다.** 반대도 마찬가지다.

🔴 **두 제외 조건을 모두 SQL 안에 둔 것이 핵심이다.** 호출부에 `if (isFallback) return;` 을 두고 채널만 SQL 로 거르면 **과금 정책이 Java 와 SQL 두 곳에 나뉜다.** 이 저장소가 반복해서 겪은 부류다 — 규칙이 두 곳에 있으면 한쪽만 고쳐진다. `saveAnswer` 는 이미 `isFallback` 을 인자로 받고 있으므로 그대로 바인딩하면 된다. **"무엇이 과금되는가" 를 알고 싶으면 이 문장 하나만 읽으면 된다.**

> ⚠️ **`saveAnswer` 는 `getReferenceById` 로 프록시만 쓰고 있다**(SELECT 를 아끼려고). 위 문장은 네이티브 쿼리라 그 최적화를 건드리지 않는다 — 엔티티를 새로 읽지 않는다.

## 쓰기 경로 ② — 평가 실행 (메꾸기)

**평가 실행이 끝나는 것은 Python 이 안다.** `eval_runs.status` 를 `completed` 로 바꾸는 것이 Python 이고, 과금은 Spring 소유다. Python 이 `usage_events` 에 쓰면 테이블 소유권 원칙이 깨진다(`AGENTS.md` 소유권 표).

그래서 **Spring 이 나중에 메꾼다.** 사용량을 읽기 직전에 한 번 돌린다.

```sql
INSERT INTO usage_events (user_id, bot_id, kind, source_ref, occurred_at)
SELECT b.user_id, r.bot_id, 'eval_run', r.id, r.created_at
  FROM eval_runs r
  JOIN bots b ON b.id = r.bot_id
 WHERE b.user_id = :userId
   AND r.status = 'completed'
ON CONFLICT (kind, source_ref) DO NOTHING
```

- **멱등하다.** 몇 번을 돌려도 결과가 같다. `ON CONFLICT` 가 그것만 한다.
- **`occurred_at` 은 `r.created_at`** 이다. 메꾼 시각이 아니라 **실행이 시작된 시각**이 청구 기간을 가른다. 8월 31일에 시작한 실행을 9월에 메꿨다고 9월분으로 청구하면 안 된다.
- **화면을 안 봐도 기록된다** — 폴링에 얹지 않은 이유다. 폴링에 얹으면 아무도 대시보드를 안 열면 계량이 안 된다.

> ⚠️ **처음엔 여기가 열린 구멍이라고 봤다 — 반증됐다.** 평가 실행은 `eval_runs` 가 지워지면(봇 삭제) 메꾸지 못한 것이 사라질 수 있고, 채팅 답변과 달리 조회 시점 메꾸기라 원자적이지 않다. 이 창을 좁히려면 **4번 조각(청구)의 마감 시점 처리가 필요하다**고 판단해 미뤘었다. 그런데 실제로 닫아야 할 창은 "마감"이 아니라 "삭제" 하나였다 — `BotService.deleteBot` 이 실제 삭제 전에 `usageEventRepository.backfillEvalRuns(userId)` 를 **같은 트랜잭션 안에서** 한 번 더 부르는 한 줄로 끝난다. 청구 기간을 마감하는 별도 메커니즘은 필요 없었다. 미뤘던 이유(period-close 가 필요하다)가 틀렸던 것이다.

## 기간과 시간대

**기간 경계는 KST(`Asia/Seoul`) 달력 월**이다. 국내 서비스이고 청구서를 읽는 사람이 한국에 있다.

```sql
WHERE occurred_at >= (:month || '-01')::timestamp AT TIME ZONE 'Asia/Seoul'
  AND occurred_at <  ((:month || '-01')::timestamp + INTERVAL '1 month') AT TIME ZONE 'Asia/Seoul'
```

`occurred_at` 이 `TIMESTAMPTZ` 라 저장은 UTC 로 되고 경계만 KST 로 잡는다. **컬럼을 `TIMESTAMP` 로 두면 이 계산이 조용히 틀린다** — 9월 1일 오전 8시 KST 사건이 8월분으로 세어진다.

## API 와 화면

**`GET /api/usage?month=YYYY-MM`** (생략하면 이번 달) — 인증 필요, `@AuthenticationPrincipal` 로 받은 `userId` 로만 조회한다. 쿼리 파라미터로 남의 `userId` 를 받지 않는다.

```json
{ "month": "2026-09",
  "chatAnswers": 128,
  "evalRuns": 3,
  "periodStart": "2026-09-01T00:00:00+09:00",
  "periodEnd": "2026-10-01T00:00:00+09:00" }
```

호출되면 **먼저 평가 실행을 메꾸고** 나서 센다. 순서가 반대면 방금 끝난 실행이 다음 조회까지 안 보인다.

**화면은 `/dashboard` 에 카드 하나.** 봇별이 아니라 **계정 단위**이므로 봇 화면이 아니라 대시보드가 맞는 자리다. 보여줄 것은 이번 달 답변 수와 평가 실행 수, 그리고 **"금액은 아직 없습니다"** 한 줄 — `/pricing` 이 이미 그렇게 말하고 있고, 여기서만 금액이 있는 척하면 거짓말이 된다.

## 검사

**통합 테스트** (`UsageIntegrationTest`, 진짜 톰캣 + 진짜 PostgreSQL):

1. 위젯 답변 1건 → `chatAnswers` 가 1 이다
2. **fallback 답변은 세지 않는다** — 답변은 저장되는데 사용량은 0 이다
3. **테스트 채팅(`channel='test'`)은 세지 않는다** — 같은 봇에 위젯 1건·테스트 1건이면 1 이다
4. **`completed` 평가 실행만 센다** — `completed`·`partial`·`failed` 를 하나씩 넣고 1 이 나온다
5. **메꾸기가 멱등하다** — 사용량 조회를 3번 하면 `evalRuns` 가 3 이 아니라 1 이다
6. **계정 격리** — 남의 계정 사용량이 내 숫자에 섞이지 않는다
7. **봇을 지워도 이미 센 것은 남는다** — 답변 후 봇 삭제, 사용량은 그대로다 (이 설계의 존재 이유이므로 반드시 있어야 한다)
8. **기간 경계** — 9월 1일 00:00 KST 직전·직후 사건이 각각 8월·9월로 갈린다

3·4·5·7 이 이 설계의 핵심 주장이라 하나라도 빠지면 안 된다.

## 한계 — 알고 남기는 것

- ✅ ~~평가 실행 메꾸기는 원자적이지 않다.~~ **구현에서 닫혔다.** `BotService.deleteBot` 이 실제 삭제 직전, 같은 트랜잭션 안에서 한 번 더 메꾼다(멱등이라 안전하다). "4번 조각의 마감이 필요하다"던 예상은 틀렸다 — 필요했던 건 삭제 경로의 한 줄뿐이었다.
- **`bot_id` 에 참조 무결성이 없다.** 봇이 지워지면 화면에 "삭제된 봇" 으로 보인다. 의도한 것이다 — 무결성을 걸면 청구 근거가 삭제에 딸려 사라진다.
- **과거 데이터는 세어지지 않는다.** 이 기능 이전의 답변에는 이벤트가 없다. 채팅은 소급이 불가능하고(정확히는 `messages` 로 만들 수 있지만 이미 지워진 봇의 것은 못 만든다), 평가 실행은 메꾸기가 과거 것까지 전부 집는다. **이 비대칭을 화면에 적을지는 2번 조각에서 정한다.**
- **금액이 없다.** 이 조각은 개수만 센다. 단가·플랜·포함량·초과 계산은 전부 2번이다.
- **동시성.** 같은 답변이 두 번 저장되는 경로는 없지만, 만약 생기면 `uq_usage_source` 가 막는다. 메꾸기가 동시에 두 번 돌아도 마찬가지다.

## 다음 조각과의 경계

이 조각이 **끝나는 지점**은 `GET /api/usage` 가 정확한 개수를 돌려주고 대시보드가 그것을 보여주는 곳이다.

2번 조각이 **시작하는 지점**은 그 개수에 플랜을 곱하는 곳이다. `usage_events` 는 그때 **읽기만** 한다 — 플랜이 바뀌어도 과거 이벤트는 손대지 않는다. 그게 이 테이블을 append-only 로 둔 이유다.
