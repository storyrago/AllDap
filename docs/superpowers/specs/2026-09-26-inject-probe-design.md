이어받는다. 핸드오프 [`handoff-2026-09-25.md`](../handoff-2026-09-25.md) §5 가 지시한 슬라이스다.

## 1. 왜 하나

2026-09-18 에 q3 한 문항에서 이런 일이 있었다. 답변 문자열을 고정하고 근거 목록에
청크 327(`56_시간제근로자` 의 근무시간 절) 하나가 끼자 채점자 충실성이 **1.0 ×10 → 0.0 ×10** 이
됐다. 정답 청크 27 은 그대로 3번째 자리에 있었다
(`docs/superpowers/plans/2026-09-18-eval-set-difficulty-results.md` §5).

남은 질문은 둘이다.

1. **q3 만의 일인가, 일반적인가.** 한 문항으로는 모른다.
2. **무엇에 약한가.** 근거의 <장수>가 늘어서인가, <헷갈리게 비슷한 내용>이 들어와서인가.

사람 라벨 44건(2026-09-25)이 나온 지금이 할 때다. 출발점이 "확실히 맞는 답안" 이어야
점수가 떨어졌을 때 그것을 채점자 실수라고 말할 수 있는데, 그 판정을 사람 라벨이 해준다.

### 1-1. 이 슬라이스가 재는 것은 <채점자> 하나다

채점자와 생성 모델은 같은 근거 목록을 받는다. 생성 쪽까지 재면 검색 설정(`top_k` ·
`max_distance`)의 근거가 되지만, 이번에는 **채점자만** 잰다. 이유 둘:

- **새 답변의 정오를 판정할 자가 없다.** 채점자에게 맡기면 "채점자가 무관한 청크에 약하다" 를
  재는 중이라 순환이고, 사람이 보려면 라벨링을 또 해야 한다. 생성은 `temperature=0` 에서도
  흔들린다고 실측돼 있어(2026-08-11) 조건마다 반복도 필요하다.
- **이번 결과가 다음 탐침을 싸게 만든다.** "몇 장째부터 무너지나" 를 알면 생성 쪽은 그 근처만
  재면 된다.

## 2. 대상 문항: 38건

`testdata/judge_labels.json` 44건 중 **사람 1.0 · 채점자 1.0** 인 것만 쓴다.
사람 1.0 이 40건이고, 그중 채점자가 0.5 를 준 2건(q70 · q59, AGENTS.md "남은 불일치")을 뺀다.

🔴 **왜 이것만인가.** 답변은 끝까지 고정된다. 그러니 출발점이 "맞는 답을 맞다고 채점한 상태"
이면, 주입 뒤 점수가 떨어진 것은 **정의상 채점자 실수**다. 출발점이 0.5 나 0.0 이면 "원래
틀린 답을 뒤늦게 잡은 것" 과 구분할 수 없다.

## 3. 조건: 문항당 채점 8회

| 조건 | 근거 | 보는 것 |
|---|---|---|
| `base` | 원래 5장 | 지금 다시 채점해도 1.0 인가 |
| `near+1` · `near+2` · `near+4` | 원래 5장 **끝에** 비슷한 청크 | 비슷한 내용에 약한가, 몇 장째부터인가 |
| `far+1` · `far+2` · `far+4` | 원래 5장 **끝에** 딴 얘기 청크 | 대조군. 장수만 늘어도 약한가 |
| `near+1@front` | 비슷한 청크 1장을 **1번 자리에** | 자리가 중요한가 |

### 3-1. 더하기이지 바꿔 끼우기가 아니다

원래 5장을 하나도 빼지 않는다. 바꿔 끼우면 "엉뚱한 종이가 들어와서" 와 "원래 종이가 빠져서" 가
섞인다. 2026-09-18 에 조건 C(A ∩ B)를 따로 둔 것도 이 둘을 가르기 위해서였다.
약점: 실제 서비스는 늘 5장이라 6장 이상은 현실에 없다. 다만 `+1` 은 q3 에서 실제로 일어난
일과 같은 모양이다.

### 3-2. 끝에 붙이는 이유, 그리고 맨 앞 조건 하나

끝에 붙이면 원래 5장의 **번호가 그대로**다(`judge.score` 는 `[근거 1]`, `[근거 2]` 로 번호를
매긴다). 정답이 "근거 3" 이면 계속 "근거 3" 이다. 바뀐 것이 주입된 청크뿐이다.
약점은 채점자가 앞쪽을 더 본다면 끝에 붙인 결과가 문제를 작게 잡는다는 것이다.
그래서 `near+1@front` 한 조건만 추가해 이 의문을 싸게 닫는다(번호가 밀리는 변수가 함께 섞인다는
것은 알고 쓴다).

### 3-3. 쌓아 올린다: `+1 ⊂ +2 ⊂ +4`

`+2` 는 `+1` 에 한 장을 더 얹은 것이다. 점수가 처음 무너지는 조건에서 **바로 그 사이에 들어온
청크**가 범인으로 좁혀진다.

### 3-4. `base` 를 다시 재는 이유

DB 의 1.0 은 몇 주 전 점수다. 그사이 Cloudflare 가 모델을 바꿨을 수 있다. `base` 가 1.0 이
아닌 문항은 **탐침 집계에서 빼고 따로 적는다.** 안 그러면 "끼워서 떨어졌다" 와 "원래 떨어져
있었다" 가 섞인다. 38번의 `base` 는 재현성 확인도 겸한다.

### 3-5. 조건당 1회

채점자 온도는 0 이고(`judge_temperature = 0.0`), 2026-09-18 에 같은 입력 10회가 전부 같은
점수였다. 반복하지 않는다. ⚠️ 그 확인은 두 입력에서였으므로 `base` 가 그 가정을 38건으로 넓힌다.

## 4. 주입할 청크를 고르는 법

두 종류 모두 **그 문항의 원래 5장과 정답 문서의 청크는 제외**한다. 정답 문서는
`eval_questions.source_chunk_id` 가 속한 문서다. 후보 모집단은 **그 봇의 전체 청크**다.
(대상 38건은 전부 원래 근거가 정확히 5장이다. 2026-09-26 에 라벨 파일로 확인했다)

### 4-1. `near` (비슷한 동네)

**질문과의 벡터 거리가 가까운 순**으로 고른다. 그리고 **거리 컷 `max_distance`(0.55) 안에
드는 것만** 쓴다.

- **벡터 거리만 쓰는 이유.** 실제 검색은 벡터 · 키워드 RRF 와 리랭커를 거쳐 순위가 복잡하다.
  리랭커를 부르면 비용이 들고, 무엇보다 "비슷하다" 의 정의가 한 줄로 설명되지 않는다.
- **컷 안만 쓰는 이유.** 컷 밖 청크는 실제 서비스에서 근거에 절대 들어오지 않는다.
- **4장이 안 차는 문항**은 있는 만큼만 쓰고 보고서에 적는다. 없는 조건은 채점하지 않는다.
- 질문 임베딩은 문항마다 1회(`retriever.embed_one`). 비용은 무시할 수준이다.

### 4-2. `far` (딴 얘기)

그 질문에 대한 벡터 거리 순위가 **아래쪽 절반**인 청크 중에서 무작위로 4장을 뽑고, 뽑힌
순서대로 `+1` · `+2` · `+4` 에 쌓는다.
**씨앗값을 `question_id` 로 고정**해 다시 돌리면 같은 청크가 나온다.

### 4-3. 위험: `near` 가 사실은 무관하지 않을 수 있다

이 코퍼스에는 쌍둥이 문서가 있다(`docs/코퍼스-중복-감사-2026-09-18.md`). `near` 로 고른 청크가
**답을 뒷받침하거나 반박할** 수 있다. 그러면 "엉뚱한 종이" 가 아니다.

전부 미리 사람이 보기엔 150장이 넘는다. 그래서 **점수가 떨어진 경우에 들어간 청크만** 사람이
본다. 보고서가 그 목록을 뽑고, 사람이 결과 파일에 `무관` / `모순` / `뒷받침` 중 하나를 적는다.
보고서는 셋을 **따로** 센다. "진짜 무관한데 떨어졌다" 만이 채점자의 약점이다.

## 5. 만드는 것

| 파일 | 하는 일 |
|---|---|
| `app/eval_cases.py` (있음) | 박제된 케이스 복원. 그대로 쓴다 |
| `app/judge.py` (있음) | **한 줄도 고치지 않는다.** 운영 평가와 같은 채점자여야 결과가 의미 있다 |
| `app/inject_probe.py` (새) | `run` · `report` 두 하위 명령 |
| `app/inject_probe_check.py` (새) | CI 에서 도는 자체 점검. DB · 외부 API 없음 |
| `testdata/inject_probe_results.jsonl` (새, 커밋) | 채점 한 번에 한 줄 |

### 5-1. `run`

```
cd ai-service
.venv/bin/python -m app.inject_probe run --bot-id 1
```

1. `load_cases()` + `judge_labels.json` → 38건
2. 문항마다 주입 청크 선택 → 조건 8개 조립
3. 결과 파일에 이미 있는 `(case_id, condition)` 은 **건너뛴다**
4. `judge.score` 호출 → **한 번 부를 때마다 즉시 한 줄 추가**(`flush`)

🔴 **이어 돌리기가 필수인 이유는 비용이다.** 약 300회, 약 8,000 뉴런으로 하루 한도(10,000)에
가깝다. 한도에 걸려 중간에 죽어도 그때까지의 결과가 남고, 다음 날 같은 명령으로 이어간다.

한 줄의 모양:

```json
{"case_id": "…", "question_id": 3, "condition": "near+2",
 "injected": [{"chunk_id": 327, "filename": "56_시간제근로자.md", "distance": 0.41}],
 "faithfulness": 0.0, "relevancy": 1.0, "reason": "…",
 "review": null}
```

- 🔴 **채점 실패는 `"faithfulness": null` 이다. 0점이 아니다.** 이 저장소의 "낸 버그" 표 다섯
  번째가 정확히 이것(채점 실패를 0점으로 환산)이었다. 보고서는 `못 잼` 으로 따로 센다.
- `review` 는 사람이 채운다(§4-3). `run` 은 이 칸을 건드리지 않는다.

### 5-2. `report`

외부 API 를 부르지 않는다. 결과 파일만 읽는다.

1. **조건별 분포**: 1.0 / 0.5 / 0.0 / 못 잼 개수
2. **문항별 붕괴 지점**: 각 종류에서 처음 1.0 미만이 된 조건
3. **자리 비교**: `near+1` vs `near+1@front`
4. **떨어진 건 목록**: 들어간 청크 · 채점자 사유 · `review` 값. `review` 가 빈 건이 있으면
   "사람 확인 필요 N건" 을 찍는다
5. **`base` 가 1.0 이 아닌 문항**: 집계에서 뺐다는 사실과 그 목록

### 5-3. `inject_probe_check` (CI)

순수 함수만 검사한다.

- 조건 조립: 끝에 붙이면 원래 5장의 순서 · 번호가 그대로인가, `@front` 는 1번 자리인가
- 쌓기: `+1` 의 청크가 `+2` 의 앞부분과 같은가
- 선택: 원래 5장 · 정답 문서 청크가 결과에 없는가, `near` 가 컷 밖을 고르지 않는가,
  `far` 가 같은 씨앗에서 같은 결과를 내는가
- 이어 돌리기: 이미 있는 키를 건너뛰는가
- 집계: `null` 이 0점으로 세지지 않는가

`ci.yml` 에 한 줄 추가한다.

## 6. 결과 해석 (돌리기 <전에> 정해둔다)

돌리고 나서 해석을 고르면 원하는 결론을 고르게 된다. 그래서 여기 못박는다.
"떨어졌다" 는 `review = 무관` 인 건만 센다.

| 나온 모양 | 뜻 |
|---|---|
| `far` 에서도 떨어진다 | 내용이 아니라 **장수(길이)** 에 약하다 |
| `near` 에서만 떨어진다 | **헷갈리게 비슷한 내용**에 약하다. 검색 설정과 직결된다 |
| 둘 다 38건 중 1건 이하 | q3 는 드문 사례다. 이 방향의 채점 왜곡은 작다 |
| `@front` 에서만 떨어진다 | 끝에 붙인 본 실험은 문제를 작게 잡았다 |

⚠️ 이 표의 칸들은 서로 배타적이지 않다. 여러 칸이 동시에 맞으면 전부 적는다.

### 6-1. 모순 청크로 떨어진 것 (2026-09-26 보강, 본 실행 <전>)

1건 시험 실행(q58)에서 `near` 1·2위가 **같은 질문에 다른 숫자로 답하는 청크**였다
("연구직 징계는 다섯 가지" · "자회사 징계는 세 가지", 정답은 네 가지). 이 코퍼스는
같은 주제 · 다른 대상 문서를 일부러 넣었으므로 `near` 는 대개 이런 청크를 고른다.
그러면 `near` 의 하락은 대부분 `review = 모순` 이 되고, 위 표만 보면 "비슷한 내용에는
거의 안 떨어진다" 로 읽힌다. 그래서 결과를 보기 전에 여기서 정한다.

- **`review = 모순` 인 하락도 따로 센다.** 위 표와 섞지 않는다.
- **그것도 채점자 오류다.** 충실성은 "답변이 한 말이 근거에 있는가" 만 본다. 정답 청크가
  그대로 있으므로 모순 청크가 하나 끼어도 답은 여전히 근거에 있다.
- **다만 무관 청크 약점과는 다른 부류다.** "근거끼리 말이 다르니 조심했다" 는 변호의 여지가
  있다. 그래서 한 칸으로 합치지 않는다.

| 나온 모양 | 뜻 |
|---|---|
| `near` 하락이 대부분 `모순` 이다 | 채점자는 **모순 청크**에 약하다. 무관 청크 약점과는 따로 적는다 |
| `near` 하락에 `무관` 도 적지 않다 | 위 표의 "헷갈리게 비슷한 내용" 칸이 그대로 성립한다 |

`review = 뒷받침` 인 하락은 채점자 약점으로 세지 않는다(답을 뒷받침하는 청크가 들어와 점수가
떨어졌다면 그것은 다른 현상이고, 나오면 사례로만 적는다).

🔴 **B(모순 청크를 미리 걸러내기)는 택하지 않았다.** 사람이 150장 넘게 봐야 하고, 실제
검색에서 top5 에 끼는 것이 바로 이런 청크라 걸러내면 현실과 멀어진다.
