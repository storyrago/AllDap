# 부하테스트 PR 4b 설계: S4 장애 주입 (2026-09-11)

시리즈 전체 설계는 `2026-09-10-loadtest-design.md`, 앞 슬라이스는
`2026-09-11-loadtest-pr4a-s3-ratelimit-design.md` 다. 조사 결과는
`docs/HANDOFF-2026-09-11.md` §4 다.

**핸드오프 §4 안에 서로 모순되는 서술이 있어 정정한다**(§2). 그 정정이 이 PR 의 1순위
가설 크기를 바꾸므로 설계 앞쪽에 둔다.

## 목적

**Python 이 고장났을 때 Spring 이 약속한 대로 실패하는가.** 코드와 주석이 단언하는 것 셋을
부하 아래서 재서 확인한다.

| 약속 | 어디에 적혀 있나 | 틀리면 무슨 일이 나나 |
|---|---|---|
| 재시도는 **연결 실패에만** | `AiServiceClient.isConnectFailure` | 5xx 에 재시도가 돌면 **LLM 이 두 번 과금**되고 문서 행이 중복된다 |
| 서킷이 **5회 연속** 실패에 열리고 **30초** 뒤 닫힌다 | `application.yaml` `circuit-*` | Python 장애가 Spring 장애로 번진다 |
| 급속 503 과 느린 503 이 **지표에서 갈린다** | `AiServiceMetrics` (#112) | 운영자가 "왜 503 인가" 를 못 답한다 |

그리고 넷째, **약속이 아예 없는 자리 하나**를 드러낸다: 리랭킹 실패는 200 으로 나가고
어떤 숫자에도 안 잡힌다(§4-F3).

개선은 하지 않는다(PR 5). 발견한 결함도 고치지 않는다(§8).

## 1. 구성

```
 [k6] 맥 호스트   POST /api/bots/{botId}/chat    ← 관리자 채팅. rate limit 이 없다
   ↓                                                 (S3 와 정반대 이유로 이 경로를 쓴다)
 Spring :8080  (gradle bootRun -Ploadtest)
   │   └ :8081/actuator/prometheus
   ├─→ Postgres (docker)
   └─→ Python :8001  (uvicorn, 로그를 파일로)
         └─→ 가짜 CF :9001   ← 여기에 장애 주입 제어면을 붙인다
 Prometheus :9090 → Grafana :3001
```

**S2 와 같은 경로·같은 스크립트 구조를 쓴다.** 바뀌는 것은 부하 프로파일과 주입뿐이라
`s2_breakpoint.js` 를 복사해 고치는 것이 아니라 **공통 부분을 그대로 재사용**한다(§5).

## 2. 🔴 핸드오프 §4 의 "6.2초" 를 정정한다

핸드오프 §4 는 같은 절 안에서 두 가지를 말한다.

- 장애 후보 표: *"포트가 닫혀 `ConnectException` **즉시**. 3초 타임아웃은 안 걸린다"*
- 1순위 가설: *"각 요청이 connect 3s + 200ms + connect 3s 로 **6.2초씩** 톰캣 스레드를 붙잡고"*

**둘은 양립하지 않는다.** 앞이 맞다. uvicorn 을 죽이면 8001 을 듣는 프로세스가 없으므로
localhost 로는 커널이 즉시 RST 를 돌려준다. `connect-timeout: 3s` 는 **SYN 이 드롭될 때**만
걸리고, 그건 프로세스 종료가 아니라 방화벽 DROP 규칙이 있을 때다.

**실제로는 요청당 `재시도 지연 200ms` 정도만 남는다** (`retry-max-attempts: 2` 이므로
연결 시도 2회 + 그 사이 `Thread.sleep(200ms)` 1회).

### 이 정정이 바꾸는 것

**1순위 가설의 크기가 30배 줄어든다.** "HALF_OPEN 에서 80 스레드가 6.2초씩 물린다" 는 그림은
이 주입으로는 안 나온다. 대신 **"30초마다 서킷이 열렸다 닫혔다 하는 톱니"** 는 그대로 재현된다.

→ **가설을 다시 쓴다.** 재는 것은 "스레드가 얼마나 오래 물리나" 가 아니라
**"`allowRequest()` 가 HALF_OPEN 에서 동시 요청을 몇 건 통과시키나"** 다.
`state()` 는 30초가 지나면 HALF_OPEN 을 돌려주고 `allowRequest()` 는 OPEN 이 아니면 전부 통과시키므로,
**그 순간 in-flight 전부가 Python 을 두드린다.** 통과 건수는 VU 수만큼이다.

판정 신호는 `alldap_ai_circuit_transition_total{to="open"}` 이 **주입 시간을 30으로 나눈 값만큼**
올라가는 것이다. 1회가 아니라 반복이면 톱니가 실재한다.

🔴 **6.2초 그림을 재려면 SYN 드롭(`pfctl`)이 필요하고, 그건 범위 밖이다.**
SIGSTOP 을 뺀 것과 같은 이유다(§8). 결과 문서에 "이 정정" 과 함께 남긴다.

## 3. 원칙: 주입 사이에 서킷이 닫힌 것을 확인하고 넘어간다

운영 코드에 서킷 리셋 경로가 없다. `AiServiceCircuitBreaker.reset()` 은 테스트 전용이고,
**닫는 유일한 방법은 30초가 지난 뒤 성공 한 건**이다(`recordSuccess` 가 `openedAtNanos` 를 되돌린다).

→ 각 주입 사이에 **회복 구간**을 둔다. 조건은 시간이 아니라 **상태**다.

```
주입 해제 → 1 VU 로 성공 한 건을 만든다 → alldap_ai_circuit_state == 0 을 확인 → 다음 주입
```

시간(예: 40초 대기)으로 갈음하지 않는다. 그러면 **닫혔는지 모른 채 다음 판을 시작**하게 되고,
앞 단계의 서킷이 다음 단계 숫자를 오염시킨다. 확인에 실패하면 **그 자리에서 중단**한다.

⚠️ **`alldap_ai_circuit_state` 는 게이지라 스크레이프가 어긋나면 사실이 통째로 사라진다**
(#112 가 전이 카운터를 함께 둔 이유). 회복 확인은 Prometheus 가 아니라
**`/actuator/prometheus` 를 직접 긁어서** 한다. 15초 스크레이프 주기에 판정을 맡기지 않는다.

## 4. 장애 셋

부하는 셋 다 **20 VU 고정**이다. S2 에서 20 단계는 아직 안 꺾인 구간이라, **여기서 보이는 것은
포화가 아니라 실패 처리**임이 보장된다. 계단을 쌓으면 두 원인이 섞인다.

각 판: 정상 60초 → 주입 90초 → 해제 후 회복 확인 → 다음 판.
**정상 60초를 앞에 두는 이유**: 같은 실행 안에 대조군이 있어야 "주입 때문에 바뀐 것" 이라 말할 수 있다.

### F1. Python 프로세스 종료 (코드 0줄)

uvicorn 에 `SIGTERM` 을 보내고 90초 뒤 다시 띄운다.

| 기대 | 지표 |
|---|---|
| 연결 실패로 분류된다 | `alldap_ai_call_seconds_count{operation="chat",outcome="connect_failure"}` 증가 |
| **재시도가 돈다** | `alldap_ai_retry_total{operation="chat"}` 이 **실패 요청 수만큼** 증가 |
| 5회 연속 뒤 서킷이 열린다 | `alldap_ai_circuit_state` 가 2, `transition_total{to="open"}` 증가 |
| 그 뒤로는 **급속 거절** | `outcome="circuit_open"` 이 늘고, `sum/count` 가 마이크로초대 |
| 30초 주기 톱니 | `transition_total{to="open"}` 이 90초 동안 **여러 번** 오른다 (§2) |
| 사용자 응답 | 전부 503. **급속과 느린 것이 응답에서는 같다** (그게 맞는 설계다) |

🔴 **`circuit_open` 과 `connect_failure` 의 지연 차이가 이 판의 핵심 산출물이다.**
지난 실측이 0.000079s 대 0.211s(2700배)였는데, **그건 부하 없이 잰 값**이다.
20 VU 아래서도 그 차이가 유지되는지가 #112 의 Timer 가 값어치를 하는지를 가른다.

### F2. Python 5xx (가짜 CF 에 플래그 하나)

가짜 CF 가 모든 모델 호출에 500 을 낸다. `cf.run` 의 `raise_for_status()` 에 재시도가 없어
FastAPI 500 으로 이어지고, Spring 은 그걸 `PYTHON_SERVER_ERROR` 로 본다.

| 기대 | 지표 |
|---|---|
| 5xx 로 분류된다 | `outcome="python_5xx"` 증가 |
| 🔴 **재시도가 안 돈다** | `alldap_ai_retry_total{operation="chat"}` 이 **한 건도 안 오른다** |
| 서킷은 **열린다** | 5xx 는 `recordFailure` 를 센다 |
| 사용자 응답 | 503 |

**둘째 줄이 F2 를 넣는 유일한 이유다.** F1 만으로는 "재시도가 연결 실패에만 걸린다" 를
**반증 가능한 형태로** 증명할 수 없다. F1 은 재시도가 도는 것만 보여주고,
"다른 경우에는 안 돈다" 는 안 보여준다. 재시도가 여기서 돌면 **LLM 이 두 번 과금**된다.

⚠️ 가짜 CF 는 뉴런 0.0 을 주므로 중복 과금 자체는 여기서 안 일어난다. 증명하는 것은
**호출 횟수**다. 가짜 CF 의 `counts` 증가분이 요청 수와 1:1 이면 재시도가 없는 것이다.

### F3. rerank 조용한 실패 (이 PR 에서 가장 값어치가 크다)

가짜 CF 가 **리랭커 모델에만** 500 을 낸다. `retriever.py:302` 의
`except Exception` 이 그걸 삼키고 원래 순서를 돌려준다. **200 이 나간다.**

| 무엇을 보는가 | 기대 |
|---|---|
| HTTP 상태 | **전부 200.** 아무것도 안 바뀐다 |
| `isFallback` | **false.** 안 바뀐다 |
| `alldap_ai_call_seconds{outcome}` | **전부 `success`.** 안 바뀐다 |
| 서킷 상태 | **닫힌 채.** 안 바뀐다 |
| 가짜 CF `counts["<리랭커 모델>"]` | **정상대로 증가한다.** 호출은 됐고 응답이 500 이었을 뿐이다 |
| **uvicorn 로그 `리랭킹 실패(원래 순서 유지)`** | **주입 건수만큼.** 유일한 신호다 |

🔴 **지연을 그대로 둔 채 500 을 준다.** 가짜 CF 의 `time.sleep` 을 건너뛰면 종단 지연이
414ms 빨라져서 "장애인데 빨라졌다" 가 되는데, 그러면 **원인이 다른 두 사실(장애 · 지연 변화)이
한 숫자에 섞인다.** 이 저장소가 일곱 번 낸 부류다. 지연을 유지하면
**모든 외부 신호가 글자 하나 안 바뀌고**, 그것이 이 판이 증명하려는 것 자체가 된다.

**산출물은 표 한 장이다**: 왼쪽에 "장애 건수 N", 오른쪽에 "그 N 을 드러내는 지표: 없음(로그뿐)".
S2 실행에서 이미 한 번 실제로 났던 일이라 가상의 우려가 아니다.

## 5. 코드 변경

```
ai-service/loadtest/fake_cf.py        수정  장애 주입 제어면 + /stats 에 fault 블록
ai-service/loadtest/fake_cf_check.py  수정  주입 회귀 검사
ai-service/loadtest/s4_faults.js      신규  k6 시나리오 (20 VU 고정)
ai-service/loadtest/s4_context.py     신규  주입 제어 · 회복 확인 · 시작 조건 · 판정
```

Spring·Python **운영 코드는 한 줄도 안 고친다.**

### ① 가짜 CF 의 장애 주입 제어면

```
POST /fault  {"mode": "none" | "error_all" | "error_rerank", "status": 500}
GET  /stats  → 기존 필드 + "fault": {"mode": ..., "status": ..., "injected": N}
```

- **런타임 제어면이지 기동 옵션이 아니다.** 판 안에서 정상 60초 뒤에 켜야 하는데
  기동 플래그면 서버를 다시 띄워야 하고, 그러면 `counts` 가 초기화돼
  실행 전후 비교(마스터 설계서의 장치)가 깨진다.
- **`injected` 카운터를 센다.** F3 의 "장애 N 건" 이 이 값이다. 이게 없으면
  로그 줄 수를 세는 것 외에 주입이 실제로 일어났다는 증거가 없다.
- 🔴 **`_stats_payload` 에 함께 넣는다.** 지금 그 함수의 주석이
  *"장애 주입 플래그를 붙이게 되면 여기에도 함께 넣을 것. 쓰이지 않는 필드를 미리 만들면
  그 자체가 거짓말이 된다"* 고 적어뒀다. **그 약속을 지키는 자리다.**
  안 넣으면 시작 조건 파일이 "어떤 장애로 쟀는지" 를 말하지 못한다.
- **`mode` 를 불리언이 아니라 문자열로 둔다.** `error_all` 과 `error_rerank` 는
  서로 다른 사실이고, 나중에 지연 급변 같은 모드가 늘어난다. 불리언 둘로 두면
  "둘 다 켠 상태" 라는 의미 없는 조합이 생긴다.

### ② `fake_cf_check.py` 회귀 검사

기존 점검과 같은 방식(스레드로 띄워 실제 HTTP)으로 **일부러 깨뜨려 본다.**

| 케이스 | 기대 |
|---|---|
| `mode=none` 에서 생성 호출 | 200, `injected` 0 |
| `mode=error_all` 에서 임베딩·리랭커·생성 | 셋 다 500, `injected` 3 |
| `mode=error_rerank` 에서 임베딩·생성 | **200** (안 건드린다) |
| `mode=error_rerank` 에서 리랭커 | 500, `injected` 1 |
| `error_rerank` 의 응답 지연 | 정상과 같은 구간(§4-F3) |
| `/stats` 의 `fault` 블록 | `mode`·`status`·`injected` 셋 다 실제 상태와 일치 |
| **뉴런 0.0 회귀 검사** | 기존 검사가 그대로 통과 (주입이 그 안전장치를 안 건드린다) |

마지막 줄이 중요하다. 뉴런 0.0 은 **이 서버가 가짜라는 유일한 신호**이고
`s2_context.judge_fake_cf` 가 그 값으로 진짜 CF 를 막는다. 주입 코드가 그 경로를
건드리면 안전장치가 조용히 꺼진다.

`fake_cf_check` 는 이미 **#110 의 CI 목록에 있다.** 줄을 추가할 필요가 없고,
새 케이스가 자동으로 CI 에서 돈다.

### ③ `s4_context.py`

`s2_context.py` 의 `before`/`after` 를 따르되 **판 진행 제어**가 붙는다.

```python
def wait_circuit_closed(actuator_url: str, timeout_s: int) -> tuple[bool, str]:
    """/actuator/prometheus 를 직접 긁어 alldap_ai_circuit_state == 0 을 확인한다."""

def judge_fault_round(name: str, metrics_before: dict, metrics_after: dict,
                      cf_stats_before: dict, cf_stats_after: dict,
                      k6_counts: dict) -> tuple[bool, str]:
    """한 판의 기대 지표 변화를 전부 대조한다."""
```

`judge_fault_round` 가 판마다 다르게 단언하는 것:

- **F1**: `retry_total` 증가 > 0 이고, `circuit_open` outcome 증가 > 0
- **F2**: `retry_total` 증가 **== 0**, `python_5xx` 증가 > 0,
  가짜 CF `counts` 증가가 요청 수와 1:1
- **F3**: `outcome` 이 `success` 외에 **아무것도 안 늘고**, k6 의 상태코드가 전부 200 이고,
  가짜 CF `fault.injected` 증가 > 0. **셋이 동시에 참이어야** "보이지 않는 장애" 가 증명된다

🔴 **F3 의 판정은 "실패를 기대하는 판정" 이다.** 지표가 안 움직이는 것이 통과 조건이라,
**계측이 아예 안 붙은 경우와 구별되지 않는다**(핸드오프 §6-ⓓ 가 지적한 부류).
그래서 앞의 정상 60초에서 `success` 가 늘었다는 것을 **먼저** 확인한다.
정상 구간에 신호가 있고 주입 구간에 변화가 없어야 "안 잡힌다" 가 성립한다.

### ④ 자체 점검

`judge_fault_round` 와 `wait_circuit_closed` 의 파싱을 순수 함수로 뽑아
`s4_check.py` 에서 **일부러 깨뜨린다.** S3 와 같은 방식이고 같은 이유다.
DB·외부 API 를 안 타므로 **#110 의 CI 명시 목록에 한 줄 추가**한다.

최소 케이스: F2 에 `retry_total` 이 1 오른 입력 → 실패 /
F3 에 `python_5xx` 가 1 오른 입력 → 실패 /
`circuit_state` 시계열이 응답에 없는 경우 → **"닫혔다" 가 아니라 "못 읽었다"** 로 판정.

## 6. 관측이 아직 못 가르는 것 (결과 문서에 그대로 싣는다)

핸드오프 §6-ⓓ 를 이 실행의 맥락으로 옮긴 것이다.

- 🔴 **핸드오프 §6-ⓓ 의 "연결 거부와 읽기 타임아웃이 뭉쳐 있다" 는 부정확하다.**
  `ioOutcome()` 을 읽으면 `READ_TIMEOUT` 은 `read_timeout` 으로 **이미 따로 태깅된다.**
  실제로 뭉쳐 있는 것은 `connect_failure` **안쪽**이다:
  `ConnectException`(연결 거부, 즉시)과 `HttpConnectTimeoutException`(SYN 무응답, 3초)이
  같은 태그로 들어간다. **F1 이 만드는 것은 앞쪽뿐**이라 이 판으로는 그 뭉개기를 드러낼 수 없고,
  드러내려면 §8-③ 의 SYN 드롭이 필요하다.
- **`alldap_ai_call_seconds` 에 히스토그램 버킷이 없어 평균만 나온다.** p99 는 못 구한다.
  F1 의 "급속 대 느림" 은 평균으로도 2700배라 갈리지만, **그 판정은 평균으로 한 것**이라고 적는다.
- **`transition_total{to}` 만 있고 "언제" 는 게이지에 있다.** 30초 톱니의 주기를 정확히 재려면
  15초 스크레이프로는 모자란다. 톱니의 **횟수**는 카운터로 정확하고, **주기**는 근사다.

## 7. 측정을 무효로 만들지 않기 위한 장치

| 장치 | 무효/유효를 어떻게 가르나 |
|---|---|
| **판마다 정상 60초 선행** | 대조군이 같은 실행 안에 있어야 "주입 때문" 이라 말할 수 있다 |
| **회복 확인이 시간이 아니라 상태** | `circuit_state == 0` 을 직접 긁어 확인. 실패하면 중단(§3) |
| **가짜 CF `injected` 카운터** | 주입이 실제로 일어났다는 증거. 0 이면 그 판은 무효 |
| **F3 는 정상 구간 신호를 먼저 확인** | "안 잡힌다" 와 "계측이 없다" 를 가른다(§5-③) |
| **uvicorn 로그를 파일로** | F3 의 유일한 신호다. 안 받으면 그 판의 산출물이 없다 |
| `isFallback` 카운트 | 주입과 무관하게 0 이어야 한다. 아니면 게이트에 걸린 것이라 경로가 다르다 |
| 시작 조건 파일 | 커밋 SHA · 가짜 CF `/stats` 전체(지연·벡터 모드·fault) · 실행 시각 |
| 재시작 경계 | `process_start_time_seconds`. `-Ploadtest` 로 힙 256m 이라 OOM 이 가능하다 |

## 8. 범위 밖 (알고 빼는 것)

### ① SIGSTOP 으로 읽기 타임아웃

커널이 연결은 받아주므로 `read-timeout: 120s` 까지 간다. 90초 판에 안 맞아
**그 판만 `read-timeout` 을 5s 로 바꿔야 하고**, 그러면 설정이 다른 실행이라
별도 컨텍스트 파일이 된다.

⚠️ **빼는 근거를 정직하게 적는다.** SIGSTOP 이 주는 것은 `read_timeout` 이고 그 태그는
**이미 따로 나와 있다**(§6). 그러니 "관측이 못 가르는 것을 가른다" 는 이유로는 정당화되지 않는다.
실제로 얻는 것은 다른 쪽이다: **톰캣 스레드가 오래 물리는 그림**, 즉 §2 가 정정해 없앤
"6.2초" 의 유일하게 실현 가능한 대체물이다. 그건 값어치가 있다.
그럼에도 빼는 이유는 **설정을 바꾼 별도 실행**이라 이 PR 의 세 판과 한 표에 못 올린다는 것 하나다.
필요해지면 **독립 슬라이스**로 한다. "재도 나올 게 없어서" 가 아니다.

### ② 헤더 뒤 끊김

`RestClientException(cause=IOException)` 경로(`CONNECTION_LOST`)를 재려면 새 장애 프록시가 필요하다.
🔴 **주입기가 교란 요인이 되면 안 된다.** S2 에서 `ThreadingHTTPServer` 자체가 부하에 흔들린
전례가 있다(8,316건 중 1건). 새 프록시를 20 VU 아래 끼워 넣으면
"끊긴 것이 주입 때문인가 주입기 때문인가" 를 못 가른다.

### ③ SYN 드롭(`pfctl`)으로 connect 타임아웃 3초

§2 의 "6.2초" 그림을 재는 유일한 방법인데, 호스트 방화벽 규칙을 부하테스트가 만졌다 지우는 것은
**실패했을 때 맥이 이상한 상태로 남는다.** 값어치보다 위험이 크다.

### ④ 나머지

- **개선과 결함 수정.** 핸드오프 §5 의 결함 5건은 **고치지 않는다.** 특히 1·2번
  (서킷이 전 엔드포인트 공용 싱글턴 · "연속" 이라 성공마다 리셋)은 **이 PR 이 드러내려는 것 자체**라
  고치면 before 가 사라진다
- **운영에서의 장애 주입.** 진짜 장애다(마스터 설계서 §범위 밖)
- **"몇 % 실패율부터 서킷이 열리는가".** 핸드오프 §5-2 가 "S4 가 낼 수 있는 좋은 수치" 로
  적어둔 것인데, 채팅과 업로드를 섞어 돌려야 나온다. **부하 프로파일이 달라지므로 별 슬라이스다.**
  이 PR 은 단일 엔드포인트만 민다
