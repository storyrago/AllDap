# 평가셋 정비 설계 (2026-09-18)

평가 질문 세트를 저장소 파일로 고정하고, 질문이 묻는 대상과 정답 청크의 대상이
어긋난 문항을 가려내는 검수 절차를 만든다.

## 1. 왜 지금 이것인가

`docs/BACKLOG.md` §5 ①, `docs/superpowers/handoff-2026-09-17.md` §3 이 근거다.

**① 질문 세트가 저장소 어디에도 없다.** `V9__bigint_ids.sql` 이 전 테이블을 드롭하면서
평가 질문 16개가 사라졌다. 코퍼스는 `ai-service/testdata/corpus/` 로 정확히 재현되는데
(재적재하니 청크 306개로 일치) 질문은 DB 에만 있었다. 그래서 2026-09-17 측정은
새로 생성한 질문으로 돌 수밖에 없었고, 그 표를 과거 수치(0.875)와 이어 붙일 수 없다.
지금도 같은 상태다. 로컬 도커 볼륨이 날아가면 2026-09-17 의 A·B·C 표도 재현 불가능해진다.

**② 자동 생성 질문에 결함이 섞인다.** 2026-09-17 진단에서 실제로 드러났다.
q1 은 "수습 직원" 을 묻는데 정답 청크가 "인턴" 규정이고, q16 은 "업무용 컴퓨터" 를 묻는데
청크가 "개인 노트북" 규정이다. **둘 다 봇이 거절하는 것이 옳은 동작인데** 지표에서는
fallback 으로 집계돼 천장(0.8125)을 만든다. 파일로 남기는 것만으로는 이 결함이 함께 박제된다.

**③ 다음 슬라이스(리랭커 파인튜닝)가 이것 없이는 무의미하다.** 지금 세트는
"후보 안인데 순위가 낮아 밀려난" 문항이 0개다. 회복 여지가 0 인 평가셋 위에서는
파인튜닝이 좋아져도 나빠져도 숫자가 같게 나온다.

## 2. 범위

**이번 슬라이스는 <고정 + 검수> 까지다.** 난이도 확보(리랭커가 회복할 여지가 있는
문항을 세트에 넣는 것)는 **다음 슬라이스**로 넘긴다. AGENTS.md 작업 규칙 1번
"한 번에 하나씩" 을 따르고, PR 하나가 리뷰 가능한 크기로 떨어지게 한다.

⚠️ 따라서 이 슬라이스가 끝나도 **파인튜닝의 효과를 측정할 수 있게 되지는 않는다.**
닫히는 것은 재현 가능성과 "무엇이 결함이고 무엇이 정당한 난이도인가" 의 구분이다.

## 3. 파일 포맷

위치: `ai-service/testdata/eval_questions.json`

```jsonc
{
  "corpus": "testdata/corpus",
  "chunking": { "chunk_size": 500, "chunk_overlap": 50, "chunk_split_headings": true },
  "questions": [
    {
      "id": "q1",
      "question": "수습 직원이 처음 일주일 동안 마쳐야 하는 학습 시간은?",
      "ground_truth": "40시간",
      "source_doc": "03_인턴_운영지침.md",
      "source_text": "제4조(교육) 인턴은 입사 첫 주에 40시간의 온보딩 교육을 이수해야 한다.",
      "active": false,
      "review": {
        "verdict": "defective",
        "note": "질문은 '수습' 을 묻는데 정답 청크는 '인턴' 규정이다. 코퍼스에서 수습은 별도 규정(채용절차 3개월 등)이라 대상이 다르다. 거절이 옳은 동작인데 지표는 fallback 으로 센다."
      }
    }
  ]
}
```

### 3.1 정답 청크를 <본문 통째로> 가리키는 이유

`eval_questions.source_chunk_id` 는 DB 가 매기는 번호라 **재적재하면 바뀐다.**
파일에 번호를 적으면 아무것도 가리키지 못한다. 후보 셋 중에서 본문을 골랐다.

| 후보 | 기각 사유 |
|---|---|
| 청크 순번(`source_index: 3`) | 청킹 설정이나 코퍼스가 바뀌면 **조용히 다른 청크를 가리킨다.** 이 저장소가 여덟 번 낸 "서로 다른 사실을 한 값으로 뭉개는" 부류다 |
| 본문 해시(SHA) | 사람이 읽을 수 없다. 검수가 이 슬라이스의 절반인데, 해시로는 매번 DB 나 코퍼스를 따로 열어야 한다 |
| **본문 전문 (채택)** | 이 코퍼스는 청크가 최대 217자라 용량이 문제되지 않는다. 적재 스크립트가 글자 일치로 찾을 수 있고, **사람이 파일 하나만 열면 질문과 청크를 나란히 놓고 볼 수 있다** |

### 3.2 `chunking` 을 함께 적는 이유

`source_text` 로 청크를 찾는 방식은 **그때와 같은 규칙으로 잘랐을 때만** 성립한다.
설정을 파일에 박아두면 나중에 안 맞을 때 "코퍼스가 바뀐 것" 과 "자르는 규칙이 바뀐 것" 을
가를 수 있다. 안 적으면 둘 다 그냥 "못 찾음" 으로 뭉개진다.

### 3.3 JSON 인 이유

YAML 이 읽기는 낫지만 `pyyaml` 이 `requirements.txt` 에 없다. 지금 venv 에 깔려 있는 것은
다른 패키지에 딸려 들어온 것이다. `requirements.txt` 의 `httpx` 주석이 이미 경고한 부류다:
남의 패키지에 딸려온 것에 기대면 그 패키지를 빼는 순간 조용히 깨진다.
JSON 은 표준 라이브러리로 되고 의존성이 한 줄도 안 는다.

## 4. 데이터 흐름

```
① 지금 DB 의 16문항  ──dump──▶  eval_questions.json
② 사람이 검수 (도구가 재료 출력) ──▶ review.verdict / active 를 파일에 기입
③ 결함 2개 자리에 생성기 재호출 → 검수 통과분 2개를 파일에 추가
④ eval_questions.json  ──load──▶  DB   (앞으로 평가 세트는 항상 이 경로로 채운다)
```

**① 이 제일 먼저다.** 지금 16문항은 로컬 도커 볼륨에만 있다. 볼륨이 날아가면
2026-09-17 의 A·B·C 표가 재현 불가능해진다.

**③ 은 생성기를 다시 돌려 후보를 뽑고 검수를 통과한 것을 고른다.** 사람이 직접 쓰지 않는다.
실제 고객도 이 경로(`POST /internal/bots/{id}/eval/questions/generate`)로 질문을 얻으므로,
**검수 절차가 제품의 진짜 루프 위에서 돈다.** 덤으로 생성기가 결함 문항을 얼마나 내는지도 알게 된다.

## 5. 결함 문항의 처리

**지우지 않고 `active: false` + 사유와 함께 남긴다.** 그 자리에 검수를 통과한 대체 문항을
넣어 활성 16문항을 유지한다.

- 문항 수가 그대로라 **한 문항의 무게(0.0625)가 안 바뀐다.** 과거 표와 축이 맞는다
  (수치 자체는 세트가 달라 이어 붙일 수 없지만, 한 문항이 지표를 얼마나 움직이는지는 같다).
- 왜 뺐는지가 파일에 남아 **다음 사람이 같은 질문을 다시 만들지 않는다.**
- 면접에서 파일을 열어 그대로 설명할 수 있다.

### 5.1 검수 기준: 대상이 다른 것과 낱말이 다른 것은 다르다

| | q1 · q16 (결함) | q6 (결함 아님) |
|---|---|---|
| 무엇이 어긋났나 | **대상**. 수습 vs 인턴, 업무용 컴퓨터 vs 개인 노트북 | **낱말**. 토의 공간 vs 회의실 |
| 그 낱말이 코퍼스에 | **다른 문서에 있다** (수습은 채용절차 등에 별도 규정) | **0건**. 문서가 그 말을 아예 안 쓴다 |
| 판정 | 질문이 다른 문서를 겨냥하고 있다 → 뺀다 | 대상은 같고 표현만 다르다 → **남긴다.** 검색이 풀어야 할 정당한 난이도다 |

이 구분이 검수의 핵심이다. q6 까지 빼면 평가셋이 쉬워지기만 한다.

## 6. 도구 세 개

### 6.1 `app/eval_set.py` (DB 필요)

`python -m app.eval_set dump --bot-id 1` / `python -m app.eval_set load --bot-id 1`

- **dump**: `eval_questions` 를 `chunks` · `documents` 와 조인해 질문·정답·문서명·청크 본문을 JSON 으로 쓴다.
- **load**: `source_text` 와 **글자가 완전히 같은** 청크를 그 봇 안에서 찾아 `source_chunk_id` 를 붙여 넣는다.
  - 0건이면 실패한다. 어느 문항·어느 문서·본문 앞머리까지 한국어로 찍는다.
    **비슷한 것을 골라 넣지 않는다.** 그게 이 저장소가 반복해 낸 "조용히 다른 것을 가리키는" 실수다.
  - 2건 이상이어도 실패한다. 어느 쪽인지 모르는 채 고를 수 없다.
  - `active: false` 문항도 `is_active=false` 로 **넣는다.** 파일과 DB 가 같은 모습이어야 하고,
    `evalrun` 은 이미 `WHERE is_active` 로 거른다.

🔴 **기본 동작은 "그 봇에 질문이 없을 때만 넣는다" 다.** 지우려면 `--replace` 를 명시해야 한다.
`eval_results.question_id` 가 `ON DELETE CASCADE` 라 질문을 지우면 **과거 실행 상세가 통째로
날아가기** 때문이다. `--replace` 는 무엇이 함께 지워지는지 경고를 찍고 진행한다.

### 6.2 `app/eval_set_review.py` (DB 불필요, 파일 + 코퍼스만)

문항마다 검수 재료를 출력한다. 판정과 사유 작성은 사람이 한다.

```
[q1] 수습 직원이 처음 일주일 동안 마쳐야 하는 학습 시간은?
     정답청크 (03_인턴_운영지침.md): 제4조(교육) 인턴은 입사 첫 주에 40시간의 ...
     낱말      정답청크에  코퍼스전체   어디에
     수습          ✗ 없음      7건     11_채용_절차, 01_정규직 ...   🔴
     학습          ✗ 없음      2건     26_온보딩 ...
     시간          ✓ 있음     41건
```

- 낱말 추출은 `retriever` 의 조사 떼기를 **재사용한다.** 하이브리드 검색이 보는 낱말과
  검수가 보는 낱말이 같아야 말이 된다. 새로 짜면 두 기준이 갈린다.
- 세 칸(정답청크 포함 여부 · 코퍼스 전체 건수 · 어느 문서)이 §5.1 의 구분을 그대로 드러낸다.
- DB 도 네트워크도 안 쓴다. 세트가 바뀔 때마다 언제든 다시 돌릴 수 있다.
  이 저장소가 반복해 낸 실수가 "검사를 안 짠 것이 아니라 짜둔 검사가 아무 데서도 안 돈 것" 이다.

### 6.3 `app/eval_set_check.py` (CI 에서 돈다)

파일이 거짓말을 하지 않는지 본다. DB 도 외부 API 도 안 쓴다.

- id 중복 없음 · 필수 칸 빔 없음 · `active` 문항 수가 16
- `source_doc` 이 `testdata/corpus/` 에 실재
- 🔴 **그 문서를 파일에 적힌 `chunking` 설정으로 다시 잘라, `source_text` 가 그 결과 안에
  <그대로> 들어 있는지 확인한다.**

마지막 항목이 이 설계에서 가장 중요한 검증이다. 근거는 실제 코드다.
`chunker._pack` 이 조각을 `\n` 으로 이어 붙이고 `strip()` 하므로 **청크 본문은 원문의
글자 그대로의 부분 문자열이 아니다**(빈 줄이 한 줄로 줄어든다). 그래서 원문 부분 문자열
비교는 공백 처리에 깨진다. 반면 청커는 순수 함수라 DB 없이 돌고, 다시 잘라 대조하면
**꼬리표가 실제 청크를 가리킨다는 것을 CI 가 매번 확인한다.**

## 7. 검증 (사람이 한 번 돌린다)

1. `load` → 평가 1회 실행(약 800 뉴런) → 16문항이 그대로 돌고 결과가 나온다
2. `dump` → 처음 파일과 같은지 비교 (왕복이 재현되는가)
3. `rank_trace --bot-id 1` 이 새 세트에서 돈다

⚠️ **평가는 1회만 돌린다.** 세트가 달라졌으므로 이 수치는 새 baseline 이지만,
설정당 3회가 필요한 <설정 비교> 가 아니라 "파일에서 적재한 세트로 평가가 돈다" 는
종단 확인이다. 문서에 반드시 **1회** 라고 적는다.

## 9. 한계 (알고 남기는 것)

- **난이도는 안 바뀐다.** 회복 여지가 0 인 상태는 그대로다(§2). 다음 슬라이스의 일이다.
- **새 수치를 과거 표와 이어 붙일 수 없다.** 대체 문항 2개가 들어가 세트가 또 달라진다.
  비교가 성립하는 것은 이 세트 안에서뿐이다.
- **검수는 사람이 한다.** 문항이 수백 개로 늘면 이 절차는 안 버틴다. 지금 16문항이라
  사람이 읽는 것이 가장 정확하고 싸다(LLM 1차 스크리닝은 판정자가 또 LLM 이라
  그 판정을 다시 검증해야 한다).
- **`eval_set_check` 는 꼬리표가 실제 청크를 가리키는지만 본다.** 질문이 좋은 질문인지,
  대상이 맞는지는 검사하지 못한다. 그건 §6.2 의 사람 검수 몫이다.
