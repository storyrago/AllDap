# 페이지 전환 연출 설계 (2026-08-29)

## 문제

랜딩(`/`)은 문을 열고 들어가는 연출인데, `고용하기`를 누르는 순간 그 세계가 **잘려나가고**
흰 페이지가 튀어나온다. 로봇을 눌러 `/demo` 로 갈 때도 같다. 이동 자체는 정상인데
두 화면 사이에 아무 연결이 없어서 "확확 바뀐다"로 느껴진다.

랜딩이 문 메타포로 공들여 만들어져 있는데 그 문을 나가는 순간이 가장 거친 컷이라,
연출이 앞뒤로 이어지지 않는다.

## 결정

**랜딩에서 나가는 링크만 문 연출을 쓰고, 나머지 이동은 은은한 페이드로 통일한다.**
문 연출은 **도착 페이지가 열리는 것**만 재생한다(떠나는 화면을 닫지 않는다).

| 이동 | 연출 | 길이 |
|---|---|---|
| `/` → `/auth` (고용하기) | 문 열림 | 0.4초 |
| `/` → `/demo` (로봇) | 문 열림 | 0.4초 |
| `(site)` 그룹 안의 다른 이동 (`/features` ↔ `/faq` ↔ `/pricing` ↔ `/demo` ↔ `/auth`) | 페이드 | 0.22초 |
| `prefers-reduced-motion` | 없음(즉시) | — |
| View Transitions 미지원 브라우저 | 없음(즉시) | — |

🔴 **대시보드(`(dashboard)` 그룹)는 이번 범위가 아니다.** 레이아웃이 따로라 감싸는 파일이
하나 더 늘고, 애초 문제 제기가 공개 화면의 흐름(고용하기·데모)이었다. 필요해지면 같은
방식으로 `(dashboard)/layout.tsx` 를 감싸면 된다 — 규칙은 그대로 쓰인다.

## 구현

React 의 `<ViewTransition>` 과 브라우저 View Transitions API 를 쓴다.
**Next 16.2.12 에 실제로 들어 있는 기능이다** — `node_modules/next/dist/docs/01-app/02-guides/view-transitions.md`
와 `.../viewTransition.md` 를 읽고 확인했다. Next 에서 라우트 이동은 이미 transition 이라
`<ViewTransition>` 애니메이션이 자동으로 활성화된다.

| 파일 | 변경 |
|---|---|
| `web/next.config.ts` | `experimental.viewTransition: true` |
| `web/app/(site)/layout.tsx` | `children` 을 `<ViewTransition>` 으로 감싸 <타입 → 애니메이션 클래스> 매핑 |
| `web/app/globals.css` | `.door` · `.fade` 애니메이션 · reduced-motion 차단 |
| `web/components/ReceptionHero.tsx` | 링크 2개(`고용하기`·로봇)에 `transitionTypes={['door']}` |

⚠️ **`<ViewTransition>` 래퍼가 반드시 필요하다.** `transitionTypes` 는 이동에 이름표를 붙일
뿐이고, 그 이름을 CSS 가 쓸 수 있는 <클래스>로 바꿔주는 것이 래퍼다(공식 가이드의 방식이
그렇다). 래퍼 없이 `transitionTypes` 만 주면 아무 일도 일어나지 않는다.

```tsx
<ViewTransition enter={{ door: "door", default: "fade" }} exit={{ default: "fade" }}>
  {children}
</ViewTransition>
```

```css
::view-transition-new(.door) { animation: door-open 0.4s ...; }
@keyframes door-open {
  from { clip-path: inset(0 50% 0 50%); }  /* 가운데 틈 */
  to   { clip-path: inset(0 0 0 0); }      /* 활짝 */
}
```

**새 컴포넌트를 만들지 않는다.** 문짝 DOM 을 따로 세우는 대신 도착 페이지 스냅샷의
`clip-path` 를 벌린다 — 그 그림이 곧 문이 열리는 것이다.

규칙 전체가 **타입 이름 `door` 하나**로 읽힌다. 이 타입이 붙은 링크만 문이고 나머지는
전부 페이드라, 링크마다 "여긴 어느 쪽이지?" 를 판단할 필요가 없다.

⚠️ **`default: "fade"` 로 정한다.** 공식 예제는 `default: "none"` 을 써서 첫 로드에 아무
애니메이션도 안 걸리게 하는데, 우리는 페이지끼리의 이동에 페이드가 필요하다.
대신 <첫 로드에도 페이드가 걸릴 수 있다>. 구현 때 첫 로드가 굼떠 보이면 `none` 으로 되돌리고
페이드는 포기한다 — 첫인상이 느린 것이 페이드가 없는 것보다 나쁘다.

## 검증

1. 브라우저에서 `고용하기`·로봇을 **실제로 눌러** 문이 열리며 도착하는지 본다.
2. `/features` ↔ `/faq` 등 다른 이동이 페이드인지 본다.
   그리고 **첫 로드**가 굼떠 보이지 않는지 함께 본다(위 `default` 결정과 직결된다).
3. `prefers-reduced-motion` 을 켠 상태로 두 경우 모두 즉시 전환되는지 본다.

⚠️ **강제로 스타일을 주입해 "보이는지" 만 확인하지 않는다.** 같은 세션에서 로봇 말풍선을
그렇게 검증했다가 틀렸다 — CSS 가 맞는 것과 실제로 동작하는 것은 다른 사실이다.

## 알고 가는 한계

- **`experimental` 플래그다.** Next 업그레이드에서 이름이 바뀌거나 빠질 수 있다.
  깨져도 이동 자체는 멀쩡하고 애니메이션만 사라진다(기능 손실 없음).
- 공식 문서가 **Safari 에서 일부 애니메이션이 다르게 동작**한다고 명시한다.
- 랜딩으로 돌아오면 문이 닫힌 첫 화면부터 다시 시작한다(컴포넌트가 새로 마운트된다).
  지금 흐름에서는 자연스럽다고 보고 그대로 둔다.
- 전환 길이(0.4초 / 0.22초)는 **눈으로 정한 값**이다. 재보고 정한 수치가 아니다.

## 검토한 대안과 기각 이유

| 대안 | 기각 이유 |
|---|---|
| 모든 이동에 문 연출 | `/features` → `/faq` 에서 문이 닫히면 뜬금없다. 문이 값어치를 갖는 건 <그 문이 실제로 있는 화면>을 떠날 때뿐이다 |
| 전부 페이드만 | 거슬리지는 않지만 기억에 남지 않는다. 랜딩이 문 메타포로 만들어져 있는데 그 연결을 버리게 된다 |
| 닫히고 → 열리는 왕복 | 이동 하나가 0.7초가 되고 그 절반은 사용자가 결정을 내린 <뒤에> 기다리는 시간이다. 랜딩에서 이미 문 두 개를 지나왔는데 나갈 때 또 닫히면 연출이 아니라 관문이 된다. 구현도 떠나는 쪽 스냅샷까지 물려야 해서 타이밍 맞출 곳이 두 배다 |
| 애니메이션 라이브러리 도입 | 의존성 없이 CSS 로 되는 일이다. 이 저장소는 히어로 디오라마도 라이브러리 없이 만들었다 |
