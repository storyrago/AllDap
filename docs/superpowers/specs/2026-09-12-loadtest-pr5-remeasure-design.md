### 실행 전 준비: 측정 계정 (5b·5c 공통)

**S4(F2)와 S2 재측정은 `/api/auth/login` 을 탄다.** S3(A판)은 로그인이 없다.

✅ **이미 해결됐다. PR #133 이다** (`ai-service/loadtest/account.py`, 2026-09-11 머지).
이 절이 할 일은 **그 사실을 가리키는 것**이고, 새 방식을 제안하는 것이 아니다.

절차는 이렇다. 측정 전에 한 번:

```
cd ai-service && LOADTEST_PASSWORD='...' .venv/bin/python -m loadtest.account
```

그러면 `loadtest@example.com` 이 가입되고, **코퍼스를 이미 가진 봇의 주인이 그 계정으로
옮겨진다.** 드라이버(`s1_baseline` · `s2_context` · `s2_breakpoint.js` · `s4_context`)는
`LOADTEST_EMAIL`·`LOADTEST_PASSWORD` 에서 계정을 읽고, **비밀번호에 기본값이 없어**
빠뜨리면 로그인 401 이 아니라 "무엇이 빠졌는지" 로 죽는다.

#133 이 지킨 것 셋 (5c 가 그대로 물려받는다):
- 해시를 직접 만들지 않고 `POST /api/auth/signup` 을 부른다. Spring 의 `PasswordEncoder` 가
  **유일한 해시 생산자**로 남는다. 여기서 bcrypt 를 돌리면 인코더 설정이 바뀌는 날
  이 파일만 조용히 낡는다
- 비밀번호는 환경변수로만. 기본값을 코드에 박으면 **그 값이 곧 커밋된 비밀번호다**
- 운영 DB 에서 돌지 않도록 호스트를 검사하고, Flyway V9 로 심지 않는다
  (심으면 **운영 DB 에 측정 계정을 심는** 셈이다)

🔴 **이 설계의 초고는 다른 안을 제안했고, 그 기각 근거가 틀렸다. 지우지 않고 남긴다.**
초고는 *"기존 계정의 비밀번호를 알려진 값으로 고정"* 을 골랐고, **새 계정 안을**
*"S2 가 재는 것은 검색 SQL 부하라 새 봇에도 청크 306개가 있어야 하고, 그러려면 진짜
임베딩으로 코퍼스 50건을 다시 올려야 해서 before 와 다른 청크에서 재게 된다"* 는 이유로
기각했다.

**그 기각은 "새 계정 = 새 봇" 을 전제했는데 그 전제가 틀렸다.** #133 은 봇을 새로 만들지
않고 **`bots.user_id` 를 옮긴다.** 같은 봇·같은 청크 306개를 그대로 쓰므로 코퍼스 문제가
아예 생기지 않는다. 봇 소유자를 바꾸는 API 가 없어 SQL 로 하는데, `bots` 는 Spring 소유
테이블이지만 이건 제품 코드가 아니라 **로컬 측정 픽스처**라는 판단까지 #133 에 적혀 있다.

> **기각을 적을 때는 <무엇을 전제했는지>도 적어야 한다.** "새 봇이 필요하다" 를 안 적었기
> 때문에 그 전제가 틀렸다는 것을 아무도 짚을 수 없었다. 이 문단을 지우면 다음 사람이
> 같은 기각을 처음부터 다시 한다.

## 2. 5b: 도구 결함 셋

### ① S3 `recorded_total` 무효 판정: 정상 실행을 실패로 부른다

**증상.** S3 네 판이 전부 `valid:false` + 종료코드 1 로 끝났다. 그런데 측정은 멀쩡했다
(히스토그램 판정은 넷 다 정상). 무효 사유가 `alldap_ratelimit_recorded_total{bucket="widget-chat"}`
시계열 부재였다.

**원인.** `alldap.ratelimit.recorded` 를 올리는 곳은 `RateLimiter.record()` 하나이고,
그 호출자는 `AuthService` 의 `login-failure` 버킷뿐이다. 위젯 채팅은 `check()` 를 지난다.
**그 시계열은 원리적으로 생길 수 없다.** `cmd_after` 가 그 부재를 "제한기를 한 번도
안 지났다" 로 읽었다.

**고치는 방향.** 교차 검증 축을 **없는 시계열에서 있는 시계열로 옮긴다.**
k6 가 센 429 건수와 `alldap_ratelimit_rejected_total{bucket="widget-chat"}` 의 증가분을 대조한다.

🔴 **그리고 `recorded_total{bucket="widget-chat"}` 이 없는 것이 <정상>임을 검사에 못박는다.**
안 그러면 나중에 누가 이 축을 되살린다. 이 저장소가 이미 두 번 기각한 "정상을 실패로 부르는
검사" 부류다: `decisions.md` 2026-09-09 의 배포 검증 두 항목(내용이 같은 이미지를 다르다고
본 provenance 거짓 경보), 그리고 `AGENTS.md` 가 적어둔 Forwarded 점검 명령(본문에
`sessionId` 가 없어 `@Valid` 에서 400 이 나 언제 돌려도 실패를 보고했다).
**세 번째는 막아야 한다.**

### ② S4 `after` 가 `recover` 의 성공 1건을 삼킨다

**증상.** F3 의 success 증가분이 1,800 이 아니라 1,801 이다.

**원인.** `cmd_recover` 는 서킷을 닫으려고 **성공 한 건을 직접 만든다**(부하가 멈춘
상태에서는 아무도 서킷을 닫아주지 않으므로 의도된 동작이다). 절차가
`clear → recover → after` 라 그 1건이 `after` 스냅샷에 들어간다.
원리적으로는 `to=closed` 전이도 한 건 섞일 수 있다.

**고치는 방향.** 순서를 `clear → after → recover` 로 바꾼다.

🔴 **문서만 고치지 않고 코드로 못박는다.** `cmd_recover` 가 그 `run_id` 의 verdict 파일이
없으면 한국어 안내와 함께 거부한다. 근거는 이 저장소가 봇 소유권에서 정리한 것과 같다:
*"소유권을 검사하지 않고 조회 쿼리에 못박는다. `findById` 후 `if (남의 것) throw` 는 검사를
빠뜨려도 컴파일이 통과한다."* 절차로만 지키는 규칙은 빠뜨려도 아무 일이 안 일어난다.

⚠️ `cmd_recover` 는 **다음 판으로 넘어가는 유일한 관문**이라 없애면 안 된다.
순서만 바꾼다.

### ④ S3 `--headroom-ms` 기본값 20000 → 60000

**앞 문서가 지목한 의심 방향이 틀렸다.** "A 가 실패하면 먼저 의심하라" 고 적혀 있었는데,
100건이 **329ms** 에 끝난다(60배 여유). 시간이 모자랄 일은 없다.

**위험은 반대편이었다.** `cmd_before` 는 가짜 키 사전 확인 요청 1건을 **먼저 보내고**
분 경계 정렬을 한다. 20초면 같은 윈도우에서 시작할 수 있고, 그러면 그 1건이 한도 20 중
하나를 먹어 **정상인데도 404 가 19건** = 거짓 실패가 난다. 드라이버가 스스로 경고하며
60000 을 권하고, A·B·C 를 전부 60000 으로 돌렸다.

→ **기본값을 실제로 쓴 값에 맞춘다.** 기본값과 실사용이 다르면 그 기본값은 거짓말이다.

### 동일성 확인 (이것이 5b 의 산출물이다)

①②④ 를 고친 뒤 **A판(S3)과 F2(S4)를 한 판씩** 재실행한다.

| 기대 | 무엇을 뜻하는가 |
|---|---|
| 판정이 `valid:true` 로 바뀐다 | ①이 고쳐졌다 |
| **히스토그램·상태코드 숫자는 그대로** | 도구를 고쳤을 뿐 재는 대상은 안 바뀌었다 |
| F3 success 증가분이 1,800 (1,801 이 아니라) | ②가 고쳐졌다 |

🔴 **숫자가 바뀌면 5c 를 멈추고 보고한다.** 앞의 7판이 무엇을 잰 것인지 다시 물어야 한다.

## 3. 5c: S2 재측정

### 사다리

**before 와 같게 두고 160 한 칸만 더한다.** `1 · 5 · 10 · 20 · 40 · 80 · 160` VU,
단계 유지 120초, 판정 구간은 각 단계 앞 20초를 잘라낸 뒤. 7단계라 약 15분.

**왜 160 이 필요한가.** 새 천장 예측이 `80 스레드 ÷ 1.68초 = 47.6 req/s` 인데,
그 천장에 닿으려면 동시 요청이 80건은 되어야 한다. **옛 사다리의 마지막 칸이 새 벽과
정확히 겹친다.** 80 까지만 돌리면 처리량이 47 까지 선형으로 오르는 것만 보이고
꺾이는지는 못 본다 = "벽이 어디로 옮겨갔나" 에 답할 수 없다.

**왜 40 이하를 버리지 않는가.** before 에서 그 구간이 선형이었으므로, after 에서도 선형이어야
"원래 느렸던 것이 아니다" 를 보일 수 있다. 그리고 before/after 를 한 표에 올리려면 같은 칸이 필요하다.

### 판정 규칙 (돌리기 전에 못박는다)

| 80 VU 결과 | 뜻 | 다음에 볼 것 |
|---|---|---|
| ~47 req/s | 스레드가 벽이었음이 확인된다 (23.9 → 2배) | 160 으로 진행 |
| 24 근처 그대로 | **상한이 안 올라갔거나** 다른 벽이 이미 있었다 | `alldap_anyio_threads_total` 을 **먼저** 본다 |
| 24~47 사이 | 스레드가 벽이었지만 혼자가 아니었다 | 아래 후보 표 |

### 새 벽 후보 (160 이 평평해질 때 무엇을 보면 그것인가)

| 후보 | 그것이라는 신호 |
|---|---|
| anyio 스레드 80 | `alldap_anyio_threads_borrowed` 가 80 에 붙는다 |
| **psycopg 풀 10** | `alldap_db_pool_requests_waiting > 0` |
| Spring 힙 256m | GC 시간 증가 · OOM · `process_start_time_seconds` 변화 |
| Tomcat 스레드 200 | `tomcat_threads_busy == 200` (160 VU 면 안 닿아야 정상) |
| 가짜 CF | 지연이 설정값 합계(1,586ms)보다 커진다 |
| **k6 자체** | k6 프로세스 CPU 포화 |

🔴 **아래 둘은 before 에 없던 후보다.**
- **psycopg 풀**: S2 의 병목 판정에 이 풀은 **아예 들어 있지 않았다**(후보가 Tomcat · Hikari · anyio
  셋뿐이었다). `hikaricp_*` 는 Spring 의 풀이고 이건 Python 의 다른 풀이다. 스레드 80개가
  커넥션 10개를 두고 경쟁한다.
- **k6 자체**: 160 VU 는 k6 가 같은 기계에서 도는 부하원이다. k6 가 CPU 를 먹으면
  **지연이 서버 탓인지 측정기 탓인지 못 가른다.**

### 유효성 장치

**before 의 넷을 그대로 쓴다:** fallback 0건 · 가짜 CF 호출 배수 3.0 ·
재시작 없음 · cf-stats `neurons` 가 전 모델 0.0.

**다섯을 더한다:**

1. 🔴 **`alldap_anyio_threads_total == 80` 을 시작 조건 파일에 박는다.**
   `app/metrics_check.py` ⑤ 는 로컬 `TestClient` 의 lifespan 을 검사한 것이지
   **측정 대상 프로세스**를 검사한 것이 아니다. 이걸 안 하면 "80 으로 올리고 쟀다" 가
   **틀린 문장으로 리포트에 남는다.**
2. `alldap_db_pool_open == 1`. 0 이면 풀 선 넷이 의미가 없고, 애초에 풀을 안 썼다는
   뜻이라 측정이 이상하다.
3. 단계마다 `alldap_db_pool_requests_waiting` 기록.
4. k6 프로세스 CPU.
5. 🔴 **단계마다 `alldap_ai_circuit_state` 기록.**

**5번이 가장 중요한 추가다.** PR #134 이 `config.anyio_max_threads` 주석에 예측으로
적어둔 경로다: 풀이 마르면 30초 대기 → `PoolTimeout` → 500 → Spring 이 Python 5xx 를
서킷 실패로 세므로 5건 누적에 30초 열린다. 그러면 **처리량이 갑자기 0 으로 떨어진다.**

🔴 **그건 "천장에 닿았다" 가 아니라 "차단됐다" 다.** 둘을 뭉개면 리포트가
"160 VU 에서 처리량이 무너졌다" 고 쓴다. `circuit_state` 가 그 둘을 가른다.
이 저장소가 여덟 번 낸 부류(원인이 다른 사실을 같은 값으로 뭉개기)를 **미리** 막는 자리다.

⚠️ 30초짜리 `PoolTimeout` 대기는 15초 스크레이프 두 번 사이에 통째로 들어갈 수 있다
= 포화가 있었는데 그래프에 안 남는 판이 가능하다. 그래서 `waiting` 을 **단계마다** 찍는다.

## 5. 중단 조건과 분배

### 🔴 "오염" 과 "결과" 를 가르는 규칙

before 에서 Spring 재시작은 **오염**이었다. 그런데 after 에서 스레드를 80 으로 올린 뒤
재시작이 나면 그건 **힙이 벽이라는 결론 그 자체**일 수 있다(S2 의 2순위 가설이
"틀렸다" 가 아니라 "발현하지 않았다" 로 남은 이유가 스레드 40 이 살아 있는 객체 수도
함께 묶고 있었기 때문이다). **같은 사건을 어느 쪽으로 읽을지가 반대다.**

가르는 기준: `-XX:+ExitOnOutOfMemoryError` 로 죽었으면 **결과**,
그 외 사유면 **오염**. 로그에서 OOM 을 직접 확인한다. 못 가리면 그 판은 무효로 두고 다시 돈다.

### 판을 폐기하는 조건

| 조건 | 왜 |
|---|---|
| `alldap_anyio_threads_total != 80` | 설정이 안 먹었다. 그 판은 80 을 잰 것이 아니다 |
| fallback > 0 | 게이트에 걸려 LLM 경로를 안 탔다 |
| 가짜 CF 호출 배수 ≠ 3 | 그 경로를 안 탔다 |
| OOM 아닌 재시작 | 위 규칙 |

**k6 CPU 포화는 폐기가 아니라 그 단계를 참고로만** 쓴다. 폐기하면 측정기 문제로
서버 숫자를 전부 버리게 된다.

### 5b → 5c 관문

동일성 확인에서 히스토그램·상태코드 숫자가 바뀌면 **5c 를 멈추고 보고한다.**

### 분배

실행은 파도로 끊어 idle 세션에 맡기고 취합은 한 곳에서 한다.

| 파도 | 내용 |
|---|---|
| 1 | 5b 도구 결함 ①②④ 수정 |
| 2 | A판(S3) 재실행 + F2(S4) 재실행 = 동일성 확인 |
| 3 | 5c S2 재측정 1판 |
| 4 | 최종 리포트 |

🔴 **병렬은 안 된다.** 같은 `:8080` Spring 을 쓰고, rate limit 고정 윈도우와 서킷 상태가
판 사이에 누적되며, 세션들이 같은 워크트리를 공유한다.
**분배의 값어치는 동시성이 아니라 맥락 격리다**. 각 세션이 자기 판만 보고 판정하고,
판정의 기준과 취합은 한 곳에서 한다.

- **풀 `timeout` 을 바꿀지.** `waiting > 0` 이 실제로 관측되면 그때 바꿔 한 판 더 돈다
  (`decisions.md` 2026-09-12)
- **도구 결함 ③⑤⑥⑦.** ③은 설계서 §3 표 자체가 모순이라(k6 100건 / 드라이버 200건)
  어느 쪽으로 확정할지 판단이 필요하다. ⑤⑥⑦은 S4 판정 강화인데 판정을 뒤집지 않는다.
  전부 별 슬라이스다
- **워커 수 늘리기.** `app/metrics.py` 의 multiprocess 경고가 그때 유효해진다
