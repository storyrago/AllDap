## 꺾인 단계와 그때 벽에 닿은 신호

**꺾임이 두 번, 서로 다른 지표에서 났다. 둘을 같은 사건으로 뭉개면 안 된다.**

### ① p99 는 20 VU 에서 꺾인다 (1,744 → 3,119ms)

p50 은 1,692ms 로 그대로인데 p99 만 1.8배가 됐다. **중앙값은 아직 안 기다리는데
꼬리는 이미 기다리기 시작한** 상태다. 평균만 봤으면 (1,703 → 1,717) 아무 일도
없는 것으로 읽혔다 — 이 저장소가 `avg_faithfulness` 로 한 번 데인 것과 같은 자리다.

### ② 처리량은 40 VU 에서 천장에 닿는다 (24.0 → 23.9/s)

**VU 를 두 배로 올렸는데 처리량이 늘지 않았다.** 이게 포화의 정의다.

천장값이 이론치와 맞는다:

```
40 (스레드) ÷ 1.68초 (요청당) = 23.8 req/s   ← 실측 24.0
```

40 VU 에서 p50 이 여전히 1,680ms 인 것도 같은 이야기다 — 40 VU 는 스레드풀을
**정확히 꽉 채우는** 지점이라 아직 줄을 안 선다. 80 VU 는 그 위에 40 건이 더
얹히는 것이고, 그래서 p50 이 1,680 → 3,503ms 로 **정확히 두 배**가 된다
(자기 차례를 기다리는 시간 한 턴이 더 붙는다).

### 그때 무엇이 포화였나 — 80 VU 지점 실측

| 지표 | 값 | 읽기 |
|---|---|---|
| `alldap_anyio_threads_borrowed` | **40** | 상한에 고정 |
| `alldap_anyio_threads_total` | 40 | anyio 기본값 |
| `tomcat_threads_busy_threads` | **80** | 80건 전부 Spring 이 붙들고 있다 |
| `hikaricp_connections_pending` | **0** | **DB 는 병목이 아니다** |
| `hikaricp_connections_active` | 2 | 거의 놀고 있다 |
| Spring 종단 p99 | **6.44초** | |
| Python 몫 p99 | **2.00초** | |

🔴 **결정적인 것은 마지막 두 줄의 차이 4.44초다.** 80건 중 40건만 Python 이
처리하고 나머지 40건은 스레드를 기다리는데, **그 대기가 Spring 지연에는 잡히고
Python 히스토그램에는 안 잡힌다** — 히스토그램이 스레드를 얻은 <뒤에> 시작하기
때문이다. Python 몫 p99 가 20 VU 때와 같은 2.0초라는 것이
**"Python 이 느려진 게 아니라 순서를 기다린 것"** 을 말해준다.

이 분리가 없었으면 "6.44초가 걸렸다" 만 보고 Python 이 느려졌다고 읽었을 것이다.
PR 3 이 `alldap_chat_duration_seconds` 를 만든 값어치가 이 한 줄이다.

## 두 가설의 판정

| | 가설 | 판정 | 근거 |
|---|---|---|---|
| 1순위 | Python anyio 스레드풀 40 이 먼저 찬다 | ✅ **맞았다** | `borrowed` 가 40 에 고정되고, 처리량 천장 24/s = 40÷1.68초, Tomcat busy 80 vs borrowed 40 |
| 2순위 | 그보다 Spring 힙 256m 이 먼저 마른다 | ❌ **발현하지 않았다** | 12분 구간에 재시작 0회. 힙은 256m 로 <실제로 제한된 상태>였다(`jcmd` 확인) |

🔴 **2순위를 "틀렸다" 가 아니라 "발현하지 않았다" 로 적는다.** 힙 한도를 실제로
씌운 채 12분을 밀었는데 안 말랐다는 것이지, 어떤 조건에서도 안 마른다는 뜻이 아니다.
스레드풀이 40 에서 막아주는 동안에는 동시에 살아 있는 객체 수도 40건분에 묶인다 —
**1순위 병목이 2순위를 가려주고 있는** 구조다. PR 5 에서 스레드풀을 늘리면
그 순간 힙이 다음 벽으로 올라올 수 있다.

> ⚠️ 이 판정은 **`-Ploadtest` 를 씌웠기 때문에** 할 수 있는 말이다. 안 씌웠으면
> 로컬 힙이 기가 단위라 "안 말랐다" 가 아무 정보도 아니었을 것이다(설계서 §2).

## 새로 드러난 것 — `alldap_chat_inflight` 는 대기 큐 지표가 못 된다

설계서 §5① 은 이 지표를 *"스레드풀 대기 큐 길이의 대리 지표"* 로 뒀다.
**원리적으로 그 역할을 못 한다.**

`CHAT_INFLIGHT.inc()` 는 `chat` 함수 <안>에 있고, 그 함수는 워커 스레드를 이미
얻은 뒤에야 실행된다. 즉 **기다리는 요청은 `inc()` 에 도달조차 못 한다.**
`inflight` 는 구조적으로 `borrowed` 를 넘을 수 없다.

80 VU 실측이 그대로 보여준다 — `tomcat_busy=80` 인데 `inflight=40` 이다.

→ **실제 대기 큐 길이는 `tomcat_threads_busy_threads - alldap_anyio_threads_borrowed`** 로 읽어야 한다.
이 실행에서는 80 − 40 = 40 이다. PR 5 에서 개선 전후를 비교할 때 이 식을 쓴다.
(`inflight` 자체는 "지금 Python 이 실제로 처리 중인 건수" 로는 여전히 옳다 —
이름이 약속한 것과 다른 것을 잰다는 게 문제지 값이 틀린 게 아니다)

## 못 잰 것

- **1 VU·5 VU 단계의 p99 는 표본이 얇다.** 요청 한 건의 하한이 1.586초라 1 VU 는
  2분에 72건뿐이고, p99 는 상위 1건이 결정한다. 설계서가 미리 한계로 남긴 것이고
  실행시간을 늘리지 않았다. **p50 은 이 표본으로도 충분하다**(1,674 ~ 1,705ms 로
  다섯 단계가 30ms 안에 모여 있다 = 재현성이 좋다).
- **"동시 N명" 절대수치는 이 실행으로 말할 수 없다.** 맥의 CPU·메모리 대역이
  t3.micro 가 아니다. 여기서 얻은 것은 **어느 자원이 먼저 차는가**이고 그건 구조라
  사양과 무관하다. 24 req/s 라는 숫자도 `40 ÷ 1.68초` 라는 <식>이 본체이지
  절대값이 아니다 — 운영에서는 CF 실지연이 달라 분모가 바뀐다.
- **가짜 CF 는 고정 지연이다.** S1 실행 중 종단 p50 이 단조 상승했는데(20건째
  1,676ms → 320건째 1,779ms) 가짜 서버는 몇 건을 돌리든 같은 시간을 잔다.
  장시간 부하에서 진짜 CF 와 수치가 벌어지면 버그가 아니라 이것일 수 있다.
- **80 VU 의 503 1건은 <측정 도구>가 흔들린 것이지 포화가 아니다.**
  21:02:23 에 `httpx.ReadError: [Errno 9] Bad file descriptor` — 가짜 CF 서버
  (`ThreadingHTTPServer`)와의 연결에서 났다. 8,316건 중 1건(0.012%).
  같은 시각 로그에 `리랭킹 실패(원래 순서 유지)` 도 있어 리랭커 호출도 한 번 흔들렸다.
  🔴 **재시도 대상이 아니라 기록 대상이다** — 부하 아래서 가짜 서버가 이 정도로
  흔들린다는 것 자체가 다음 측정에서 알아야 할 사실이다.
  ⚠️ **이 원인을 가릴 수 있었던 것은 이번에 uvicorn 로그를 파일로 받았기 때문이다.**
  S1 에서 `ANSWER_INCOMPLETE` 의 원인을 못 가른 것이 로그를 안 남긴 탓이었고,
  핸드오프 §5-ⓐ 가 "다음 측정부터" 로 남긴 항목이 여기서 처음 값어치를 했다.
- **미세 탐색을 하지 않았다.** p99 는 10→20 사이에서, 처리량은 20→40 사이에서
  꺾인다. 그 구간을 25·30·35 로 좁히면 더 정확한 지점이 나오지만, PR 3 의 질문
  ("어디서 깨지고 무엇이 포화인가")에는 이미 답이 나왔으므로 하지 않았다.

## 실행 중에 드러난 절차 문제 (다음 측정 전에 고칠 것)

1. 🔴 **`s2_context.py` 의 `cf_base_url` 가드는 <드라이버 프로세스>만 본다.**
   uvicorn 이 진짜 Cloudflare 를 보고 있어도 드라이버 셸에만 가짜 값이 있으면
   **통과한다** — 위험한 방향의 오탐이다(하루 한도가 날아간다).
   이번에는 반대 방향 오탐(드라이버만 진짜 값)이 나서 걸렸을 뿐이다.
   → 실제로 믿을 수 있는 것은 **cf-stats 의 `neurons` 가 0 인지**다. 가짜 서버는
   뉴런을 안 준다. 다음 판에는 이 검사를 `before` 에 넣을 것.
2. **`w2check@example.com` 의 비밀번호가 S1 뒤 원래대로 복원돼 있었다.**
   계획서에 적힌 `S1loadtest!2026` 으로 로그인이 401 이었다. 이번 실행을 위해
   해시를 임시 교체했고 **실행 뒤 복원했다**(`AllDap-pr2/.s2-old-hash.txt`).
   → 다음 측정도 같은 일을 겪는다. 측정 전용 계정을 따로 두는 편이 낫다.
3. **`/actuator/metrics/*` 는 인증에 막힌다.** 열려 있는 것은 `/actuator/prometheus`
   와 `/actuator/health` 뿐이라, 힙 확인은 Prometheus 질의로 해야 한다.
4. **k6 v2 에서 요약 표의 표본 열이 비어 있다**(trend `values` 에 `count` 가 없다).
   표본 수는 `chat_status{stage:N,status:200}` 에서 가져왔다. 위 표의 값이 그것이다.
