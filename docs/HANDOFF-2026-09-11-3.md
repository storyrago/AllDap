## 1. S3 (rate limit 정확성) — 네 판

**순서를 지켰다: N → A → B → C.** 음성 대조를 본 판정보다 먼저 돌렸다.

| 판 | 404 | 429 | 400 | 200 | 0/500/503 | 합계 | 판정 |
|---|---|---|---|---|---|---|---|
| **N** (한도 100000) | **100** | **0** | 0 | 0 | 0 | 100 | ✅ |
| **A** (한도 20, 동시 100) | **20** | **80** | 0 | 0 | 0 | 100 | ✅ **본 판정** |
| **B** (분 경계) | **40** (앞 20 · 뒤 20) | 0 | 0 | 0 | 0 | 40 | ✅ |
| **C** (키 둘) | **40** (키당 20) | **60** (키당 30) | 0 | 0 | 0 | 100 | ⚠️ §3-③ |

- 🔴 **A 가 답한 것: 동시 100건에서 카운터가 한 건도 안 샜다.** 400·200 이 둘 다 0 이라
  2026-09-09 사고 모양(`@Valid` 에서 400 이 나 `rateLimiter` 를 지나가지도 못한 것)도 아니고
  진짜 봇을 때린 것도 아니다.
- **B**: 4.3초 안에 404 40건. 고정 윈도우 2N 이 실측으로 재현됐다(`keys` 게이지 3→5).
- **C**: 키마다 딱 20 씩 통과 = **버킷 분리는 정확하다.**
- `mode="blocked"` 는 네 판 통틀어 0건, 전부 `check` 다. 로그인 버킷은 안 건드렸다.
- 교차검증(손으로 댄 다른 축): `alldap_ratelimit_rejected_total{bucket="widget-chat",mode="check"}`
  와 `http_server_requests_seconds_count{status="429"}` 가 k6 의 429 와 **정확히 일치**.

## 2. S4 (장애 주입) — 세 판. 셋 다 `valid: true`

### F1 (uvicorn SIGTERM) — 🔴 앞 문서 §2-① 의 정정이 실측으로 확정됐다

- `connect_failure` +68, **평균 206.1ms**. `retry-delay` 200ms 말고는 아무것도 안 걸렸고
  **3초는 한 번도 안 나왔다.** "요청당 6.2초" 가설은 기각이다.
- 다시 쓴 가설의 답도 나왔다: `to=open` +4 (30초 톱니 재현) · `retry_total` +68 이므로
  **HALF_OPEN 한 번에 약 17건 통과**, VU 20 이니 사실상 in-flight 전부다.
- `retry_total` 이 연결 실패와 **정확히 1:1**.
- 급속 503 대 느린 503 = 약 **14,980배**(부하 없이 잰 지난 값 2,700배보다 더 벌어졌다.
  급속 쪽이 79us → 13.8us 로 빨라져서다). 20 VU 아래서도 갈린다.

### F2 (error_all) — 노린 것이 정확히 나왔다

- **`retry_total` 68 → 68. 증가가 정확히 0.**
- 🔴 **한 축에서만 주장하지 않았다.** 가짜 CF `counts[bge-m3]` +73 = Spring `python_5xx` +73
  = `fault.injected` +73. 전부 1:1 이라 재시도가 돌았다면 CF 쪽이 두 배로 셌을 것이다.
  **"5xx 는 재시도하지 않는다" 가 LLM 중복 과금을 실제로 막고 있다는 증거가 처음 나왔다.**
- 리랭커·생성 호출은 +0. `to=open` +4.

### F3 (error_rerank) — 🔴 "통과" 가 아니라 **결함이 재현됐다**

- `리랭킹 실패` 로그 **1,080건**(`grep -c`. `wc -l` 은 MDN 링크 때문에 2배가 난다).
  주입 1,080 = 리랭커 호출 +1,080 = 로그 1,080줄 = 주입 구간 요청 1,080건.
  **주입 구간의 모든 요청이 리랭킹에 실패했다.**
- **밖에서 보이는 것 중 바뀐 것이 하나도 없다**: 상태코드 전부 200 · `isFallback` 0 ·
  outcome 전부 `success`(실패 9종 +0) · `retry_total` 고정 · 서킷 무반응.
- **지연조차 안 바뀐다**: normal 1675.33ms vs inject 1674.85ms (차이 **0.03%**).
  지연을 유지한 가짜 CF 설계가 맞았다.
- → 이 장애는 **로그 한 줄이 유일한 신호**다. 지표로는 보이지 않는다.

### 관측 쪽에서 추가로 드러난 것 둘

1. 🔴 **`to=open` 과 `to=closed` 의 정산이 안 맞는다** (F1·F2 둘 다 open +4 / closed +2).
   락 없는 구현이라 HALF_OPEN 통과 무리가 동시에 성공하면 그중 하나만 닫힘을 센다.
   클래스 주석이 "눈금이지 정산 대상이 아니다" 라고 적어둔 그대로다.
   **두 카운터를 대차대조표로 읽으면 틀린다.**
2. `circuit_transition_total{to="half_open"}` 시계열이 **아예 없다**(세 판 모두 `null`).
   HALF_OPEN 은 "열린 시각" 에서 파생되는 값이라 전이 사건이 없어서고 버그는 아니다.
   다만 context 파일의 `null` 은 **"0회" 가 아니라 "그런 계측이 없다"** 이다.

## 3. 🔴 PR 5 로 넘기는 도구 결함 7건 (전부 고치지 않았다)

**측정을 잰 도구와 고친 도구의 경계가 흐려지면 before/after 를 주장할 근거가 사라진다.**
그래서 발견한 즉시 고치지 않고 보고만 하게 했다. **7건 다 판정을 뒤집지 않았다.**

### 먼저 고쳐야 하는 것 (다음 측정 전)

① 🔴 **S3: `alldap_ratelimit_recorded_total` 무효 판정 — 정상 실행을 실패로 부른다.**
`alldap.ratelimit.recorded` 를 올리는 곳은 `RateLimiter.record()` 하나뿐이고, 그 호출자는
`AuthService.java:205` 의 **`login-failure` 버킷 하나**다. 위젯 채팅은 `check()` 를 지나므로
`{bucket="widget-chat"}` 시계열은 **원리적으로 생길 수 없다.** 그래서 `cmd_after` 가 네 판
모두 *"제한기를 한 번도 안 지났다"* 며 `valid:false` + 종료코드 1 을 낸다.
이 저장소가 이미 두 번 기각한 부류다("정상을 실패로 부르는 검사" — `decisions.md` 2026-09-09).

② 🔴 **S4: `after` 스냅샷이 `recover` 의 성공 1건을 삼킨다.** 절차가 `clear → recover → after`
라서다. F3 의 success 증가분이 1,800 이 아니라 **1,801** 이다. 판정이 전부 "늘었나 / 0인가" 라
결론은 안 바뀌지만 숫자를 그대로 인용하면 1씩 어긋나고, 원리적으로는 `to=closed` 전이도 한 건
섞일 수 있다. **`after` 를 `recover` 앞에 두면 된다.**

③ **S3 C 판: k6 와 드라이버가 다른 숫자를 들고 있다.** k6 `ROUNDS.C = {vus:100, expected:100}`,
드라이버 `ROUNDS["C"] = {expected_total:200, pass_multiple:2}`. 🔴 **설계서 §3 표 자체가 모순**
이다("키 2개에 50 VU 씩"(=100) 과 "키마다 404 20 · 429 80"(=200) 을 함께 적어뒀다).
100건 기준으로 읽으면 기대가 `404 40 · 429 60` 이고 정확히 그렇게 나왔다.
**`s3_context.py` 주석이 "일부러 한 곳으로 합치지 않았다" 고 적어둔 이중화가 실제로 불일치를
잡아낸 두 번째 사례다**(첫 번째는 가짜 키 기본값 20자 대 22자).

④ **S3 `--headroom-ms` 기본값 20000.** 앞 문서가 "A 가 실패하면 먼저 의심하라" 고 지목했는데
**그 방향은 틀렸다** — 100건이 **329ms** 에 끝난다(60배 여유). 🔴 **위험은 반대편이었다.**
`cmd_before` 는 사전 확인 요청 1건을 **먼저 보내고** 경계 정렬을 하므로, 20초면 같은 윈도우에서
시작할 수 있고 그러면 그 1건이 한도 20 중 하나를 먹어 **정상인데도 404 가 19건** = 거짓 실패가
난다. 드라이버가 스스로 인쇄해 경고하며 60000 을 권한다. A·B·C 는 전부 60000 으로 돌렸다.
**기본값을 60000 으로 올리는 것이 맞다.**

### 나머지 셋 (S4)

⑤ `judge_fault_round` 가 **정상 구간에 실패가 있었는지 안 본다.** 대조군 검사가
`normal[200] > 0` 하나뿐이라 정상 60초에 503 이 섞여도 통과한다(이번엔 전부 200×720 이었다).
⑥ F2 판정이 **"서킷이 열린다" 를 단언하지 않는다.** 설계서 §4-F2 기대표에는 있는데 코드는
`python_5xx > 0` 과 `retry == 0` 둘만 본다.
⑦ F1 의 `clear` 는 안내문만 찍는 no-op 이라 **uvicorn 복귀를 아무도 확인하지 않는다.**
확인하는 것은 `recover` 뿐이다.

> 🔴 **권고: ①②를 고친 뒤 A 판과 F2 를 한 판씩 재실행해 같은 숫자가 나오는지 볼 것.**
> 도구를 고쳤는데 숫자가 바뀌면 앞의 7판이 무엇을 잰 것인지 다시 물어야 한다.

## 6. 이 세션에서 배운 것 (기록)

### ⓐ 🔴 "판정이 무효를 냈다" 와 "측정이 실패했다" 는 다른 사실이다

S3 네 판이 전부 `valid:false` + 종료코드 1 로 끝났는데 **측정은 멀쩡했다.** 무효 사유가
`recorded_total` 시계열 부재였고, 그 시계열은 원리적으로 생길 수 없다(§3-①).
히스토그램 판정(`verdicts[0]`)은 넷 다 정상이었다.

**종료코드 하나에 두 사실이 뭉쳐 있다**: "재보니 기대와 달랐다" 와 "재는 도구가 틀렸다".
`AGENTS.md` 의 "낸 버그" 표가 일곱 번 적은 그 부류가 이번엔 **판정기 자신**에서 났다.
→ 무효 사유를 읽고 둘을 가르는 것이 측정자의 일이다. 종료코드만 보고 판을 다시 돌리면
영원히 같은 무효가 난다.

### ⓑ 🔴 한 축에서만 주장하지 않은 것이 F2 의 값어치를 만들었다

`retry_total` 증가 0 은 그것만으로는 "재시도가 안 돌았다" 와 "카운터가 안 붙었다" 를 가르지
못한다. 가짜 CF 의 호출 수(+73)와 주입 수(+73)를 나란히 놓아서야 **"요청이 실제로 한 번만
갔다"** 가 된다. 재시도가 돌았다면 CF 쪽이 두 배로 셌을 것이다.
**"키가 있고 0" 과 "키가 없다" 를 가르는 규칙**(앞 세션이 `judge_round` 에 넣은 것)과 같은
생각이고, 이번에는 그것을 **서로 다른 서비스의 카운터 사이**에 적용했다.

### ⓒ 앞 문서가 지목한 의심 대상이 틀렸고, 위험은 반대편에 있었다

`--headroom-ms` 20000 은 "얕은 값" 으로 적혀 있었고 실제로 얕았지만, **위험한 방향이 반대**
였다(§3-④). 실측 329ms 라 시간이 모자랄 일은 없고, 모자란 것은 **분 경계까지의 여유**였다.
→ "근거가 얕다" 를 적을 때 **어느 방향으로 틀리면 무엇이 깨지는지**까지 적어야 다음 사람이
헛다리를 안 짚는다.

### ⓓ 분배는 이번엔 전부 됐다. 다만 병렬은 절반도 안 됐다

앞 세션은 4건 중 2건이 거절됐는데 이번엔 4개 파도가 전부 완주했다. 사양을 넘겨서 온 것도
넷 다 같다(Grafana 고장 지점 분리 · `recorded_total` 이 도구 결함임을 밝힌 것 ·
해시 원복 문자열 대조 · 두 벌이 본문 동일함을 문자 단위로 대조).

🔴 **그런데 네 파도 중 병렬로 돈 것은 0개다.** 측정이 같은 포트·같은 상태·같은 워크트리를
쓰기 때문이다. **분배의 값어치는 동시성이 아니라 <맥락 격리>에 있었다** — 각 세션이 자기 판만
보고 판정했고, 취합은 main 세션이 했다. 앞 세션의 교훈("틀리면 측정이 통째로 거짓이 되는
부분은 main 이 직접")과 합치면 규칙은 이것이다: **실행은 나누고, 판정의 기준과 취합은 한 곳에서.**
